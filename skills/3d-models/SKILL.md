# 3D models, point clouds and splats

**Check freshness first.**
Written on 2026-11-17 (ORDER 17, milestone 1) from measurements in a throwaway container of Debian testing with the edition's repository: KIO 6.30.0, kio-extras 26.04.0+stereo3d5, F3D 3.5.0, CloudCompare 2.13.2+git20240821 (it shows itself as v2.14.alpha), Mesa 26.1.6+stereo3d21, Stereo KWin 6.7.4+stereo3d54.
Package versions move: read `apt-cache policy` again before relying on one.

## Working recipe: what Dolphin shows for a model

1. Install `f3d` in the container. It ships five freedesktop thumbnailers (`/usr/share/thumbnailers/f3d-plugin-*.thumbnailer`, `Exec=f3d --config=thumbnail ... --output=%o --resolution=%s,%s %i`) listing the MIME types of its readers.
2. KIO reads them: `FilePreviewJob::standardThumbnailers()` collects every `*.thumbnailer` file of `$XDG_DATA_DIRS/thumbnailers` as a plugin of category `standardthumbnailer` and runs its `Exec` through `StandardThumbnailJob` (kio 6.30.0, `src/gui/filepreviewjob.cpp`, `standardthumbnailjob.cpp`). `KIO::PreviewJob::availableThumbnailerPlugins()` lists them beside the compiled ones.
3. Run the real path without Dolphin: a small program calling `KIO::filePreview(items, QSize(256, 256), &plugins)` with `plugins = KIO::PreviewJob::defaultPlugins()` (what Dolphin uses until the person saves another list: `kfileitemmodelrolesupdater.cpp`, dolphin 26.08.0), offscreen, `HOME` and `XDG_CACHE_HOME` in scratch, inside `dbus-run-session`, with a passwd entry for the user. It prints GOT or FAILED per file and leaves the thumbnails in the freedesktop cache.
4. Read the cache's text chunks: a marked picture's thumbnail carries `X-KDE::Stereo3DLayout=sideBySideLeftFirst`, a model's carries only `Thumb::Mimetype`. Measured 2026-11-17: STL, OBJ, GLB and glTF get a flat 256x256 render; a marked `.pns` gets a 256x128 pair.
5. Put a wrapper named `f3d` first in `PATH` that logs its arguments to learn whether KIO started the thumbnailer at all.

## What does not get a preview, and why (measured)

- **`.ply`, `.splat`**: shared-mime-info has no type for them, so KIO types `.ply` as `text/plain` and `.splat` as `application/octet-stream`, and F3D's thumbnailer lists `application/vnd.ply` and `application/vnd.splat`. F3D itself renders both when called directly (1.8 to 11 kB PNGs). The fix is a MIME package with globs for the model formats, not a thumbnailer.
- **`.3mf`**: the compiled `opendocumentthumbnail` plugin lists `model/3mf` (the thumbnail a slicer embeds) and comes before the standard thumbnailers, so a 3MF without an embedded thumbnail fails and never reaches F3D. With only F3D's plugins enabled the same file gets a preview.
- **STEP, FBX, DAE, OFF, PTS, SPZ, E57, LAS, LAZ, XYZ**: no glob in the rig's `/usr/share/mime/globs2` either (the file has stl, obj, glb, gltf, 3mf, 3ds, dxf and blend); grep it before blaming a thumbnailer.

## Traps

- **Symptom:** `KIO::filePreview` fails every model, log line `Could not get plugin for ... emitting result`, no thumbnailer process. **Cause:** a null plugin list enables only the directory, image and JPEG thumbnailers (`PreviewJob::PreviewJob`, `enabledPlugins` null: `PreviewSettings` `Plugins` default), so no standard thumbnailer is enabled. **Fix:** pass `defaultPlugins()` or Dolphin's own list. **Found by:** `QT_LOGGING_RULES="kf.kio.gui=true"` (the category is `kf.kio.gui`; `kf.kio.gui.*` matches nothing) and reading `previewjob.cpp`.
- **Symptom:** `dbus-run-session` says `Failed to start message bus: Memory allocation failure`. **Cause:** the container user has no passwd entry. **Fix:** mount a passwd file naming the uid read-only over `/etc/passwd`.
- **Symptom:** `xdotool key F10` opens KWin's window overview, not the program's action. **Cause:** F10 is a KWin global shortcut in the rig. **Fix:** click the toolbar action.
- **Symptom:** a combo box in a Qt dialog ends on another item, once. **Cause:** `Down Down Return` sent at once races the popup. **Fix:** open the popup, wait two seconds, then `xdotool key --delay 400 Home Down Down`, and capture before pressing Return so the evidence shows the chosen item.

## F3D in stereo: our packages (ORDER 17, milestone 2)

Written 2026-11-17 from the build of `f3d` 3.5.0+dfsg-3+stereo3d1 and the new `libf3d3` and `libf3d-dev`.

- **The source:** Debian's own `f3d` source package (3.5.0+dfsg-3), seven patches added to `debian/patches`, taken from branch `order17-stereo` of our F3D fork on upstream's v3.5.0: `render.stereo` (VTK's quad buffer through a stereo GLX window, declared by our Mesa as one full side-by-side surface under Stereo KWin through Xwayland), the per-eye shear, the size of one eye, the eye taken from the left-eye flag or from the caller, the pair in an image (`renderToImage` with `render.stereo` returns left and right side by side), the program's options as the contract has them (`--stereo` is Enable 3D, F3 switches it, F4 opens Display Settings, `--stereo-eye-angle` is gone, ten-language sentences) and the UI-only frame fix below.
- **Why 3.5.0:** it is the release Debian testing ships; the three older patches applied to it with `git am -3` without a conflict.
- **libf3d:** Debian builds F3D with `BUILD_SHARED_LIBS=OFF` and removes `/usr/lib`. Ours builds it ON, installs the default components into `debian/tmp`, the `sdk` component beside them (`cmake --install obj-... --component sdk`; it is `EXCLUDE_FROM_ALL`, so `dh_auto_install` skips it), and splits `libf3d3` and `libf3d-dev`.
- **The pair thumbnail:** `f3d-thumbnail-pair PLUGIN SIZE INPUT OUTPUT`, a small libf3d program in the package. It sets `render.stereo` on an offscreen engine and renders each eye in turn from a parallel, sheared camera (never a rotation of one camera); the picture is SIZE by SIZE/2, left eye first. libf3d's PNG writer keeps no text chunk (`image::setMetadata` is not written), so the program inserts the `tEXt` chunk `X-KDE::Stereo3DLayout=sideBySideLeftFirst` itself (zlib's crc32). The package rewrites the `Exec` line of F3D's five `.thumbnailer` files to call it.
- **Measured:** the pair of three squares at known depths: near -7.27 px, at the focal plane -0.08 px, far +5.00 px of horizontal disparity between the eyes, vertical disparity at most 0.17 px (`disp.py`), so the sign and the zero plane are those of two parallel sheared cameras. The numbers were not predicted: the helper's camera is oblique.
- **KIO carries the key:** (measured twice) a standard thumbnailer's PNG text chunk survives into the freedesktop cache (measured with a fake thumbnailer in the rig: the cached file holds the key), so no KIO change is needed for the pair; it shows as a pair where the file manager shows pairs and as its left half elsewhere.
- **MIME types:** the package `sparky-stereo-mime-models` defines `model/x-ply`, `model/x-gaussian-splat`, `model/x-spz`, `model/x-pts`, `model/x-fbx`, `model/vnd.collada+xml`, `model/x-off`, `model/x-draco`, `model/step`, `model/x-brep`, with F3D's `application/vnd.*` names as aliases. **KIO does not follow an alias:** it looks a thumbnailer up by the file's canonical type name, so the package also rewrites the `MimeType=` of F3D's `.thumbnailer` files to carry the canonical names beside the aliases. Search shared-mime-info's master first: STEP, BREP, IGES, OBJ, 3MF, glTF and STL are there already (STEP and BREP are not in the release Debian testing ships, so they are carried as they are upstream); PLY, splat, SPZ, PTS, FBX, COLLADA, OFF and Draco are not.

### Traps

- **Symptom:** a file typed `model/x-ply` shows no thumbnail although F3D's thumbnailer lists `application/vnd.ply` (`supported: false`, FAILED, no process started). **Cause:** `FilePreviewJob::preparePluginForMimetype` finds the plugin by the type's own name and its ancestors, never its aliases. **Fix:** list the canonical name in the thumbnailer's `MimeType=`. **Found by:** the thumbnail run printing `supported: false` for the new types while the old fake thumbnailer (on the canonical name) had worked.
- **Symptom:** the thumbnail is a pair but the cache file has no `X-KDE::Stereo3DLayout`. **Cause:** libf3d's `image::save` writes no PNG text chunk. **Fix:** insert it in the program. **Found by:** `textkeys.py` on the helper's own output (`{}`).
- **Symptom:** every thumbnail FAILED with a permission error on `thumbnails/large`. **Cause:** a cache folder in the mounted work folder was made earlier by a root run. **Fix:** the cache in the container's own `/tmp`, as the user.
- **Symptom:** `f3d --stereo` under Stereo KWin is a declared stereo window (capture two outputs wide, `_KDE_NET_WM_STEREO_CONTENT` 3) but the two halves are identical. **Cause:** F3D redraws the interface over the cached layers of the last frame whenever no render was requested (the event loop, every input event: `RENDER_UI_ONLY` in `vtkF3DRenderPass`); the layers hold the last eye drawn, so the left eye of that frame is the right eye's picture. **Fix:** a UI only frame draws the scene again when the window has two eyes (`GetStereoRender()`). **Found by:** reading the render framebuffer before VTK's `StereoMidpoint` blit in a debug override of `vtkF3DGLXRenderWindow` (it held the previous frame's right eye in 219 of 223 frames); VTK's own blits and our Mesa were cleared first (an FBO blitted to `GL_BACK_LEFT` red and `GL_BACK_RIGHT` blue, through a visual and through an fbconfig window, `blitstereo.c`), and an apitrace of the frame showed the calls in VTK's expected order. A trace shows order, not contents: read pixels.
- **Symptom:** the default 3D set in `/etc/f3d/configs/config.d/` does nothing. **Cause:** F3D reads `/etc/f3d/config.json` and `/etc/f3d/config.d`; Debian installs its own configuration in `/etc/f3d/configs`, which nobody reads. **Found by:** `f3d --verbose=debug --no-render` lists every candidate path.
- **Symptom:** `lean.debian_prepare` stops with "Missing toolkit input: packages/dpkg-stereo/LICENSE", then the build with unmet `node-acorn nodejs python3-yaml`, then `check-link needs --archive-config / --scratch`. **Fix:** sparse-checkout `sparky-os/packages/dpkg-stereo`; install the three packages; run as a user (uid 1000) with bubblewrap, `--security-opt seccomp=unconfined apparmor=unconfined systempaths=unconfined`, `SPARKY_LC_ARCHIVE_CONFIG` (a JSON list with the Debian archive and its keyring), `SPARKY_LC_SCRATCH`, `SPARKY_LC_PREVIOUS_SIBLINGS_FILE` (the published pool's .deb list) and `SPARKY_BUILD_INVOCATION`/`SPARKY_BUILD_STARTED` for `check-debs`; a `SOURCE_DATE_EPOCH` in the future makes every file "in the future" for lintian and tar.
- **Symptom:** `dh_dwz: Allocatable section ... after non-allocatable ones` after `patchelf --set-rpath`. **Fix:** `dh_dwz -Xlibf3d.so.3.5`.
- **Symptom:** `package-name-doesnt-match-sonames libf3d3` for a package named libf3d3. **Fix:** name the package after the soname (`libf3d.so.3`, package `libf3d3`).
- **3MF:** KIO picks one plugin per type; a plugin of its own (`threemfthumbnail`, `ThreeMFPreferRender` in the `PreviewSettings` group of kdeglobals) shows the slicer's `Metadata/thumbnail.png` first and F3D's pair when there is none, the other way round when the person prefers the render (measured with `QT_PLUGIN_PATH` and an enabled-plugins list: the embedded picture, then the pair, then both pairs).

- **Symptom:** `dpkg-source: error: ... patch ... subprocess failed` with "Reversed (or previously applied) patch detected" at `dpkg-buildpackage`. **Cause:** a prep script appended the patch's name to `debian/patches/series` twice (it had run once before and failed after the append). **Fix:** make the script idempotent, `awk '!seen[$0]++'` on the series. **Found by:** the doubled "applying" line in the build log.
- **Symptom:** a script in a Debian base container says `python3: not found`. **Cause:** `debian:testing` has no Python. **Fix:** install `python3-minimal` first, or write the edit as a shell step.

## Eye separation and the 3MF package (ORDER 17, milestone 3)

**Where the separation selector belongs.** Daniel's 2026-10-22 design (a user selector: flat TV or output, gentle; flat headset, larger; never read from the output) was first built for the browser. On 2026-11-10 he removed it from our browser: "this last one is not even needed in sparky stereo os, it is a measure for upstream, all other settings are up to kwin into the depht setting" (memory ours-first-upstream-second). So the selector is an upstream offer on a separate branch (F3D fork branch `order17c`, one patch, `render.stereo_view`, `--stereo-view`, F5), not part of the edition's f3d package; our window's separation is the desktop's (KWin writes `_KDE_NET_WM_STEREO_DEPTH_LIMITS` on a declared X11 window, skill native-linux). Ask the main session before building a program's separation menu into a package.

**The values and the derivation.** An eye angle is not an interaxial distance. The browser's two flat modes have an interaxial that grows with the screen plane: 3.47 mm for each metre (flat TV) and 8.7 mm for each metre (flat headset), skill stereo-two-cameras (x3d-in-the-browser.md). For parallel sheared cameras that meet at the focal distance, the angle is `2 atan(interaxial / 2 m)`: 0.199 degrees (flat TV) and 0.498 degrees (flat headset). The accepted M2 default of 2 degrees is ten times the flat TV value.

**Proof.** `winproof.py` predicts `d = F * 2 tan(angle/2) * (1 - f/z)` from the mono capture. At 0.2 degrees the three squares of `depth.ply` (offsets of 1 unit) differ by under a pixel, below the centroid's resolution; use `mkdepth.py FILE 3` (offsets of 3 units) and `OFFSET=3 winproof.py`. Measured on the AMD render node (window 600x400): flat TV near -2, far +1 px (predicted -1.93, +1.17), flat headset near -5, far +3 px (predicted -4.83, +2.94), vertical 0 in both, window declared `_KDE_NET_WM_STEREO_CONTENT` 3.

**The link gate with the published tree.** The archive configuration takes the published tree as a second source, `{"uri": "file:///repo", "suite": "mashtabba", "components": ["main"], "keyring": "/repo/sparky-stereo-repo.asc"}`, beside Debian's; with the previous kio-extras .debs as `SPARKY_LC_PREVIOUS_SIBLINGS_FILE` and an empty siblings file the link check passes for kio-extras and kio-extras-data without adding any stage folder or other sibling (the NVIDIA lock came only from adding every sibling to a tree that lacked libstereo-layer1).

**Comparing a rebuilt package.** `dpkg-deb -c` of both builds gives the file list; `md5sums` of both shows which files differ. A rebuild in another container differs in every binary by its build id alone (the sizes are equal and `cmp` stops in the ELF note); the real differences are the files that left or arrived, the Depends line (`libstereo-layer1 >= 1.21.1` where the published says 1.18.0: shlibs takes the layer the build saw), the changelog and the Lean Code record. kio-extras +stereo3d7 against +stereo3d6: one file arrived (`threemfthumbnail.so`), none left; lintian (pedantic) gives the same seven tags.

**3MF in the preview path (KIO and Dolphin).** `with-picture.3mf` (a `Metadata/thumbnail.png`) gives the slicer's picture, plain, no layout key; `without-picture.3mf` gives F3D's pair marked `sideBySideLeftFirst` with differing halves; `ThreeMFPreferRender=true` under `[PreviewSettings]` of kdeglobals gives the pair for both. The published +stereo3d6 gives the picture for the first and no preview for the second. In Dolphin on a 3D output the picture's eyes are equal (0 px differ) and the render's differ; on a 2D output Dolphin shows the picture and the render's left eye.

## A VTK program's separation from the person's depth limits (ORDER 17, milestone 4)

F3D (+stereo3d2) takes the separation of its two cameras from the limits Stereo KWin gives the window, through libstereo-declare 1.10 (`stereo_depth_x11_get_limits`, skill native-linux, references/depth-limits-declare.md); no selector, no angle option (Daniel 2026-11-10, memory ours-first-upstream-second: "all other settings are up to kwin into the depht setting").
- **The maths.** The limits are pixels of a view 1920 wide: `S = sunk * W / 1920`, `P = popped * W / 1920`, W one eye's width in the window's own pixels (`vtkRenderWindow::GetSize()[0]` in a stereo GLX window). Parallel sheared cameras give `d(z) = 2 t F (1 - f / z)` pixels (perspective, F = H / (2 tan(view angle / 2)), f the focal distance, t = tan(angle / 2) the shear), `d(z) = t (z - f) H / scale` for a parallel projection. The scene's depth range along the view direction (the 8 corners of `ComputeVisiblePropBounds`) gives the largest t under which the far side stays inside S and the near side inside P: `t = min(S / (2F (1 - f / zmax)), P / (2F (f / zmin - 1)))`; a flat scene at the focal plane takes the infinity bound `S / (2F)`. This is the edition's practice (the largest separation the limits allow, as the Theme Studio's camera fit does), not Daniel's words. At the default limits (10 and 4) the popped limit binds first (a scene with the focal plane in the middle), so the far side uses less than the sunk limit.
- **Live.** KWin rewrites `_KDE_NET_WM_STEREO_DEPTH_LIMITS` when the person's limits change; the program polls the property each tick of its event loop (one read) and renders again when the state or the numbers changed. States: delivered, not offered (support under 10 or a library older than 1.10), not delivered yet; with none of them the eyes are the same picture and the log says so in the program's ten languages (`window::pollStereoDepth`).
- **Our Mesa's GLX stereo window already carries the property** (`[2560, 1024]` = 10.0 and 4.0 in 24.8 fixed point on the declared window), the program declares nothing itself; `x11_props.py` does not list it, a `list_properties()` walk does.
- **Proof.** `winproof2.py STEREO MONO SUNK POPPED` (`OFFSET=3 EYEW=1200`) predicts the three squares of `depth4.ply` from the limits and the mono capture. Measured: limits 10/4 near -2, far +2 px (predicted -2.5, +1.5); the same window after `[StereoDepth] SunkLimit=20 PoppedLimit=8` in kwinrc and a reconfigure: -5, +3 (predicted -5.0, +3.05), at 125 % the same as at 100 % (the rig's display factor is 1); a parallel projection -2, +2 (both bound by the popped limit); the staged +stereo3d1 with its fixed 2 degrees -35 and +21 against limits that allow 2.5 and 6.25; no limits (property hidden by an `LD_PRELOAD` of `XGetWindowProperty`, `shim.c`): both eyes equal, one sentence in the log (checked in en and pt_BR). The centroid is an integer pixel, so predictions are checked to 1 px.
- **Pair thumbnails keep their fixed angle** (an image has no window to take limits from; `f3d-thumbnail-pair` gives 2 degrees by `window::setStereoImageEyeAngle`, a method and not an option; its pictures are identical to +stereo3d2's, 0 pixels differ): their depth has no recorded design, Daniel's call.

### Traps met in milestone 4
- **`'glx' was not declared`, `vtkF3DGLXRenderWindow` not a class:** `VTK_USE_X` comes from `vtkRenderingOpenGLConfigure.h`; an `#include` under `#ifdef VTK_USE_X` placed before that header is silently skipped. Include the configuration header first.
- **A patch that did not change after the fix:** `git format-patch -1 -o DIR` leaves an old file of the same name in DIR (and `--force` is not an option); remove the file, regenerate, grep the patch for the new lines, then rebuild. The first rebuild of this milestone compiled the old patch.
- **Link gate: `libavcodec63 ... Depends libaom3 (>= 1:3.15.3) ... [no choices]`** when the archive has the published tree but not deb-multimedia: the tree's `libavcodec63` (epoch 10, dmo) wins and its library is in deb-multimedia only. Put deb-multimedia (`https://www.deb-multimedia.org`, suite forky, keyring mounted at `/dmo.pgp`) in the archive configuration beside Debian and the tree.
- **A new Build-Depends from our tree** (`libstereo-declare-dev (>= 1.10.0)`) goes into the builder image (`dpkg -i` from the pool) and into the shlibs line of the Depends (`libstereo-declare1 (>= 1.10.0)` appears by itself).
- **`kscreen-doctor ... Invalid config`** on the virtual output, with or without a D-Bus session: set the scale with `kwin_wayland --virtual --scale 1.25`. `qdbus6` and `kwriteconfig6` are not in the rig image: write the kwinrc group with `printf` and reconfigure with `dbus-send --session --dest=org.kde.KWin --type=method_call /KWin org.kde.KWin.reconfigure`.
- **A library option that sets the separation stays reachable through the generic option switch and the configuration file.** Symptom: `f3d --help` offers only "Enable 3D" and the resolution, yet `f3d --stereo -D render.stereo_eye_angle=6` drew the two eyes -104 and +63 px apart (the same window with the person's limits: -2 and +2), and a configuration file with that option did the same. Cause: removing the command line option (milestone 2) left the libf3d option, which the generic `-D` switch, the configuration files and the API all write; milestone 4's limits only applied when the option was zero. Fix (+stereo3d3, patch 0009): in the edition's build (`F3D_WITH_STEREO_DECLARE`) the option is not used at all, from any route, and a non-zero value is said once in a warning in the ten languages (`library/private/depth_notice.h`; never ignored in silence); the pair of an image takes its angle from `window::setStereoImageEyeAngle`, a method and not an option. How it was found: the reviewer ran the same window with `-D`; the red row is part of the proof now (the option set: still the limits' numbers, plus the sentence in the log). Rule of thumb: after removing a control from a program, grep the library for the option it wrote and try every route that writes options (`-D`, config files, the API), not only `--help`.
- **A rig container left running for two hours** (the interrupted command): remove it by its literal name before the next case.

## CloudCompare in stereo (ORDER 17, milestone 5)

cloudcompare 2.13.2+git20240821+ds-7+stereo3d1+lc1, Debian's own Qt 5 source in `sparky-os/packages/cloudcompare-stereo-17` (three patches, Lean Code, link gate, `check-debs`). Role lists (scientist and engineer, `roles.tsv`) and a Media entry of the app center (fork branch order17f), not the image.
- **What upstream has.** Debian's source has a quad-buffered stereo window (`ccGLWindowStereo`, a `QWindow` in a widget container) and a dialog of glass types and physical parameters (screen width, distance, eye separation 64 mm, strength). Upstream's side-by-side mode (pull request 2274, merged 2026-02-03, Daniel Girardeau-Montaut) does not apply to the 2024-08 source (11 of 17 hunks fail in the renderer, 4 of 5 in mainwindow); it was read and not needed, because our Mesa declares the quad-buffered window.
- **The window gets no stereo visual: cause.** `ccGLWindowStereo` kept the stereo `QSurfaceFormat` in `m_format` for the OpenGL context and never set it on the window; Qt chooses the native window's visual from the window's own format, so the visual had no GLX_STEREO and `isQuadBufferSupported()` said no (M1's "Quad Buffered Stereo not supported" and the lead about the default format). Found by reading the constructor after the rig showed the window's tree ("3D View Stereo 1" five container windows deep) and no declaration. Fix: `setFormat(m_format)` (patch 1).
- **One mode.** The dialog is not built (patch 2), the glass type is neither stored nor read, the exclusive full screen requirement and the forced field of view are gone; the toolbar's Enable 3D draws the generic quad-buffered path.
- **Separation = the person's limits** (patch 3, the maths of F3D's section: `t = min(S / (2F (1 - f / zMax)), P / (2F (f / zMin - 1)))`, e = t f, with CloudCompare's own `zMinDisplayed`, `zMaxDisplayed` and focal distance; F = half the view's width in pixels over `distanceToHalfWidthRatio`). `StereoParams` lost the physical fields. A QTimer polls the limits every 250 ms and says once, in the ten languages, when there are none.
- **The 3D view is the declared child.** Mesa lists the QWindow's native window in the toplevel's `_KDE_NET_WM_STEREO_CONTENT_CHILDREN` and declares it (`_KDE_NET_WM_STEREO_CONTENT` 3); the capture is two outputs wide with the rest of the window equal in both eyes. Measured on Stereo KWin +stereo3d58, Xwayland +stereo3d3, Mesa +stereo3d24, Qt 5.15.19, AMD render node.
- **The limits arrive on the child (KWin +stereo3d59, declaration support 11), and the child shows its pair at once (Mesa +stereo3d26).** `stereo_depth_x11_get_limits` on the declared child answers the person's limits (`_KDE_NET_WM_STEREO_DEPTH_LIMITS` 2560 1024 at the defaults 10 and 4); the program reads them from that window and from no other, with no default when they do not come. The real stack, no stand-in, no redraw sent, Enable 3D pressed once: ten of ten fresh starts a pair with the limits on the child; rows measured with `ccproof.py` (OFFSET=3): 10/4 near -2.00 / far +1.00 px (predicted -1.92 / +1.08), changed live to 20/8 near -4.00 / far +2.00 (predicted -3.83 / +2.16); the "no limits" sentence never shown in a session that has limits. The first pair, the infrastructure behind it and the red stack (flat, told) are in [native-linux: a declared child's limits and first pair](../native-linux/references/x11-declared-child-limits-and-first-pair.md).
- **Rig recipe.** `cc-first.sh` (kwin virtual with Xwayland, `LIBGL_DEBUG=verbose`, CloudCompare on `depth4.ply`, Return for the PLY dialog, one click on the last button of the left toolbar at 20,631, a capture five seconds later and nothing else sent to the window; CHANGE=1 appends kwinrc `[StereoDepth]` 20 and 8, reconfigures and captures again), `ccproof.py` (colour-segmented squares: red near, green on the focal plane, blue far; mask thresholds keep the blue background gradient and the axes symbol out; OFFSET=3), one fresh container per start.

### Traps met in milestone 5
- **The stereo capture stays one output wide ("shown flat") on a stack older than Mesa +stereo3d26 / KWin +stereo3d59:** two causes, a present made before Xwayland gave the child a surface and a flip that Xwayland completes as SUBOPTIMAL_COPY read as a copy; both are fixed below the program. The milestone-5 workarounds (ten F5 refreshes, up to four tries) are gone: do not bring them back, a flat first capture is a failure of the stack and is reported with the `LIBGL_DEBUG=verbose` lines.
- **X11 headers before Qt's:** `<X11/Xlib.h>` (through stereo-declare.h) defines `None`, `Status` and others, and Qt's `qurl.h` stops with "expected identifier before numeric constant". Keep the X11 calls in a file of their own (`ccGLWindowDepthLimits.cpp`).
- **`target_link_libraries` signatures:** the library used the plain form; adding `PRIVATE` stops CMake.
- **Lean Code needs clang** in the builder (the C token stream), and a source date not in the future ("modification time ... in the future").
- **A message sent only on a change is lost when the enabling path polls first:** enableStereoMode polled and the timer saw no change, so the equal eyes were silent; the timer alone polls now (found by a debug build: `make QCC_GL_LIB` in the build tree and the rebuilt library mounted over the installed one with `LD_LIBRARY_PATH` to find `libCC_FBO_LIB.so`).
- **`isExposed()` is false for the embedded window** whenever Qt has not delivered an expose: do not gate the property read on it.
- **Colour masks against a blue gradient:** a blue mask matched the background and a red or green one the axes symbol; use the saturated values (> 200 against < 70) and a box around the squares.

## A Qt Quick window on libf3d with a declared stereo area (ORDER 17, milestone 7)

The recipe (sparky-stereo-model-viewer in the build tree, sparky-os/packages):
- Qt6 and Kirigami on xcb (Xwayland): `QT_QPA_PLATFORM=xcb` when the person set none. libf3d's GLX window is made a child of the Qt window's X window (`f3d::window::setParentWindowId(id)`, our patch 0010 of the libf3d recipe, with `getNativeWindowId()`), so Mesa lists it in `_KDE_NET_WM_STEREO_CONTENT_CHILDREN` and Stereo KWin writes the person's `_KDE_NET_WM_STEREO_DEPTH_LIMITS` on it: libf3d's `pollStereoDepth` then separates the eyes by the limits and the viewer repeats nothing.
- libf3d lives in one worker thread (engine, window, `interactor.start(1/30, callback)`); the GUI thread posts commands (place, load, reset, play, stereo) that the callback drains. The QML item only reports its rectangle (`mapToItem(null)`, device pixels); the worker moves and sizes the child. The child is declared one view of the rectangle's size with `_KDE_NET_WM_STEREO_CONTENT_ONE_VIEW_SIZE` (CARDINAL/32 w,h), so a render resolution per eye other than the area's is scaled once, by KWin.
- Controls outside the rectangle stay flat (same pixels in both eyes: measure the strip above the area). Depth: three squares at known offsets (a mesh as PLY, a point cloud as PLY, a splat, a STEP of three plates) and the closed form of stereo-two-cameras; all four kinds matched within 1 px at limits 10/4 and live 20/8.
- Dialogs are windows already; every in-window popup (QQC2.Menu, a Kirigami action's sub-menu) needs `popupType: Popup.Window` or it is hidden under the native child. A Kirigami.Action with child actions cannot take it: use `displayComponent` with a ToolButton and your own Menu.

### Traps met in milestone 7
- A resized child showed the scene stretched twice as wide (symptom: squares 2:1, GLX_WIDTH half of the X width after a resize). Cause: not Mesa and not libf3d: the proof's `K3V_HIDE=notoffered` shim hid `_KDE_NET_WM_STEREO_CONTENT_SUPPORTED` from every caller, so Mesa believed the compositor announced nothing and used its legacy twice-as-wide rule (patch 0014: the X window holds both eyes). With a compositor that announces support, as Stereo KWin does, the drawable follows the X width after every resize (tests/glx-child-resize.c: green at a resize at 0 ms and at 3 s, with and without ONE_VIEW_SIZE; red only under the hiding shim). Fix: hide the property from libstereo-declare only (the shim checks `dladdr` of its caller), and size the child plainly. A first fix that measured the ratio and corrected the X width was wrong and is gone. Found by logging glXQueryDrawable next to XGetWindowAttributes, then by running the same resize in a bare GLX program with and without the shim.
- KF6's kservice does not read `InitialPreference`: a desktop entry's offers all get preference 1 (kbuildservicefactory.cpp:233) and the stable sort keeps the sycoca scan order, which changed between rebuilds of the cache (3 of 4 rebuilds put the viewer first, 1 put F3D). A default for a type is a line in a mimeapps list; the edition's is sparky-stereo-look's /etc/xdg/kde-mimeapps.list (a person's ~/.config/mimeapps.list still wins and survives a reinstall). `XDG_CURRENT_DESKTOP=KDE` must be set for kde-mimeapps.list to be read: kioclient in a rig without it ignores the file.
- On an NVIDIA machine a GLX client gets NVIDIA's own libGLX (glvnd), which offers no stereo visual: the viewer, F3D and CloudCompare are flat there with no declaration. With `__GLX_VENDOR_LIBRARY_NAME=mesa MESA_LOADER_DRIVER_OVERRIDE=zink` Mesa's GLX runs on the NVIDIA Vulkan driver and the pair, the declared child and the limits all work (same disparities as AMD). KWin itself may draw on software (no render node) in the rig; lane 501's capture there used Vulkan and its own X11 child, not GLX.
- Dropping a file on the 3D area added it to the scene by libf3d's own XDND handling, without the program knowing (title, recent files, errors unchanged). Fix: delete `XdndAware` on the child, set `XdndProxy` on the child to the Qt window and on the Qt window to itself; one `DropArea` over the whole window then takes every drop. Found with `tools/xdnd.py`, a drag source of pure X messages (a QML drag with xdotool never started in the rig).
- The first click of an xdotool session in the virtual KWin is lost: click twice before judging a button.
- Concurrent rig runs sharing one HOME overwrite each other's config (Enable3D, Resolution): one HOME per case.
- `LC_ALL=C.UTF-8` in the rig image makes gettext ignore LANGUAGE: set `LC_ALL=pt_BR.UTF-8` and generate the locale. Japanese shows boxes without a CJK font.
- KDECompilerSettings builds without exceptions: `kde_target_enable_exceptions(target PRIVATE)` for libf3d's throws; `KF6::I18nQml` is a target of KF6I18n, not a find_package component.
- libf3d's reason for a failed load is English: say the sentence in the person's language and log the reason.


### Round 3 (ORDER 17, milestone 7): a session's NVIDIA row, the packaged window, the desktop's arrangement
- A rig's NVIDIA row loads the session's environment or it measures a system nobody runs. The edition's hardware layer exports the Mesa vendor order, Mesa's GLX, zink and LIBGL_KOPPER_DISABLE=1 from /etc/xdg/plasma-workspace/env/sparky-stereo-opengl.sh, reading /etc/sparky-stereo/opengl-stereo.conf (`desktop=nvidia`, written by `sparky-stereo-opengl-default` from /sys and /dev/dri: with only the NVIDIA card's render node visible it answers `desktop=nvidia card=card1`). The recipe: a real startplasma-wayland login (stereo-proof-rig, login-splash), KWin given NVIDIA's own EGL for its start only (the container has no DRM master and Mesa's zink cannot make KWin's EGL on that node: `eglInitialize failed`, KWin then draws on the processor and the hardware layer says so), then every program started with plasmashell's own environment read from /proc/PID/environ. The viewer, F3D and CloudCompare were then pairs on NVIDIA through zink with the same disparities as AMD.
- Symptom: the viewer stops at start with "Cannot find GLX library" while F3D runs. Cause: `f3d::engine::createGLX()` loads `libGLX.so`, the unversioned development symlink (libglx-dev), which a user's system lacks; F3D itself uses `engine::create()`. Fix: the viewer uses `engine::create(false)` (0.1.1). Found by a rig image without libglx-dev; earlier rigs had it, so their green runs were not the user's system.
- Folder View `arrangement`: the config key's label in main.xml says 0 = Rows, 1 = Columns; System Settings lists index 0 as "In Columns" and 1 as "In Rows"; measured in a fresh login of Plasma 6.7.4, 0 (the default) lays the icons left to right along the first line and 1 stacks them down the first column. Prove a desktop default by capturing the desktop with and without its icons and diffing the two pictures (the icons' positions), not by reading the key.
- A desktop probe that must act like a person runs the program through the session's environment (`insession`), and fake input for a Wayland-native program (Dolphin) comes from KWin's fake input client, not xdotool.
