# Bluetooth voice (HFP) over a USB dongle: telling a dongle that cannot carry voice from a profile or codec problem

Written 2026-11-07 (ORDER 133), extended 2026-11-26 (row 129). Versions measured: Linux 7.3.1 and 7.3.4, BlueZ 5.87 and 5.88, PipeWire and WirePlumber 1.6.9 and 0.5.18.

## Which layer refuses

Read the layers in this order, each with one command.

1. **The controller's buffers.** `btmon -w FILE` before the adapter powers up, `btmon -r FILE` afterwards: the reply to `Read Buffer Size` lists `SCO MTU` and `SCO max packet`. `hciconfig -a hci0` shows what the kernel kept (`SCO MTU: 48:0`).
2. **The kernel's decision.** `hci_cc_read_buffer_size()` (net/bluetooth/hci_event.c) sets `sco_pkts` from the reply, applies `HCI_QUIRK_FIXUP_BUFFER_SIZE` (64 and 8), then sets `sco_pkts = 0` when `read_voice_setting_capable()` is false. btusb sets `HCI_QUIRK_BROKEN_READ_VOICE_SETTING` on every fake CSR clone it detects (`btusb_setup_csr()`: HCI revision different from the LMP subversion). `hci_connect_sco()` then returns `-ECONNREFUSED` before any HCI command is sent. Measured on a clone (USB 0a12:0001, bcdDevice 88.91, LMP subversion 0x2312): the controller answered `SCO MTU: 48  SCO max packet: 16` and the kernel logged `SCO MTU: 48:0`, so the zero buffers were the kernel's rule and not the chip's report.
3. **The connect.** PipeWire's native backend logs `sco_do_connect: connect(): Connection refused`; in btmon no `Setup Synchronous Connection` command appears. With a working buffer count the command appears and `Synchronous Connect Complete` (link type eSCO, air mode CVSD) follows.
4. **The USB side.** `lsusb -v -d VID:PID`: interface 1 must have isochronous alternate settings. mSBC (transparent data) needs alternate setting 6; PipeWire logs `bluetooth host adapter does not support USB ALT6` and offers no mSBC profile.
5. **The profile and codec.** `pw-dump` lists the card's profiles (`headset-head-unit` on the gateway side, `audio-gateway` on the hands-free side in PipeWire 1.6). A missing profile is a profile problem; a profile whose transport fails is layer 3 or 4.

## The two-machine test with no person wearing a headset

The gateway is a disposable VM with the adapter (QEMU `usb-host`, vendor and product), BlueZ and PipeWire. The headset is a second machine with a real adapter. A known tone is the headset's microphone, and the gateway records the headset's microphone and checks the tone.

- Gateway: `bluetoothctl --agent NoInputNoOutput` fed from a fifo; a watcher answers `yes` to every `(yes/no)` prompt. Roles `[ hfp_ag hsp_ag ]`. Select the card profile, `pw-record --target bluez_input.ADDR.N`, `pw-play --target bluez_output.ADDR.N` for the other direction.
- Headset: roles `[ hfp_hf hsp_hs ]`, trust the gateway as soon as it is paired, select the profile `audio-gateway`, play the tone into the card's sink.
- Check: `bench/tone-check.py WAV --freq HZ` passes only when the loudest peak is within the tolerance, the level is above the floor and the peak holds enough of the energy. Prove the checker with a pure tone (pass), the wrong frequency, silence, a quiet tone and noise (all must fail).
- Control: the same run on the unpatched kernel must show the refusal of layer 3.

## Traps met

- **Symptom:** the first command times out (`command 0x1001 tx timeout`, `CSR: Local version failed (-110)`) and every retry does too. **Cause:** these clones answer only after the device has been suspended once; a USB reset (QEMU's default when the guest resets the port) undoes it, and the guest cannot suspend the host device. **Fix:** `-device usb-host,vendorid=...,productid=...,guest-reset=false`, and start the guest only when the host driver has finished its own retries (powered, idle for 10 s). **Found by:** the guest's `btmon` showing nine `Read Local Version` commands and no event.
- **Symptom:** the headset side shows no Bluetooth devices in `pw-dump` and advertises no hands-free profile. **Cause:** WirePlumber's Bluetooth monitor waits for an active seat; a desktop session without one has none (`monitor.bluez.seat-monitoring`). The login screen's own WirePlumber may hold the audio gateway profile, and oFono, when running, holds the hands-free profile before PipeWire. **Fix:** a drop-in with `support.logind = disabled` and `monitor.bluez.seat-monitoring = disabled` in the `main` profile, stop the other holders for the test and put them back. **Found by:** `bluetoothctl show` listing the profile UUIDs (`0000111e` hands-free, `0000111f` audio gateway) before and after each change.
- **Symptom:** pairing stops at `Request authorization` or `Authorize service` and the link drops. **Cause:** bluetoothctl's agent waits for a typed answer. **Fix:** the fifo watcher above, and `trust` the peer as soon as it is paired so services need no authorization.
- **Symptom:** one run in three finds no `hci0` in the guest. **Cause:** the dongle re-enumerated on the host (new device number) while the container held the old node. **Fix:** find the node by vendor and product in sysfs for every start, and retry the guest once or twice.
- **Symptom:** `btmon > file` is empty or cut. **Cause:** stdout buffering when the guest powers off. **Fix:** `btmon -w file.snoop` and decode with `btmon -r` afterwards.
- **Symptom:** the temperature gate reads 66 C on an idle machine. **Cause:** the battery sensor is among the hwmon files. **Fix:** read only the `k10temp` (or the CPU package) sensor.
- **Symptom:** the SCO link is made (`Synchronous Connect Complete`, eSCO, CVSD) but no `SCO Data` packet crosses it. **Cause (found by reading `btusb_work()`):** btusb chooses the USB alternate setting from `hdev->voice_setting`; on a controller whose voice setting is never read (`BROKEN_READ_VOICE_SETTING`) it stays 0, so a 16 bit CVSD link (setting 0x0060, as `Setup Synchronous Connection` asks) gets alternate setting 1 (9 bytes) instead of 2 (17 bytes). **Fix to test:** write the voice setting at setup (`HCI_OP_WRITE_VOICE_SETTING` 0x0060), which also sets `hdev->voice_setting`. **Found by:** `btmon` showing `Input Sample Size: 16-bit` in the command and `grep voice_setting drivers/bluetooth/btusb.c`.
- **Proving a script that unloads the Bluetooth stack:** run it in a VM guest on the same kernel build with the real modules and a stand-in `systemctl`, and test the restore after a normal end, an insmod error, SIGINT (a background job ignores SIGINT: start it with Python's `signal.SIG_DFL` and `execvp`), SIGTERM, `kill -9` (a detached watcher does the restore), a deadline and an abort flag; include a check that must fail while the test modules are loaded.
- **Chip identity (public record):** Hans de Goede's `0671c0662383` (2020-12-05) describes a fake CSR receiver with a Barrot 8041a02 chip, bcdDevice 0x8891, HCI revision 0x0810 and LMP subversion 0x1012; the dongle in these tests has the same bcdDevice and HCI revision with subversion 0x2312, so treat it as that family. His two findings: the bulk RX endpoint reports nothing until the device has been suspended once, and remote wakeup is broken on that endpoint. Ismael Ferreras Morezuelas's `f4292e2faf52` (2021-07-17) applies the force-suspend to every fake and says of these clones: "Except on Windows, they work fine". Nothing public says what Windows sends.
- **Symptom:** `CSR: Couldn't suspend the device for our Barrot 8041a02 receive-issue workaround` after a module reload or rebind, although the first probe after boot suspended fine (a 330 ms gap and no warning). **Cause:** `btusb_open()` sets `needs_remote_wakeup`, and the USB core's `autosuspend_check()` returns -EOPNOTSUPP for a device that cannot wake up; the workaround ends with `device_set_wakeup_capable(udev, false)`, so every later probe fails. **Fix to test:** give the capability back from the configuration descriptor before the force-suspend (`USB_CONFIG_ATT_WAKEUP`). **Found by:** reading `drivers/usb/core/driver.c` after the warning appeared only on the second probe; torvalds/linux master still has the original code.
- **Symptom:** eSCO is up (`Synchronous Connect Complete`, Status Success, eSCO, CVSD, 60-byte packets) with the voice setting written and the chip's own 48:16 buffers kept, but `btmon` shows 0 SCO data packets and the recording is silence. Not yet explained; the next suspects are the isochronous endpoint of the same receive issue and what Windows writes at init.
- **Symptom:** `rmmod bluetooth` says "in use by: bnep" after `systemctl stop bluetooth`, and the holder list shows bluetoothd. **Cause:** D-Bus activation (KDE's Bluetooth monitor asks `org.bluez`) starts bluetoothd again at once. **Fix:** `systemctl mask --runtime bluetooth.service` for the swap and unmask it after.
- **Symptom:** the hands-free side lists no `Audio/Source` or `Audio/Sink` node. **Cause:** PipeWire 1.6 shows the call as streams, `bluez_input.*` (Stream/Output/Audio) and `bluez_output.*` (Stream/Input/Audio). **Fix:** start the tone player and the recorder with `node.autoconnect = false` and join them with `pw-link` (port names such as `output_MONO` and `input_MONO`); checked on the A10 with a tone through two such streams (1000.1 Hz, SNR 70 dB).

## Native windows on the dongle (2026-11-07): what was measured, and where it stopped

- Three windows with the dongle on the station's own stack, the other end a real adapter on a second machine: the stock btusb, a variant that writes the voice setting 0x0060 and keeps the chip's 48:16 (B), B plus the wakeup capability restored before the force-suspend (C), and the Bluetooth core swapped as well (A). B: pairing, HFP, `Setup Synchronous Connection`, `Synchronous Connect Complete` (eSCO, CVSD, 60-byte packets both ways), 0 SCO data packets, a recording that is silence. C: `CSR: Local version failed (-110)` after the reload (a reload leaves the clone without its first answer; see the first trap). A: no card.
- It is a known limit of these clones (public record above), so the work stopped there: the kernel's rule that leaves such a clone without SCO is the maintainers' guard against a controller lock-up, and a patch that removes it for every owner of a clone was not kept.
- **Symptom:** the second variant of a run finds the second machine's bench lock still held. **Cause:** the headset-side process of the first variant was still in its cleanup (restoring the pairing and the audio defaults) when the next one started. **Fix:** before starting the next session, wait until `flock -n` on the lock succeeds, or until the previous process has exited.
- **Symptom:** a swap script's first try failed at once with the Bluetooth module in use. **Cause:** `kdeconnectd` held an RFCOMM socket and the user's WirePlumber a SCO listening socket; neither goes away with `bluetooth.service`. **Fix:** swap only the USB driver when the core can stay; pause the holders only when the core must change.

## The kernel series for the clone (row 129, series group 48): what the guard protects and how SCO comes back without reaching it

Written 2026-11-26 on Linux 7.3.4 (the edition's build 18); bluetooth-next f57f78086a, torvalds master at v7.4-rc4 and linux-7.3.y v7.3.6 have the same code in every function below.

- **What the guard is.** Pedro Nishiyama's 14d17c78a4b1 ("Bluetooth: Disable SCO support if READ_VOICE_SETTING is unsupported/broken", 2025-03-01) sets `sco_pkts = 0` in `hci_cc_read_buffer_size()` when `read_voice_setting_capable()` is false, with the reason "A SCO connection without the proper voice_setting can cause the controller to lock up". In the review thread (linux-bluetooth, V3 1/2, 2025-02-24 to 02-27) he reported on these clones that an SCO connection could be made "but the connection is not usable" (no sound, then "corrupted SCO packet" in the log), and Luiz Augusto von Dentz asked for SCO to be disabled when the voice setting cannot be read.
- **Every place that reads the counts.** `hci_connect_sco()` refuses with `-ECONNREFUSED` when `sco_pkts` is 0 (hci_conn.c); the scheduler sends at most `sco_pkts` packets in a row without SCO flow control, `sco_cnt` with it (hci_core.c, flow control only with `HCI_QUIRK_SYNC_FLOWCTL_SUPPORTED`); a SCO socket's MTU is `sco_mtu`; `HCIGETDEVINFO` reports both; the `HCISETSCOMTU` ioctl (`hciconfig hciN scomtu MTU:PKTS`, root) sets both after init, so upstream already lets an administrator lift the guard at run time.
- **What "proper voice setting" means in code.** A fake's voice setting is never read, so `hdev->voice_setting` stays 0. `btusb_work()` picks the isochronous alternate setting from it (`voice_setting & 0x0020`: 16-bit input gives alternate setting 2 for one link; otherwise the number of links, 1), while the link itself is set up with the socket's setting (0x0060, 16-bit, as `Setup Synchronous Connection` asks); an incoming link is accepted with `hdev->voice_setting` as its content format (hci_event.c). So with the guard lifted and nothing else, a 16-bit link runs over the 8-bit alternate setting: the guard's own case.
- **The held ORDER 133 form was wrong in three ways** (held from 2026-11-07 as b481dcaa, then `kernel/held/csr-clone-sco`): it left the voice setting at 0 (the case above; in a VM with USB passthrough the dongle completed eSCO, crossed no data and left the USB bus about 8 s later); it reused `HCI_QUIRK_FIXUP_BUFFER_SIZE`, which replaces the clone's own 48 bytes and 16 packets by 64 and 8, more than the SCO packet length the controller declares; and it lifted the guard in the core for every controller with that quirk, so any clone given `btusb.force_scofix=1` lost the guard.
- **Group 48 instead:** `HCI_QUIRK_VOICE_SETTING_BY_DRIVER` keeps the reported SCO buffers only for a driver that writes the voice setting itself; btusb sets it for this clone alone (fake detection plus bcdDevice 0x8891, HCI revision 0x0810 and LMP subversion 0x2312; a genuine CSR8510 also reports bcdDevice 0x8891, and the Barrot 8041a02 with subversion 0x1012 is left as it is) and writes 0x0060 in `post_init`, which runs after the HCI_Reset of init and before any SCO connection can exist. A failed write sets `sco_pkts` back to 0; `btusb.disable_scofix=1` turns the exception off; `dmesg` says `CSR: Writing the voice setting after init, SCO kept`.
- **It ships only after a person hears the microphone.** With SCO enabled, `sparky-stereo-hardware`'s notice (it keys on `sco_pkts` 0) no longer fires for this clone; if voice still does not cross, the group is dropped so the person is told again.
- **Searching upstream for this kind of fault:** clone the list's public-inbox mirror (`git clone --bare --shallow-since=2025-01-15 https://lore.kernel.org/linux-bluetooth/0`, about 130 MB, 23,303 messages), list subjects with `git log --format=%s` and search bodies with `git log -G 'BROKEN_READ_VOICE_SETTING|force_scofix|corrupted SCO packet'`; read a message with `git show HASH:m` through Python's `email` module. Compare function bodies across trees (stable tags fetched at depth 1, bluetooth-next and master shallow since a date) rather than trusting `git log -G` on a shallow clone: the graft commit at the boundary matches every symbol.
- **Trap: a case-insensitive subject search** for `PATCH V4` matched another series' `[PATCH v4 ...]` posted the same day; anchor the pattern on the subject's own words.

## Proving a SCO change without the clone: KUnit and a virtual USB clone

The scripts are in the build repository, `kernel/tests/csr-clone-sco` (its README has the commands).

1. **KUnit on the handler.** The test file is included at the end of `hci_event.c` (`CONFIG_BT_HCI_EVENT_KUNIT_TEST`, `bool`, `depends on BT=y && KUNIT=y`), so the static `hci_cc_read_buffer_size()` and `hci_cc_write_voice_setting()` are called with the parameters a controller sends. A device from `hci_alloc_dev_priv()` needs no registration and is freed through `kunit_add_action_or_reset()` (an unregistered `hci_dev` is only `kfree`d). Mark a controller that lists HCI_Read_Voice_Setting with `commands[9] |= 0x04`. Run it on QEMU x86_64, never UML (the edition's tree does not build there). Result: 10 of 10 with group 48, 8 of 10 without.
2. **Red for a test that names a new quirk.** Apply only the header hunk of the fix (`git apply --include='include/*' FIX.patch`) and the test: it compiles, and the old behaviour fails exactly the cases the fix is for.
3. **A virtual USB clone, so the real `btusb_probe()` and `btusb_setup_csr()` run.** In a QEMU guest booted from the kernel package itself: `dummy_hcd` (`is_high_speed=0`, full speed as the clone), a configfs gadget 0a12:0001 with the clone's bcdDevice, one FunctionFS function whose descriptors copy the clone's first interface (interrupt 0x81 of 16 bytes, bulk 0x02 and 0x82 of 64) and give the isochronous interface alternate setting 0 only. Flag `FUNCTIONFS_ALL_CTRL_RECIP`, or btusb's HCI commands (class requests to the device, `bRequestType` 0x20) never reach the daemon. The daemon bridges H:4 to a `btvirt -s` server device; Debian's bluez 5.88 source with a 28-line test patch (`BTDEV_IDENTITY=VER:MANUFACTURER:HCI_REV:LMP_SUBVER:SCO_MTU:SCO_PKTS`) makes that device answer Read Local Version and Read Buffer Size as the clone, also after HCI_Reset. A second server device driven by a small host program is the headset.
4. **What the kernel keeps, read in the guest:** `hciconfig -a` (`SCO MTU: 48:16` or `48:0`), `/sys/kernel/debug/bluetooth/hci0/voice_setting`, a SCO socket's connect and its `SCO_OPTIONS` MTU, and btusb's `set USB alt:(N) failed!` (the virtual device has no alternate setting above 0, so the one btusb asks for shows in its log). Measured on build 18: clone red `48:0`, 0x0000, refused; green `48:16`, 0x0060, connected, MTU 48, alternate setting 2; the held ORDER 133 form `64:8`, 0x0000, MTU 64, alternate setting 1.
5. **Controls in the same rig:** the Barrot 8041a02 clone (subversion 0x1012) and a genuine CSR8510 (revision equal to subversion, 0x22bb) give the same answers with and without the series.

Traps of the rig, each with how it was found:
- **Symptom:** `Opcode 0x0c03 failed: -110` on a vhci controller nobody answers, and btvirt logs `Failed to open Virtual HCI device` and exits. **Cause:** hci_vhci creates a controller by itself one second after `/dev/vhci` is opened (`vhci_open_timeout()`), and an emulated guest on a loaded machine needs longer than that between btvirt's open and its create request, even when btvirt runs from tmpfs. **Fix:** no vhci controller in the rig; the headset is a second btvirt server device. **Found by:** btvirt's own log, then `drivers/bluetooth/hci_vhci.c`.
- **Symptom:** `SCO MTU: 72:0` in the guest while a direct query of btvirt said 48. **Cause:** btdev reloads its default buffer sizes on HCI_Reset (`btdev_reset()` calls `btdev_init_param()`), and the kernel resets the controller during init. **Fix:** apply the identity after every reset too; the check program sends HCI_Reset first.
- **Symptom:** the 9p root does not mount (`mounting root on /newroot failed: Invalid argument`). **Cause:** `modprobe --show-depends 9p 9pnet_virtio` takes the second name as a parameter of the first, so 9pnet_virtio was never in the initramfs. **Fix:** `modprobe -a`.
- **Symptom:** no `usb_gadget` folder in configfs. **Cause:** configfs is a module in the edition's kernel and was mounted before anything loaded it. **Fix:** load the modules first. FunctionFS itself appears in `/proc/filesystems` only once the first `ffs.NAME` instance exists, which is normal.
- **FunctionFS limits:** it counts every endpoint descriptor as its own endpoint and enables them all, so alternate settings that reuse an endpoint address cannot be described; a real isochronous path is out of reach of this rig.
- **The published build 18 boots with a `vsnprintf` WARNING** from `input_print_modalias_parts()` in a guest; that is the EV_BTN group's negative size, fixed on main by row 664 (6e9b57f0), not a Bluetooth matter.

## Telling the person (no silent failure)

A microphone that stays silent is the worst answer. `sparky-stereo-hardware` reads each adapter through the HCI socket (`HCIGETDEVLIST` 0x800448D2, `HCIGETDEVINFO` 0x800448D3, as any user; `struct hci_dev_info`: flags at 16, features at 21, `sco_mtu` at 48, `sco_pkts` at 50) and keeps a problem in the engine for an adapter that is up, BR/EDR capable (LMP features byte 4 bit 5 clear) and has `sco_pkts` 0. Python builds may lack `socket.AF_BLUETOOTH`: use 31 and 1. On a real chip (Qualcomm Atheros) the same read gives `sco 50:8` and no notice.

## A new headset or speaker takes the sound

- **Symptom:** a Bluetooth or USB output connects and the sound stays on the chosen one. **Cause:** WirePlumber adds 30000 to the priority of the sink the person chose, and `find-best-default-node` returns at once when a node above 15000 is already selected, so no priority rule can win (`priority.session = 40000` on the new sink was measured: no effect). **Fix:** a hook before `default-nodes/find-selected-default-node` that sets `selected-node` and `selected-node-priority` 50000 for the newest eligible sink; it changes only the live default, so the chosen sink returns by itself when the output goes.
- **"Newly connected":** a sink that appears in the first 10 seconds after WirePlumber starts (a desk DAC at boot) is recorded by a `node-added` hook and never moves the default; the same sink plugged in later does, and again after it left (the record is pruned at each `select-default-node`). Eligible: `bluez_output.*` and `device.bus = usb`, any form factor (Daniel, 2026-11-07: "speakers as well"); a PCI sink never.
- **Symptom:** the script is never loaded with the profile entry `optional`. **Cause:** a feature set `optional` alone loads nothing; a component loads only when a required feature requires or wants it. `required` loads it but stops WirePlumber (exit status 78/CONFIG, no sinks) if the script fails to load, so a convenience could take the sound away. **Fix:** the profile requires a small virtual component (`policy.sparky-new-output`) that only `wants` the script. Measured with WirePlumber 0.5.18 and a script that does not parse, one that fails at load, and a missing file: WirePlumber starts, the sinks are there, a test sound plays, and the user journal has `optional component '...' failed to load`; with the profile requiring the script itself the same broken script left WirePlumber failed and `wpctl status` with no sinks. **Found by:** `wireplumber.conf`'s profile and component comments, then the three broken scripts.
- A virtual sink for such tests: `pw-cli create-node adapter '{ factory.name=support.null-audio-sink node.name=... media.class=Audio/Sink object.linger=true device.bus=usb }'` and `pw-cli destroy ID`; it survives a WirePlumber restart, which is how "present at start" is tested. `pw-loopback` sinks did not show in `wpctl status`.
- `bluetooth.autoswitch-to-headset-profile` is true in WirePlumber 0.5.18's settings (`wpctl settings`); the switch back after recording needs a real headset.
