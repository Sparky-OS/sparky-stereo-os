# contrib-ffmpeg: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Answering a bot or human review on a SEI bitstream filter series: for each finding write a test that is red on the first revision and green on the new one (4 FATE entries: cbs-h264-frame-packing, cbs-hevc-frame-packing, cbs-hevc-frame-packing-constraint, cbs-hevc-frame-packing-sublayers), check them per commit with `make fate-cbs` in its own worktree (C1 to C4 37 pass, C5 41 pass), then full FATE with GCC and clang, then `git range-diff` old against new head for the reply, push with `git push --force-with-lease=<branch>:<old sha>`. Reply point by point with the clause page. (lane ffmpeg-25395-review-416)

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: a FATE test fails in a clean tree. Cause: FATE dependencies include helper programs used while probing the test input (extract_extradata when later cases rely on codec-parameter extradata), and an amended test's own registration fix belongs in that test's commit. Fix: declare the helper and fold the registration into the test commit. Found by: build matrices gcc/clang with and without the feature disabled (lane ffmpeg-round7-213-gpt)
- Symptom: after rebasing a series on a newer master, `fate-cbs-h264-metadata-sei` fails in GCC full FATE although every earlier per commit run passed. Cause: a test added to master after the PR base (b6b101f2e9) has an md5 that changes because commit 1 now places a new H.264 SEI before the IDR slice. Fix: update that reference inside commit 1 and say so in the PR description ("no changed output among shared tests" is no longer true). Found by: the first full GCC FATE run on the rebased head listed exactly one failing entry. (lane ffmpeg-25395-review-416)
- Symptom: two E-AC-3 tests (eac3-5, eac3-core-bsf) fail in one full GCC run, pass alone, clang full FATE has 0 failures out of 6075. Cause: not found here, but lane 377 found uninitialised reads in the E-AC-3 parser (Valgrind 3.27.1, 51 errors on the_great_wall_7.1.eac3, fixed by patch 0065, tested by 0066). Fix: run the failing entries alone, run clang, report both totals in the PR text and say which tests are known flaky. Found by: rerunning the two entries alone. (lane ffmpeg-25395-review-416)
- Symptom: a FATE test for stereo side data needs `showinfo`, `sed`, `echo` and `&&` chains and the maintainers ask for plain entries; `ffprobe` shows no Stereo 3D fields for frame side data. Cause: ffprobe printed the fields only for packet and stream side data. Fix: add the commit "fftools/ffprobe: print the fields of Stereo 3D frame side data" first, then one plain probeframes entry per sample with container only inputs from make rules (TAG = GEN); compare every regenerated reference frame by frame with the old one (condense.py). Found by: trying to write the plain entry. (lane ffmpeg-24628)
- Symptom: a multiview FATE test passes at 4 threads and a layer leak is invisible. Cause: frame thread copy timing hides leaks of shared decoder state. Fix: run multiview state-leak entries at THREADS=1 (the report ran every new test at THREADS=1 and 4). Found by: leak visible at one thread only. (lane ffmpeg-24628)
- Proving a new test can fail: mutate the code and require the entry to fail (VVC low delay reset removed fails temporal-low-delay; movenc rejecting any flag fails upsampled-mp4; helper bypassed fails both container entries); also run the tests of PR B on a build without PR A's decoder code (17 of 20 entries differ, the 3 that match are regression coverage). (lane ffmpeg-24628)
- Reviewing a second bot round on the same series (ORDER 476): clone the fork, rebase on master and list `git log up/master..` on the touched files first (181 commits, none on them); copy the new test into a worktree of the old head and run it there for the red column, run it on the new head for the green; build with `tools/dev.sh` style containers (image with gcc, clang and nasm, `--network none`, source read-only, build dir separate). (lane ffmpeg-bot-review-476)
- Symptom: `make tests/api/api-bsf-frame-packing-test` says "No rule to make target" or "Nothing to be done" and the binary still lacks the new test lines. Cause: API test programs are built as dependencies of their FATE entries, not as plain targets. Fix: `make fate-cbs-h264-frame-packing` builds the program, then run it by hand with the sample. Found by: the new lines missing from the output after the edit. (lane ffmpeg-bot-review-476)
- Symptom: a test message in an SEI NAL unit with nuh_layer_id 1 vanishes from the output. Cause: cbs_h2645.c skips every HEVC NAL unit with nuh_layer_id above 0 except VPS, SPS and PPS, so a bitstream filter built on CBS never sees other layers. Fix: no per layer tracking, no test for it. Found by: 0 arrangements counted in the packet before any filtering. (lane ffmpeg-bot-review-476)
- Symptom: a fabricated SEI payload of type 0 or 129 makes the filter fail with "VPS id 5 not available for active parameter sets" or "SPS id 1 not available", while types 1 and 200 pass. Cause: CBS parses and checks the buffering period and active parameter sets messages and keeps unknown types as raw bytes. Fix: use types 1 and 200 when a test only needs a message of a group that takes a NAL unit for itself. Found by: the filter log of the test. (lane ffmpeg-bot-review-476)
- Symptom: the committed reference of a frame packing test shows payload 45 next to payloads 129, 0 and 1 and looks right. Cause: describe prints messages, not NAL units, and the arrangement had been added to the unit of the buffering period (H.265 D.3.1 p.323 forbids it). Fix: print the payload types of each SEI NAL unit in the test (sei_layout) and give the new message a unit of its own. Found by: the first review finding of ORDER 476, reproduced with a fabricated payload 200 and 1. (lane ffmpeg-bot-review-476)
- Symptom: a cancellation that reaches a B picture before a persistent arrangement is output is missed. Cause: persistence was tracked in decoding order, while H.264 D.2.26 p.391 and H.265 D.3.16 p.353 run it in output order. Fix: record each message with the packet timestamp and ask which ids are in force at the timestamp of the picture that gets the new message; give packets explicit pts in the test (pts 0, 8, 4 in decoding order). Found by: a three packet sequence whose second packet cancels at pts 8 and whose third inserts at pts 4. (lane ffmpeg-bot-review-476)
- Symptom: the output of an ITU PDF extracted with `pdftotext -layout` cites the wrong page. Cause: the page number is a footer, printed after the text of its page (even pages as "322 Rec. ITU-T ...", odd pages as "Rec. ITU-T ... 323"). Fix: the page of a line is the next footer below it; check against a clause whose page is known (H.265 D.3.16 persistence text ends before footer 353). Found by: comparing with the pages of the 416 report. (lane ffmpeg-bot-review-476)
- Symptom: `consult_knowledge` returns EMPTY for a long query on norms_specs_corpus but OK for a short one with the clause's own words. Cause: the query is embedded as a whole, so wording that does not appear in the text scores below the cut. Fix: query with the words of the clause ("SEI NAL unit shall not contain any other SEI message buffering period picture timing"), then open the clause in the local PDF. Found by: four EMPTY results, then a hit at H.264 V16 p.72 and p.477. (lane ffmpeg-bot-review-476)
- Symptom: a stream whose flagged parameter sets exist only in the extradata is refused before a flush and quietly gets an arrangement after it. Cause: the flush wiped the per-id records of the parameter sets, and the extradata is never sent again. Fix: keep the records across a flush; a later parameter set of the same id replaces its record. Found by: reading the flush path in review, then the commit's own line that the first packet after a flush may have no SPS. (Opus, ORDER 476)
- Symptom: none in the tests; a cancelled id stays in force after a compaction when a stream reorders pictures. Cause: an in-place compaction decided in the loop that overwrote the array, so an entry already dropped was gone for a later entry that needed to see it. Fix: mark in one pass, move in a second. Found by: reading the loop against the array it writes. (Opus, ORDER 476)
- Reviewing a lane's series: one mutation per fix in a worktree (the fix's test must fail, by name), and the build rerun on the head that will be pushed, after any change made in review. A full FATE from before the last change is not a result for the pushed head. `tools/opus-check.py` of lane ffmpeg-bot-review-476 is the shape. (Opus, ORDER 476)

## Measured facts

- Bitstream filter insert/remove rules that a reviewer will test: insertion must clear general and sub-layer non_packed flags in every VPS and SPS passed on in a sequence that gets any message of the filter, cancellations included, those repeated later in it too (extradata, and NEW_EXTRADATA judged with the packet that brings it), any message is an explicit error in a sequence where a decoder that starts at one of its access units (first packet, flush, sequence start, key frame, IRAP picture) has a VPS or SPS that declares the flag, its own else the extradata's, a repeat after the first picture keeps the content in force, and extradata that still declares it while the packets bring the layout is a warning (updated by ORDER 527); a new message cancels the other persistent ids in force at its picture in output order, where a later message of an id or any later cancellation ends an arrangement (tracked with the packet timestamps, decoding order only when there are none and then said, a missing timestamp after INT64_MAX an error; extradata messages count with the next access unit, again after every reset and at every key frame; reserved ids are ignored; reset at IDR, BLA and flush, and after the access unit that holds a trailing EOS or EOB; no limit on the number of ids; a persistent message passed on that would stay in force at a picture already written is an error; a message passed on after the written one must have its self-contained flags) (updated by ORDER 523); an SEI NAL unit that holds a buffering period, picture timing, decoding unit information, active parameter sets, SEI manifest or prefix indication message takes no frame packing message (H.265 D.3.1 p.323), so the filter writes a unit of its own; H.264 types 0, 1 and 6 need both self-contained flags 0 and every message of a sequence the same flags, so the layout is an error in a sequence with other values; HEVC has no 2D type so a 2D description cancels and writes nothing; extraction must skip flipped and quincunx layouts; remove must also process extradata. (lane ffmpeg-25395-review-416)
- FFmpeg skip_frame values are noref, bidir, nointra, nokey, all ("nonintra" is rejected). ITU PDFs download from itu.int with dologin_pub.asp (H.264 V16 06/2026, H.265 V11 01/2026, H.266 T-REC-H.266-202601-I); H.274 01/2026 returned "Request Rejected" while 09/2023 and 05/2022 download. Do not wait with `pgrep -f` on a pattern that is in the loop's own command line. (lane ffmpeg-24628)

## Adding a stereo type to FFmpeg (ORDER 163, 2026-11-09)

Recipe, from master at 16a345b022: (1) enum value after the last one in `libavutil/stereo3d.h` with its picture and clause, (2) its name in `stereo3d_type_names[]` in `stereo3d.c`, (3) a minor bump in `libavutil/version.h` and an entry in `doc/APIchanges`, (4) the decoder side in `libavcodec/h2645_sei.c` (`is_frame_packing_type_valid()` and the switch of `ff_h2645_sei_to_frame()`) with the value in `libavcodec/sei.h`, (5) the `stereo_mode` frame metadata in `ff_h264_sei_stereo_mode()`, (6) the unit test of `libavutil/tests/stereo3d.c` (its loops stop at the last value) and a sample test. The muxers need no change: matroskaenc bounds-checks its table, movenc warns "Unsupported stereo_3d type", pngenc warns.

- Symptom: x264 `--frame-packing 6` (2D) gives no Stereo 3D side data although `h2645_sei.c` has a case mapping type 6 to AV_STEREO3D_2D. Cause: the export is gated on `content_interpretation_type` 1 or 2, and H.264 D.2.26 (V16 p.389) requires 0 for type 6, so the case can never run. Fix: let type 6 through whatever the field says, and do not read the eye order from it. Found by: `ffmpeg -v trace ... -bsf:v trace_headers` showing `content_interpretation_type = 0` on x264's stream.
- Symptom: a type 7 (tile format) stream shows `stereo_mode=mono` in `ffprobe -show_frames`. Cause: `ff_h264_sei_stereo_mode()` returns "mono" for every value without a case. Fix: a case per value. Found by: the same ffprobe run before any change.
- Symptom: a test of frame side data cannot print the type of a Stereo 3D frame side data. Cause: on master ffprobe prints the fields of Stereo 3D only for packet and stream side data (the frame version is in pull request 24628). Fix: a small `libavcodec/tests` program that decodes the sample through the H.264 parser and prints `av_stereo3d_type_name()`, flags and view per frame, registered as `TESTPROGS-$(CONFIG_H264_DECODER)` and run from `tests/fate/h264.mak` with `$(TARGET_SAMPLES)`.
- Sample recipe: x264 `--frame-packing N --keyint 1 --bframes 0 --preset ultrafast --threads 1` on a 192x144 picture (a multiple of 3 both ways, 16 aligned) whose five regions of Figure D-12 have distinct luma, one stream per type, concatenated (each starts a new coded video sequence). x264 writes content_interpretation_type 1 for every type but 6; patch the six bit field (low bits of payload byte 1 after `00 00 01 06 2d SIZE`) for the inverted cases and check with trace_headers. x264 does not move any pixel: the regions are the source's.
- Tile format geometry (H.264 D.2.26, D-32 to D-43, Figure D-12, V16 p.388 to 389, figure on pdf page 422): cells of one third of the cropped size; first view R0 (2x2 cells, top left); second view R1 (1x2 cells, top right) left of R2 over R3 (bottom row, first two cells); R4 (bottom right) discarded.
- A page of an ITU PDF with a figure: `pdftoppm -f N -l N -r 90 -png`, then look at it; `pdftotext` loses the picture. The figure number's page is not the clause's page (V16 pdf 422 shows Figure D-12 for clause text on pdf 411 to 412).

## Multilayer HEVC and the 3D reference displays SEI (ORDER 174, 2026-11-09)

- **Loosening a probe keeps its guard.** Symptom: none in FATE; the review saw it. `hevc_probe()` returned 0 on any layer above the base, and that return was also what kept random bytes from being called HEVC. Cause: once layers above 0 are allowed, a NAL unit of any layer could count towards the VPS, SPS, PPS and IRAP the score needs. Fix: count only NAL units of the base layer, and reject only the forbidden zero bit and layer 63. How found: reading the changed line for what it no longer rejected, not from a failing test.
Four old findings re-run on master 16a345b022 (libavutil 61.20): all four were still real. Each got its own branch from master, the fix first and its test in a second commit.
Samples for such tests are made by small scripts, kept in [sample-scripts](sample-scripts/): `make-tdrdi-sample.py` (a prefix SEI 176 with long mantissas before the first slice of any single layer stream), `add-hvcc-sei.py` (the same SEI also in the hvcC array of an MP4 made by `ffmpeg -c copy -fflags +bitexact`) and `set-vps-bit.py` (one bit of the VPS RBSP).

- Symptom: a raw `.hevc` file with an x265 alpha layer ends with "Invalid data found when processing input" unless `-f hevc` is given. Cause: `hevc_probe()` returned 0 at the first NAL unit header with nuh_layer_id above 0, and a demuxer that has a read_probe function gets only 1 point from its extension. Fix: reject only the forbidden bit and layer 63 (H.265 V11 7.4.2.2). The same stream pasted behind a large base picture probes fine, because the probe's first 2048 bytes never reach a layer 1 NAL unit: test with a small stream, and without `-f`. Found by: `cat file | ffprobe pipe:` on the 152 fate-suite MV-HEVC files passed and the 2.7 KB alpha stream failed; the first layer 1 NAL unit sat at byte 9478 in the passing files. (lane ffmpeg-depth-bugs-174)
- Symptom: a VPS extension with the auxiliary type reads AuxId from the wrong dimension_id; the stream still decodes as alpha. Cause: `decode_vps_ext()` counted only the multiview type before the auxiliary one, but the dimension_id values follow every set bit of scalability_mask_flag in index order (texture/depth 0, multiview 1, spatial/quality 2, auxiliary 3: F.7.4.3.1.1, ScalabilityId[i][smIdx] = dimension_id[i][j++]). x265 writes spatial and auxiliary (mask 0x3000) with both ids 1, so the wrong index gave the right value by chance. Fix: `av_popcount(mask & (DEPTH | MULTIVIEW | SPATIAL))`. Test: change the spatial id to 0 (`set-vps-bit.py`, bit 190, the decoder's bit counter 206 minus the 16 header bits) and decode with `-err_detect compliant`: master drops the alpha (6144 byte frames), the fix keeps it (10240). Without that option master falls back to "treating as alpha" and the output is the same, so the test needs the option. Found by: a temporary `av_log` of mask, ids and index in decode_vps_ext(), then the aux2 sample (AuxId 2) decoding to the same md5 as the alpha one. (lane ffmpeg-depth-bugs-174)
- Symptom: a bit position taken from a decoder's debug print is off by 16 when applied to the RBSP. Cause: `get_bits_count()` in the parameter set decoders counts from the start of the NAL unit, header included. Fix: subtract 16 before editing the unescaped payload. Found by: the edited stream behaved exactly like the original.
- Symptom: the frames of a raw `.hevc` stream with an in-band SEI 176 carry no 3D reference displays side data. Cause: `hevc_sei_to_context()` runs only on the extradata when the decoder opens; the in-band message is parsed but used only for the view positions. Fix: none needed for the test, put the message into the hvcC array of an MP4 (`add-hvcc-sei.py`; the mov muxer writes numOfArrays and the arrays, mdat before moov keeps the chunk offsets, only the boxes above hvcC grow). Found by: ffprobe `frame=side_data_list` empty on the raw stream and complete on the MP4.
- Symptom: a CBS round trip test (`md5 ... -bsf:v hevc_metadata -f hevc`) of a hand made stream never equals the input md5 although every NAL unit is the same. Cause: the hevc muxer writes four byte start codes before VPS, SPS and PPS and three byte ones before every other NAL unit. Fix: write the sample that way. Found by: `cmp -l` of input and output showing a shift of one byte from the first non parameter set NAL unit.
- Symptom: a mantissa read by CBS is wrong by its high bits and an H.265 message with a 40 bit mantissa is refused with "not supported". Cause: H265RawSEI3DReferenceDisplaysInfo keeps the mantissas in uint8_t and the template refuses more than 32 bits, while G.14.3.3 makes them Max(0, exponent + prec - 31) bits, up to 62. In libavutil the public AV3DReferenceDisplay keeps 8 bits as well, and master has already had a major bump, so fields cannot change size: append the whole values. Found by: `trace_headers` of the input (632259) against that of the rewritten stream (195, the low 8 bits). (lane ffmpeg-depth-bugs-174)
- A test for a decoder's side data needs a printer first: master's ffprobe did not print frame side data type 3D reference displays and showinfo printed only the count, so the series carries "fftools/ffprobe: print the 3D reference displays information" before the test. Proving the red column when the fix adds a field the test prints: print the old 8 bit fields once (a scratch edit, reverted) and keep that output as the evidence.

## Answering a review of a test program (pull request 25398, 2026-11-11)

Recipe that worked, for a bot finding on a `libavcodec/tests` program:
1. Red column first: a worktree at the fix's parent with the test files checked out from the test commit (`git worktree add --detach DIR FIX^`, then `git checkout TEST -- libavcodec/Makefile libavcodec/tests/NAME.c tests/fate/libavcodec.mak tests/ref/fate/NAME`). Run the old test there: on #25398 only 2 of 8 lines changed, which was the evidence that 6 cases tested existing behaviour.
2. Probes of the test program itself: copy the edited `NAME.c` into the out-of-tree build directory at `libavcodec/tests/NAME.c`; make's vpath takes the build directory's copy before `SRC_PATH`, so one `make fate-NAME` runs the probe. Print a marker to stderr from the probe, so a run whose output still matches the reference shows the probe did run.
3. The new test: one line per case, the callback's own observations printed into the same line (`printf("%s:", name)` before `ff_get_format()`, `printf(" query_failed=%d", ret < 0)` in the callback), so a second or missing callback call also changes the output.
4. One mutation per kept case, each caught by that case alone (cleanup after a hardware choice: only the hardware control; freeing the private data but not the frames: only the kept-frames case; cleanup only when frames were kept: only the discarded-frames case).
5. Valgrind on the test program (`valgrind --leak-check=full --error-exitcode=9`), then full FATE with GCC and clang on the head that will be pushed.

Traps:
- Symptom: `fate-get-format` passes although `frame_params()` was made to fail. Cause: the callback returned `AV_PIX_FMT_NONE` when the query result differed from what the case expected, and three cases expected `format=none` anyway. Fix: print `query_failed=%d` and continue with the requested format; the expectation moves into `tests/ref`. Found by: the bot's own probe, rerun with a stderr marker: marker printed, output identical to the reference.
- Symptom: a probe of `libavcodec/decode.c` copied into the build directory stops with `decode.c:44:10: fatal error: avcodec.h: No such file or directory`. Cause: quoted includes are looked up next to the including file first, and the build directory has no headers; test programs work because they include `libavcodec/...` paths. Fix: mutate library sources in a separate `git worktree`. Found by: the first lines of the probe's make log.
- Symptom: `configure: Unknown option "--enable-libglslang"` while enabling the FFV1, ProRes, DPX or APV Vulkan hwaccels. Cause: their shaders are compiled at build time now (`probe_glslc` tries `glslc`, then `glslang`); the hwaccels depend on `spirv_compiler`. Fix: install a GLSL compiler (Debian `glslang-tools`); no configure option. Found by: `grep -n spirv_compiler configure`.
- Symptom: a leak reproducer will not link against an ASan build (`Package libavformat-uninstalled was not found`). Cause: the `.pc` files in the build directory are the installed ones; there are no `-uninstalled.pc` files. Fix: link the static libraries directly (`libavformat/libavformat.a libavcodec/libavcodec.a libavutil/libavutil.a` plus the `EXTRALIBS-*` of `ffbuild/config.mak`, here `-lm -lz -ldrm -latomic -pthread -ldl`). Found by: the pkg-config error, then `grep ^EXTRALIBS ffbuild/config.mak`.
- Symptom: a `get_format()` callback that keeps the queried frames and chooses the hardware format decodes 0 frames (`get_buffer() failed`) on master too. Cause: `avcodec_get_hw_frames_parameters()` returns a frames context that is not initialized; the caller must call `av_hwframe_ctx_init()` before putting it in `avctx->hw_frames_ctx`. Fix: initialize it in the reproducer. Found by: the same failure with and without the change under test.

Perks:
- The FFV1 Vulkan hwaccel runs on lavapipe (Mesa's software Vulkan, `VK_DRIVER_FILES=/usr/share/vulkan/icd.d/lvp_icd.json`): its decoding is compute shaders and needs no video queue, so a Vulkan decode lifecycle bug can be reproduced under AddressSanitizer with no GPU (`--toolchain=gcc-asan --enable-vulkan --disable-everything --enable-decoder=ffv1 --enable-hwaccel=ffv1_vulkan --enable-demuxer=matroska --enable-protocol=file`). An FFV1 sample comes from FFmpeg itself: `ffmpeg -f lavfi -i testsrc2=size=320x240 -frames:v 10 -c:v ffv1 -level 3 -slices 4 -pix_fmt yuv420p out.mkv`. H.264 and HEVC Vulkan stop earlier on lavapipe: the bootstrap refuses a device without `VK_KHR_video_decode_queue`.
- The fate-suite over HTTPS (`make fate-rsync` uses plain `rsync://`): fate-suite.ffmpeg.org serves an Apache listing, so `wget -r -np -nH -nc -e robots=off --reject-regex '\?C=' -R 'index.html*'` per top-level folder, six folders in parallel. Measured on 2026-11-11: 1.3 GB in 2750 files, about an hour; TLS pull errors and connection timeouts lost files even with `--tries=5`, so repeat the whole run with `-nc` until a pass adds nothing, and let FATE be the check: a failure on a missing sample (here the five `wavpack-lossy-*` entries and `zmbv-8bit`) is rerun alone once the sample is there. Many folders carry an `md5sum` file in one of several layouts (`SUM  name`, `name SUM`, `MD5 (name) = SUM`); `kega/md5sum` is older than `kega/kgv1.avi` and no longer matches it, while `fate-kgv1` passes.

Measured facts:
- Full FATE with the samples on master c1b3b086e4 plus #25398: 6108 tests with GCC 16.2.0 and with clang 21.1.8, all passing. `fate-eac3-5` failed once in a full GCC run of a branch that touches only hwaccel code and passed three times alone, the same E-AC-3 flakiness as above.
- Only the Vulkan hwaccels keep state in `hwaccel_priv_data` from `frame_params()` (`vulkan_decode_bootstrap()`); dxva2, d3d12va, vaapi, vdpau, videotoolbox and nvdec do not touch it. `hwaccel_internal.h` still told `frame_params()` to assume the private data is invalid.
- A discarded Vulkan query leaks the shared decode context (12352 bytes with FFV1 on lavapipe, allocated in `vulkan_decode_bootstrap()`), on master and after #25398. VAAPI's `uninit()` dereferences `ctx->hwctx` when `va_context` is 0, so calling every hwaccel's `uninit()` on query-only state is unsafe: the fix is opt-in per hwaccel.
- On master, a callback that keeps and initializes the queried Vulkan frames and then chooses software makes the FFV1 software decoder write through a NULL plane (`ffv1dec.c:145`, ASan SEGV); with #25398 all 10 frames decode.

## A third bot round on the frame packing filters (ORDER 523, 2026-11-11)

The bot said the fixes of the round before were only partly done.
Each partial fix had applied a rule at a smaller unit than the specification states it for: the access unit instead of the coded video sequence, the message's own id instead of every earlier message, the first message's flags instead of every message.
Before fixing a finding, write down the unit the clause names, and test at that unit's edges: a later access unit of the same sequence, a message of another id, a message passed on after the one written, a flush.

Recipe:
- Read the whole review, not the mail: it is an issue comment on the pull request, `curl -s 'https://code.ffmpeg.org/api/v1/repos/FFmpeg/FFmpeg/issues/N/comments?limit=100'` (the `/pulls/N/reviews` list stays empty for the bot). It names the branches it kept on `https://code.ffmpeg.org/Forgejo_Fairy/FFmpeg`: `fairy/prN-tooling` holds its probes, `fairy/prN-*-fix` an amendment.
- Fetch them read-only (`git remote add fairy ...; git fetch fairy fairy/prN-tooling`), build the unchanged head, compile the probe against its static libraries (`cc -O2 -I/src -I. probe.c libavformat/libavformat.a libavcodec/libavcodec.a libavutil/libavutil.a -pthread -lm -latomic`; the probe includes the test program by a relative path, fix the include) and keep its output as the red evidence.
- For an overflow finding, compile only the file under test with UBSan and link it into the probe: `gcc -O1 -g -DHAVE_AV_CONFIG_H -fsanitize=undefined -fno-sanitize-recover=undefined -I/src -I. -c /src/libavcodec/cbs_sei.c -o cbs_sei_ubsan.o`, then the probe with `-fsanitize=undefined` and that object before the libraries.

Keep the search terms, date, candidates and diffs; an inaccessible archive is a recorded gap, not a negative result.
2. Keep the original fix and test separate, fix first. Rebase in your own checkout and preserve carried authorship and trailers. Compare the old and new series with `git range-diff`; a changed subject is distinct from a changed source tree.
3. Build unchanged master first. For an intermittent FATE entry, keep each invocation's exit status and failing output, rather than trusting the CLI's exit status alone. Reuse the same compiler, options and sample view for the fixed comparison.
4. Copy only the test and its registration into the unchanged checkout for the deterministic red control. The library must still be master. Record the reference diff, then restore the clean source before moving to the fixed head.
5. Walk the [pre-push audit](pre-push-audit.md) before rerunning the tests. Mutate the fix to establish which cases are necessary, run the final sanitizer checks, then full FATE with GCC and clang on the exact final head. Record every failed run even when a later run passes.
6. Keep a single build directory when disk space is shared. Preserve logs and references before removing it; reconfigure from a clean directory when changing compilers. A symlink view can combine a read-only fate-suite with a separately verified missing sample without modifying either source.
7. Write the pull request description from the measured final result and the current template. Keep related issues separate from issues actually closed, and name the other promised follow-ups without adding them to this series.

Traps:
- Symptom: a local reference clone checks out most files, then reports `unable to read sha1 file` and leaves apparent deletions. Cause: the source is a partial clone, but the local clone did not inherit a public promisor remote able to fetch its missing objects. Fix: fetch from the public upstream with `--filter=blob:none --refetch`, then restore the intended clean head. Found by: the checkout errors and a history walk failing on another missing object; both succeeded after the filtered refetch.
- Symptom: a container command says `/usr/bin/bash: cannot execute binary file`. Cause: the reused image already has a shell entrypoint, and another shell name became its script argument. Fix: set `--entrypoint /bin/bash` explicitly and pass `-c` as its first argument. Found by: the launch log before configure ran.
- Symptom: the existing build image has both compilers but no Valgrind. Cause: the earlier lane used a different sanitizer path. Fix: check tool availability before the long build and add only the missing tool in a separately named image, following the local HTTPS package-source policy. Found by: `valgrind --version` returning command not found.
- Symptom: apt update fails on an inherited `file:` source or a keyring that lived in a previous container's bind mount. Cause: the saved development image retained a lane-specific source configuration. Fix: in the throwaway image only, use the distribution's signed HTTPS archive, then rerun apt and keep its log. Found by: apt's missing Release file and missing-keyring diagnostics.
- Symptom: the old monthly mailing-list URL returns 404 for current months. Cause: the legacy archive stops before the period being searched. Fix: inspect its index, follow the current archive link, and search an indexed public mirror when the current archive has a bot wall. Record which route was readable. Found by: the last month in the legacy archive index and the current archive's challenge page.

- Symptom: all 30 runs of each named E-AC-3 FATE entry pass on unchanged master, although the parser still reads uninitialized metadata. Cause: a short run need not expose a bad stack pattern. Fix: retain the measured zero failure rate, then use Valgrind and a deterministic prefix-versus-tail test to establish the fault. Found by: on master 986bab2b475, 90 ordinary runs passed while Valgrind reported 10,848 errors from 48 contexts; all eight lines of the deterministic regression differed.
- Symptom: a standalone bitstream-filter probe fails to link with unresolved `swr_*` symbols despite explicitly linking libavcodec and libavutil. Cause: the configured static libavcodec also pulls decoder objects that depend on libswresample. Fix: link libswresample after libavcodec and before libavutil, using the configured libraries and EXTRALIBS rather than installed package assumptions. Found by: the linker diagnostics and ffbuild/config.mak.
