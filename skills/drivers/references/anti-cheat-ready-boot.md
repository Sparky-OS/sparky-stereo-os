# An anti-cheat ready start: one restart with lockdown, the usual start with hibernation

Written on 2026-11-27 from row 190 (sparky-stereo-boot 0.1.17, plasma-workspace 4:6.7.4-2+stereo3d14), Linux 7.3.4, GRUB 2.14-5, shim 16.1, Plasma 6.7.4.
Check the versions before carrying a line forward.

Easy Anti-Cheat for Linux, version 2 (Epic Online Services, 2026-10-14; the list is in [`proton-wine`](../../proton-wine/SKILL.md#easy-anti-cheat-linux-v2)), wants kernel lockdown in integrity mode, kexec disabled at boot time, the IOMMU on without passthrough and the BPF LSM, beside Secure Boot with well-known keys, TPM 2.0 and measured boot.
The edition's usual start keeps hibernation and so has no lockdown (Daniel, 2026-10-08), and Epic's FAQ allows a separate boot entry for protected games.
Daniel, 2026-10-21: the anti-cheat entry is a one-time choice in Plasma's restart menu, like "restart to UEFI firmware setup", and hibernation stays the default start.

## The checker's rules

The rules follow Bazzite's `ujust check-anticheat` (Universal Blue; Ted O'Hayer and stellaberrant by its commits, Apache-2.0), the existing readiness check, adopted in the edition's own code: a key is on Epic's list when a certificate's subject or issuer names one of its keys (Canonical, Fedora, Universal Blue, Debian, openSUSE, SUSE, Rocky Linux, Microsoft's UEFI CA, AlmaLinux), measured boot needs the boot manager's own measurements, the kernel's unsigned-module taint counts, a Valve device is told not to turn Secure Boot on, and a handheld needs no IOMMU.

- **Secure Boot:** the `SecureBoot` and `SetupMode` variables; a BIOS start has none.
- **The kernel's key:** the running kernel's file, its PE certificate table (data directory 4, `WIN_CERTIFICATE` type 2), each PKCS #7 blob's certificates through `openssl pkcs7 -print_certs`; the edition's own certificate (fingerprint match) is not on Epic's list; another signer is met when its name or its issuer's is on the list (a Debian-signed image is), not met otherwise.
- **MOK:** `MokListRT` as `EFI_SIGNATURE_LIST`s (UEFI 2.10, 32.4.1); shim's own vendor key (Debian's CA) is on the list; the edition's key, this computer's DKMS key or any other is not met (Epic: every enrolled MOK must be well-known).
- **Modules:** loaded modules with taint O or E and their `modinfo` signer (by `/usr/sbin/modinfo`: a session's PATH has no sbin); this computer's DKMS key (serial of `/var/lib/dkms/mok.pub`) is not met; the kernel's `tainted` bit 13 counts a module loaded and gone. Lockdown refuses a module whose signature the kernel cannot verify (taint E today, unsigned files in `updates`), so the usual start names them for the anti-cheat start, and the anti-cheat start names them when its kernel log holds `Lockdown: ...: unsigned module loading is restricted` (the line carries no module name). A person outside the adm and systemd-journal groups cannot read the kernel's log, so for them the row says, as unknown, that only an administrator can see the refusals.
- **TPM 2.0:** `/sys/class/tpm/tpm0/tpm_version_major`.
- **Measured boot:** `/sys/kernel/security/tpm0/binary_bios_measurements` exists (root:tss 0440, so a person sees only that it exists); as root, the TCG event log is parsed (the SHA-1 first event with Spec ID Event03, then the crypto-agile events, SM3_256 banks included) and PCRs 8, 9, 11 or 12 must hold the boot manager's own measurements. A real log of OVMF, swtpm, Debian's shim and GRUB 2.14 has 137 entries, as `tpm2_eventlog` counts them, 78 in PCR 8 and 15 in PCR 9.
- **IOMMU:** `/sys/class/iommu` has a unit, there are groups, and no group's `type` is `identity` (the firmware's DMAR unit is listed even when no device is behind it).
- **Lockdown:** `/sys/kernel/security/lockdown` at integrity or confidentiality.
- **kexec:** `kexec_load_disabled` is 1 and the kernel line set it; 1 set later by sysctl is unknown (whether Epic counts it is not known).
- **BPF LSM:** `bpf` in `/sys/kernel/security/lsm`.

## Traps

| Symptom | Cause | Fix | How it was found |
| --- | --- | --- | --- |
| A one-time start would repeat at every boot | GRUB cannot write `/boot/grub` on LVM, RAID, btrfs or ZFS (`check_writable` in `00_header`), so `save_env next_entry` does nothing; `grub-reboot` itself warns of it | keep the request where GRUB writes: the edition's block on the EFI system partition, read by the entry's script; with no such place, offer no restart and say how to choose the entry in the menu | `grub-reboot`'s own NOTE text and `00_header`'s `next_entry` block |
| The anti-cheat start would leave a hibernation image unread, and the next usual start restores memory over changed disks | under lockdown `hibernation_available()` is false and `resume_store()` returns at once (`kernel/power/hibernate.c`); `nohibernate` sets noresume | an initramfs guard in that start finds the image and restarts into the usual start | reading `resume_store()` and `software_resume_initcall()` in the published kernel's source |
| The guard restarted the machine and the usual start then dropped the image: `Hibernate inconsistent memory map detected!`, `Image mismatch: architecture specific data`, `resume failed (-1)` | after a start that ran a kernel, OVMF's reset gave the next start another memory map, and x86 refuses an image made under a different one (`arch/x86/power/hibernate.c`); a reset at GRUB alone, or a cold start, kept it | the guard switches the machine off and says to turn it on again | three runs on the same guest: guard with its reset (resume refused), a reset at GRUB with no kernel started (resumed), the guard with the power cut during its wait (resumed) |
| After the guard and a resume, the next restart was the anti-cheat start again | GRUB cleared `next_entry` on the disk while the system slept; the resumed system still held the old block, and Debian's `grub2-common.service` (after every resume: `grub-editenv ... unset recordfail`) wrote it back whole | drop the clean cached pages (`posix_fadvise(DONTNEED)`) after the resume, before grub2-common | `dd iflag=direct` of grubenv against `grep` of the cached file, then the unit's journal times |
| No guard in the boot image | the image was made by dracut, Debian testing's default; the guard is an initramfs-tools script (the edition ships initramfs-tools) | install initramfs-tools; with dracut the anti-cheat start has no guard (not built) | `lsinitramfs: command not found` in the guest |
| In the anti-cheat start the check run by the person shows no refused modules, `sudo` shows evdi, spl, vhba, zfs | the kernel logs `Lockdown: modprobe: unsigned module loading is restricted` without the module's name, modprobe's own error never reaches the journal, and the person's `journalctl -k` shows nothing outside the adm and systemd-journal groups | name this kernel's unverifiable modules that did not load when such a line is there; when `journalctl -b -k -n 1` prints nothing, say that only an administrator can read the refusals | the A10's second anti-cheat start, the check run both ways |
| A DisplayLink screen or a pad stays dark in the anti-cheat start | DKMS modules without a signature are refused under lockdown (the test laptop had evdi, vhba, spl and zfs loaded with taint E) | the checker names them before the restart and in that start | the A10's `/sys/module/*/taint` in the baseline |
| The Leave menu's anti-cheat item restarted at once, with nothing said about Secure Boot or the key | 170's menu items trigger their action directly | the item opens the confirmation with the checker's rows first | review of the first draft |
| The checker said "unknown" for measured boot to every person | the event log is readable by root and tss only | a person is told the log exists (met), with the command that reads its entries | `ls -l /sys/kernel/security/tpm0` |
| `mmdebstrap --mode=unshare` fails in a container: `newuidmap: write to uid_map failed` | the container's uid mapping cannot be written without privileges | build the guest from Debian's own `nocloud` testing image and install inside the running guest | the mmdebstrap log |
| The guest waits at systemd-firstboot's questions and a line feed does nothing | firstboot reads the serial console in raw mode | send `\r` | sending `\n`, then `\r` |
| `root` asks for a password on Debian's `nocloud` image | its root account is locked | at GRUB's command line (it is on the serial console): `linux ... systemd.mask=serial-getty@ttyS0.service systemd.debug_shell=ttyS0`, then write an autologin drop-in for `serial-getty@ttyS0` | the login prompt; a debug shell on ttyS0 loses to the getty unless the getty is masked for that start |
| `kill -0` says QEMU still runs after the guest powered off | `sleep infinity` as the container's PID 1 does not reap the zombie | start the rig container with `--init` | `/proc/PID/status` State Z |

## The rig

- Guest: Debian's `debian-14-nocloud-amd64-daily.qcow2` (SHA-512 from the folder's `SHA512SUMS`; cloud.debian.org answers 302 to a mirror, so `curl -L --proto-redir =https`), as a qcow2 overlay, grown in the guest with `growpart` and `resize2fs`; a second disk as the swap partition for hibernation (`RESUME=UUID=` in `conf.d/resume`).
- Firmware: OVMF `OVMF_CODE_4M.secboot.fd` with `virt-fw-vars --enroll-generate 'CN' --secure-boot --add-mok 605dab50-e046-4300-abb6-3dd810dd8b23 EDITION-CERT.der` on `OVMF_VARS_4M.fd`: a throwaway platform key, Microsoft's KEK and db (Debian's shim is signed by Microsoft's UEFI CA), the edition's public certificate in MokList (its kernels are signed with the edition's key). No private key of the edition is used.
- TPM: `swtpm socket --tpm2 --tpmstate dir=... --ctrl type=unixio,path=...`, `-tpmdev emulator -device tpm-crb`; OVMF then writes the measured boot log.
- IOMMU: `-machine q35,kernel-irqchip=split -device intel-iommu,intremap=on`; the usual start leaves it off (no `intel_iommu=on`), the anti-cheat start turns it on.
- The published round and the stage as read-only 9p shares; the serial console through a chardev with a `logfile`, so every boot's GRUB and kernel lines are kept.
- BIOS row: the same disk under SeaBIOS (no `-drive if=pflash`).
- The guest is Debian's nocloud image with the round added, not an installed edition: its Qt, KScreen and FFmpeg are Debian's, so a settling `full-upgrade` removes edition packages that pin the edition's builds (libstereo-layer1, libstereo-av1, sparky-stereo-graphics). Judge the plan of the staged packages alone (`apt-get -s install` of them, `Remv` lines), and never full-upgrade the guest.
- After a hibernation and a good resume (same boot id, a witness unit alive), this QEMU and OVMF guest wedged once and reset itself once within about a minute, with no kernel message; the first time on a build without the resume unit. Read every reading of a resume at once, and do not take a later reset for the package's fault without a control.
