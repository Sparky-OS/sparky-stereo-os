# A security build of the edition's kernel

Written on 2026-11-16 from kernel build 17 (ORDER 627: CVE-2026-99288 "NoisyTCP" and the two follow-ups of CVE-2026-98432, on 7.3.1).
The build tree's `kernel/NEXT-BUILD.md` holds the build recipe itself; this page is the order of work when the reason for a build is a security fix, with the traps met on the way.
Design that governs it: "kernel is the soul" (every flavour carries the same fixes, headers and DKMS always work), check upstream before fixing (carry upstream's commit, credited), and the build is a new number, never a reused name.

## The recipe

1. **Prove the gap on what ships.**
   Unpack only the files of the fix from the published `linux-stereo-FLAVOUR_VERSION.orig.tar.xz` of each flavour (`tar -xJf ... --wildcards '*/net/ipv4/inet_hashtables.c' ...`) and look for the fix's own line.
   `kernel/tests/stable-security/source-proof.sh SOURCE_DIR` does it for build 17's TCP fixes: one line per fix, the fix's text inside its function, plus CVE-2026-98432's own fix as a control that every build since 13 has.
   Red on the three published 7.3.1-16 sources (exit 1, five lines missing, both controls present) before anything else.
2. **Find what stable took, in one scratch repository.**
   `git init`, then fetch with `--shallow-exclude=v7.3` (about 600 MB together): linux-7.3.y with its `v7.3.*` tags from the stable tree, stable-rc's linux-7.3.y (the next release in review), and torvalds' master.
   - The stable form of a mainline commit: `git log --grep=SHA12 v7.3.1..stable/linux-7.3.y` (stable's message says `[ Upstream commit SHA ]` or `commit SHA upstream.`).
   - What is queued but not released: a shallow clone of `stable-queue.git` (3 GB, queue-7.3 and releases/7.3.*); grep it for the 12-character hash.
   - Which fixes carry a CVE: a shallow clone of the kernel CNA's `vulns.git` (590 MB). Each `cve/published/YEAR/CVE-*.dyad` has one line per branch, `introduced-version:introduced-sha:fixed-version:fixed-sha`; list the records whose fixed version is 7.3.N above the base (48 records named 7.3.2 to 7.3.4 on 2026-11-16).
   - The researcher's advisory (oss-security) says whether a public reproducer exists. NoisyTCP's names none: proof is then the source and the boot, and no exploit is written.
3. **Sort the fixes by what they need.** For each stable commit, `git log --format=%h v7.3.1..FIX^ -- $(git show --format= --name-only FIX)`: every commit listed that is not itself carried is a prerequisite to judge.
   Also read each commit's `Link:` message id (siblings of one series share the id with another `-N-`), `Stable-dep-of:`, and later stable commits whose `Fixes:` names a carried commit (a 7.3.3 xen-netback fix had its own fix in 7.3.4).
   Carry: the named fixes with their prerequisites and series, and every CVE fix whose files need no other 7.3.y commit. List, do not carry: the fixes that need non-security 7.3.y commits (build 17: ksmbd, nfsd, three SMB client fixes, sch_teql), and anything else that needs judgment; that is the rebase's work, not the security build's.
4. **Write the group in stable's form.** `git format-patch --zero-commit --no-signature --abbrev=9 --start-number N -1 -o RAW STABLE_SHA` for each, in the order chosen (the named fixes first, then stable order), then strip `[PATCH] ` from the subject and add one `[ORDER NNN: CVE, stable commit (release), ...]` line before `---`.
   A fix no stable tree has yet is the mainline commit with `(cherry picked from commit SHA)` added, as group 41 did.
   Map raw files to commits by their number, not by subject (format-patch folds long subjects).
   Add the group to `series.txt` with a status line, what it carries, what it leaves and why, and when it goes (at the rebase onto a release that has the commits).
5. **Apply strictly on a fresh export, then hash it.** `git archive v7.3.1 | tar -x -C DIR`, `kernel/series/apply-series.sh DIR FLAVOUR` (git apply, no fuzz), then hash with a git directory outside the tree (`git --git-dir="$(mktemp -d)" --work-tree=DIR add -A -f` and `write-tree`), so the export never becomes a clone. The tree hashes go in the lane's `accepted-source-manifests.json` (build 16's fields: tag, commit, source_tree, flavour, timestamp, baseline, patches with sha256); `kernel/lean/check-flavours.py` checks base and rt parity.
6. **Compile the touched code before the long builds.** In the kernel build image, out of tree on a read-only source: `configure.sh FLAVOUR /obj/FLAVOUR`, `make O=... modules_prepare`, then `make O=...` on the directories the group touches (a header such as `tcp.h` or `request_sock.h` reaches whole directories: build `net/ipv4/ net/ipv6/ net/core/ net/mptcp/` whole). Base and rt in parallel at 6 CPUs took about 4 minutes each (572 and 558 objects); 0 warnings and 0 errors is the result to expect.
7. **Prepare the three sources in containers.** `prepare-kernel-source.py FLAVOUR --counter N --source-dir EXPORT --manifest FILE` with `SPARKY_MIGRATION_WORK` in the lane's scratch; the image needs devscripts besides the build tools. Commit the recipe first: the source records the packaging commit, and `kernel/tests` goes into the source package.
8. **Build the flavours, two at a time if the disk allows.** `run-kernel-build.py FLAVOUR --counter N --container NAME --cpus 6 --jobs 6 --floor-gb FLOOR --detach` (options added in ORDER 627). Measured on build 17: BUILDTIMES. A flavour's job peaks at about 22.5 GB plus about 1.5 GB of container layer on `/`; two whose peaks meet need about 48 GB above the floor, so start the second about 45 minutes after the first (the first half hour of each is the single-threaded source projection), and the third when the first finishes. `docker update --cpus 12 NAME` gives a running build the CPUs a finished one freed.
9. **Prove, in this order:** the source proof on the prepared sources; `qualify-kernel-unsigned.py` per flavour (boot, BTF, sched_ext, binder, Realtek modules, vkms); DKMS (`dkms-inner.sh` both orders, `dkms-nogcc-inner.sh`); KUnit for the groups the build adds (`kernel/tests/kunit/run.sh`, read the parsed counts, not the exit status); the metas (`sparky-stereo-meta` build.sh with `PACKAGES` the six kernel metas and `KERNEL_META_VERSION_SUFFIX=+lc1`); `kernel/tests/upgrade-proof.sh` (control and upgrade, read on `Inst` and `Remv`); the stage with complete sources and `SHA256SUMS`.

## Traps

- **Symptom:** `curl` of `https://git.kernel.org/.../torvalds/linux.git/patch/?id=SHA` exits 0 with an empty file. **Cause:** cgit answers automated clients with an empty body. **Fix:** fetch the history with git and use `git format-patch`. **Found by:** the four downloaded patches all had the SHA-256 of an empty file.
- **Symptom:** `git am` stops with `fatal: empty ident name (for <>) not allowed`. **Cause:** a patch whose `From:` header holds only a name. **Fix:** a kernel series patch keeps the commit's own `From: Name <address>` (it is a git patch, applied with `git apply` and `git am`); the name-only rule is for a Debian patch's DEP-3 `Author:`. **Found by:** a two-line `git am` test before writing the group.
- **Symptom:** `prepare-kernel-source.py` in a container stops in `lean/prepare.py` with `FileNotFoundError: 'dch'`. **Cause:** the kernel build image has no devscripts. **Fix:** install devscripts in the preparing container (as root, then `setpriv --reuid --regid --clear-groups` for the preparation). **Found by:** the traceback's last line.
- **Symptom:** `qualify-kernel-unsigned.py` stops copying `SPARKY_INPUTS_DIR/kernel-soul/work/bench-run/r2/initrd-tree/guest`. **Cause:** the guest tools were a fixture in a lane folder that its cleanup removed after build 16. **Fix:** `kernel/qualification/guest-tools/build.sh SOURCE VMLINUX_BTF OUT` rebuilds `bin/scx_simple` from the kernel tree's own `tools/sched_ext` (its own bpftool and libbpf; clang, llvm, libelf-dev, zlib1g-dev, libzstd-dev in the container) and `lib/` with the loader and libraries; point `SPARKY_INPUTS_DIR` at a folder that holds it at that path. **Found by:** the lane folder's MANIFEST.txt ("work ... left out").
- **Symptom:** a kernel job builds every package, then its last step stops: `lean.release check-debs` says "the build script did not call sparky_provenance_init, so no host fact reached this container". **Cause:** since ORDER 412 (2026-11-06) the build record needs the host's facts, and `run-kernel-build.py` passed none (builds 15 and 16 ran before the rule). **Fix:** the driver passes them as `build-provenance.sh` makes them (commit, dirty flag, image id and digests, invocation id, start time; not its source date, which the prepared source already has). A job started before the fix gets its record afterwards from its measured facts, with the invocation id left unrecorded. **Found by:** reading `lean/buildrecord.py` while the first flavour was compiling, before it reached that step.
- **Symptom:** a container appears as `hardcore_banzai` or another random name. **Cause:** `kernel/tests/kunit/run.sh` gave no name. **Fix:** `NAME=LANE-kunit-SUITE` (option added in ORDER 627).
- **Symptom:** a short `docker run --rm IMAGE sh -c 'apt-cache policy ...'` through the lane's socket prints nothing. **Cause:** the lane's socket proxy cuts attached output. **Fix:** write every result to a bind-mounted file, and run long builds with `--detach`. **Found by:** the same command writing to a file returned the full output.
- **Symptom:** removing a scratch export is refused: "would remove work that exists nowhere else ... 96146 uncommitted or untracked". **Cause:** `git init` in the export to hash it made it a clone in the branch keeper's eyes. **Fix:** hash with a git directory outside the tree (step 5); a tree made that way is plain scratch. **Found by:** the hook's message.

- **Symptom:** `docker run` of a DKMS proof fails at once, exit 125: "error while creating mount source path '/var/tmp/sparky-repo-current': mkdir ...: file exists". **Cause:** the published repository's local copy is a symbolic link, and the Docker daemon does not follow it for a bind mount. **Fix:** mount `$(readlink -f PATH)`. **Found by:** the first line of each case's log (six cases failed in one second).
- **Symptom:** a flavour's source prepared a second time from the same commit and the same tree has another `.dsc` hash. **Cause:** `prepare-kernel-source.py` packs the orig tarball with `tar` from the export's own file times (the first export kept v7.3.1's times, a tree restored from a bundle has the restore time); the contents are equal. **Fix:** none in this build (the three sources of build 17 record the same commit, f3b65e60d, and the same trees); a reproducible orig needs `--sort=name --mtime=@EPOCH --owner=0 --group=0 --numeric-owner` there. **Found by:** `tar -tvJf` of both origs: the same files, other dates.
- **Symptom:** free space on `/` swings by 10 to 15 GB within minutes while a flavour builds. **Cause:** other lanes' package builds write and clean their scratch on the same disk. **Fix:** count your own peak (22.4 GB per flavour plus about 1.6 GB of container layer) against the house floors only (/ 1 GB, /mnt/build 2 GB, /K3D 2 GB; a brief's stricter figure is a starting place, not a stopping rule), keep 12 GiB free on `/` for the link gate inside each job, and use `docker pause NAME` (nothing is lost) rather than a floor stop, which loses the job: a stopped job's source has been projected in place, so the flavour is prepared again. **Found by:** `du` of the other lanes' scratch folders between two `df` readings.

## Perks

- The kernel CNA's records lag the releases: on 2026-11-16 v7.3.4 (1,254 commits, 10 November) had 10 records, v7.3.2 (548 commits) 35. A security build carries what the records and the advisory name; the rest of a stable release is the rebase's.
- A memory-ordering fix such as `refcount_inc_not_zero_acquire()` changes nothing on x86; carry it with its series anyway, so the lookup code is stable's.
