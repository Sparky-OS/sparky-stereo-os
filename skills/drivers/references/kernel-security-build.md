# A security build of the edition's kernel

Written on 2026-11-16 from kernel build 17 (ORDER 627: CVE-2026-99288 "NoisyTCP" and the two follow-ups of CVE-2026-98432, on 7.3.1); the rebase onto a newer stable release added from build 18 (ORDER 636: the series moved to v7.3.4).
The build tree's `kernel/NEXT-BUILD.md` holds the build recipe itself; this page is the order of work when the reason for a build is a security fix, with the traps met on the way.
Design that governs it: "kernel is the soul" (every flavour carries the same fixes, headers and DKMS always work), check upstream before fixing (carry upstream's commit, credited), and the build is a new number, never a reused name.

## The recipe

1. **Prove the gap on what ships.**
   Unpack only the files of the fix from the published `linux-stereo-FLAVOUR_VERSION.orig.tar.xz` of each flavour (`tar -xJf ... --wildcards '*/net/ipv4/inet_hashtables.c' ...`) and look for the fix's own line.
   `kernel/tests/stable-security/source-proof.sh SOURCE_DIR` does it for build 17's TCP fixes: one line per fix, the fix's text inside its function, plus CVE-2026-98432's own fix as a control that every build since 13 has.
   Red on the three published 7.3.1-16 sources (exit 1, five lines missing, both controls present) before anything else.
2. **Find what stable took, in one scratch repository.**
   `git init`, then fetch with `--shallow-exclude=v7.3` (about 600 MB together): linux-7.3.y with its `v7.3.*` tags from the stable tree, stable-rc's linux-7.3.y (the next release in review), and torvalds' master.
   - The stable form of a mainline commit: `git log --grep=SHA12 v7.3.1..stable/linux-7.3.y` (stable's message says `[ Upstream commit SHA ]` or `commit SHA upstream.`).
   - What is queued but not released: a shallow clone of `stable-queue.git` (3 GB, queue-7.3 and releases/7.3.*); grep it for the 12-character hash.
   - Which fixes carry a CVE: a shallow clone of the kernel CNA's `vulns.git` (590 MB). Each `cve/published/YEAR/CVE-*.dyad` has one line per branch, `introduced-version:introduced-sha:fixed-version:fixed-sha`; list the records whose fixed version is 7.3.N above the base (48 records named 7.3.2 to 7.3.4 on 2026-11-16).
   - The researcher's advisory (oss-security) says whether a public reproducer exists. NoisyTCP's names none: proof is then the source and the boot, and no exploit is written.
3. **Sort the fixes by what they need.** For each stable commit, `git log --format=%h v7.3.1..FIX^ -- $(git show --format= --name-only FIX)`: every commit listed that is not itself carried is a prerequisite to judge.
   Also read each commit's `Link:` message id (siblings of one series share the id with another `-N-`), `Stable-dep-of:`, and later stable commits whose `Fixes:` names a carried commit (a 7.3.3 xen-netback fix had its own fix in 7.3.4).
   Carry: the named fixes with their prerequisites and series, and every CVE fix whose files need no other 7.3.y commit. List, do not carry: the fixes that need non-security 7.3.y commits (build 17: ksmbd, nfsd, three SMB client fixes, sch_teql), and anything else that needs judgment; that is the rebase's work, not the security build's.
4. **Write the group in stable's form.** `git format-patch --zero-commit --no-signature --abbrev=9 --start-number N -1 -o RAW STABLE_SHA` for each, in the order chosen (the named fixes first, then stable order), then strip `[PATCH] ` from the subject and add one `[ORDER NNN: CVE, stable commit (release), ...]` line before `---`.
   A fix no stable tree has yet is the mainline commit with `(cherry picked from commit SHA)` added, as group 41 did.
   Map raw files to commits by their number, not by subject (format-patch folds long subjects).
   Add the group to `series.txt` with a status line, what it carries, what it leaves and why, and when it goes (at the rebase onto a release that has the commits).
5. **Apply strictly on a fresh export, then hash it.** `git archive v7.3.1 | tar -x -C DIR`, `kernel/series/apply-series.sh DIR FLAVOUR` (git apply, no fuzz), then hash with a git directory outside the tree (`git --git-dir="$(mktemp -d)" --work-tree=DIR add -A -f` and `write-tree`), so the export never becomes a clone. The tree hashes go in the lane's `accepted-source-manifests.json` (build 16's fields: tag, commit, source_tree, flavour, timestamp, baseline, patches with sha256); `kernel/lean/check-flavours.py` checks base and rt parity.
6. **Compile the touched code before the long builds.** In the kernel build image, out of tree on a read-only source: `configure.sh FLAVOUR /obj/FLAVOUR`, `make O=... modules_prepare`, then `make O=...` on the directories the group touches (a header such as `tcp.h` or `request_sock.h` reaches whole directories: build `net/ipv4/ net/ipv6/ net/core/ net/mptcp/` whole). Base and rt in parallel at 6 CPUs took about 4 minutes each (572 and 558 objects); 0 warnings and 0 errors is the result to expect.
7. **Prepare the three sources in containers.** `prepare-kernel-source.py FLAVOUR --counter N --source-dir EXPORT --manifest FILE` with `SPARKY_MIGRATION_WORK` in the lane's scratch; the image needs devscripts besides the build tools. Commit the recipe first: the source records the packaging commit, and `kernel/tests` goes into the source package.
8. **Build the flavours, two at a time if the disk allows.** `run-kernel-build.py FLAVOUR --counter N --container NAME --detach`, with `SPARKY_MIGRATION_WORK` on any local solid-state disk with room (`kernel/qualification/scratch_disk.py` refuses a hard disk or a network mount; the stop floor is that disk's house floor, 1 GiB on `/`, 2 GiB on another). Since ORDER 638 the driver gives the container every processor of the host and make the jobs `nproc` grants inside it (`--cpus` and `--jobs` only to share the machine), `build.sh` passes the build's `parallel=` to Kbuild instead of a fixed 4, and the Lean Code steps (source projection, payload projection, check-debs, the link gate's inventories) run on every processor; each step prints its seconds and processors. Build 18 base alone on 12 processors: the source projection 595 s (build 17: 38 to 41 minutes on one processor). Build 17's figures, with make at 4 jobs: base 7,327 s, v3 8,760 s and rt 8,711 s. A flavour's job peaks at 22.1 GiB (build 18 v3, measured every 10 s; its link gate's own scratch 0.7 GiB of it) plus about 1.6 GB of container layer on `/`; since ORDER 638 the gate keeps the house floors (1 GiB on `/`, the scratch's own disk's floor), not 12 GiB. Two flavours whose peaks meet need about 45 GiB on one disk, or one flavour per disk: `prepare-kernel-source.py` waits for 23 GiB plus the floor where it prepares.
9. **Prove, in this order:** the source proof on the prepared sources; `qualify-kernel-unsigned.py` per flavour (boot, BTF, sched_ext, binder, Realtek modules, vkms); DKMS (`dkms-inner.sh` both orders, `dkms-nogcc-inner.sh`); KUnit for the groups the build adds (`kernel/tests/kunit/run.sh`, read the parsed counts, not the exit status); the metas (`sparky-stereo-meta` build.sh with `PACKAGES` the six kernel metas and `KERNEL_META_VERSION_SUFFIX=+lc1`); `kernel/tests/upgrade-proof.sh` (control and upgrade, read on `Inst` and `Remv`); the stage with complete sources and `SHA256SUMS`.

## Traps

- **Symptom:** `curl` of `https://git.kernel.org/.../torvalds/linux.git/patch/?id=SHA` exits 0 with an empty file. **Cause:** cgit answers automated clients with an empty body. **Fix:** fetch the history with git and use `git format-patch`. **Found by:** the four downloaded patches all had the SHA-256 of an empty file.
- **Symptom:** `git am` stops with `fatal: empty ident name (for <>) not allowed`. **Cause:** a patch whose `From:` header holds only a name. **Fix:** a kernel series patch keeps the commit's own `From: Name <address>` (it is a git patch, applied with `git apply` and `git am`); the name-only rule is for a Debian patch's DEP-3 `Author:`. **Found by:** a two-line `git am` test before writing the group.
- **Symptom:** `prepare-kernel-source.py` in a container stops in `lean/prepare.py` with `FileNotFoundError: 'dch'`. **Cause:** the kernel build image has no devscripts. **Fix:** install devscripts in the preparing container (as root, then `setpriv --reuid --regid --clear-groups` for the preparation). **Found by:** the traceback's last line.
- **Symptom:** `qualify-kernel-unsigned.py` stops copying `SPARKY_INPUTS_DIR/kernel-soul/work/bench-run/r2/initrd-tree/guest`. **Cause:** the guest tools were a fixture in a lane folder that its cleanup removed after build 16. **Fix:** `kernel/qualification/guest-tools/build.sh SOURCE VMLINUX_BTF OUT` rebuilds `bin/scx_simple` from the kernel tree's own `tools/sched_ext` (its own bpftool and libbpf; clang, llvm, libelf-dev, zlib1g-dev, libzstd-dev in the container) and `lib/` with the loader and libraries; point `SPARKY_INPUTS_DIR` at a folder that holds it at that path. **Found by:** the lane folder's MANIFEST.txt ("work ... left out").
- **Symptom:** a kernel job builds every package, then its last step stops: `lean.release check-debs` says "the build script did not call sparky_provenance_init, so no host fact reached this container". **Cause:** since ORDER 412 (2026-11-06) the build record needs the host's facts, and `run-kernel-build.py` passed none (builds 15 and 16 ran before the rule). **Fix:** the driver passes them as `build-provenance.sh` makes them (commit, dirty flag, image id and digests, invocation id, start time; not its source date, which the prepared source already has). A job started before the fix gets its record afterwards from its measured facts, with the invocation id left unrecorded. **Found by:** reading `lean/buildrecord.py` while the first flavour was compiling, before it reached that step.
- **Symptom:** a container appears as `hardcore_banzai` or another random name. **Cause:** `kernel/tests/kunit/run.sh` gave no name. **Fix:** `NAME=LANE-kunit-SUITE` (option added in ORDER 627).
- **Symptom:** a short `docker run --rm IMAGE sh -c 'apt-cache policy ...'` through the lane's socket prints nothing. **Cause:** the lane's socket proxy cuts attached output. **Fix:** write every result to a bind-mounted file, and run long builds with `--detach`. **Found by:** the same command writing to a file returned the full output.
- **Symptom:** removing a scratch export is refused: "would remove work that exists nowhere else ... 96146 uncommitted or untracked". **Cause:** `git init` in the export to hash it made it a clone in the branch keeper's eyes. **Fix:** hash with a git directory outside the tree (step 5); a tree made that way is plain scratch. **Found by:** the hook's message.

- **Symptom:** `docker run` of a DKMS proof fails at once, exit 125: "error while creating mount source path '/var/tmp/sparky-repo-current': mkdir ...: file exists". **Cause:** the published repository's local copy is a symbolic link, and the Docker daemon does not follow it for a bind mount. **Fix:** mount `$(readlink -f PATH)`. **Found by:** the first line of each case's log (six cases failed in one second).
- **Symptom:** a flavour's source prepared a second time from the same commit and the same tree has another `.dsc` hash. **Cause:** up to build 17, `prepare-kernel-source.py` packed the orig tarball with plain `tar`, from the export's own file times, owners and write order (the first export kept v7.3.1's times, a tree restored from a bundle has the restore time); the contents are equal. **Fix (build 18, ORDER 636):** `kernel/qualification/orig_archive.py` packs it with `--sort=name --mtime=@STAMP --owner=0 --group=0 --numeric-owner --mode=go-w --format=gnu` (STAMP is the recipe's date, the source's SOURCE_DATE_EPOCH) and xz's fixed preset and threads; `kernel/tests/orig-reproducible/test.py [TREE]` is its red and green (two copies of one tree with other times, modes and write order: plain tar differs, the packing is equal), on a fixture and on the real tree. **Found by:** `tar -tvJf` of both origs: the same files, other dates.
- **Symptom:** free space on `/` swings by 10 to 15 GB within minutes while a flavour builds. **Cause:** other lanes' package builds write and clean their scratch on the same disk. **Fix:** count your own peak (22.4 GB per flavour plus about 1.6 GB of container layer) against the house floors only (/ 1 GB, /mnt/build 2 GB, /K3D 2 GB; a brief's stricter figure is a starting place, not a stopping rule), keep 12 GiB free on `/` for the link gate inside each job, and use `docker pause NAME` (nothing is lost) rather than a floor stop, which loses the job: a stopped job's source has been projected in place, so the flavour is prepared again. **Found by:** `du` of the other lanes' scratch folders between two `df` readings.
- **Symptom:** `qualify-kernel-unsigned.py` fails boots at random ("the guest did not finish"; QEMU killed at the bench's 420 s), the kernel log holding only the firmware's console codes, while other boots of the same image reach `/init` in 4 s. **Cause:** the guests ran beside two kernel builds, KUnit and DKMS (36 runnable threads on 12 processors): starved before the kernel's first line (build 18 base, 5 boots of features, Secure Boot and the hibernate resume). **Fix:** run the qualification with no build beside it (`docker pause` the builds; nothing is lost): the same image passed every scenario in 2 min 20 s. **Found by:** `boot1.status` 137 and the size of `boot1.kernel.log` (193 bytes) against a passing run's first line, `Linux version`.
- **Symptom:** two flavours side by side, / with 22 GB free in mid-compile, and the disk guard would pause the later one at 16 GiB. **Cause:** a paused build keeps every byte it wrote; the room the first flavour's link gate will have is today's free space minus what every running build still writes (about 14 GB each from mid-compile to the 22.4 GB peak), and that gate needed 12 GiB free on `/` (the house floor since ORDER 638, 1 GiB). **Fix:** count it before starting the second flavour; if the sum does not fit, run the flavours one after the other, or stop the later one (`docker stop` by name, remove its job) and build it again alone: build 18's rt was stopped at mid-compile so v3's gate kept its room. **Found by:** `du` of each job folder against `df /` and base's measured peak.
- **Symptom:** a command that runs `kill $(pgrep -f 'run-kernel-build.py rt ...')` ends with exit 144 before its next step. **Cause:** `pgrep -f` matched the shell running that very command, whose own command line holds the pattern. **Fix:** take the PID from the driver's own record or from `ps` filtered by parent, or stop the container by name first; never `pgrep -f` a pattern the command itself contains. **Found by:** the three PIDs pgrep printed: the build's wrapper, its driver and the current shell.

## Moving the series to a newer stable release (build 18, ORDER 636)

A security build carries single fixes; when stable has taken many, the series moves to the newest released 7.3.y instead, and only what that release lacks stays carried.
Daniel, 2026-11-16, for this step: "there's no need to re-check what upstream merged, just that our patches still work": the signed release tag is the evidence for the base; the proof effort goes to our own patches.

1. **Fetch and verify the release.** kernel.org's git answered at about 6 MB a minute; GitHub's mirrors are fast: `git fetch --depth 1 https://github.com/gregkh/linux refs/tags/v7.3.4:refs/tags/v7.3.4` for the tag, `--shallow-exclude=v7.3.1` for its history, and torvalds' mainline commits by full hash. A mirror is only a transport: compare the tag object's id with `git ls-remote` of kernel.org's stable tree, and check its signature in a throwaway GNUPGHOME with Greg Kroah-Hartman's key from kernel.org's pgpkeys.git (`keys/38DBBDC86092693E.asc`, by the key id; a path by the whole fingerprint returns 404): `git verify-tag --raw` must say GOODSIG and VALIDSIG 647F28654894E3BD457199BE38DBBDC86092693E.
2. **Survey every file on a plain export.** `git archive v7.3.4 | tar -x`, then for each series file in order: `git apply --check` (applies), `git apply --check -R` (the base already has it), or neither (a port). Record all three lists. A file that applies in reverse is left out only with stable's commit of the same subject found in `git log` (a series line becomes a comment naming that commit).
3. **Check the files that apply forward for duplicates.** For every patch that applies and touches a file stable changed, look for each block it adds already in the base, and compare its subject with stable's log. Build 18's 46/0016 (udlfb) applied forward although v7.3.4 has it, because a later 7.3.4 commit moved its context; `git apply` would have placed its hunk a second time.
4. **Port in order, on one work tree.** A small script applies the series in order and stops at the first file that does not apply (state kept in a file beside the tree, so a hand-ported file is not tried again). For a port: copy the touched files aside, make the patch's change by hand on the new code, `diff -u --label a/F --label b/F` the copies against the tree, and compare the changed lines (+ and -) of the port with the original's: only the differences the new upstream code forces may remain (a renamed symbol, a new argument). Write the port with the original header, an `[ORDER NNN: ported to v7.3.4: upstream COMMIT (TITLE, AUTHOR) changed ...; ...]` line before `---`, and the new diff; then `git apply --check -R` it on the work tree. Read each port's function on the new code for what the patch relies on (group 43: both commit hooks still return only 0; every error after the prepare hook still reaches the abort).
5. **Restructure the series.** Remove the files and groups the release has (git rm, a comment line naming each stable commit), move what the release lacks into a new group with fresh notes, and cherry-pick mainline-only fixes with `git format-patch --zero-commit --no-signature --abbrev=9` plus `(cherry picked from commit SHA)`. Then apply the whole series strictly (`apply-series.sh`) on fresh exports for every flavour and hash them with an outside git directory: the ordered work tree and the fresh base export must give the same tree (build 18: e637af87fe1d both).
6. **Pin the release** in `kernel/lean/upstream.py` (tag, verified commit, `CURRENT`) and the `TAG`/`TAG_COMMIT` defaults of `build-deb.sh` and `tests/config-proof.sh`; write a new manifest (tag, commit, trees, the tag's commit time as timestamp, every patch's sha256) and run `check-flavours.py`.
7. **Prove our additions in source.** `kernel/tests/stable-security/carried-present.sh TREE` (default: the files of the carried security group) says present, MISSING or UNCLEAR for each: red on the pristine release, green on the edition's trees. Compile what the ports and the carried group touch (step 6 of the security recipe) before the long builds.

Traps of the rebase:
- **Symptom:** `git log v7.3.1..v7.3.4 -- FILES` fails or lists everything. **Cause:** with `--shallow-exclude=v7.3.1` the history stops at a boundary commit (build 18: 1a9c180cd, stable's first commit after v7.3.1) that is a root in the shallow clone, so it seems to add every file, and v7.3.1 itself is not in the history. **Fix:** `git diff --name-only BOUNDARY v7.3.4` plus the boundary's own files for what stable changed; `git log v7.3.4 -- FILES` with the boundary excluded. **Found by:** the first list of stable's files holding the whole tree.
- **Symptom:** removing a scratch clone is refused by the branch keeper (an untracked file). **Cause:** a fetch log written inside the clone. **Fix:** keep logs, state files and scripts outside every git directory. **Found by:** the hook's message naming `fetch.log`.
- **Symptom:** the in-order script retries a file you just ported by hand and stops on it. **Cause:** its state file does not know about the manual application. **Fix:** append the patch's path to the state file after each port. **Found by:** the second stop on the same file.
- **Symptom:** after `run-kernel-build.py` starts, `kernel-sources/FLAVOUR/source` is gone. **Cause:** the driver moves the prepared source into its job folder. **Fix:** a later check on the prepared tree unpacks the `.dsc` (`dpkg-source -x`) instead. **Found by:** `ls` before a planned reread.

Measured on build 18 (v7.3.1 to v7.3.4, 1,806 stable commits): of build 17's 285 files, 233 applied unchanged, 47 were in the release (46/0016 among them, which would have applied forward a second time), and 5 needed a port (asus-wmi 17/0024 and 17/0026 after upstream renamed a flag, oxpec 29/0001 after upstream added a model to every switch, amdgpu 43/0001 and 43/0002 after upstream changed one call's argument); with group 47's six carried fixes the series has 241 files (242 for v3).

## Perks

- The kernel CNA's records lag the releases: on 2026-11-16 v7.3.4 (1,254 commits, 10 November) had 10 records, v7.3.2 (548 commits) 35. A security build carries what the records and the advisory name; the rest of a stable release is the rebase's.
- A memory-ordering fix such as `refcount_inc_not_zero_acquire()` changes nothing on x86; carry it with its series anyway, so the lookup code is stable's.
