# drivers: lessons from the lanes of 25 October to 11 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Prove DKMS signing in a clean Debian container: install dkms, headers and a small DKMS module (v4l2loopback-dkms 0.15.4-2 reproduced it on Debian testing with dkms 3.2.2-1 and headers 7.2.12-1), build, then verify the CMS signature trailer with `openssl cms` and add a negative control without openssl. Expect "0 of N signed" without openssl and "N of N" with it. (lane dkms-openssl-369)
- To sign modules that were built unsigned (a package that gains openssl later does not repair them): on configure, for every installed module whose file lacks the signature trailer, run `dkms build --force` then `dkms install --force`; only when the kernel has CONFIG_MODULE_SIG_HASH; put DKMS's built copy back when the rebuild fails so the installed module and `dkms status` stay as they were; hand a failure to the problems engine and let the dpkg step complete. dkms's own `running_in_chroot` and `try_sign_modules=false` are respected and said, not overridden. Result: 0 of 3 signed after +sparky2, 3 of 3 after +sparky3; no-op builds nothing. (lane dkms-unsigned-370)
- First-boot signing and key enrolment for DKMS modules under Secure Boot: (1) a oneshot `dkms-sign-unsigned.service` signs once, in the background, not in a live session or container, and marks itself done with a file (/var/lib/dkms/dkms-sign-unsigned.first-boot); it checks what the kernel will load (`modinfo -k -n`) and rewrites stale boot images after signing; (2) the machine's /var/lib/dkms/mok.pub is copied as a .der next to shim on the ESP and a second GRUB entry (guarded by the ESP UUID) reaches MokManager's "Enroll key from disk", which asks only for a confirmation; (3) a boot check compares shim's MokListRT with each module's sig_key and keeps a problem record until the key is enrolled. Measured: 59.5 s wall, 67.9 s CPU, 693 MB, boot targets reached at 5.05 s. (lane dkms-firstboot-enrol-374)
- Install NVIDIA's i386 libraries by themselves after the apt run that needs them: a path or trigger unit waits with `DPkg::Lock::Timeout=-1` (no polling loop), simulates first without locks to say "the version is gone" in words, honours policy-rc.d, detects and says chroot, no systemd and masked unit, keeps a problem record with its Repair, and runs with no nice and no caps. KillMode=process and TimeoutStopSec=900 follow Debian's apt-daily-upgrade.service. (lane nvidia-i386-auto-363b)
- Test a udev rule without hardware: umockdev with made-up controls plus `udevadm test`, commands run on the fake controls. Red on the published rules gave 10 failures, exit 1. Green on the rebuilt rules plus helper gave 0 failures. Helper-only paths get a separate script (failure exit 1, one problem per wheel, Repair fails while the cause stays and works when it is gone). (lane no-fallbacks-drivers-346f1)
- HDMI-CEC display power: adapters emit a structured problem(kind, detail, evidence) beside the old failed(text). Kinds: start (cec-ctl could not run), address (no usable playback address), unacknowledged (Standby, Image View On, Active Source). Intentional refusals (another input is active, screen already on) stay notices and keep nothing. Test with a private Wayland server with KDE DPMS, private logind and real cec-ctl over simulated ioctls; red is the old wiring built with `-DOLD_WIRING=ON` (5 failed, 24 passed), green 29 passed. (lane no-fallbacks-drivers-346f1)
- A launcher that refuses on purpose (SteamVR only inside gamescope) keeps the refusal but reports it to the problems engine with the log tail as evidence and an "Open the log" action, clears it on the next start that gets a display, and says so on stderr when the engine is absent. A `..._TRIES` variable lets tests wait less than the 150 tries default. (lane no-fallbacks-drivers-346f1)

- Read an amdgpu devcoredump's gfx ring before guessing: `python3 scripts/amdgpu-ring-layout.py data` walks the ring from 0 to Wptr (type-3 header: bits 31:30 = 3, count in 29:16, opcode in 15:8; 0x80000000 is gfx6's one-dword NOP) and says whether a job's INDIRECT_BUFFER and an EVENT_WRITE_EOP (with its sequence number) are still there. A ring that holds only ME_INITIALIZE, the clear-state preamble, ring tests (SET_CONFIG_REG 0x140 = 0xdeadbeef) and NOPs, with Rptr equal to Wptr, has nothing left that can write the timed-out fence. The devcoredump keeps one dump per device: write to its `data` file to free it, so the next reset leaves its own. (lane a10-hainan-webgpu-wedge-525)
- Prove a reset-path fix without the hardware: copy the kernel's own functions unchanged into one file (an extractor that takes each function from its definition line to the first line that is exactly `}`), compile them against a small shim with the kernel's field names, and simulate only the hardware they drive (the command processor reading the ring, the IP block's soft reset, the scheduler's timer). Expect red on the shipped source and green with the patch, plus a negative control that makes each comparison fail. For the gfx6 soft-reset loop: shipped v7.3.1 wedged in two of four scenarios, the carried patch recovered in all four, the in-flight alternative wedged in two. (lane a10-hainan-webgpu-wedge-525)
- Search the amd-gfx list by the function you suspect, not only by commit: `https://lore.kernel.org/amd-gfx/?q=guilty_fence+NULL&x=A` (an Atom feed curl can read) found the in-flight patch and its review thread that no tree had yet. (lane a10-hainan-webgpu-wedge-525)

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: frame sequential locks after DisplayPort cases. Cause: KWin's software frame-sequential twin was paced one frame at a time (DrmOutput::maxPendingFrames(), RenderLoop leaves triple buffering when the maximum is under 2), needing a predicted render time near one refresh (4 to 8 ms at 119.8 Hz); stock build reproduces it with the side-by-side and top-and-bottom twins, the DisplayPort code plays no part. Found by: A/B of the stock branch against the fix, 52 repeats in 9,120 frames under host load (lane dp-stereo-257-m4b)
- Symptom: KUnit cannot run on the edition kernel tree under UML. Cause: BORE's MIN_BASE_SLICE_NS lives in kernel/Kconfig.hz which only x86 sources. Fix: run KUnit on x86_64 QEMU. Also: DRM CRC debugfs entries are `0x%08x frame 0x%08x crc...` each LINE_LEN bytes ending in "\n\0" (parse the frame as hex, handle the NUL); an in-tree single `.ko` build runs modpost against vmlinux.o, not Module.symvers (check symbols with `scripts/mod/modpost -M -e -i <headers>/Module.symvers -T list`); amdgpu DC finds: hubp2 lacked the stereo flip latch, `dcn10_config_stereo_parameters` converter check reads a never-set `ddc->dongle_type`, the HPO (UHBR) encoder has no stereo sync (lane dp-stereo-257-m5)
- Symptom: DKMS modules install but are unsigned, and Secure Boot refuses to load them; the log shows only "openssl not found, can't generate key and certificate." and then "Autoinstall ... succeeded". Cause: Debian's dkms names openssl in no dependency field (only its autopkgtest), and the edition's upgrade tools run `apt full-upgrade --no-install-recommends`, so a Recommends added later never arrives; dkms prints the cause (upstream commit 95ca2fc) but not the consequence. Fix: make openssl a Depends of the edition's dkms build (dkms 3.4.4-1+sparky2); never a Recommends. Found by: reading the dkms.in message lines, then a red/green container run, 0 of 3 modules signed before and 3 of 3 after, each verified with `openssl cms`. (lane dkms-openssl-369)
- Symptom: an installed image boots under Secure Boot with every DKMS module unsigned ("Running in chroot, modules won't be signed"). Cause: the ISO builds DKMS modules inside a chroot where dkms (since #574/#575, `try_sign_modules`) makes no key and signs nothing, and the packer removes the chroot's key. Fix: sign on the installed system's first boot with the machine's own key (see dkms-firstboot-enrol-374). Found by: the dkms message text and the modinfo signature check of an installed image. (lane dkms-unsigned-370)
- Symptom: a unit with ConditionFirstBoot never runs on the installed system. Cause: the packer empties /etc/machine-id (systemd does not count that as a first boot), the installer writes a real ID, and a true first boot would also preset every unit (machine-id(5) "First Boot Semantics"). Fix: the unit marks itself done with its own file. Found by: reading machine-id(5) and systemd.unit(5), then testing in a VM. (lane dkms-firstboot-enrol-374)
- Symptom: `dkms` fails for every module in a minimal container after installing `linux-headers` with `--no-install-recommends`. Cause: the headers pull `gcc-16-for-host` but no `gcc` command. Fix: install gcc (or a package that Depends on it) explicitly; real systems without NVIDIA's package hit it because only nvidia-kernel-open-dkms-stereo3d's g++ Depends brought gcc. Found by: the DKMS build log "no gcc" in the minimal container (red on headers 14.2, green on 15 for every flavour and install order). (lane kernel-build-14-295)
- Symptom: kernel build container name collides, or a stop at the disk floor cannot resume. Cause: the build driver names its container per flavour and has no resume option. Fix: name per counter; resume by rerunning only the binary steps with `-nc` after deleting outputs written just before the kill. Also: the local `debian:forky` tag can be an i386 image; `git add -A` drops tracked dot files; the qualifier leaves root-owned boot-work files, remove with a root container. (lane kernel-build-14-295)
- Symptom: KUnit run "passes" with failing tests. Cause: `kunit.py --raw_output` exits 0 even with failures, and `python3 -I` breaks `kunit.py parse` (it imports from its own folder). Fix: read the parsed counts, run without -I. Found by: comparing the parsed summary with the exit code. (lane kernel-build-15-364)
- Symptom: kernel oops in virtio-gpu with stereo=on (BUG_ON at virtgpu_vq.c:126). Cause: `struct virtio_gpu_set_scanout_stereo` is 104 bytes, larger than MAX_INLINE_CMD_SIZE (96). Fix: raise the limit to 104 with a BUILD_BUG_ON on the struct size. Found by: the guest oops during the virtio-gpu stereo test. (lane kernel-73-263)
- Symptom: NVIDIA open modules fail to build on Linux 7.3. Cause: 7.3 changed `dmem_cgroup_register_region()`. Fix: backport NVIDIA 615.78.08's conftest change as a patch, and make the headers Breaks the older DKMS package so both ship together. Found by: DKMS build log on 7.3. (lane kernel-73-263)
- Symptom: amdgpu hangs: 128 "Can't handle page fault (-12)" lines in 70 ms, then a device coredump and "ring gfx timeout", GPU and gem_create/gem_open wedged. Cause: `amdgpu_vm_update_range`, `update_pdes` and `pt_clear` leak the prepared VM update job (1 KiB each) when a page-table allocation fails after the prepare hook; 128 leaked jobs fill the 128 KiB immediate IB pool, and `drm_suballoc_new` waits forever with no fence. The coredump and ring reset are victims. Fix: carry Cascardo's two-patch amd-gfx series (abort hook that frees the job), not our own patch; Benjamin Cheng's narrower patch is recorded. Found by: the journal count (exactly 128), reading the stack to `amdgpu_sa_bo_new`, and a model built on the real `drm_suballoc.c` (red wedges at 128 failed updates; green completes 200000 faults; sweep of 50 seeds). (lane amdgpu-devcoredump-deadlock-417)
- Symptom: a Southern Islands GPU (Radeon R5 M430, Hainan, gfx_v6_0) prints, every 3.5 s and without end, `ring gfx timeout, signaled seq=N, emitted seq=N+1`, `Starting gfx_v6_0 IP block soft reset`, `Successful gfx_v6_0 IP block soft reset`, `[drm] device wedged, but no recovery needed` and a new devcoredump; the same sequence number never retires; the program, TTM's delayed-delete workers and anything waiting on the GPU stay in D state until a reboot. It started with one WebGPU compute submission that ran longer than amdgpu's 2000 ms watchdog (`lockup_timeout` default in 7.3). Cause: gfx6 has no wave-kill soft recovery, so every gfx timeout goes to the IP block soft reset (1fc76380c6ce, v7.3-rc1). When the same fence times out again (the first replay did not complete), or a later job's fence is allocated at the address `ring->guilty_fence` still holds from an earlier reset, `amdgpu_ring_backup_unprocessed_commands` skips the backup and sets `ring->guilty_fence` to NULL; `amdgpu_multi_ring_reset_helper_end` restores the ring with that NULL, and since b3f73daa1c24 (in v7.3) a NULL guilty fence skips the force completion. The reset "succeeds" because the ring tests pass on the re-initialised ring; nothing is left that could write the fence, the handler returns NO_HANG and the timer fires again; every other cycle replays a stale backup (NOPs) from a write pointer that no longer exists. Fix: carry Jesse Zhang's (AMD) amd-gfx patch "[PATCH v3 02/15] drm/amdgpu: complete the guilty fence at the end of a multi ring reset" (2026-10-28), which passes the guilty fence to the end helper: the repeated fence ends with -ETIME, the rest of the ring with -ECANCELED, the program gets a lost device. Its v4 replacement (Timur Kristóf's 02/13, skip the begin helper on a repeat) replays the first backup every time and loops the same way on gfx6 when that replay cannot complete; it also replays a stale backup on an address match. Found by: the devcoredump's ring (Rptr == Wptr, init, clear state, two ring tests, NOPs, no EOP), reading `amdgpu_job_timedout`, `amdgpu_device_ip_soft_reset` and the backup and reemit helpers of the exact kernel, the git history of the guard (ce3f23a78085, 930a915de89c, b3f73daa1c24), a lore search by function name, and a model on the real functions that reproduces the dump's layout. On the hardware (kit run on 7.3.1, three first resets): the first soft reset replays the job's stream with its IBs as NOPs, the command processor consumes it (Rptr == Wptr), and the fence write still has not landed when the next timeout fires; about ten VM protection faults on the job's VMID follow the SRBM pulse. Once the fence write landed late, and the next cycle's end helper found the fence memory at sync_seq and completed the job. So the first replay cannot be counted on to complete on gfx6, and the loop is the normal outcome, not a corner case. gfx8 (Carrizo) tries wave-kill soft recovery first, but on the same laptop a compute-ring timeout was not soft recovered and went to one IP block soft reset, which recovered. Proved on the hardware (2026-11-11): a test build of 7.3.1 with the carried patch ran the same kit on the same laptop; each 8 s job got two timeouts of one sequence number and then nothing more, the program ended with a lost device on its next submission, nothing stayed in D state, and an ordinary reboot afterwards took 65 s. (lane a10-hainan-webgpu-wedge-525)
- Symptom: two candidate fixes for the gfx6 soft-reset loop above look the same in a short test. Cause: with an 8 s job both end it at the second timeout. Fix: measure with a much longer job and state the prediction first. Measured on the Radeon R5 M430 (2026-11-11, test builds of 7.3.1, one 60 s compute job): with Jesse Zhang's v3 02/15 (the carried group 45) the job was ended at the first timeout, 3.4 s after submission; with Timur Kristóf's v4 02/13 (replay again, skip the begin helper) after three timeouts, 10.8 s after submission; in both the program got a lost device on its next submission and nothing stayed in D state. Unpatched 7.3.1 looped until a reboot. A user-space model of the reset code had predicted about seventeen timeouts for v4 (it assumed the job's waves outlive the soft reset, from three 8 s jobs that completed at about their own length); the hardware refuted it, so a model's number is a prediction to test, never a result. Found by: building both test kernels and running the same kit on the same laptop. (lane a10-hainan-webgpu-wedge-525)
- Symptom: a Vulkan program's `vkWaitForFences` returns VK_SUCCESS for a job that the kernel ended with -ETIME after a GPU reset (A10, radv, 7.3.1). Found by: the kit's wedge case, the program's own result line, then `amdgpu_ctx.c` and `sched_entity.c`. (lane a10-hainan-webgpu-wedge-525)

## Perks of the part

- amdgpu in 7.3 kills any job after 2000 ms on every queue (`lockup_timeout`, "the timeout for all queues is 2000"); a browser's WebGPU submission that encodes a whole procedure in one command buffer is one job, so a page that is fast on a newer GPU (701 ms on a Renoir iGPU) can be killed on an older one (about 3.6 s on Carrizo by the same page's own 1024-pixel time). Soft recovery (`.soft_recovery`, killing the job's waves) exists on gfx7 and gfx8 but not gfx6, and when it does not end the job in 10 ms the IP block soft reset follows; gfx6, gfx7 compute and gfx8 declare the IP block soft reset. `/sys/kernel/debug/dri/N/amdgpu_fence_info` gives each ring's signaled and emitted sequence numbers. (lane a10-hainan-webgpu-wedge-525)
- The drivers skill says Debian's zfs-dkms does not build on 7.3 and the edition builds zfs-linux; proof pattern for this: the red run shows Debian's package failing and ours installing, with apt `Inst` lines and no `Remv` or `Purg`. (lane zfs-restore-385)
- A tester without tools can send EDIDs decoded on the spot (maker, product, serial, name, first timing, extension count) and zipped; checksums show whether 2D and Half SBS send the same EDID (lane xreal-control-235)
- Upstream search for udev-rule changes: check each driver repository's rules file history, issues and open pull requests (hid-fanatecff, hid-tmff2, new-lg4ff); a rules file that is a documented edition difference gets one more documented line in its header. (lane no-fallbacks-drivers-346f1)

## Measured facts

- `dkms install --force` copies the module already built and does NOT sign it; `dkms build --force` followed by `dkms install --force` signs it. Upstream has no command to re-sign installed modules (dkms issue 372 closed as stale on 2026-07-26; Debian bug 1035707 open). `apt-get upgrade` also keeps back a package that gains a new Depends. (lane dkms-openssl-369)
- The no-op check (one `modinfo` per installed module file) costs about 0.4 s for 21 files (NVIDIA open modules on 2 kernels), dominated by decompressing nvidia.ko.xz at about 206 ms per kernel; about 30 ms for one small module. `xargs` searches PATH for `sh` (9 failed execve per run in strace); name /bin/sh. (lane dkms-unsigned-370)
- Debian's shim-signed `update-secureboot-policy` already compares the DKMS key serial with `mokutil --list-enrolled` when run by hand; it enrols and keeps nothing. Debian #1076269 and dkms #429 ask for automatic enrolment and are open or closed as stale. (lane dkms-firstboot-enrol-374)
- Disk planning for a Lean Code kernel build: one flavour's job peaks at 22.4 GB; the link gate needs 12 GiB on / inside the container; plan 26.5 GB on the build disk per flavour; another image build can take / down by about 2 GiB a minute, so free space before a kernel round. (lane kernel-build-14-295)
- Build 15 qualification (7.3.1-15, base, v3, rt): headers and DKMS in all three flavours; zram stays a module for the opt-in and zswap stays off by default; security fixes enter as the upstream commits with their authors; the pin file names the new build and the old build leaves the pool at publication. (lane kernel-build-15-364)
- Rebase of ~35 patch groups onto a new final tag: verify the tag signature (git tag -v), adapt by hand only the groups that conflict, drop commits upstream already took, qualify: unsigned VM matrix in all flavours, EFI mixed boot 100 of 100 with KASLR per flavour, KUnit drm-stereo 319/319, amdgpu-dm 1675/1675, 18 signed DKMS modules per kernel in both install orders. (lane kernel-73-263)
- Valve's VRAM helpers (dmemcg-booster, plasma-foreground-booster) need CONFIG_CGROUP_DMEM=y; the foreground booster also raises the foreground app's CPU weight to 10000 (upstream default). Not proven: AMD dGPU init and display output. (lane kernel-73-263)
- Qualify EFI-mixed (32-bit firmware, 64-bit kernel) boots with KASLR by counting boots: 100 of 100 per flavour passed on kernel 7.3 (carried from the 7.3 lane). The lane itself has no report body. (lane efi-mixed-kaslr-246)
- Known USB-C 3D glasses come up in full side by side as a per-output option (stereoGlasses in BackendOutput::State, kwinoutputconfig.json, Capability::StereoGlasses 1<<24 on DRM, table keyed by EDID product codes 0x0435..0x043e); when no saved mode fits, chooseMode() picks the glasses twin. Control: base build lists only 3840x1080@59.97 and the right half is black (0 right-eye samples), so the twin check fails first (lane xreal-driver-233)
- Protocol contract test fails first on version 28 (2 failures, 1 error), passes (8 OK) at 29; KScreen label test shows "60 Hz" where "60 Hz (3D side by side full, for USB-C 3D glasses)" is expected, then 3 of 3 pass (lane xreal-driver-233)
- No public control path for the 3D mode of One series glasses: no HID path in the open driver (set_sbs_mode returns false), its TCP link on the glasses' sensor port is only read, the vendor's Android tool switches the mode, the SDK has a getter only, and the guide says the mode is not kept after reconnection. Only a read-only DDC/CI probe (Windows Monitor Configuration API, Linux ddcutil) and EDID dumps (registry HKLM...\Enum\DISPLAY\<pnp>\<instance>\Device Parameters\EDID, /sys/class/drm/*/edid) answer whether 2D and half SBS send different EDIDs (lane xreal-control-235)
- DisplayPort checks 25 of 25 in every run: mode list (21: 640x480@59.94 (3D-FS-DP), twin 34 virtual-3D:19), TEST_ONLY accepted on DP-1 and refused on DP-2 (lane kwin-followups-294)
- Kernel uAPI names both depth structures (DRM_MODE_FLAG_3D_L_DEPTH, _L_DEPTH_GFX_GFX_DEPTH, drm_mode.h:75-84) but drm_edid.c lists only 0/3/6/8 and CRTC_STEREO_DOUBLE does not time them; no 3D_Meta in hdmi.h; FFmpeg parses SEI 176 only (names 50, 52-54, 177-181), hevc/ps.c:603 refuses AuxId 2; H.264 depth NAL 21 and SEI 50, H.265 SEI 177 (G.14.2.4) (lane depth-as-3d-source)
- VRAM protection detector: the failures to hand to the shared problems engine are a mode that is not a mode, a missing dmem controller on a computer whose GPU could use it, an unreadable dmem.capacity, and a bound GPU that never registered VRAM. Expected registrants are bound amdgpu, xe and nouveau devices (amdgpu only in amd-dgpu mode). A boot helper clears the keys it did not raise, so a cause that went away ends the problem. Mode off, no GPU, NVIDIA's driver, i915 are not problems. Red 9 failures, green 0. (lane no-fallbacks-drivers-346f1)
- Detector on real /sys, read only: 9.5 ms off, 97.9 ms on. This is detection time, not a benefit measurement. A boot run takes one snapshot and never sleeps or polls; the proof records elapsed time under one second and rejects any sleep call. A retired value (`auto`) is read as off so an old default never becomes an opt-in, and an explicit local value wins over the shipped conffile on upgrade. (lane no-fallbacks-drivers-346f2)
- XREAL One series: USB VID 0x3318, PIDs 0x0435/0x0436 One Pro, 0x0437/0x0438 One, 0x043e/0x043d 1S. The 3D side by side mode is switched only on the glasses' on-screen menu (Full SBS 3840x1080 or Half SBS 1920x1080), no HID or USB command; orientation arrives at 1000 Hz over a USB network protocol (xrealOneDeviceKit over xreal_one_driver, Rust, MIT); Breezy Desktop is GPL-3 with a KWin 6 integration; Monado has no One series driver. Reading the EDID on hardware is step 0. (lane crash-course-231)
- Carry an input or HID series without a full kernel build (ORDER 15): extract the published `.orig.tar.xz` of each flavour (it already holds the series), apply only the new group with `apply-series.sh` and a `SKIP` regex, `configure.sh FLAVOUR /obj`, `make O=/obj modules_prepare`, then `make O=/obj drivers/input/ drivers/hid/` (about two minutes on four CPUs, no `.ko`). Detail and traps: skills/gamecontroller/references/ev-btn.md.
- Symptom: a patch fetched from a mailing-list archive is HTML with masked addresses. Cause: lkml.iu.edu masks `@gmail.com` as `@xxxxxxxxx` and ends lines with `<br>`. Fix: split on the body markers, turn `<br>` back into newlines, unescape, restore the domain, and compare the diff with the author's tree. Found by: reading the saved page next to the author's own tree before building the patch files.
