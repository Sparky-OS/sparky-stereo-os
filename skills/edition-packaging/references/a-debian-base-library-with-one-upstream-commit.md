# The edition's own build of a Debian base library with one upstream commit

For a library every program loads (GLib) when Debian's package lacks a fix that upstream has merged: the edition builds its own, amd64 and i386, with upstream's commit as its one patch, and retires it when Debian ships the commit.
Written 2026-11-20 from ORDER 768b: Debian's glib2.0 2.90.1-2 plus Thomas Hebb's GLib commit 4301b49671, which removes the deadlock that kept the location service (geoclue) from starting.
The route first stopped at the Lean Code step (trap 1); the toolkit then learned to keep a hook the rules file already defines, and the recipe below ran to the end on both architectures.

## Recipe, as run

1. **Reconcile first.** Nothing is built if Debian or a release already has the commit.
   - Debian: in a clean `debian:testing` container with `deb-src` and the suites testing, unstable and experimental, `apt-cache madison` for each binary of the source and `apt-cache showsrc NAME`.
   - The packaging: Salsa's API, `projects/<team>%2F<repo>/repository/branches` sorted by commit date, then `repository/files/debian%2Fchangelog/raw?ref=debian%2Flatest` and `debian%2Fpatches%2Fseries`, grepped for the file, the function, both commit hashes, the merge request and the issue numbers; `merge_requests` for one in flight.
   - Upstream: GitLab's `repository/commits/SHA/refs?type=all` for the branch commit and for the main commit. A list with branches only means no tag, so no release has it; `repository/tags?order_by=updated` names the newest release.
   - Debian's tracker over SOAP (`get_bugs`, `src`, for the library and for the program that showed the symptom, then `get_status` one bug at a time: an array of ids answers `Not an ARRAY reference`).
2. **Debian's source and binaries through apt**, so apt checks them against the signed indexes: `dpkg --add-architecture i386`, `apt-get source --download-only NAME=VERSION`, then `apt-get download PKG:ARCH=VERSION` for every name of the `.dsc`'s `Package-List` (the Architecture: all ones on amd64 only, no udeb). The `.dsc`'s SHA-256 goes into the recipe. These are the link gate's predecessors and the comparison's reference.
3. **The patch is upstream's commit.** Compare its code with the forge's own diff (`repository/commits/SHA/diff`) byte for byte, then write the header in the form of KWin's carried commits: `From: Name`, upstream's message, one line saying it is carried unchanged, `Origin: upstream, <commit URL>`, `Author:`, `Bug:`, `Applied-Upstream:` (branch commit and main commit, with their merge requests), `Forwarded: not-needed`, `Last-Update:`, `Assisted-by:`. Names only: an address in `From:` or `Signed-off-by:` stays out of our files.
4. **The recipe in `librsvg`'s form** (`sparky-os/packages/NAME/`): `build.sh` makes the source once and the `+lc1` source, then builds amd64 with the link and start gate against Debian's build; `build-i386.sh` builds `-B` from that same `+lc1` `.dsc` and checks that every file under `/usr/share` is the same bytes as amd64's; `changelog-stereo3d1.txt`; `patches/`; `tests/` with the fix's own reproducer and runner. `SPARKY_BUILD_IMAGE` names a lane's own builder image; the main session's default stays `sparky-lc-migration:20261020`. Commit before building: the build record's `recipeDirty` reads the tree. Every `docker run` of the recipe and of its test rig carries `--ulimit core=1` (the [working-practices](../../working-practices/SKILL.md) skill says why), and `tests/supply-chain/test-wiring.sh` fails a launcher without it.
5. **A lane's builder image** is `debian:testing` by digest plus the edition builder's package list (`build-essential debhelper devscripts dpkg-dev fakeroot equivs python3 python3-yaml nodejs node-acorn perl ca-certificates pkgconf git`, after `apt-get dist-upgrade`), built through `tools/https-only-build.sh` with the base as a build argument.
6. **Debian's udeb is not built:** `DEB_BUILD_PROFILES=noudeb` beside `DEB_BUILD_OPTIONS='parallel=4 nocheck'`, on both architectures, as `packages/gtk4` does (trap 8). The edition publishes no udeb; its installer, Calamares, does not use Debian-Installer.
7. **The link gate's folder** (`SPARKY_LC_ARCHIVE_DIR`): `sources.json` with Debian forky main, deb-multimedia forky main non-free and the published round as `file:/repo`, each with a keyring path as the container sees it (`/archive/keyrings/...`). The gate copies each keyring to a `.gpg` name, so it must be binary: `gpg --dearmor` the edition's `sparky-stereo-repo.asc`.

## The proof, as run on GLib 2.90.1-2+stereo3d1+lc1

The checks ORDER 768b set for a library every program loads, each with what GLib gave; the commands are the lane's rig scripts.

- **Both architectures from one recipe commit**, at 4 threads: amd64 and i386 7 to 9 minutes each (9 with another 4-thread run beside them), build records with `recipeDirty` false and `unrecorded` empty, the link and start gate passed for every package; the twin check (trap 9): 15 `Multi-Arch: same` packages, 356 shared files, all the same bytes.
- **The library's own test suite**, as Debian's packaging runs it (`debian/rules override_dh_auto_test-arch` after `debian/rules build-arch` with `DEB_BUILD_OPTIONS='parallel=4 nocheck'`), on the `+lc1` tree as built (its configure hook projects the sources) and on Debian's unpatched source in the same container: 414 OK, 0 failed, 11 skipped of 425 on both, every test in the same state.
- **Every binary package against Debian's**, both architectures: the control fields are Debian's plus the lc1 `Breaks: dpkg-stereo (<< 0.1.6)`; no NEEDED or SONAME changes; the defined dynamic symbols of libglib (1,897), libgio (2,155), libgobject (480), libgmodule (10), libgthread (2) and libgirepository (236) identical; every typelib and every GIR file identical, and every documentation page; every other differing file explained by kind (lc1 projections whose manifest `sha_hr` is Debian's exact bytes, rebuilt ELF files, static archives with the same members and symbols, the changelog and copyright, a PNG's `tIME`), nothing left open (before the 32 headers of trap 3 were kept, the GIR source positions and 530 pages' `[src]` anchors were).
- **apt's plan** over the published round plus the stage, on a system with GLib for amd64 and i386: 13 `Inst` lines to the edition's version, no `Remv`, nothing kept back.
- **Real program starts** in a session under `kwin_wayland --virtual` (`--cap-add SYS_NICE`, software rendering) with the edition's GLib installed by apt: Dolphin, Konsole, Kate, System Settings and gtk4-demo each still running after `timeout 12` (124), no crash, each mapping the installed `libglib-2.0.so.0.9000.1`, whose sha256 is the package's.
- **Red and green on installed packages**, each in a freshly booted systemd container from one image, the edition's packages installed by apt for green: the reproducer hung 10 of 10 on Debian's 2.90.1-2 (`timeout 20`, 124) and finished 10 of 10 in 0.62 s on ours; geoclue.service timed out in 31 and, in a second run, 27 of 200 starts on Debian's and in 0 of 200 on ours, both times. The start loop and the reproducer are the system-housekeeping skill's [D-Bus service page](../../system-housekeeping/references/dbus-service-never-takes-its-name.md).

## Retirement

The build is retired when Debian's package carries the commit: a Debian revision with the patch, or a new upstream release that contains it (check with step 1's commands).
Ours stays the candidate while the repository ships it, because the pin file that blocks Debian's builds is generated from the repository's index (the skill's "Only our builds are candidates"); retiring it means leaving it out of the next round, so the generated block list drops the names and Debian's build is the candidate again.

## Traps

1. **Symptom:** `build.sh` says `the build failed (exit 1)`, and `build.log` ends right after `extracting unsigned source package (NAME_VERSION+stereo3d1.dsc)` with `Existing execute_before_dh_auto_configure: preserve and integrate its behavior explicitly`.
   **Cause:** `lean.debian_prepare` adds three targets of its own (`execute_before_dh_auto_configure`, `execute_before_dh_auto_clean`, `override_dh_builddeb`, the `TARGETS` of `sparky-os/lean/debian_prepare.py`) and refuses a `debian/rules` that already has one, with or without `-arch`/`-indep`. Debian's glib2.0 has `execute_before_dh_auto_configure: cross-tools` (it writes the wrappers for gi-compile-repository and the other introspection tools used when cross-building).
   **How found:** the build log, then `grep -nE '^(execute_before_dh_auto_configure|execute_before_dh_auto_clean|override_dh_builddeb)(-arch|-indep)?\s*:' debian/rules`.
   **Fix (ORDER 768b):** the toolkit keeps the hook. When the rules file defines `execute_before_dh_auto_configure` or `execute_before_dh_auto_clean`, Debian's rule stays as it is and the toolkit's commands go into a target of their own (`sparky-lean-source-project`, `sparky-lean-source-restore`) appended as `HOOK: .WAIT TARGET`.
   GNU make merges the prerequisites of all the rules of one target in file order and runs them before its one recipe, and `.WAIT` (GNU make 4.4) keeps that order under `make -j`, so the toolkit runs after the hook's own prerequisites and before its recipe. Measured with make 4.4.1: without `.WAIT`, `make -j4` ran the appended prerequisite first.
   dh runs a plain hook target for every package and then never its `-arch` or `-indep` form (`Debian::Debhelper::SequencerUtil`, `run_hook_target`), so the toolkit joins the plain hook only when the rules define it, and otherwise both forms. An existing `override_dh_builddeb` is still refused, now as `debian/rules:LINE: Existing override_dh_builddeb: ...`.
   In GLib's real build the log shows `mkdir -p debian/cross-tools` and the wrappers first, then `Build-input Lean Code: 761/1493 files projected`, then the `%:` rule's `dh execute_before_dh_auto_configure`, which Debian's own build runs too because its rule has no recipe.
   `repo/plain-from-lc.py` reads the kept form too (ORDER 768b): it takes what precedes the step's header line (`# Distribution-only processing; ...`) as the plain rules file and accepts the tail only when it is exactly what `lean.debian_prepare`'s own `lean_rules` writes for that file, so the two tools cannot drift apart. Before that it stopped on GLib's `+lc1` source with `the rules file does not end with the lc1 targets`. Its test is `tests/reproducible-sources/plain-kept-hook.sh` (a kept configure hook, a kept clean hook, one with a preserve plan, a source with neither; red on the older `plain-from-lc.py`).
2. **Symptom:** `diff -rq` of Debian's `debian/` and ours shows `Only in Debian's: debian/tests/manual/.gitignore`. **Cause:** `dpkg-source -b` of a 3.0 (quilt) source leaves out files that match its default ignore list. **Fix:** none needed: no binary package carries it; say it in the comparison. **How found:** comparing the two `debian.tar.xz` files after the first source build.
3. **GLib's introspection, measured:** `lang_c.py` leaves a whole C file authored when it holds a `/**` or `/*!` comment longer than four characters, so every gtk-doc block that g-ir-scanner reads (annotations such as `(transfer full)`) reaches it unchanged, and every typelib came out byte-identical to Debian's.
   **Symptom:** `GLib-2.0.gir` and `Gio-2.0.gir` still differ from Debian's, in 1,092 and 328 lines, every one a `<source-position filename=... line=N/>`; and 530 pages of libglib2.0-doc differ only in their `[src]` links' `#LN` anchors. **Cause:** g-ir-scanner records each symbol's line in its header, and headers with only plain comments (32 of them, `gio/gaction.h`, `glib/gdate.h` among them) were projected before it read them, so the lines are the lean ones and the documentation's source links point a few lines off in upstream's file. **Fix (ORDER 768b, decided: keep them as written):** the recipe passes `--preserve-source HEADER REASON` to `lean.debian_prepare` for exactly those 32 headers (the source-consumer plan, [native source consumers](../../lean-code/references/native-source-consumers.md)), each with its reason, and stops if the list changes size or a header is missing. Which ones (trap 13): the scanner reads 297 headers of the tree, the projection changes 95, and in 32 it moves a line the scanner records; in the other 63 the kept notices and the place of the removed comments leave every recorded line where it was. With them kept the build-input projection goes from 761 to 729 files, both GIR files and every page of libglib2.0-doc are the same bytes as Debian's, and the comparison has no open point left. **How found:** comparing every `.gir` and `.typelib` file with Debian's, then a diff of the two GIR files, whose `filename=` values named the 32.
4. **Symptom:** an empty folder appears on the host where a keyring file was expected. **Cause:** `docker run -v HOSTPATH:...` creates a missing host path as a folder, as root. **Fix:** `ls -la` every mounted host file before the first run.
5. **Symptom:** the build stops at the toolchain record with no message. **Cause:** `dpkg-query -W NAME` exits 1 for a name that is not installed, and the script runs under `set -e`. **Fix:** record only names the Build-Depends install.
6. **Symptom:** a diff for another project carries times like `-0300`. **Cause:** `diff -Nru` writes local times with the zone. **Fix:** `touch -d '... UTC'` the new files and run `TZ=UTC diff -Nru`.
7. **Symptom:** after `dpkg-buildpackage`, the build log ends with `dpkg-source: info: unapplying ...` for every patch, and a test target run afterwards (`debian/rules override_dh_auto_test-arch`) would recompile. **Cause:** a tree extracted with `dpkg-source --skip-patches -x` has its patches applied by `dpkg-source --before-build` and unapplied again by `--after-build`, so the tests would run on sources that were not built. **Fix:** `QUILT_PATCHES=debian/patches quilt push -a` before `dpkg-buildpackage` (exit 2 means nothing left to apply); then `--after-build` leaves them, and a tree already built gets the same push before its tests. **How found:** the last lines of the first build log, then `ls .pc` (gone).
8. **Symptom:** the build fails in `override_dh_builddeb` after `Payload Lean Code: libglib2.0-udeb ...`, with `archive case-...-solve failed` and `libglib2.0-udeb : Depends: libc6-udeb (>= 2.43) but it is not installable` (also libffi8-udeb, libpcre2-8-0-udeb, zlib1g-udeb). **Cause:** the link and start gate solves each package against the deb archives, where no udeb lives. **Fix:** `DEB_BUILD_PROFILES=noudeb` (Debian's own profile for the package), as the gtk4 recipe has done since its first build. **How found:** the gate's case log; the other 32 cases had solved.
9. **Symptom:** `build-i386.sh` ends after a successful build with `PACKAGE-lc-hr_..._i386.deb: /usr/share differs between amd64 and i386: ['dpkg-stereo/hr/PACKAGE/amd64/HASH.xz', ...]`, then, with that folder named alike, with `glibconfig.h`'s authored copy, then with `gdb/auto-load/usr/lib/TRIPLET/...-gdb.py`. **Cause:** librsvg's twin check, copied, compares `/usr/share` path by path, but each architecture ships paths of its own: an `-lc-hr` companion's `/usr/share/dpkg-stereo/hr/PACKAGE/ARCH/` (GLib's `glibconfig.h` under `/usr/lib/TRIPLET` differs by architecture, so its authored copy does too) and Debian's own gdb scripts under the triplet. **Fix:** check what dpkg requires of a `Multi-Arch: same` package installed beside its twin: every path both architectures ship is the same bytes, over the whole package, and only for `Multi-Arch: same` packages (a `foreign` one such as libgio-2.0-dev-bin is never installed twice and rightly differs). GLib: 15 such packages, 356 shared files, all identical. **How found:** each message named the path; three forms of the check failed before this one, each on a different path.
10. **The toolkit's own test suite in a container:** `python3 -m unittest discover -s lean/tests` errors on six modules without `python3-pytest` and on `test_standalone`'s relative import; `python3 -m pytest lean/tests` runs them all. The link gate's tests need bubblewrap with the build containers' `--security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined` (else `bwrap: No permissions to create a new namespace`), and `test_appstream_off_publishes_what_main_published` needs the git history (`git show COMMIT:...`), so run it in a clone, not an export. On the toolkit at the time: 540 passed, 60 skipped.
11. **No regression from a toolkit change, measured on published sources:** unpack the round's `.dsc`, make it plain with `repo/plain-from-lc.py`, then run the step three ways: today's code with today's toolkit, the new code with today's toolkit (`PYTHONPATH=NEW python3 -m lean.debian_prepare TREE VERSION --toolkit TODAY`: only the logic differs, the trees must be identical), and the new code with its own toolkit (only the copied changed file may differ). Done for librsvg and kscreenlocker: identical, and both rules files equal the published ones.
12. **The round trip `plain-from-lc.py` then the step, on a published source:** to give back the published `+lc1` source byte for byte, run the step that made it (the source's own `debian/sparky-lean-toolkit`, rebuilt as a toolkit folder: `lean/`, `repo/provenance.sh`, `packages/dpkg-stereo/LICENSE`) for the version and the date of its own `+lc1` entry (`dpkg-parsechangelog -S Version`, `-S Timestamp`), with `--save-plan`/`--preserve-plan` when it has a preserve plan. **Symptom:** the only difference is the `+lc1` entry's trailer line, dated today. **Cause:** a step older than ORDER 421b dated its entry with `dch` by the clock, not by `SOURCE_DATE_EPOCH` (librsvg's and kscreenlocker's published steps mention no `SOURCE_DATE_EPOCH`). **Fix:** run such a step under `env TZ=UTC faketime -f "@YYYY-MM-DD HH:MM:SS"` at the entry's own time. GLib, librsvg and kscreenlocker then come back byte for byte.
13. **Which headers g-ir-scanner reads:** configure the package as Debian does (`debian/rules override_dh_auto_configure` after `apt-get build-dep`) and read the `COMMAND = ` lines of `debian/build/FLAVOUR/build.ninja` that call `g-ir-scanner`. **Symptom:** the command lines hold no `.h` argument at all. **Cause:** meson hands the scanner its sources as `--filelist=FILE`, one path a line. **Fix:** read each file list; then run the source's own projection (`python3 -m lean.source_tree project TREE`) and take the headers whose record in `.sparky-lc/source.json` says `projected`. GLib 2.90.1: 297 headers read, 95 projected.
14. **Symptom:** `ulimit: error setting limit (Operation not permitted)` from a script inside a container started with `--ulimit core=1`. **Cause:** a shell's `ulimit -c` counts in blocks (512 bytes in dash, 1024 in bash), so `ulimit -c 1` asks for more than the container's hard limit of 1 byte; outside a container it sets 512 or 1024 bytes, which a piped `core_pattern` does not take as "no dump". **Fix:** the limit belongs on the launcher only; a script that must not run without it reads it from `/proc/self/limits` and stops with the reason (the reproducer's `run.sh` does). In a systemd rig booted in a container, units get `DefaultLimitCORE=1:1` from `system.conf.d`, but PID 1 itself showed `unlimited` while the rig had `CAP_SYS_RESOURCE`: systemd raises its own limit, so a crash of systemd itself would reach the host's crash list. **How found:** the message in the program-start run, then `grep 'Max core' /proc/self/limits /proc/1/limits` in the rig.
