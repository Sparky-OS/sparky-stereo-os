# A program fetched on the person's machine and kept current by a reviewed hash

For a program the edition may not redistribute (no licence grants it) but may install: our package holds only the installer and the integration, the vendor's file is fetched from the vendor's own address when the package is set up, checked against a size and SHA-256 that a person reviewed, and replaced only after the new copy passed every check.
First built for CNJ's PJeOffice Pro (ORDER 18, milestone 2: `sparky-os/packages/sparky-pjeoffice`, with `sparky-pjeoffice-codec`); the program's own facts are in [brazil-certificates](../../brazil-certificates/references/pjeoffice-installed.md).

What the older references already cover, so this page does not repeat it: the declaration of an install-time download and its two readers, consent, refusal and retry ([licensed data at install time](licensed-data-at-install.md)); an app center row that brings tools and the review rule for `Depends` ([an app center entry that needs tools](app-center-entry-tools.md), whose appimage kind is the nearest relative); the Lean Code build of a conventional debhelper source ([the camera page's recipe](../SKILL.md)).
What was missing, and is here: the install transaction, the watcher, the first package entry of a main page, and a private library package.

## The recipe

1. **A reviewed catalogue is the one source** (`catalogue/catalogue.json`): `current`, and for each version its address (https), size, SHA-256, the archive's top folder, the bundled Java the version was reviewed with and the review date.
   The control file declares the same download (`XB-Sparky-Install-Download-Size`, `XB-Sparky-Install-Download-Source` in the source stanza; `tests/catalogue-matches-control.py` fails when the two disagree, on the recipe and on the built `.deb`).
2. **The transaction** (`sparky-pjeoffice install`, run by the package's `postinst configure` and by the problems engine's Repair): lock; space check (the ZIP plus a margin in the cache, 1 GiB for the program); fetch with `curl --proto =https --continue-at -` into `NAME.zip.part` (a partial file is resumed; one larger than the catalogue's size is dropped); verify the size and SHA-256 (a mismatch deletes the file); unpack the top folder into `versions/.VERSION.new` with safe names and explicit modes (CNJ's ZIP carries none); write `SHA256SUMS.cnj` of every file as shipped, then the one change our installer makes; qualify (the files are there, the jar passes `testzip`, the bundled Java runs as the reviewed version); rename into `versions/VERSION` (a folder that was there is set aside and restored on any later failure); make the derived data (here the certificate list and the FFmpeg link); only then rename a new symbolic link over `current`; keep the previous version, prune the rest.
3. **Every failure is told and kept** by the one engine (`sparky-stereo-problems keep --machine --repair '["/usr/bin/sparky-pjeoffice","install"]'`), with its own sentence in the ten languages: download, refused file (what differed), prepare (naming the version still in use), no space (path, needed, free), certificate list, signing. The installer exits 10 when it failed and the version in use is still in use; 1 when nothing is installed.
3b. **`postinst` follows the exit status.** A first installation that fails stops dpkg (the engine kept why; `dpkg --configure PACKAGE` retries); an update that fails with 10 configures the package, says on stderr that the version in use is still in use, and leaves the problem kept. This is a choice made without a recorded design: it keeps apt usable offline and the program working, and it is told twice.
4. **Rollback and removal:** `rollback` switches to the previous version; `remove` (the package's `prerm remove`) deletes the program, its derived data and its cache and touches nothing of the person's (`~/.pjeoffice-pro`, `~/.config`, `~/.local/state`); the purge removes the state and cache folders and the conffiles.
5. **The watcher** (`watcher/watch.py`, not installed, not scheduled): reads the vendor's page for the Linux link, fetches the file twice into two new folders, and compares them with each other and with `Content-Length` (and, as a fact only, with a digest the server keeps in its object metadata). Exit 0: the reviewed file, unchanged. Exit 3: a new version, alike twice, with a proposal (the catalogue with the new entry marked NOT REVIEWED, and the facts a reviewer reads: bundled Java, updater settings, launcher flags). Exit 2: any disagreement, nothing proposed. Exit 1: anything else, said. A person edits the catalogue; the watcher never approves.
6. **The tests use the real format.** A generated stand-in for the vendor's ZIP (`tests/make-fixture.py`: the same layout, a real Java to write its store) served by a small HTTPS server with byte ranges (`tests/serve.py`, a generated authority trusted by the container) tests the transaction without any file of the vendor's: wrong digest, a cut connection and its resume, an update, a version whose Java fails, a failed switch (an injected `os.replace` error), a changed system certificate list, removal.
   Then the same package against the real file once. The red controls are scripted (`tests/mutations.sh`): each rule broken in a copy must make its test fail.
7. **The app center entry** is a `kind: apt` row of a main page (`section: main`, `sizes: true`, `problem_key: install`, `author`, `note`) that installs the package; its tools are the package's Recommends (the app center package depends on none of them: `tests/entry-tools.py`). The card says before the button the download's size and address always (`entry_notes`, the shared reader's own sentences), apt's sizes for the package and what it brings, then the shared metered notice when the setting asks; a failed setup shows the engine's sentence after apt's exit status (`kept_problem`). The same entry for SparkyLinux's main app center is Paweł's own scripts in his form (`aptus-app`, `aptus-package-install`, `-reinstall`, `-remove`, both trees), on a separate branch, prepared and not sent.
8. **Private libraries** the program needs and the system no longer has (FFmpeg's ABI 59 for JavaFX) are a package of their own in a private folder, with `$ORIGIN` as run path, `dh_makeshlibs -n` and `dh_shlibdeps -l` (so no library is registered or replaced), and only the launcher puts the folder on `LD_LIBRARY_PATH`, for the program's process.
   The recipe fetches the signed release, checks the pinned SHA-256 and the release key, and builds with `lean.debian_prepare --preserve-source '*' REASON` (the upstream source keeps its own bytes).

## Building and proving it with Lean Code

- Container: Debian testing with the edition's published tree as an apt source (a pin at 1001), `devscripts` (`dch`), the KF6 and Qt 6 development packages, `sparky-stereo-problems`; the build runs the recipe's `build-in-container.sh` with the link gate's archive folder (`sources.json` and dearmoured keyrings of Debian, deb-multimedia and the edition's tree as `file:///repo`).
- The link gate needs a sibling built together: build the library package first, list its `.deb` in a file inside the output folder (mounted at the same path) and pass `SPARKY_LC_SIBLINGS_FILE`; without it apt cannot resolve the main package's `Depends` on the library and the gate stops there.
- The app center package needs two passes (the first says `build record NOT complete, unrecorded: buildinfo`); its two builds were byte for byte equal.
- Proof order that found the most: install from a flat repository with the edition's `Origin` by apt (the real `Inst` lines), the install-time declaration through apt's own hook, then every failure through the entry's action, then the integration in a Plasma login.

## Traps

- **Symptom:** the first `declaring()` of an entry page runs for minutes. **Cause:** the shared reader's `declaring()` reads the record of every package (171,767 in a container with Debian, deb-multimedia and the edition: 365 s), and the page asked twice. **Fix:** a single entry's page marks its packages in apt's dependency cache in memory and reads only their records (`entry_downloads`); the whole pass stays for the start page's many entries. **Found by:** the first page render still running after nine minutes.
- **Symptom:** a fixture catalogue put in place before `apt-get install` is overwritten by the package's own. **Fix:** `path-exclude=/usr/share/NAME/catalogue.json` in `/etc/dpkg/dpkg.cfg.d` (a test file in a container), and for an update `dpkg --unpack`, then the new catalogue, then `dpkg --configure`.
- **Symptom:** the entry's tools-note is empty for an `apt` row of a main page. **Cause:** `tools_note` skipped every `section: main` row (they were appimage rows that make their own plan). **Fix:** `with_main` for apt rows only; DisplayCAL's row must not change (its tests ran in 0.03 s before and after; a first version made them wait for NetworkManager).
- **Symptom:** a test image cannot install `ffmpeg` ("libavcodec63 Depends libaom3 (>= ...)"). **Fix:** deb-multimedia's source with the keyring from the edition's `carried/` ([the repository](repository.md)).
- **Symptom:** `dpkg-source: error: non-native package version does not contain a revision`. **Fix:** a `3.0 (quilt)` source needs `5.1.10-1`, and the orig tarball is upstream's file under the source package's name. **Symptom:** `dh_missing: error` for upstream's example sources: remove `usr/share` in `override_dh_auto_install`. **Symptom:** `make distclean` fails on a tree never configured: `override_dh_auto_clean` does nothing.
- **Symptom:** Python's `ssl` refuses a generated authority ("CA cert does not include key usage extension"). **Fix:** `-addext basicConstraints=critical,CA:TRUE -addext keyUsage=critical,keyCertSign,cRLSign` (Python 3.14); curl accepted the same file.
- **Symptom:** a lane's cleanup `rm -rf rig/*` is refused by the harness as a removal it cannot resolve. **Fix:** give every run a new scratch folder (`rig/NAME-$(date +%s)`) and remove a finished one by its literal path at hand-back.
