# edition-packaging: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Make a source package byte-reproducible from its recipe commit: take the recipe date from SOURCE_DATE_EPOCH, else the committer date of the last commit touching the recipe's own paths (clean tree only), else stop with the reason (no clock fallback). Write changelog dates in UTC (email.utils.format_datetime, TZ=UTC), export SOURCE_DATE_EPOCH (dpkg-source(1) 1.23.11: it clamps tar member mtimes), and normalize debian/ plus include-binaries files to mtime = recipe date and modes 0644/0755 before `dpkg-source -b`. Expect identical .dsc and .debian.tar.xz sha256 across three clocks, zones, umasks and checkout times. Test: build the same fixture under three zones/umasks, compare, plus a red self-check (a packer without normalization must differ): 12 ok (lane reproducible-sources-421)
- Audit pattern for "every driver wires X": a wiring test that is red when a host driver reaches the gate with none of the init, the helper, the opt-out or the shared build script. Red on main: 12 FAIL lines; green on the branch: 28 wired build scripts checked, 85 files audited, ALL PASS. Red unit run was `Ran 8 tests, FAILED (failures=4, errors=1)`; green `Ran 18 tests OK` (lane provenance-stated-412)
- Per-round supply-chain step: make-sbom (SPDX), check against the tree, make-provenance per stage folder (in-toto style statements), check again, SHA256SUMS, then a sync script that is a dry run by default, owns only its own sbom/ROUND and sbom/latest folders, and refuses `--go` without a verifying signature. Tools image installs its Python packages with `--require-hashes`, hashes checked against the index's JSON digests. Proof on a 2,188-link forest: SPDX 1,374 packages 0 problems, 195 statements 0 problems; 10 green and 8 red test cases (invalid licence expression, missing relationship id, sha256 differs, unknown predicate field, builder.id missing, cohort file changed) (lane sbom-provenance-394 / sbom-round-394b)
- Retire a conffile-based block in a later package version with dpkg-maintscript-helper rm_conffile: prior-version = new version + "~", an unmodified file is removed, a modified copy becomes NAME.dpkg-bak and the maintainer script says so. Test three cases in a clean container: red (published old version as "new": 10 failing checks), green (unmodified: 23 PASS, block gone, plain http source converted to https with comment kept and backup), modified (edit kept byte for byte as .dpkg-bak, 23 PASS) (lane retire-http-block-413)
- Make every build that runs apt use https only: one helper script that installs ca-certificates and writes the block file, called by a Dockerfile wrapper (named build contexts host-ca) and by container scripts; one place to switch it off. A static check (`check.py`) lists findings by class; RED on the old tree 115 findings (dockerfile 30, plain-http 10, container-script 38, launcher 37), GREEN 0 after, with 7 explicit ALLOW entries carrying reasons (lane https-build-machinery-400b)
- Install simulation for a stage: fresh testing container, sources over https, prior publication plus the stage as local repositories with the edition's own pin files, then `apt-get -s install` of the meta packages (575 Inst for the APTus case); lean verification prints "lc1: verified N packages" and `python3 -m lean.release check-identity` checks all staged debs (26 identities) (lane round-prep-406)
- check-installable: apt verdict, static walk and dose-distcheck over profiles (base, nvidia, arm64); publish-tree step with SPARKY_INSTALLABLE=report|refuse|off and a known-list file. Live tree findings: a library that left the archive (kdenlive), a package removed from testing (flightgear-data, RC bug), a pin without architecture blocking Debian's arm64 packages, a pin lacking `:any` letting the vendor's i386 build win (lane installability-317)
- Publication copy proof set: a throwaway key signs the candidate copy (official key never touched), `check-repo` verifies N packages, tree diff by script (pool +66 -66, dists changed), proofs in fresh testing containers: red on live version, green on candidate, upgrade "0 upgraded ... 0 to remove" with the `Inst` lines read, `dpkg --audit` clean; station steps as a script with `--only-upgrade` and a red compile first. Match dpkg-query snapshots with `^ii +name` (lane publish-39-305)
- Container-only Lean gate with nested bubblewrap needs `systempaths=unconfined` besides SYS_ADMIN and the apparmor/seccomp options (lane one-handler-per-failure-368 / engine-run-unlisted-375)
- Developer ISO build: rootfs about 19 min, pack about 31 min (1,718 s), 5,117,478,912 bytes with 3,750 packages and no i386; keep `.keep` on the output until upload; check-iso includes a CVE check ("kernel carries the fix" found in the live kernel, initramfs, links, /boot, /usr/lib/modules and the DKMS builds, "no older kernel is left") with a red control on the previous ISO (4 FAIL lines); boot matrix: UEFI Secure Boot off, Secure Boot on without key (menus lead to MokManager), BIOS, 32-bit UEFI (KASLR on, no failed units, KWin up) (lane dev-iso-297)
- In-build link gate for a recipe that depends on an edition package not yet published: put the dependency in a flat local archive signed by a throwaway key (sources.json `file:/archive/lane`, suite `./`, empty components), point SPARKY_LC_ARCHIVE_DIR at it and pass EXTRA to the build script. Worked for dkms +sparky3 with the problems engine. (lane dkms-unsigned-370)
- Switching between the main (615) and legacy (580) NVIDIA stacks: simulate first, remove only the previous stack's leftovers by exact list and say it (never a general autoremove); legacy to main failed in Hardware Setup 0.1.22 because the 580 lock pins the open module at -1. Leftover orphans seen: firmware-nvidia-gsp 615 after main to legacy, libnvidia-egl-wayland1 after legacy to main. (lane nvidia-stacks-gate-390)
- Carry NVIDIA's own Debian 12 packages for older cards (Maxwell, Pascal, Volta) as the 580 stack: verify the repository Release with gpgv at build time (key 3BF863CC unchanged, cuda-keyring 1.1-1), carry NVIDIA's files byte for byte and the edition's files through Lean Code, add a libc6 Depends only where NVIDIA declares none, install the i386 libraries on both paths when dpkg has i386, and make the 580 path install the CUDA repository package (needed for the EGL platform libraries with their epoch). Debian's newest NVIDIA is 550.163.01 (555.58.02 in experimental) and NVIDIA's Debian 13 repository starts at 590.44.01, so the carry is needed. (lane nvidia-legacy-354)
- Publish a DEP-11 (AppStream) catalogue with the repository on every publication: run the generator in a pinned Debian testing container (no network, 4 CPUs, archives mounted read-only, as the invoking user), publish `Components-<arch>.yml(.gz)` and the icon tarballs as both `.tar` and `.tar.gz` (Debian's Release lists both), check the image before the gates (they can take hours), stop before signing if the generator or an archive is missing, and give an explicit `SPARKY_APPSTREAM=0` to publish without. Result: 56 amd64 components (44 from metainfo, 12 from a .desktop file alone), 9 i386, 7 arm64. (lane repo-dep11-252b)
- Frozen publisher and symlink-forest copy for lane runs: run the publisher from a `git archive` export (bash reads a script as it runs, so an edit mid-run changes what runs); make the SRC and DEST pools as `cp -rs` forests and copy `dists/` and the two top files with `cp -a` (links there would write into the base); 0.8 GB per copy, every base file keeps its ctime, a run with no new package skips the link gate and takes about 10 minutes. (lane repo-dep11-252b)
- Wheel-driver DKMS recipes must not cap update-time builds: use `${parallel_jobs+-j$parallel_jobs}` in dkms.conf for a quoted `'make'` (dkms(8) appends `-j$parallel_jobs` only to unquoted make; dkms 3.4.4 sets it to nproc); never a fixed -jN. Upstream forms: fanatecff has no MAKE line, lg4ff `make KVERSION=$kernelver`, tmff2 a quoted `'make' KDIR=...` (runs on one job alone). (lane forbid-zram-update-speed-361)
- Local FDK-AAC FFmpeg rebuild helper contract: failed plans, cleanup, query and dispatch stay visible failures through the shared problems engine; a detached `setsid --fork` acknowledges its fork while `Popen` can show exec success before the launcher returns; "no new version" and "the check failed" are never the same answer; legacy evidence is removed only after the engine has accepted the record, and an old cleanup record without a baseline is never guessed. Unsafe removal keeps the build tools and names the extra packages. (lane fdk-zfs-no-fallbacks-346d)
- Carrying held upstream fixes into the edition's FFmpeg (deb-multimedia source): one patch per fork commit with a DEP-3 header (Origin, Forwarded: no held, Author), patches 0055 to 0066, same package set, Depends, file lists and exports as before. Proof is red on the previous source plus the test patches and no fix patch (a full package build, e.g. +stereo3d9~red377), green on the new one, at THREADS=1 and 4, amd64 and i386 from one .dsc; full FATE lists the same 21 common failures in red and green (0 failing only in green); lean link gate on both arches; upgrade from the published version removes nothing. Example red results: mv-vps-max-layer-id.hevc `-map 0:view:all` 5 frames with "Dependent layer not included in layer ID?" against 10; eos-cra.vvc red 1 picture "Duplicate POC in a sequence: 32" with exit 0, green 2. (lane ffmpeg-six-fixes-377)
- Adding a language to an edition package: `lang/*/en` is the canonical key list; new files keep keys byte identical and in order, check with `diff <(grep -o '^LOCAL[0-9]*' en) <(grep -o '^LOCAL[0-9]*' <lang>)`, `bash -n`, placeholders (`%s` count), multi line strings, and for .po `msgfmt --check --statistics`. Packages install languages by glob (`lang/*`) or `ki18n_install(po)` so no build file needs a language list. Nine languages: en de fr ja ko pl pt_BR zh_CN zh_TW. (lane i18n-gaps-279)
- Metadata language audit: scan `.desktop`, KDE plugin `.json`, `.actions`, `.notifyrc` and AppStream metainfo for the nine languages, and also generate the Dolphin menus (gen.py, make-pack.py) and audit the generated `.desktop`; fix the generator, not the output. Result 0 missing. (lane i18n-audit-290)
- Second model review of new strings: make packets with the changed messages diffed against base (107 messages), ask one model per language group (CJK, European), then judge each point and write accepted and rejected with the reason. Accepted types: one idea one name across English and all languages ("colour depth" not "colour resolution"), Korean particles written attached, ja 許可 to 対応. - Install time download declaration: binary control fields `Sparky-Install-Download-Size` and `Sparky-Install-Download-Source` (the "Sparky-" prefix per deb-src-control(5); Debian's Size, Installed-Size, Extra-Size and AppStream artifacts do not name an install time download), read by apt through `AptCli::Hooks::Install` in an apt.conf.d file with notice at install.statistics, metered check through NetworkManager's Metered property over busctl, setting Announce metered|always|never, a hook failure never stops an install. ## Traps: the symptom, the cause, the fix, how it was found

- Symptom: two builds of one source differ in every .dsc and .debian.tar.xz (diffoscope: tar member mtimes, modes, changelog trailer). Cause: four inputs reach the bytes: the clock (formatdate(localtime=True), `dch` default date), the time zone, the checkout time and umask (dpkg-source packs debian/ with the tree's mtimes and modes), and debian/source/include-binaries files with their own mtime and mode. Not causes: member order, owners, xz, work directory name. Fix: see the recipe row. Found by: run the same commit under two clocks/zones/umasks and diffoscope the .dsc and .debian.tar.xz (lane reproducible-sources-421)
- Symptom: dpkg-source warns when a native 3.0 source has a version with a revision (2024.1.5-1); it accepts it with the warning, exit 0. Cause: native format forbids a revision in policy but not in the tool. Fix: relax the adapter's version check instead of renaming the package version. Found by: measured with dpkg-source -b (lane installer-source-407)
- Symptom: the build record of a source that makes several binary packages exists twice, and the one named after a binary says `buildinfo` unrecorded although `SOURCE_VERSION_ARCH.buildinfo` sits beside it (sparky-stereo-skills and sparky-stereo-skills-engine, 2026-11-06). Cause: the record groups .deb files by their own `Source:` field (`Source: name (source version)` when the binary version differs, else `Package:`), and finds the .buildinfo, .changes and .dsc by that source name, because dpkg names them after the source (dpkg-genbuildinfo: SOURCE_BINARYVERSION_ARCH.buildinfo; a binNMU's files carry the binary version, the .dsc the source version). A recipe that writes DEBIAN/control by hand and leaves out `Source:` makes the binary its own source. dpkg-gencontrol adds the field whenever the names differ (Policy 5.6.1), so a hand-written control must too. Fix: write `Source:` in the control (build-engine.sh); the gate also places a binary without the field by the .buildinfo or .changes beside it that lists the very file by SHA-256, says so in the log (`has no Source field; ... lists it as built from ...`), and with no such file keeps the package's own name and the unrecorded `buildinfo`. make-provenance.py and supply_chain.py read the same field from the pool, so there only the control fix helps. Found by: `dpkg-deb -f engine.deb Source` printed nothing while the lc-hr companion (written by lean.package) had it; rerun on a copy of the stage with `PYTHONPATH=sparky-os python3 -m lean.release check-debs *.deb` (host facts as SPARKY_BUILD_INVOCATION and SPARKY_BUILD_STARTED) shows the record files in seconds. (lane buildrecord-source-439)
- Symptom: a Lean Code build record is written with all four host facts (recipe commit, builder image, invocation id, start time) listed as unrecorded and `lc1: build record NOT complete` on stdout, exit 0. Cause: the recipe never called the provenance init, so no SPARKY_BUILD_* variables reach the container; many recipes redirect container output to a log, so nobody sees the line. Same silence when the init ran but `"${SPARKY_PROV_ARGS[@]}"` is missing from the docker run, for Python drivers (they cannot source the shell file) and for containers started by hand. Fix: the record step stops (`lc1: release blocked`) unless the init ran or `SPARKY_PROVENANCE_OPTOUT="<reason>"` is set; the opt-out is recorded with its reason, an empty reason or an opt-out beside the init also stops; Python drivers call release/provenance_args.py. Found by: reading a staged record (all four facts unrecorded) and grepping the 12 host drivers that reach check-debs without the init (lane provenance-stated-412)
- Symptom: `trivy sbom` vulnerability scan does not run: "Unsupported os family none". Cause: the SBOM names no operating system. Fix (proposed): an OPERATING_SYSTEM package in the document, a design call because Debian's tracker data applies to Debian's versions. Found by: running Trivy on the generated SBOM. Licence scan still works: 1,276 findings (UNKNOWN 1,141, HIGH 135) on 1,374 artifacts, 1,173 with a licence (lane sbom-provenance-394)
- Symptom: Scorecard on a large fork fails on the Contributors check (GitHub 403 for huge histories). Cause: API refuses the contributor listing. Fix: run with `--checks` that omits Contributors. Also: `ghcr.io/ossf/scorecard` works as registry (gcr.io needs billing); pass the token only inside the command (`GITHUB_AUTH_TOKEN="$(gh auth token)"`), never print it. Measured 104 repositories scored 1.1 to 6.1, median 3.0 (lane openssf-practices-393)
- Symptom: a retirement test fails only in the green case with a name that cannot be resolved. Cause: the test container could not resolve the repository host (a LAN host). Fix: `--add-host` for that host in the test runner. Also: a container started with a helper that writes the same conffile name needs that file removed first, else the package's file is not the one tested. Found by: the first run's single failing check (lane retire-http-block-413)
- Symptom: bare `docker build` of an edition Dockerfile now stops with `failed to resolve source metadata for docker.io/library/host-ca`; a built image without mounts: `apt-get update` exit 100. Cause: the Dockerfile expects the named contexts the wrapper supplies. Fix: build through the wrapper (tools/https-only-build.sh style). Found by: the acceptance rerun of the bare build (lane https-build-machinery-400b)
- Symptom: a build "succeeds" (exit 0, one package built) while the image's package lists were stale or a source was unreachable; or a test image builds with `sparky-remsu` missing and only fails far away. Cause: `apt-get update` exits 0 when a source cannot be reached (only `W: Failed to fetch ... ignored, or old ones used instead`); `|| true` was not even the main hider. Fix: `apt-get update --error-on=any` (apt 3.3.5), print the tail of apt's log and say what to do, exit 1; the old tolerant behaviour stays as an explicit `APT_UPDATE=no` that is said (other values exit 2); drop `|| true` on required installs. Found by: red/green with a tiny .dsc and an image whose extra source is `https://127.0.0.1:9` (connection refused): old script exit 0, new script apt's E: lines and exit 1 (lane hidden-apt-failures-400c)
- Symptom: after a stopped build the output folder is root-owned. Cause: the chown-back ran only on success. Fix: a trap chowns the output and build folders on every exit. Found by: the lane's own first red run (lane hidden-apt-failures-400c)
- Symptom: `FROM debian:testing@sha256:...` fails (BuildKit HEAD 400) or a tag pulls an i386 image. Cause: pinning by digest through the proxy failed; the local debian:testing/forky/sid tags can be i386. Fix: tag the amd64 digest locally and use that tag. Found by: `docker image inspect` architecture (lane hidden-apt-failures-400c)
- Symptom: a rebuild of the same package version gives different catalogues or a different block list than the published one. Cause: (a) the stage had been built with an older problems-catalogue engine than the published one, so the 21 language catalogues differ (a new entry, 63 entries); (b) the only-ours block list generated with KEEP_ONLY_OURS from a snapshot drifts from the live tree (four dbgsym names appeared after the earlier build). Fix: regenerate the block list from the merged index of the live tree plus the cohort; build catalogues with the published engine binary. Found by: diffing the staged .deb contents against the prior stage and the live index (lane round-prep-406)
- Symptom: a throwaway publication copy's installability report lists superseded versions (1458 packages checked against 1355 in the published tree) and "0 removed". Cause: the copy's pool is symlinks, publish-tree removes superseded files with `find -type f`, and dpkg-scanpackages follows symlinks. Fix: trust the gate results, not the copy's indexes; use a real `cp -a` pool for faithful indexes (lane nvidia-dkms-link-gate-329)
- Symptom: dh_shlibdeps sends a static-pie program to dpkg-shlibdeps. Cause: its "statically linked" filter misses "static-pie linked". Fix: Debian's qemu works around it with `-Nqemu-user`. Found by: gate failure on qemu (lane lean-linkcheck-foreign-elf-340)
- Symptom: the edition's linux-libc-dev and Debian's cross toolchains exclude each other (the workstation kept 7.2.11-1). Cause: Debian's linux source builds 30 linux-libc-dev-ARCH-cross packages that Depend on linux-libc-dev (= ${binary:Version}); without ours the headers conflict. Fix: ship the -cross twins from the kernel source (a helper package until then). Do not propose "linux-libc-dev Provides the -cross names": Debian withdrew it (#1065416). Debian's cross gcc searches /usr/GNU-TYPE/include, then /usr/include/MULTIARCH, then /usr/include (lane libc-dev-cross-256)
- Symptom: a translated catalogue patch drops lines silently. Cause: a `.po.patch` hunk header with a wrong `+1,N` count on a new file; patch(1) accepts it. Fix: validate hunk counts (run `patch --dry-run` and count declared against held lines) and run translations-shipped.py on the stage before signing. Published +lc1 sources come in four shapes for plain-from-lc.py (none, --no-build-depends, --edition-entry, --lc-successor) (lane catalogue-rebuilds-391)
- Symptom: `apt-get install libplacebo360:amd64 libplacebo360:i386`, `ffmpeg libavfilter12:i386` and `mpv wine32 gstreamer1.0-libav:i386` exit 100. Cause: the 32-bit and 64-bit twins of an edition build must come from one source (shared files differ); consumers include our i386 FFmpeg, Wine's libwine, deb-multimedia's gstreamer1.0-libav:i386. Fix: publish the i386 twin from the same .dsc as amd64. Found by: simulated installs in the checker's own universe with Recommends on, using signed indexes; publish-tree's own link gate skips i386 on an amd64 host, so the i386 gate runs by hand (lane libplacebo-i386-split-333)
- Symptom: amd64 and i386 OpenCL ICDs cannot be installed together. Cause: Debian's libclang-cpp21 has no Multi-Arch field (Policy 5.6.34.1, Multi-Arch: no). Fix: report to Debian's LLVM packaging or accept with a `--known` entry before refuse mode (lane libplacebo-i386-split-333)
- Symptom: nothing that includes <QtCore>, <QtDBus>, <QtGui> or <QtWidgets> compiles against the published qt6-base-dev. Cause: a QtCore module header includes five headers that no package ships (qconfig-bootstrapped.h and four JNI headers), because the Qt syncqt runs unordered. Fix: reorder the runs and test every module header (header test: red on the broken build 0 of 13, green 13 of 13; 2,741 headers resolve apart from 9 known). A Qt -dev publication needs a compile test of the module headers. Found by: configure of KWin and plasma-workspace failing on QtCore/QtDBus/QtConcurrent units (lane publish-qt14-309)
- Symptom: a package builds with 0 translations and exits 0. Cause: the grub-l10n build script needs gettext; the test image lacked it. Fix: build in the tools image that has gettext (43 languages). Also: neither kwin nor lean.standalone recipe reproduces its accepted bytes (build time stamped into the changelog, member times): .text and .data of libkwin and kwin_wayland identical, .rodata differs by a few hundred bytes, documentation PNGs differ by their tIME chunks (lane publish-39-305)
- Symptom: the publish-tree link gate blocks for any package that depends on sparky-stereo-apt or sparky-remsu. Cause: the archive public-sources configuration lacked SparkyLinux's repository (core and tiamat), which those packages need. Fix: add it to the gate's source list. Found by: the 286 copy blocking (lane publish-ed521-286)
- Symptom: a KCM package never builds (memory-kcm 0.1.1). Cause: `KDEI18nInstallMacros` does not exist. Fix: use the real KDE i18n install macro; published 0.1.0 had no translations at all. Also sparky-stereo-locales had no Korean lookup until fixed (lane publish-ed521-286)
- Symptom: a new conffile is installed over an unowned file even with `--force-confold`. Cause: dpkg installs a conffile that no package owned yet over an existing file. Fix: use `path-exclude` in the proof container, or ship a rename. Also: SparkyLinux's base-files 14.sparky9~0 ships /bin and /sbin as directories and breaks merged-/usr Debian when it wins at the sparky-apt 1001 pin; after `apt-get purge`, dpkg keeps an "un" record (lane publish-ed521-286)
- Symptom: a message generator in a command substitution fails but the build still reports success. Cause: `x=$(gen); next` hides the generator's exit code. Fix: propagate explicitly. Also: test both dpkg's nonzero result and its retryable state (a visible error alone does not mean the package failed); test `postrm purge` after a successful remove, because a direct purge can fail earlier in postrm remove and leave another state (lane installer-no-fallbacks-344)
- Symptom: manual Repair with an older hardware-setup version fails immediately with LOCAL6 / status 100 while another apt frontend holds the dpkg lock. Cause: no lock wait in the manual install path. Fix (0.1.22): `DPkg::Lock::Timeout=-1` on the manual install plus a terminal explanation of the wait through the shared engine; no lock deletion. Also: the launcher forced LC_ALL=C.UTF-8 before its early exec, suppressing translated messages: move the override after dispatch (detection stays in C). Do not require apt's progress line on a non-terminal pipe in tests (lane one-handler-per-failure-368)
- Symptom: a first-install failure is cleaned up as if the package had been removed, or an old failure record survives a real removal. Cause: removal cleanup was inferred from the current absence of the package. ## Perks of the part

- apt_preferences(5): "The first specific-form record matching an available package version determines the priority of the package version", so a per-package record (`Package: nvidia-detect`, `Pin: release o=Debian`, 1010) inside a source-wide pin works; a `src:` selector cannot exclude one binary. NVIDIA's CUDA repository publishes a documentation-only `nvidia-detect` with the same source name as Debian's real one. Pin files that sort first (`10...`) win. (lane nvidia-stacks-gate-390)
- The pt_BR/ko/ja reviews are quick to rerun: ACIG's GPT path answered "bootstrap pending" and ask_cloud returned empty, so a second model review went through a local model server; record the model per language group. (lane stereo-layer-i18n-221)
- The generated policy is the single ownership list: only-ours names reject any Debian replacement even if a pin raises it; other names use the configured signed archives; absent non-only-ours programs are hidden with no promise; only-ours failures keep a visible Repair. Keep the installed policy as the shared source for later front ends. (lane sparky-stereo-appcenter-104)
