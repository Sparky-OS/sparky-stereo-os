The rule says we carry them when they are worth it; this milestone carries none (see the hand-back for which, and why OpenLinkHub, a Go program that expects its own working folder, is the first).

## The table

`share/peripherals/*.ids` is made by `tools/make-peripheral-ids.py` from each tool's own device list, so every id has a source and a regeneration shows what changed: OpenRGB's `60-openrgb.rules` (1,173 devices, game controllers left out: Sony's DualSense is the controller flow's), Solaar's receiver table `base_usb.py` (22), libratbag's `*.device` files (147 gaming mice, with Piper), liquidctl's `71-liquidctl.rules` (99), g810-led (13), OpenRazer's `99-razer.rules` (267) and OpenLinkHub's own `99-openlinkhub.rules` (193 lines, 190 distinct ids, tag 0.9.4, commit a08204cf) read together with its `src/devices/devices.go`, whose registry names the folder that drives each id; the edition's `openlinkhub.ids` keeps 43 of them (below). `lib/detect.py` reads `lsusb` and emits `found`, `fact peripheral TOOL IDS`, `package` and `action` lines; the setup installs the packages without a question. ckb-next has no id list outside its compiled sources and is left out of the table.
A desktop board of a maker OpenRGB's detectors name gets `i2c-tools`, `i2c-dev` and the chipset's driver (`i2c-i801` Intel, `i2c-piix4` AMD), the steps of OpenRGB's own `SMBusAccess.md` (it ships in the openrgb package under /usr/share/doc/openrgb), because the board and memory lights sit on the SMBus and no USB id shows them.
OpenRGB starts with the session minimized (`/etc/xdg/autostart/sparky-stereo-openrgb.desktop` runs `openrgb-session`, which looks for the mark the setup writes and leaves a person's own autostart entry alone).

## The carried tool: OpenLinkHub (milestone 7)

OpenLinkHub was never packaged in Debian or SparkyLinux, so the edition carries it: `sparky-os/packages/openlinkhub`, built from the tag's source (go-release-packaging.md has the recipe). Detection installs it only for the families **hub, cooler, lighting-node and power-supply**, told by the **folder of its `src/devices` that drives each id** (the `deviceRegisterMap` in `devices.go`, its `X.Init` names the folder; a table in `tools/make-peripheral-ids.py` maps folders to families). Of 190 distinct ids in its rules: hub 7 (`lsh` iCUE LINK System Hub, `cc`, `ccxt`, `cduo`, `cpro`), cooler 22 (`platinum`, `hydro`, `elite`, `xc7`, `nautilusLcd`, `cone`), lighting-node 3 (`lncore`, `lnpro`), power-supply 11 (`psuhid`, `psudongle`); 140 are keyboards, mice, headsets, dongles, the LT100 and ST100 and the rest ("other": OpenRGB's); 7 are in the rules but in no folder's registry in 0.9.4 ("unlisted", not carried: 1b1c:0a45, 0a6a, 0c33, 0c39, 0c43, 0c4e, 2b3d). Daniel, 2026-11-17: "I agree with the corsair plan - the user can always change it inside openrgb". `share/peripherals/openlinkhub-families.tsv` lists every id with its folder, family and whether it is carried.

## One owner per device

OpenLinkHub and OpenRGB (or liquidctl) both open Corsair devices; the measured case is an iCUE LINK System Hub (1b1c:0c3f) on which a power supply read about 1,800 W. For the four carried families the owner is OpenLinkHub (37 ids that another tool of the table lists too: `owners.tsv`; milestone 6 had 99, the 62 that left are keyboards, mice, headsets, the LT100 and the ST100, which stay OpenRGB's). Three parts: the plan installs OpenLinkHub for the device and does not install the other tool for it; `62-sparky-stereo-peripheral-owner.rules` takes OpenRGB's `uaccess` tag away from the owned devices once OpenLinkHub is there (`TEST==` on its unit file in `/usr/lib/systemd/system` or `/etc/systemd/system`, or `/opt/OpenLinkHub`); `sparky-stereo-peripheral-owner` tells the person once per device through the problems engine. **A copy of OpenLinkHub the person installed with upstream's scripts is theirs** (the fact `openlinkhub-upstream`: `/opt/OpenLinkHub`, its unit in `/etc/systemd/system` or its rules in `/etc/udev/rules.d`): the plan does not install the package beside it (Daniel, 2026-11-07, "If manually installed leave it"), and the package's own `postinst` leaves that install alone (the container proof: install, upgrade, removal and purge of ours leave the upstream unit, its process, `/opt` and the rules byte for byte as they were). A shipped setting the person can change: an empty file of the same name in `/etc/udev/rules.d` gives the devices back to OpenRGB (udevadm control --reload-rules, then unplug and plug the device again).

## The proof with recorded devices (no device needed)

`tests/peripherals-owner.sh`: umockdev with a recorded USB device and its hidraw child (`tests/peripherals/hub.umockdev`), `umockdev-run -d FILE -- udevadm test --action=add SYSPATH`, and read `CURRENT_TAGS=` and the owner property. Red: with OpenLinkHub installed and only OpenRGB's rules the hub still carries `uaccess` (the clash); green: with the owner rule it does not; without OpenLinkHub it does; a device only OpenRGB drives keeps it, and so does a Corsair keyboard (`tests/peripherals/keyboard.umockdev`, 1b1c:1b11); the override file gives it back. `tests/peripherals.py` runs the plan on recorded `lsusb` listings through `sparky-stereo-hardware --auto --dry-run --fixture`.

## Traps

- **udev's `TAGS=` keeps a tag that `TAG-=` removed; `CURRENT_TAGS=` does not.** Symptom: the green case "still has uaccess". Cause: the first property is the history, and the `uaccess` builtin reads the current tags. Found by printing both from `udevadm test`.
- **Rules that name a device by `ATTRS{}` need the parent chain in the recording.** The hidraw node alone has no vendor: record the USB device and the hidraw under it (`P:` paths nested), or the rule never matches.
- **A tool's id list can include devices another flow owns.** OpenRGB's rules list Sony's DualSense; without an exclusion a gamepad would make the machine start OpenRGB and the existing controller test (`steam-devices`) gained `openrgb`. The generator names the vendors it leaves out in the file's header.
- **Existing fixtures with a peripheral change their expected plan.** Seven fixtures carry a Corsair K70 or a Razer keyboard; the old tests' package sets and "nothing else" action checks had to say so. A new action kind needs the old tests' filters updated in the same change.
- **`deb-systemd-helper`-style states are not the only "told once".** The telling keeps one mark per device in `/var/lib/sparky-stereo-hardware/owner-told` and forgets it when the device or the owner goes, so a later return is told again.
- **A tool's own rules list ids its own code does not drive.** OpenLinkHub 0.9.4's `99-openlinkhub.rules` has seven ids that no folder of `src/devices` registers (read `devices.go`, not the rules, to say what a device is); they are listed as unlisted and not carried.
- **An owner list is read from what the tool drives, not from the overlap with another list.** Milestone 6 gave OpenLinkHub every id both lists held (99), including 62 keyboards and mice the edition does not carry it for: OpenRGB lost access to a K95 for a program that was not installed for it. Narrow the list to the families carried and test one device outside it (the keyboard recording).
- **Detection must not plan a second copy beside the person's.** The upstream installer writes `/opt/OpenLinkHub` and a unit with the same file name as the package's; `/etc/systemd/system` wins over `/usr/lib/systemd/system`, so a second copy would be shadowed and the package's `postinst` would restart upstream's service. Both the plan and the maintainer scripts check.
- **A Razer device is in OpenRGB's list and in OpenRazer's.** Both are installed (Bazzite ships both); whether they fight over one Razer device is not measured here.
