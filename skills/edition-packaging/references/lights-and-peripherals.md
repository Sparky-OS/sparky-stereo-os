## The two carried in milestone 10: recipes, proofs and traps

### LACT 0.10.1 (`sparky-os/packages/lact`)

A Rust workspace (420 crates in `Cargo.lock`, 414 vendored, GTK 4 and libadwaita), MIT. The route is go-release-packaging.md's, for cargo: `make-orig.sh` pins the tag by the tarball SHA-256, the commit its `pax` header names and the git tree id, runs `cargo vendor --locked` (Cargo.toml and Cargo.lock hashed before and after) and writes `crate-licences.tsv` with `crates/legal files/sha256`; the vendor tree is a component tarball (`lact_V.orig-vendor.tar.xz`, 27 MB xz, 621 MB unpacked). `cargo-config.toml` is cargo's own source replacement, committed, with its `directory` rewritten to the build tree by `debian/rules`. `ORIG_CACHE` lets a rebuild reuse the archives (the xz of 621 MB takes minutes). Build: 4 min 24 s offline on 6 cores with Debian's rustc 1.98 (the repository's `rust-toolchain.toml` names rustup channel 1.97.0, which Debian's cargo does not read); upstream's tests run except `apply_settings`, which mounts a FUSE file system and is skipped by name.

- **Proof under systemd** (`tests/systemd-proof.sh`): upstream's own recorded cards (`tests/snapshots/amd/rx5500xt` of the source tarball) are read through `_LACT_DRM_SYSFS_PATH`, set by a drop-in (the proof's only deviation). The package installed by apt: enabled and active, `/run/lactd.sock`, `lact cli list` names `1002:7340 Radeon RX 5500` and `info` says `Driver Used: amdgpu`; the person's `/etc/lact/config.yaml` survives an upgrade byte for byte; a disable survives an upgrade; removal keeps `/etc/lact`, purge takes it; a copy made by upstream's makefile (`/usr/local/bin/lact`, `/usr/local/lib/systemd/system/lactd.service`, which systemd reads before `/usr/lib`) stays the same process with the same files through install, upgrade, removal and purge. `tests/baseline-qemu.sh`: the daemon and `lact cli list` run on a qemu64 processor.
- **Trap: `.orig` files.** *Symptom:* `failed to calculate checksum of vendor/anyhow/Cargo.toml.orig`. *Cause:* `cargo vendor` lists `Cargo.toml.orig` (the manifest before cargo normalised it) in every crate's `.cargo-checksum.json`, and dpkg-source leaves `.orig` files out of the tree it unpacks (`ignoring deletion of file ...`: 411 of them). *Fix:* `debian/strip-missing-checksums.py` drops an entry only when its name ends in `.orig` and the file is absent; any other missing or changed file still stops cargo.
- **Trap: the adapter and a Rust workspace.** The record of `lean.source_tree` projected 6 of 114 `.rs` files of the workspace, 15 were unchanged and 93 stayed authored with the reason: 58 because `lact-gui/build.rs` opens files and names source folders, 35 because `include_str!` takes a computed path. This is the adapter being conservative where it cannot prove a reader absent; nothing was forced.
- **Trap: the licence table.** 414 crates carry 30 distinct licence expressions (`MIT OR Apache-2.0` 208, `MIT` 93, `Apache-2.0 OR MIT` 33, Unicode-3.0 18, ...), one LGPL-3.0-or-later crate (amdgpu-sysfs, linked statically: the source package is the relinking offer), 13 crates with no legal file. `gen-copyright.py` writes one stanza per expression and stops at a licence it does not know.
- **cpu-baseline.py does not know Rust**: it lists 7,131 instructions above the baseline (crates choose AES-NI and friends by CPUID, as the Go standard library does); the proof is the run on qemu64. Teaching the tool Rust is the next step if more Rust programs are carried.

### HeadsetControl 4.3.0 (`sparky-os/packages/headsetcontrol`)

C++20 with CMake, GPL-3.0, hidapi from Debian (`libhidapi-dev`), no vendored code. `make-orig.sh` pins the tarball SHA-256, the commit and the tree id of the *unpacked tarball* (it leaves out what `.gitattributes` marks `export-ignore`, so it is not the commit's own tree: pin what you unpack and say so). Two packages: `headsetcontrol` (the program and `/usr/lib/udev/rules.d/70-headsets.rules`, which the built program writes with `headsetcontrol -u`) and `headsetcontrol-dev` (headers and `libheadsetcontrol.a`). Upstream's 14 unit tests run in the build (they use a mock HID interface).

- **Proof** (`tests/udev-proof.sh`, umockdev, no headset): a recorded HyperX headset (03f0:018b) has no `uaccess` before the package, has it after, an unlisted device of the same maker (03f0:ffff) does not; the installed rules equal what `headsetcontrol -u` writes (comments aside: Lean Code leaves out the comments of installed files, which here are the device names); with no headset the program says "No supported device found" and exits 1; an upgrade installs without a removal and keeps the access; removal takes the rules; purge leaves no file; upstream's copy in `/usr/local` (program and rules) is the same bytes through all of it.
- **Detection** (`share/peripherals/headsetcontrol.ids`, 119 ids from the rules the program writes): the package is installed for a listed headset; 9 ids are OpenRGB's too and 4 libratbag's, and each tool is installed for them (they open different interfaces; no clash has been seen, so no ownership row). A HeadsetControl in `/usr/local/bin` is the person's: the plan says `headsetcontrol-local` and installs nothing.
- **Trap: the library's name.** *Symptom:* `dh_install: Cannot find "usr/lib/libheadsetcontrol_lib.a"`. *Cause:* the CMake target is `headsetcontrol_lib` but its output name is `libheadsetcontrol.a`. *Found by:* `cmake --install`'s own list in the log.

### CoolerControl: what the milestone 11 reading found (nothing built)

- **Pieces.** `coolercontrold` (Rust, edition 2024, MSRV 1.95, 505 crates in its Cargo.lock: 31 licence expressions, `MIT OR Apache-2.0` 276, `MIT` 107; the workspace's own crates are GPL-3.0-or-later and AGPL-3.0-or-later; `libdrm_amdgpu_sys` links libdrm; no git dependency) with the Vue interface embedded by `include_dir!` from `resources/app`; `coolercontrol` (the Qt 6 window, CMake, Qt6 Core Widgets WebEngineWidgets WebChannel: Debian has `qt6-webengine-dev`); `liqctld`, a Python service in `daemon/resources/liqctld` that calls Debian's `liquidctl`. The unit is `Type=notify` with a watchdog and starts after `lm-sensors`.
- **What it opens (for the ownership rows later).** hwmon: it writes `pwm*_enable` and the PWM values of every fan channel it finds (`repositories/hwmon`), and AMD cards' fan curves through the same driver files; liquidctl devices through liqctld (the same USB devices as OpenLinkHub's coolers and `liquidctl.ids`, 37 of whose ids are OpenLinkHub's in `owners.tsv`); NVIDIA cards through NVML. So the rows to write: Corsair hubs, coolers, lighting nodes and power supplies stay OpenLinkHub's (CoolerControl does not take them; the person can change it); an AMD card's fan belongs to LACT while LACT is installed (both write the card's fan control); every other hwmon fan channel and every liquidctl device that is not OpenLinkHub's is CoolerControl's. What the detection facts can know without loading modules or probing: the presence of `/sys/class/hwmon/hwmon*/pwm*` (a controllable fan), the USB ids of `liquidctl.ids`, the PCI class of a card; not whether a driver will let a channel be written.
- **Upstream's rules.** The AI_POLICY.md says: "You may use whatever tools you like, AI tools included. There must however be a **human in the loop** who understands the work, stands behind it, and does the talking." and "AI agents must not open issues, merge requests, or comments on their own." The edition packages and sends nothing to the project.

## The table

`share/peripherals/*.ids` is made by `tools/make-peripheral-ids.py` from each tool's own device list, so every id has a source and a regeneration shows what changed: OpenRGB's `60-openrgb.rules` (1,173 devices, game controllers left out: Sony's DualSense is the controller flow's), Solaar's receiver table `base_usb.py` (22), libratbag's `*.device` files (147 gaming mice, with Piper), liquidctl's `71-liquidctl.rules` (99), g810-led (13), OpenRazer's `99-razer.rules` (267) and OpenLinkHub's own `99-openlinkhub.rules` (193 lines, 190 distinct ids, tag 0.9.4, commit a08204cf) read together with its `src/devices/devices.go`, whose registry names the folder that drives each id; the edition's `openlinkhub.ids` keeps 43 of them (below). `lib/detect.py` reads `lsusb` and emits `found`, `fact peripheral TOOL IDS`, `package` and `action` lines; the setup installs the packages without a question. ckb-next has no id list outside its compiled sources and is left out of the table.
A desktop board of a maker OpenRGB's detectors name gets `i2c-tools`, `i2c-dev` and the chipset's driver (`i2c-i801` Intel, `i2c-piix4` AMD), the steps of OpenRGB's own `SMBusAccess.md` (it ships in the openrgb package under /usr/share/doc/openrgb), because the board and memory lights sit on the SMBus and no USB id shows them.
OpenRGB starts with the session minimized (`/etc/xdg/autostart/sparky-stereo-openrgb.desktop` runs `openrgb-session`, which looks for the mark the setup writes and leaves a person's own autostart entry alone).

## One owner per device

OpenLinkHub and OpenRGB (or liquidctl) both open Corsair devices; the measured case is an iCUE LINK System Hub (1b1c:0c3f) on which a power supply read about 1,800 W. For the four carried families the owner is OpenLinkHub (37 ids that another tool of the table lists too: `owners.tsv`; milestone 6 had 99, the 62 that left are keyboards, mice, headsets, the LT100 and the ST100, which stay OpenRGB's). Three parts: the plan installs OpenLinkHub for the device and does not install the other tool for it; `62-sparky-stereo-peripheral-owner.rules` takes OpenRGB's `uaccess` tag away from the owned devices once OpenLinkHub is there (`TEST==` on its unit file in `/usr/lib/systemd/system` or `/etc/systemd/system`, or `/opt/OpenLinkHub`); `sparky-stereo-peripheral-owner` tells the person once per device through the problems engine. **A copy of OpenLinkHub the person installed with upstream's scripts is theirs** (the fact `openlinkhub-upstream`: `/opt/OpenLinkHub`, its unit in `/etc/systemd/system` or its rules in `/etc/udev/rules.d`): the plan does not install the package beside it (Daniel, 2026-11-07, "If manually installed leave it"), and the package's own `postinst` leaves that install alone (the container proof: install, upgrade, removal and purge of ours leave the upstream unit, its process, `/opt` and the rules byte for byte as they were). A shipped setting the person can change: an empty file of the same name in `/etc/udev/rules.d` gives the devices back to OpenRGB (udevadm control --reload-rules, then unplug and plug the device again).

## The notice of upstream's own copy, in the person's language (milestone 8)

When a copy installed with upstream's scripts and the package `openlinkhub` are both on the computer (a person installed the package by hand beside their own copy), the package's `postinst` prints one English line, which stays as apt's own output, and `sparky-stereo-peripheral-owner check` tells the person at the desktop, once, through the problems engine and in their language: `sparky-stereo-problems say sparky-stereo-hardware LOCAL89`, title `LOCAL88`, in all ten catalogues (`problems-lang/`, same ten as `required-languages`). It is a notice, not a failure: nothing is kept in `sparky-stereo-problems list`, the mark `owner-told/notice-openlinkhub-upstream` stops a second telling, and it is forgotten when either copy goes, so a return is told again. The message carries the steps of README.Debian unchanged (disable the service, copy `database` and `config.json` to `/var/lib/openlinkhub`, remove upstream's unit and rules, enable the package's service) and says that nothing is moved for the person. The fact is `openlinkhub-upstream` (`/opt/OpenLinkHub`, the unit in `/etc/systemd/system`, or `/etc/udev/rules.d/99-openlinkhub.rules`). Proof: `tests/peripherals-owner.sh` (neither, upstream alone and the package alone are silent; both is told once, forgotten, told again), `tests/upstream-notice-lang.py` (the ten catalogues carry the six steps and are not the English text), and the real engine in a container saying it in each of the ten languages. *Trap:* `sparky-stereo-peripheral-owner` silences the engine's own output (`engine()` sends it to the null device), so a container test of the telling reads the stub's log or the mark, and the text is read by calling `say` itself in each `LANG`.

## Traps

- **udev's `TAGS=` keeps a tag that `TAG-=` removed; `CURRENT_TAGS=` does not.** Symptom: the green case "still has uaccess". Cause: the first property is the history, and the `uaccess` builtin reads the current tags. Found by printing both from `udevadm test`.
- **Rules that name a device by `ATTRS{}` need the parent chain in the recording.** The hidraw node alone has no vendor: record the USB device and the hidraw under it (`P:` paths nested), or the rule never matches.
- **A tool's id list can include devices another flow owns.** OpenRGB's rules list Sony's DualSense; without an exclusion a gamepad would make the machine start OpenRGB and the existing controller test (`steam-devices`) gained `openrgb`. The generator names the vendors it leaves out in the file's header.
- **Existing fixtures with a peripheral change their expected plan.** Seven fixtures carry a Corsair K70 or a Razer keyboard; the old tests' package sets and "nothing else" action checks had to say so. A new action kind needs the old tests' filters updated in the same change.
- **`deb-systemd-helper`-style states are not the only "told once".** The telling keeps one mark per device in `/var/lib/sparky-stereo-hardware/owner-told` and forgets it when the device or the owner goes, so a later return is told again.
- **A tool's own rules list ids its own code does not drive.** OpenLinkHub 0.9.4's `99-openlinkhub.rules` has seven ids that no folder of `src/devices` registers (read `devices.go`, not the rules, to say what a device is); they are listed as unlisted and not carried.
- **An owner list is read from what the tool drives, not from the overlap with another list.** Milestone 6 gave OpenLinkHub every id both lists held (99), including 62 keyboards and mice the edition does not carry it for: OpenRGB lost access to a K95 for a program that was not installed for it. Narrow the list to the families carried and test one device outside it (the keyboard recording).
- **Detection must not plan a second copy beside the person's.** The upstream installer writes `/opt/OpenLinkHub` and a unit with the same file name as the package's; `/etc/systemd/system` wins over `/usr/lib/systemd/system`, so a second copy would be shadowed and the package's `postinst` would restart upstream's service. Both the plan and the maintainer scripts check.
- **A Razer device is in OpenRGB's list and in OpenRazer's.** Both are installed (Bazzite ships both); whether they fight over one Razer device is not measured here.

### CoolerControl as built (ORDER 108 milestone 13, 2026-11-18)

- **Recipe:** `sparky-os/packages/coolercontrol`: `make-orig.sh` (five pinned archives, three licence tables), `build.sh` (checks the trees' fingerprints and every legal file's hash), `debian/` (`rules` builds Rollup's native part, the interface, the daemon with its tests and the Qt window offline; `debian/patches/0001` is the interface's build chain). Two binary packages: `coolercontrold` (the service, with the interface built into the binary by `include_dir!`) and `coolercontrol` (the Qt window). The daemon's 2,645 tests run in the build.
- **What our package does not do that upstream's does:** upstream's `postinst` rewrites the computer's apt sources to the project's own repository (a Cloudsmith entry becomes `apt.coolercontrol.org`) and the package installs the project's archive keyring in `/usr/share/keyrings`. Ours does neither (the package manager's sources are the person's); its service scripts are LACT's: enabled on first install, a person's disable kept, a copy made by upstream's makefile in `/usr/local` or `/etc/systemd/system` left untouched through install, upgrade, removal and purge.
- **Proof without the machine:** the recorded machine is this station's `/sys/class/hwmon` as plain files (`tools/record-hwmon.sh`, `tests/fixtures/hwmon-station.tar.xz`), bind-mounted over `/sys/class/hwmon` in a systemd container with `--cap-add SYS_ADMIN` (no `--privileged`, `/sys` otherwise read only) and VERIFIED (a marker file, the mount a tmpfs) before anything starts: the fans of a real station are never written. The daemon has no sysfs override, which is why the mount; `CC_SENSORS_DETECT=OFF` in a drop-in is the one deviation (it would run sensors-detect). Set a fixed duty with `PUT /devices/UID/settings/fan1/manual {"speed_fixed":40}`: `pwm1` of the fixture reads 102 and `pwm1_enable` 1; a graph profile with a temperature source of the same device on `fan2` gives `pwm2` 135 at 41 degrees (the curve 20/30, 40/50, 60/100). The API's Basic authentication only works at `/login` (it returns the session cookie).
- **Detection (sparky-stereo-hardware 0.1.36):** a hwmon folder that holds a pwm channel (the `hwmon-fans` fact, read with no module loaded: a Super I/O whose driver is not loaded shows no fan) or a liquidctl-listed USB device that is not a lights-only controller; Corsair's stay OpenLinkHub's, an AMD card's fan is LACT's while LACT is planned, a CoolerControl made by upstream's makefile (`coolercontrol-local`) is the person's.
- **Traps:** `dpkg` removes the window when its daemon is upgraded alone (its Depends names the exact version): upgrade both, and purge with `dpkg --purge` (`apt-get purge` cannot find a package that is no longer installed); a `Depends: x (= ${binary:Version})` bumped by hand needs the same bump in the sibling.

### The headset in Plasma's battery list and the notice of CoolerControl's own copy (ORDER 108 milestone 14, 2026-11-18)

- **The headset's battery (`sparky-stereo-headset` 0.2.0, ORDER 700).** The route, measured and chosen by the design (the kernel first, then UPower's way in from user space), is in [power-idle: a peripheral's battery in Plasma](../../power-idle/references/peripheral-battery-in-plasma.md). As built: `src/battery.cpp` (the system service `sparky-stereo-headset-battery`, `/usr/libexec`, Qt Core and the engine only) reads the charge through HeadsetControl every 30 seconds and keeps one virtual HID device per headset through `/dev/uhid` (descriptor: one Consumer Control application collection with the Battery System usages and two volume keys that are never sent; bus virtual with the headset's own vendor and product numbers, so no real driver binds; `uniq` `sparky-stereo-headset:VID:PID`); `data/72-sparky-stereo-headset-battery.rules` gives that input node `SOUND_INITIALIZED` and `SOUND_FORM_FACTOR=headset`; the generated `71-` rules start the unit with the headset (`ENV{SYSTEMD_WANTS}`, `StopWhenUnneeded=yes`), so nothing runs without one. - **Trap: a Docker container without `CAP_SYS_ADMIN` cannot write to a recorded folder bound over `/sys`.** *Symptom:* `Permission denied` (not `Read-only file system`) on `/sys/class/hwmon/probe` where a host folder is bound, while the rest of `/sys` correctly says read only. *Cause:* Docker's default AppArmor profile (`docker-default`) denies writes under `/sys` whatever is mounted there. *Fix:* `--security-opt apparmor=unconfined` for a recorded-machine run in a plain container, with `/sys` still read only and no `CAP_SYS_ADMIN` (`CapEff` has no bit 21), both checked before the service starts. *Found by:* the coordinator's rerun of milestone 13, then reproduced here: default profile `Permission denied` on the bound folder, `unconfined` writes it, `/sys/class/drm` read only in both (`CapEff a80425fb`). With `--cap-add SYS_ADMIN` (as the systemd proofs do, for the `mount --bind` itself) `apparmor=unconfined` is needed as well.
- **Trap: `docker cp` into a path under a `--tmpfs /run` of a systemd container puts the file under the tmpfs, where it is never seen.** *Fix:* bind-mount the file (`-v file:/run/NAME:ro`) when the container starts.
