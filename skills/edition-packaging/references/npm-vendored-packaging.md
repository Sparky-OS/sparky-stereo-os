# Carrying a program with a vendored npm tree

**For** whoever carries a program whose interface is built with npm (Vue, React, Vite): how to take its inventory, what must be true before anything is built, how the build proves nothing was fetched, and the stop that CoolerControl 5.1.2 met on 2026-11-18. Part of the [`edition-packaging`](../SKILL.md) skill; the Go and Rust routes are in [go-release-packaging.md](go-release-packaging.md) and [lights-and-peripherals.md](lights-and-peripherals.md).
Written from a measurement, not a finished package: the first program through this route stopped at step 2.

## The route, in order

1. **Take the inventory from the lock file, before any build.** `package-lock.json` (lockfileVersion 3) has one entry for each package with `resolved`, `integrity` (sha512), `license`, `dev`, `optional`, `os`, `cpu` and `hasInstallScript`. Count the entries; count the licence expressions; list the entries with no `license` (read their `LICENSE` file instead); list `hasInstallScript`; list every entry with `os` or `cpu`. CoolerControl's interface: 567 entries, all from registry.npmjs.org, none without an integrity hash; 476 MIT, 32 ISC, 14 Apache-2.0, 13 BSD-2-Clause, 12 MPL-2.0 (lightningcss), 9 BlueOak-1.0.0, 4 BSD-3-Clause, 2 CC0-1.0, one each of GPL-3.0-or-later (the program itself), CC-BY-4.0 (caniuse-lite, data), 0BSD; 2 without a licence field (memorystream, vue-color); 4 install scripts (`@parcel/watcher`, `vue-demi`, `core-js`, `fsevents`: the program's own `allowScripts` switches them off).
2. **Find the native binaries in the build path. This is the step that decides.** An npm package for a native tool carries a compiled `.node` file or an executable under a name that ends in the platform (`@rolldown/binding-linux-x64-gnu`, `lightningcss-linux-x64-gnu`, `@esbuild/linux-x64`, `@rollup/rollup-linux-x64-gnu`, `@parcel/watcher-linux-x64-glibc`). They are upstream's prebuilt binaries, which the edition does not carry. Install the tree (step 4) in a scratch container and look: `find node_modules -name '*.node' -o -type f -perm -u+x`, then take each away in turn and run the build; the ones whose absence stops the build are in the path. **For each: where is its source, and can the source be built without an earlier copy of itself or of another prebuilt npm binary?** If the answer is no for any of them, stop and hand back the evidence; do not change the program's lock file or its bundler to get past it.
3. **Check the licences**: nothing that forbids redistribution (none in 567), the two entries without a field read from their files, the data package (caniuse-lite, CC-BY-4.0) credited.
4. **Fetch once, with the lock as the authority.** In a disposable container with network: `npm ci --ignore-scripts --no-audit --no-fund` (npm checks every tarball against its `integrity` and stops on a mismatch; 530 packages for linux-x64 installed in 29 s). Take the fingerprint of the tree (sorted `sha256sum` of every file, then its sha256), as for `vendor/` in the Go and Rust recipes; pack `node_modules` as a component tarball made with `tar --sort=name --mtime=@COMMIT_TIME --owner=0 --group=0 --numeric-owner`.
5. **Legal files out of git, pinned by hash.** They carry authors' addresses (the publish check refuses them): commit a table of `package, version, licence, path:sha256` and let `build.sh` take the texts from the tree and stop unless every one matches, none is extra, none is missing (the same as `debian/vendor-licences.tsv` of OpenLinkHub and `crate-licences.tsv` of LACT).
6. **Build offline, and prove it.** `docker run --network none` for the build step (the container has no route, so a fetch fails at once), `npm_config_offline=true`, `npm run build-only` (here `vite build`, 42 s and a 4.1 MB `dist/` on four cores). Say in the record how nothing was fetched: the network-less container, the unchanged `package-lock.json` hash before and after, the tree fingerprint equal to the pinned one after the build. The daemon of CoolerControl embeds `dist/` with `include_dir!`, so the interface is part of the binary: the interface build comes first and its output is copied to `coolercontrold/resources/app` before `cargo build`.
7. **The language plan.** JavaScript and Vue single-file components are the program's own source: name the language (`js`) in `debian/sparky-lean-languages.json` only for the files the toolkit can prove, and preserve `node_modules/*` as authored (a vendored tree is never projected).

## What CoolerControl 5.1.2 showed (2026-11-18, `debian:testing` container, Node 24.22.2, npm 12.2.2)

The interface is built with Vite 8.3.6, whose bundler is **Rolldown 1.2.16** and whose CSS minifier is **Lightning CSS 1.33.0**; both are Rust programs that npm delivers as prebuilt shared objects.

| Package in the build path | File | Size | Without it |
| --- | --- | --- | --- |
| `@rolldown/binding-linux-x64-gnu` 1.2.16 | `rolldown-binding.linux-x64-gnu.node` | 21,090,848 bytes | `vite build` stops: "Cannot find native binding" |
| `lightningcss-linux-x64-gnu` 1.33.0 | `lightningcss.linux-x64-gnu.node` | 10,032,264 bytes | `vite build` stops: "[lightningcss minify] Cannot find module '../lightningcss.linux-x64-gnu.node'" |
| `@parcel/watcher-linux-x64-glibc` 2.6.0 | `watcher.node` | 523,152 bytes | not in the build path (an optional watcher of `sass`, its install script switched off by the program) |

Debian testing has neither (`rolldown`, `lightningcss`, `node-vite` are not packages; `esbuild` and `rollup` are, but this lock uses neither). Rolldown's own source cannot be built without an earlier prebuilt copy: its `packages/rolldown/build.ts` bundles itself with `import { build } from './src/index'` (Rolldown building Rolldown), its dev dependencies are `rolldown: workspace:*`, `@oxc-node/cli` and `oxc-parser`, and both of those are npm packages with 17 and 19 prebuilt platform bindings. A bootstrap would start from a prebuilt copy of the thing built, so the stop is real for Rolldown. Lightning CSS builds with `node scripts/build.js` (`@napi-rs/cli`, cargo), no self-hosting seen, its dev dependencies include `esbuild` and `parcel`; it was not built in this measurement.

**What a stop hands back:** the table above, the options with their costs: (a) accept the two named binaries as vendored inputs pinned by integrity hash (a change of the edition's rule about prebuilt binaries: Daniel's call, not the lane's); (b) bootstrap Rolldown from source through `@oxc-node` and `oxc-parser` from source, which are themselves self-hosted (a separate project); (c) a different bundler for the same interface (Vite 7 with Rollup and esbuild, or Debian's `esbuild` and `rollup`), which means a changed `package.json` and lock file and a build nobody upstream tests; (d) wait for a Debian package of Rolldown. None was taken.

## Traps

- **`npm ci` installs for the machine it runs on.** The lock lists 39 platform packages; a tree made on amd64 holds the linux-x64 ones only (`os`/`cpu` filter), so a vendor tarball is per architecture, as `GOAMD64` builds are.
- **`--ignore-scripts` is not optional** for a recipe: the install scripts run arbitrary shell at fetch time. The program's `allowScripts` shows which ones it needs (none for the build).
- **A prebuilt binary hides in a package with a harmless name.** The scan is by file type, not by name: `.node` files and executables in the unpacked tree.
- **npm's integrity check protects the fetch, not the provenance.** The lock pins what was published; it does not say the published binary was built from the repository's source. That is why binaries stop the route.
