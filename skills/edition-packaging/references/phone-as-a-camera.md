# A phone as the computer's camera (ORDER 25, 2026-11-18)

DroidCam's Linux client and scrcpy's camera mode write the phone's picture to a v4l2loopback device; PipeWire lists the device as a camera and System Settings, Camera shows it like any camera.
Check freshness first: written on 2026-11-18 from droidcam 2.1.7 and extended on 2026-11-24 by the first run with a real phone (DroidCam app 6.28 on an Android 10 phone, droidcam 2.1.7-2; see "The real phone" below); the rest was written from droidcam 2.1.7, scrcpy 4.1-1+b1 (Debian contrib), v4l2loopback-dkms 0.15.4-2, kernel 7.3.4-stereo3d18, PipeWire 1.6.9, WirePlumber 0.5.19, sparky-stereo-camera 0.1.0, KDE Connect 26.08.3.

## Recipe

1. **Reconcile first.** `madison` for the package (`curl 'https://api.ftp-master.debian.org/madison?package=scrcpy&text=on&s=unstable,testing,stable,experimental'`), Debian's removal log (ftp-master.debian.org/removals.txt), open wnpp bugs over SOAP (get_bugs package wnpp, get_status in chunks, the subject), SparkyLinux's `core` and `tiamat` indexes (`https://repo.sparkylinux.org/dists/SUITE/main/binary-amd64/Packages.gz`), and `grep -rn -i` over the app center's whole fork (pages, changelogs and scripts, not one kind of file). Found: DroidCam is in none of them; scrcpy 4.1-1 is in Debian testing's **contrib** (the first `apt-cache policy` with only `main` shows nothing); Paweł's pages had scrcpy and removed it in a later release.
2. **The client:** `sparky-os/packages/droidcam/` (make-orig.sh pinned by archive SHA-256, commit and git tree id; debian/ with upstream's Makefile and Debian's v4l2loopback-dkms instead of the bundled module). Build it with `tests/plain-build.sh` in a container that has the build dependencies.
3. **The glue:** `sparky-os/packages/sparky-stereo-phone-camera/`: `/etc/modprobe.d` options (`devices=1 exclusive_caps=0 card_label="Phone camera"`), `sparky-phone-camera` (checks, says what is missing in ten languages, loads the camera when a phone session starts, runs the client or scrcpy in the foreground and removes the camera when the session ends), the root helper and its polkit action (below), two menu entries. No modules-load file is shipped: a camera that is always listed is the person's choice (a file `/etc/modules-load.d/phone-camera.conf` with the line `v4l2loopback`; the command leaves a camera that was already loaded). Its test uses a fake root and stand-ins for modinfo, pkexec and adb: `python3 -I tests/test.py` (29 cases).

## The camera comes and goes with the phone session (Daniel, 2026-11-16 and 2026-10-15: a device is there while it is connected)

- `/usr/lib/sparky-stereo-phone-camera/sparky-phone-camera-helper` is a `/bin/sh` script run as root through `pkexec` under the polkit action `org.sparky.stereo.phonecamera.run` (`/usr/share/polkit-1/actions/...policy`, `allow_active` yes, `allow_inactive` and `allow_any` no, `org.freedesktop.policykit.exec.path` annotation, descriptions in ten languages). It takes exactly one word: `load` runs `modprobe v4l2loopback` (modprobe reads the package's options file), `unload` runs `modprobe -r v4l2loopback` and answers exit 3 when the module is in use; anything else (another word, an extra argument, none) is exit 64 and loads nothing. It fixes its own PATH and unsets `MODPROBE_OPTIONS`.
- The command remembers that it loaded the module (`LOADED_BY_US`) and removes it only then; if a program still holds the camera, the module stays and the command says so once (`still_in_use`). A denied action (pkexec exit 126 or 127) has its own sentence (`not_authorised`).
- Proof in the guest: a real polkitd on a system bus, the user `tester` granted by a rule file that exists only in the guest (it has no login session, so the active-session answer is stood in for; the shipped action is the one pkexec asks), the user `other` with no rule: before a session no module, no `Phone camera` in sysfs, in PipeWire or on the Camera page; during one all three; after it none; a second session works; the helper refuses `nvidia`, `load v4l2loopback`, `load exclusive_caps=1`, `unload nvidia`, `-r nvidia` and no argument, each with the module still unloaded.
4. **The entry:** `kind: apt`, `section: main`, `sizes: true` in `stereo/main-entries.json` and Paweł's link in `8/` and `9/` (bytes, not text: the pages have CRLF line endings), the note in the ten languages, `stereo/tests/phonecamera.py`. The package's own Depends bring everything; the app center's Depends do not change (`tests/store.py` with `APTUS_BUILD_SH` set checks that).
5. **The virtual machine proof** (published kernel, no host module, no host /dev/video*): a container installs the published kernel image and headers from the edition's repository (read only), `v4l2loopback-dkms` (it builds and signs the module: "Signing key: /var/lib/dkms/mok.key", `modinfo -F signer` says "DKMS module signing key"), our two packages, PipeWire, WirePlumber, v4l-utils and sparky-stereo-camera (with deb-multimedia in the sources, or libavcodec63 does not resolve); the container's filesystem is exported to a tar, written into an ext4 image with `mke2fs -d` (no root needed on the host side), and booted with `qemu-system-x86_64 -enable-kvm -kernel vmlinuz -initrd initrd.img -append "root=/dev/vda rw console=ttyS0 init=..." -drive file=root.img,snapshot=on -serial file:LOG`. A second tiny drive (`mke2fs -d` of a folder) carries the test scripts so a change costs seconds, not a new image. The guest's init prints `VMTEST ...` lines and powers off.
6. **The stand-in for the phone** (it answers at once, which is why it never showed the first-frame delay below; the 731 version in `sparky-os/packages/droidcam/tests/first-frame/server.py` sleeps like the phone): a Python server that speaks what `droidcam-cli` 2.1.7 expects (src/av.c `VideoThreadProc`, src/common.h `VIDEO_REQ`): the client sends `CMD /v3/video/jpg/WxH`; the server answers 9 bytes (width and height as big-endian 16-bit numbers, five more bytes) and then frames, each a 4-byte little-endian length and a JPEG. The picture is left half red, right half blue, with a white bar that moves 16 pixels a frame; the check reads six frames from the loopback device with `v4l2-ctl --stream-mmap --stream-count=6 --stream-to=FILE` (YU12, 640x480, 460800 bytes each) and tests U and V per half and the bar's position.

## Traps (symptom, cause, fix, how found)

- **`apt-cache policy scrcpy` shows nothing on Debian testing.** Cause: scrcpy 4.1-1 is in `contrib`, and the container had `main` only. Fix: components `main contrib non-free non-free-firmware` (the installed edition has them). Found by: madison (`testing/contrib`).
- **Debian's scrcpy fetches a program from the internet when it is installed.** Its postinst runs `/usr/libexec/scrcpy-update-server` (debconf `scrcpy/update_server`), which downloads the prebuilt phone-side server from GitHub's release page and checks a pinned SHA-256; Debian could not build the server any more (the package's copyright file says so). The entry's note says so in ten languages; a proof that must not download it pre-seeds `scrcpy scrcpy/update_server boolean false`. Found by: reading `x/DEBIAN/postinst` of the downloaded `.deb`.
- **The client does not build against Debian's libusbmuxd-dev.** Symptom: `Package libimobiledevice-glue-1.0 was not found`, then `undefined reference to usbmuxd_get_device_list`. Cause: `libusbmuxd-2.0.pc` requires `libimobiledevice-glue-1.0` and the -dev package does not depend on it; and upstream's Makefile `USBMUXD := ...` is overridden by a value on make's command line (the pkg-config call vanishes). Fix: Build-Depends on `libimobiledevice-glue-dev`; give `USBMUXD` and `APPINDICATOR` through the environment (`export` in debian/rules), never as `dh_auto_build -- USBMUXD=...`. Found by: the build log's two `Package ... not found` lines.
- **The client prints `unexpected video image stream subsampling: 0` for every frame.** Cause: it wants 4:2:0 JPEGs; the stand-in's Pillow default for `subsampling=0` is 4:4:4. Fix: `subsampling=2`. Found by: the client's own output in the guest.
- **`Video: Connect failed` to a server that is listening.** Cause: in a bare guest the loopback interface is down. Fix: bring `lo` up (`ioctl SIOCSIFFLAGS` from Python when `ip` is not installed). Found by: the same sentence from the wrapper's own probe and from the client.
- **The loopback device exists, frames flow, and PipeWire lists no camera** (`wpctl status`: the device under Devices, Sources empty; the Camera page's `list` answers `[]`). Cause: with `exclusive_caps=1` the device announces OUTPUT only until a program writes to it, PipeWire's V4L2 monitor enumerates a device once, when udev adds it, and a later change of the capabilities makes no event it acts on. Fix: either `exclusive_caps=0` (the device is a camera as soon as the module is loaded: the edition's default) or, with `exclusive_caps=1`, `sparky-phone-camera announce` (a udev remove and add for that one device; measured: PipeWire then lists `Phone camera (V4L2)` and the Camera page lists it with key `platform:v4l2loopback-000|Phone camera`, YU12 640x480 30 fps). Found by: `pw-dump` and `wpctl status` before and after, and `cat /sys/class/video4linux/video0/uevent`-style remove and add.
- **The module loads in a guest with `module verification failed: signature and/or required key missing`.** That is the kernel's taint message for a signature whose key it does not trust; without Secure Boot or `module.sig_enforce=1` the module loads. With `module.sig_enforce=1` the load is refused with `Key was rejected by service`, which the command turns into its Secure Boot sentence. The key is the machine's (`/var/lib/dkms/mok.key`, made by dkms when it is not in a chroot); the edition's first-boot enrolment (drivers, lessons-2026-11.md, `dkms-firstboot-enrol-374`) is what makes Secure Boot accept it. Found by: `modinfo -F signer`, `dmesg`, and the guest started with and without `module.sig_enforce=1`.
- **`wifi_check` probing the phone's port, then the client connecting, doubles the connection to a phone app that takes one client at a time.** Fix: no probe; the client's own `Connect failed` line is turned into the sentence. Found by: the stand-in accepting the probe as its one connection.
- **A background loop in a guest `exec`ed `tail -f /dev/null | program`** is how the client keeps a stdin open (`droidcam-cli` reads the keyboard and stops at end of file unless `-nocontrols`).
- **Killing a stuck guest:** a QEMU process of the lane is found by `ps -eo pid,ppid,comm,args | awk '$4 ~ /qemu/ && /-name dc25-vm/'` and killed by PID; a pattern kill (`pkill -f`) can hit another lane's machine and the shell itself.

- **A second session fails with `Error opening '/dev/video0': 13 'Permission denied'`.** Cause: the program started between `modprobe` and udev giving the new node its group and access. Fix: the command waits up to five seconds until it can open the node (`wait_usable`). Found by: the guest's second session, with the node's mode and the client's own line; the first session had won the race by luck.
- **The image used to build says `The repository 'file:/repo mashtabba Release' does not have a Release file`.** Cause: the builder image still held the edition's sources file, and the first container of a recipe (the one making the orig archive) mounts no /repo. Fix: keep the image free of the edition's sources and pins; the recipes add them in the container that mounts the tree. Found by: the first line of the build log.
- **The link gate stops with `sparky-stereo-phone-camera Depends droidcam but it is not installable`.** Cause: droidcam is in no archive yet. Fix: build droidcam first and give the gate `SPARKY_LC_SIBLINGS_FILE` (a file listing the unpublished edition packages as paths the container sees; the recipe's `build-in-container.sh` passes it). The archive folder (`sources.json` and dearmored keyrings: Debian, deb-multimedia, SparkyLinux core and tiamat, the published tree as `file:/repo`) is the same for every recipe.
- **The app center fork's `origin/master` is not the fork's master.** In a clone of the submodule folder, `origin/master` is Paweł's old main (bc0f0fe); a rebase onto it replays 55 commits. The build tree's pointer names the fork's real head (e1f7d82 then); rebase only the build tree and the skills and keep the fork branch on its own base.
- **`apt-get -s` of an entry whose package depends on scrcpy** asks nothing, but a real install runs scrcpy's postinst and downloads its server: preseed `scrcpy scrcpy/update_server boolean false` in any container that installs it.
- **Emptying `/var/lib/apt/lists` breaks `apt.Cache()`** if the `partial` folder goes too: keep `mkdir -p /var/lib/apt/lists/partial`. Found by: the app center's page script failing with a Python traceback.
- **A guest init written for sh cannot use `declare -f`.** Run the test script with bash. And kill the stand-in server by its PID (`$!`), not by `pidof python3`, which also stops the command under test.
- **A Debian -dev package whose pkg-config file requires another -dev package** (libusbmuxd-dev and libirecovery-1.0-dev both need libimobiledevice-glue-dev): the test is `pkg-config --exists NAME` in a fresh container with the package alone (exit 1) and with a package rebuilt with the added Depends (exit 0); the rebuilt library package must come with it (`Depends: libusbmuxd-2.0-7 (= 2.1.1-1)` is exact, and the archive's is `+b1`).

## The OBS Studio source, the entry's name and "Use as webcam" (continuation 3, 2026-11-18)

- **The OBS plugin is its own package** (`droidcam-obs`, from the 2.5.1 tag; the phone-camera package only Suggests it), so the entry never brings OBS Studio: the apt simulation of the entry is read for `obs-studio` and `libobs` and finds none. It is installed where OBS finds a system plugin: `/usr/lib/<multiarch>/obs-plugins/droidcam-obs.so` and `/usr/share/obs/obs-plugins/droidcam-obs/`. On the edition OBS is deb-multimedia's 33.0.1 (Debian testing has 32.2.2); the plugin is built against the first and Depends on `libobs0t64 (>= 1:33.0.1)`.
- **Proving a plugin without OBS's window:** a 90-line C program against `libobs-dev` loads the `.so` with `obs_open_module` and `obs_init_module`, lists `obs_enum_input_types` (the source id is `droidcam_obs`, "DroidCam OBS"), then, under `xvfb-run` (libobs asks for an X display even without a window: "Unable to open X display" and `obs_startup failed` otherwise), calls `obs_reset_video` with `libobs-opengl`, creates the source with `activated`, `cur_dev_id=dev_id_wifi`, `cur_dev_ip`, `app_port`, `cur_dev_type=1`, `video_format=1`, puts it in a scene and sets the scene as output source 0 (the plugin starts only when it is showing: `obs_source_inc_showing` alone did not start it), and reads the output frames with `obs_add_raw_video_callback` (NV12). The stand-in server speaks the plugin's protocol, which is not the client's: the plugin sends `GET /v5/video/jpg/640x480/port/..../` and reads 12-byte headers (pts and length, big-endian) each followed by a JPEG, with no reply header. Result: 60 output frames, red left and blue right in 44 of them (the first ones are black before the first picture), the white bar moving in 24.
- **Upstream's link line drops the libraries.** Symptom: `dlopen` fails with `undefined symbol: lockdownd_client_new` (or `blog`) although the build passed. Cause: the Makefile puts `LDD_LIBS` before the source files and the linker's as-needed default discards them there; a value given on make's command line also replaces the Makefile's own `LDD_LIBS`. Fix: the libraries go in `STATIC` (it comes after the sources) through the environment, and `LDD_FLAG=-Wl,--no-undefined` makes the next fault a build failure. Found by: loading the `.so` in libobs, then reading the link line in the build log.
- **The harness exports `SRC`.** Symptom: only in the lean build, `No rule to make target 'droidcam-obs-2.5.1', needed by 'build/droidcam-obs.so'`. Cause: the edition's build script exports `SRC` (the source folder's name) and upstream's Makefile appends its source files to a variable of that name. Fix: `unexport SRC` in debian/rules. Found by: the plain build passing and the lean one failing with the same sources.
- **A name in the app center's row is data in the language files.** `common.title(row)` reads `ID_name` and falls back to the row's own name; the card heading, the messages that name the entry and the apt sizes line use it; Paweł's page keeps its English link text in every language.
- **A command started from a menu has no terminal**, so its sentences are shown in a window too (`kdialog --error`, or `notify-send`) when `stderr` is not a terminal; a test that runs the command with pipes sets `SPARKY_PHONE_CAMERA_NO_WINDOW`.
- **Use as webcam** (`sparky-phone-camera webcam [NAME]`): KDE Connect's daemon on the session bus, `devices(onlyReachable, onlyPaired)` on `/modules/kdeconnect`, then `type`, `name`, `reachableAddresses` of each device (`busctl --user`, no extra package); phones and tablets only; the address is a bare IPv4 (the real daemon gave `as 1 "172.18.0.2"`) or `ADDRESS:PORT`; the Wi-Fi session starts against it. A menu entry with `TryExec=kdeconnect-cli` and `OnlyShowIn=KDE;` is shown only where KDE Connect is installed. KDE Connect has no extension point for another package's device action (device plugins are C++ modules the daemon loads, the Plasma applet's rows are QML inside the applet, Dolphin's action is for files), so a row inside KDE Connect's own menus means changing KDE Connect; the menu entry is the route that needs no change.
- **The first call starts the daemon.** Symptom: the command says KDE Connect is not running although it is installed. Cause: D-Bus activation starts `kdeconnectd` on the first call and its object registers a moment later (`No such object path '/modules/kdeconnect'`). Fix: wait and ask again, up to ten times. Found by: the real daemon in a container with no network.
- **A real daemon needs the right Qt platform in its activation environment.** Symptom: `qt.qpa.xcb: could not connect to display`, signal 6, "Activated service 'org.kde.kdeconnect' failed". Cause: the dbus-daemon of `dbus-run-session` starts the daemon with the environment it had, not the shell's later exports. Fix: `-e QT_QPA_PLATFORM=offscreen` on `docker run`. A container also needs a passwd entry for its uid (dbus: "Looking up user ID 1000: not found"): run it as root.
- **Never test device discovery on a docker network.** A network made with `--internal` still has an address of the host on it, and the host's own KDE Connect daemon (and any other listener of UDP 1716) answers discovery and shows up in the device list; a script that pairs with every device in the list then sends a pairing request to the machine's owner. Stand-in devices for KDE Connect are a second daemon with `PLASMA_PLATFORM=phone` (that is how a Plasma Mobile phone announces its type) in a network that has no host address, or recorded replies; the lane that learned this had no such network and used recorded replies for the paired case.

## The real phone (ORDER 731, 2026-11-24)

Symptom that started it: the client (`droidcam-cli` 2.1.7) connects, the app's camera starts, nothing is written to the video device, and `ffmpeg -f v4l2` cannot open the device ("Inappropriate ioctl for device"; `v4l2-ctl --get-fmt-video` says "Invalid argument" because a loopback device has no capture format until its first frame).

### The run as a recipe (what is checked, in this order)

1. **Reconcile.** The staged package's debian/patches, control and rules; upstream's tags and commits after the release; the diff of the previous client against this one in `src/av.c`, `src/common.h`, `src/connection.c`, `src/decoder*.c` (2.0.0 against 2.1.7: only the request line, the codec table, a transform buffer and the loopback format handling differ); upstream's issues and pull requests for the symptom words (timeout, first frame, no picture, black screen, connection reset), by the forge's search API.
2. **Red, by you, on the real phone, with the script that will also run the green** (one folder per case, new each time). Expect: `CMD /v3/video/jpg/640x480` out, 9 bytes back, zero bytes after, no frame on the device, a client that stays running.
3. **Read the socket.** `strace -f -tt -e trace=network,write -s 64` on the client shows the 9-byte answer and the next `recvfrom` of 4 bytes ending in `EAGAIN` after the receive timeout. A probe copy of the client that prints the seconds until the first byte after the header (and the bytes) shows what the app does: here the first frame came 7.3, 12.6, 15.6 and 17.6 s after the header.
4. **Vary one thing at a time against the same app** (request version, size, codec word, idle time) before naming a cause: the 2.0.0 request, the 3 request with `jpg` and with `avc`, and the size gave the same header and the same delay, so the request was not the cause; the first-frame delay was.
5. **Replay without the phone** (`tests/first-frame/run.sh staged|fixed CLIENT` in the droidcam recipe): a stand-in with the recorded header and framing that waits before the first frame, a shim for the V4L2 device (so the client can run in a container), red on the staged client, green on the repaired one, and a fast-phone control that passes on both.
6. **Then the phone cases** (USB 640x480, USB 1280x720 on a device that accepts it, Wi-Fi 1280x720, USB after the app sat idle for two minutes, a port nothing listens on), each with the count of frames, the size and the picture itself opened and looked at.

### What the client asks and what the app answers (app 6.28)

| Client | Request | Answer |
| --- | --- | --- |
| droidcam-cli 2.0.0 | `CMD /v2/video.4?WxH` | 9 bytes: width and height as big-endian 16-bit numbers, five bytes the client ignores; then frames, each a 4-byte little-endian length and a JPEG (4:2:0) |
| droidcam-cli 2.1.x | `CMD /v3/video/jpg/WxH` (`avc` is in the code's table, not offered by any option) | the same 9 bytes and the same frames; the app answered 640x480 to a request for 1280x720, so the size in the header is the app's own setting |
| DroidCam OBS 2.5.1 | `GET /v5/video/jpg/WxH/port/P/os/OS/obs/V/client/V/hdr/0/nonce/N/` | a 12-byte header per frame (64-bit time stamp, 32-bit length, both big-endian) and no answer header; our hand-made copy of that line got `HTTP/1.1 400 Bad Request` from the app |

- The header comes at once; the first frame only after the app has started the phone's camera: **7 to 18 s on a mid-range Android 10 phone**, for every request and also after the app sat idle for two minutes (the camera is started for each connection).
- After the first frame the same phone sent frames in bursts with gaps of 5 s and more in one run and steadily (about 7 to 9 frames a second counted by the watcher) in the others.
- The phone's own log (`adb logcat`) is dominated by other apps; the app's lines are a "Slow Looper ... DroidCam/.DroidCam is 10015ms late" warning and the camera HAL opening about when the first frame arrives.

### Traps of the run (symptom, cause, fix, how found)

- **The client connects, writes nothing and says nothing.** Cause: `connection.c` gives every socket a receive timeout of 5 s plus the microseconds `select()` left in the same `timeval` (Linux's `select` rewrites its timeout; `strace` shows `SO_RCVTIMEO_OLD` with a non-zero microsecond field, so about 6 s), `av.c` reads the 4-byte frame length with it, and on `EAGAIN` `break`s out of the video thread without a message; `main` then waits for ever (`v_running` is still 1). Fix (edition patch 0001 of droidcam 2.1.7-2, nothing upstream: no commit after v2.1.7, no issue about it; #241 of 2023, "Connection reset ... I can see the camera starting up", is the same phone behaviour called a network problem): wait for the first frame in steps of one second up to 60 s and say so, give a running stream 15 s between frames, say "The phone sent no picture" (exit 3) or "The connection to the phone was lost" (exit 4), exit instead of waiting. Found by: `strace` (the `EAGAIN` 5 s after the 9 bytes), then a probe client that printed seconds to the first byte.
- **The case script's own reader sees nothing although the client works.** Cause: `run-case.sh` starts `ffmpeg` 10 s after the client and the first frame comes at 7 to 18 s; opened before the first write, `ffmpeg -f v4l2` fails. Fix: a watcher started before the case that retries until the first frame (frame.png), then counts 5 s of frames; prove it first on the red client (it must say "no frame in 45 s"). `ffmpeg` reading an idle loopback device blocks and ignores SIGTERM: `timeout -k 2 N ffmpeg`.
- **`-size=1280x720` is ignored on a device that was used before.** Symptom: the request still says 640x480. Cause: the client sets the loopback control `keep_format` after its first `S_FMT`, and the driver answers a later `S_FMT` with return 0 and the old size, so the client never knew. Fix: the client now says "stays at WxH (asked for WxH)"; the size of a device is changed by loading the module again (the glue loads a fresh device for every session, so `-size` works there), or, for a test, `v4l2-ctl -d DEV -c keep_format=0` before the client runs. Found by: `strace -e ioctl` (S_FMT with 1280x720 answered 640x480).
- **A timeout that is longer than the code says.** A `timeval` reused after `select()` carries what `select` left in it (here 999998 microseconds), so `tv_sec = 5` gave about 6 s and a replay with a 6 s gap did not fail the staged client (8 s did). Set `tv_usec = 0` whenever a `timeval` is reused, and read the timeout back from `strace -e trace=network` before using it in a test.
- **"The connection was lost" printed when the person stops the client.** Cause: SIGINT interrupts the receive (`EINTR`) before the signal handler has cleared `v_running`. First fix (too wide, see the second round below): an `EINTR` is the stop. Final: a receive goes on after `EINTR` while the program runs, and `EINTR` reaches the caller only when `v_running` and `a_running` are clear.
- **A shim that answers `ioctl` never matches.** Cause: the client's `xioctl(int fd, int request, ...)` passes the request sign-extended; compare `(unsigned int) req`. `LD_PRELOAD` on `timeout ... client` loads the shim into `timeout` too, whose exit overwrites the count: `timeout ... env LD_PRELOAD=... client`.
- **A package's unit tests found the real `adb`.** `which('adb')` on a PATH that ends in /usr/bin found the machine's adb and ran `adb devices`. Package tests run in a container with no adb (the test that wants adb missing says so).
- **A stand-in that sends the first frame at once cannot show a timeout.** The first lane's stand-in did, and the delay stayed unseen until a real phone was used; the stand-in now sleeps before the first frame, sends bursts with gaps, and stalls.
- **A `docker run sh -c "rm -f ..."` is refused by the harness's removal check**; `make` rebuilds from the changed source without it.

### The second round (row 731, continuation 2): stop and continue, whole receives, the window program

- **A client stopped and continued (Ctrl+Z, `fg`) stops receiving and says nothing.** Symptom: 80 frames before, 81 three seconds after the continue, 81 fifteen seconds after, the process still running; the same in the first-frame wait. Cause: `recv()` on a socket that has a receive timeout returns `EINTR` after `SIGCONT` even when no handler is installed (signal(7), "Interruption of system calls and library functions by stop signals"), while `v_running` is still 1; code that takes `EINTR` for the person's stop (the first 2.1.7-2 did, on purpose) breaks out of its loop and the thread ends silently. Fix: `RecvExact()` retries on `EINTR` while the program runs and fails with `EINTR` only when `v_running` and `a_running` are both clear (the signal handler's stop). Found by: the main session's review kit (`kill -STOP`, a second later `kill -CONT`, the shim's count read every three seconds), red on 2.1.7-1 and on the first 2.1.7-2, green on the fix.
- **A short count from `recv(..., MSG_WAITALL)` is taken for a whole header or frame.** Cause: a timeout (or a signal) in the middle of an item returns the bytes so far, not -1; the next read then takes the rest of the frame for a length. Upstream also never checked the frame length against its buffer (`f->length` from the wire went straight into `RecvAll` into a slot of `m_Yuv420Size` bytes). Fix: receive whole or fail (`RecvExact`: EAGAIN only when no byte of the item arrived, ETIMEDOUT or ECONNRESET in the middle), and end the stream on a length of 0 or above the slot. Not changed: `RecvAll` itself, because the battery reader depends on its short count at the end of a short HTTP answer. Test: `cut:8` (a frame cut in two by 8 s of silence: the staged client writes about 6 pictures where 25 were sent) and `cutstall`.
- **A shim that writes its count when the client ends cannot read a running client.** The review copy writes at every frame; the recipe's shim now does too (`SHIM_COUNT_FILE`), and accepts `/dev/video*` nodes and `SHIM_SIZE=WxH` (a device that takes another size than the phone sends, for the scaled-picture line).
- **One reader at a time on the loopback device** (`exclusive_caps` is `Y` for the first device on the station): a second `ffmpeg -f v4l2` answers "Device or resource busy". Never start a watcher beside the case script's own reader.
- **What the window program (`droidcam`) shows when a stream ends** (container display, `tests/first-frame/run-gui.sh`): the staged program and the first 2.1.7-2 stay on "Stop", the address and port greyed, WB and EL enabled, no picture and no word (the first 2.1.7-2 shows its error dialog and then still stays on "Stop"); a click on Stop is the way back. Fix: `StreamEnded(code)` is the client's one hook, `droidcam-cli` keeps the code for its exit status and the window program runs its Stop button's own path from the main loop (`gdk_threads_add_idle`, since the video thread cannot join itself), so the dialog is followed by "Connect" and Connect works again without restarting. Because `droidcam` and `droidcam-cli` share `av.c`, a change in it changes both binaries: compare both with the package they replace.
- **A GTK program in a container, headless:** `Xvfb :99`, a character device for the video node made as root (`mknod /dev/video0 c 1 3`) and the program started as an unprivileged user with `setpriv`; `NO_AT_BRIDGE=1`; no window manager, so a dialog opens undecorated at the top left. Read the button's state by comparing its pixels with references taken in the same session (Stop while streaming, Connect after the Stop button): fuzz 3 %, the mouse moved away first (the hover changes the button). Press Return only when a dialog exists (`xdotool search --name '^Error$'`): with none, Return clicks the focused button.
- **The advice in a sentence is tied to the vendor's own words or dropped.** Dev47Apps' help (https://www.dev47apps.com/droidcam/help/, read 2026-11-24): "Make sure you don't have a lot of background apps on the phone, and there aren't any Task Manager apps or Energy Saving modes turned on that might rate limit the app", and "with the screen off, your phone may enter power saving mode after a while and freeze the app/wifi/the camera"; nothing there about another app using the camera, so that clause was dropped. "Open the DroidCam app" (cable case) is the client's own question "Is the app running?" and a measured dead-port run.
- **Building the glue by the route:** its `build-in-container.sh` starts an unnamed container (log creations by the image name, not the container name, if IDs must be kept); the file named by `SPARKY_LC_SIBLINGS_FILE` must be under a folder the script mounts (the scratch folder), not beside it; the builder image needs debhelper, dpkg-dev, python3, bubblewrap and git at rest (the migration image installs them at run time in the droidcam recipe's own script); the link-gate archive folder for it needs Debian testing with `contrib` (scrcpy), deb-multimedia (its FFmpeg libraries) and the published tree, with the dmo keyring taken from the published `deb-multimedia-keyring` package; a git worktree is not a buildable tree in a container (its `.git` is a file pointing outside the mount): use a clone.

## Perks

- Everything on the Camera page works on the loopback camera as on any V4L2 camera (the key is by bus_info and card, so the choice follows the device); the camera's own format list is the one format the writer set (YU12, 640x480 here).
- `droidcam-cli -dev=/dev/videoN` picks the device; `-size=WxH` is for the regular module and only works on a device that has not kept another size; `ANDROID_SERIAL=serial` picks one phone of several on adb.
- scrcpy 4.1: `--video-source=camera` (Android 12 or newer), `--v4l2-sink=/dev/videoN`, `--no-playback`, `--no-audio` (doc/camera.md and doc/v4l2.md of the project).
