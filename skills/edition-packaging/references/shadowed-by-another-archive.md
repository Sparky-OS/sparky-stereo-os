# A package of another archive that ships our files under another name

ORDER 458 (2026-11-09). Blocking an archive's builds by NAME does not stop a package of another name from shipping the same files.
deb-multimedia ships MLT 7 as `libmlt7-data`, `libmlt-7-7`, `melt7` and others; our MLT is `libmlt-data`, `libmlt7`, `melt`.
`libmlt7-data` has `Replaces: libmlt-data` and no `Conflicts`, so it installed beside ours, took over its 400 files under `/usr/share/mlt-7` (Debian Policy 7.6.1: the overwriting package's file "will no longer be listed as owned by the old package"), and our MLT 7.40 ran with 7.42 data while `dpkg-stereo --verify libmlt-data` reported 16 changed files and `dpkg -S /usr/share/mlt-7` named both.

## Recipe

1. Fetch the other archive's `dists/SUITE/COMPONENT/Contents-ARCH.gz` and `Contents-all.gz` for every component and architecture we ship (amd64, i386), and check each SHA-256 against its Release. Our published tree has the same files. An Architecture: all package is only in `Contents-all`: reading `Contents-amd64` alone missed `libmlt7-data`, the one that mattered.
2. `sparky-os/repo/find-shadowing.py --ours TREE/dists/mashtabba/main --theirs DMO/dists/forky` lists every pair (their package, ours, the shared files) and exits 1 for a pair not in `sparky-os/apt/shadowed.py`. Contents lines are `path`, spaces or a tab, `SECTION/PACKAGE`: split from the right (`rsplit(None, 1)`), ours uses a tab and theirs spaces.
3. Read each pair's relation in the other archive's Packages (Replaces, Conflicts, Depends of its dependents). Sort them: replaces without conflicts (co-installs and owns our files), conflicts and replaces (apt takes ours out when something asks for it), and a shared file with no Replaces (dpkg refuses the unpack for ours and for Debian's alike: not a shadow, listed in `NOT_SHADOWS` with the reason; `oss4-dev` and the kernel headers).
4. `make-only-ours.py` writes the pins from `shadowed.py`: `Pin: release o=Unofficial Multimedia Packages`, `-1`, each name qualified by the architectures OUR package is shipped for (the generator's own rule, so an amd64-only package also blocks i386). It also writes `shadowed-by-dmo.tsv`, which the package installs. Regenerate over the same inputs as the committed file (the published tree plus the round's cohort `Packages`) and confirm the diff is only the new block.
5. A pin does not remove an installed package. `sparky-stereo-apt` ships `shadowed-by-dmo` (dpkg post-invoke hook, a systemd unit that waits for the apt lock): automatic and needed by nothing else, removed, then ours reinstalled where installed; manual, left and kept as a dismissible problem in `sparky-stereo-problems`; needed by a staying package, left and told which. Nothing is decided inside the apt run, because apt rewrites the automatic marks when it ends.
6. Prove it red and green in containers (`sparky-stereo-apt/tests/shadowed`: red is the published package as the "new" one), reading apt's `Inst` and `Remv` lines.

## Traps

- Symptom: `apt-get -s remove` and `apt-mark showauto` in the post-invoke hook give a wrong "manual". Cause: the hook runs before apt writes its state file, so a package this very run installed as automatic is not marked yet. Fix: the hook only says and starts the unit; the unit decides after the locks are free (`apt-get -o DPkg::Lock::Timeout=-1 check`), as `thermald-manual` does.
- Symptom: removing the shadowing package leaves our package with missing files. Cause: dpkg gave the files to the replacer and deletes them with it; ours is still "installed". Fix: `apt-get install --reinstall OURS` after the removal, in a second step (one transaction may unpack ours before the removal and fail on the overwrite).
- Symptom: a pin on a name leaves other archive programs uninstallable. Cause: `libmlt-7-7` is a versioned dependency of deb-multimedia's `shotcut`, `flowblade` and `synfig*`, which cannot link our 7.40; the Debian builds of those programs use ours. Fix: say so in the README and the hand-back; check with `apt-get -s install shotcut` (Inst lines).
- Symptom: a melt test reads white or nothing. Cause: an 8x2 test picture; and MLT's Qt module needs a display. Fix: a 64x16 P6 picture under `xvfb-run -a melt avformat:FILE ... -consumer avformat:OUT f=rawvideo vcodec=rawvideo pix_fmt=rgb24`, compared with `cmp` against a computed reference.
- Symptom: `apt-get` in the rig downloads 500 MB every run. Cause: the image's `docker-clean` deletes the .debs. Fix: remove `/etc/apt/apt.conf.d/docker-clean` and mount a cache folder on `/var/cache/apt/archives`.
- Symptom: build fails with `copy-recipe: No such file ... 'git'`, then `dubious ownership`. Fix: git in the build container and `git config --global --add safe.directory '*'`; commit new files first, because the recipe is copied as git tracks it.
- Symptom: `lean.release check-debs` after `bash build.sh` prints `build record NOT complete, unrecorded: buildinfo`, and the stage has no .buildinfo or .changes. Cause: a standalone script package (`lean.standalone`) is not built by `dpkg-buildpackage`. Fix: build the finished .dsc again with `release/build-from-lc-dsc.sh DSC amd64 sparky-lc-migration:20261020 REPO OUT` (with `SPARKY_LC_ARCHIVE_DIR`: a folder with `sources.json` and the keyrings, the keyring paths written as the container sees them). The script reads the source date from `DSC.debian.tar.xz`, which a native `3.0 (native)` source does not have: for sparky-stereo-apt use a copy that reads `debian/changelog` from the `.tar.xz`. The .debs came out byte-identical to the standalone build, and the record had `"unrecorded": []`.
- Symptom: `apt-get -s install PROGRAM` says `Unable to satisfy dependencies` after the pin. Cause: the other archive's PROGRAM (deb-multimedia's shotcut, epoch 1) depends on a name now blocked and stays the candidate, so apt does not fall back to Debian's. Fix: pin that program and the binaries of its source out as well (`PROGRAMS_ON_SHADOWED`), and read the `Inst` lines. A conflict that remains for another reason (here GTK's `gtk-update-icon-cache` in the r1107a tree) shows the same words: look at the first "Reached two conflicting assignments" line, and run the same simulation under the old pins with the Debian version named before blaming the new pin.
- Symptom: the proof's "unpack" check fails although the filter works. Cause: `stereo3d_unpack` gives one view (32x16 of a 64x16 picture) and the consumer's buffer stays the profile's size, so the bytes after the view are not meaningful; and `dpkg -S DIR` lists its owners in no fixed order. Fix: compare only the view's bytes (`cmp -n`), and sort owners before comparing.
- A pin of -1 stops apt from choosing a package, not the person from naming it: `apt-get install libmlt7-data=1:7.42.0-dmo1` still plans the install (measured, apt 3.3.6), and an installed version with a -1 pin is left alone by `dist-upgrade` (candidate `(none)`, no downgrade proposed).

## Proving the unit under systemd (ORDER 458b)

ORDER 458 ran the unit's command by hand because its containers had no systemd. The hook starts the unit with `systemctl --no-block`, so only a systemd container proves that it starts, waits for apt's locks, acts and says it in the journal.

Recipe (`sparky-stereo-apt/tests/shadowed/run-systemd.sh MODE`, same checks as `run.sh`, `SYSTEMD=1` in `inside.sh`):

1. An amd64 forky image with `systemd systemd-sysv dbus ca-certificates` and `/etc/systemd/system.conf.d/core.conf` with `[Manager]` and `DefaultLimitCORE=0:0`.
2. `docker run -d --cgroupns=private --security-opt writable-cgroups=true --tmpfs /run --tmpfs /run/lock --tmpfs /tmp --ulimit core=0 --stop-signal SIGRTMIN+3 IMAGE /sbin/init`. No `--privileged`, no added capability. Mount files for the rig (CA bundle, the https-only helper) under `/run` beside the tmpfs: Docker orders the mounts, and they stay.
3. Wait for `systemctl is-system-running` to say `running` (2 s here), then `docker exec -e SYSTEMD=1 NAME bash inside.sh MODE`. After the install of the new package, wait for the unit: `systemctl show -p ActiveState --value UNIT` is `inactive` and the journal holds its `Finished` line (`Result=success`, `ExecMainStatus=0`). The first `apt-get install` of the stack takes minutes (dpkg-stereo's postinst qualifies the files): keep a download cache mounted on `/var/cache/apt/archives`, one per container that runs at the same time (apt locks it).
4. Read what the person would: `journalctl -u UNIT -o cat`, and apt's `Inst` and `Remv` lines.

Traps:

- Symptom: the container exits 255 at once with no output. Cause: Docker mounts `/sys/fs/cgroup` read-only and systemd 262 will not run as PID 1 on it (`mount | grep cgroup` shows `ro`; run `/usr/lib/systemd/systemd --system --log-level=debug --log-target=console` by hand to see). Fix: `--cgroupns=private --security-opt writable-cgroups=true` (Docker 25 and later; the cgroup tree is the container's own). Not `-v /sys/fs/cgroup:/sys/fs/cgroup:rw --cgroupns=host`, which hands the host's tree to a systemd that wants to manage it.
- Symptom: `Failed to set RLIMIT_CORE: Operation not permitted`, exit 255, with `--ulimit core=0`. Cause: PID 1 tries to set the core limit and the hard limit is 0. Fix: `DefaultLimitCORE=0:0` in the image; the house rule `--ulimit core=0` stays, so a crash in the container reaches no host core handler.
- Symptom: `journalctl -u sparky-stereo-apt-shadowed.service` shows apt's lines but not what `sparky-stereo-problems say` printed, which the hook names as the place to look. Cause: journald finds a line's unit from the writing process's cgroup, and a child that has exited when journald looks leaves the line with no `_SYSTEMD_UNIT` (a native line from the engine, and the unit's own stderr line from it, both; `journalctl -b -t sparky-stereo-apt` still shows them). apt's lines come from processes that live longer. Found by `journalctl -b -o json` and the lines' `_SYSTEMD_UNIT`, `_PID` and `_COMM`. Fix: the script captures the engine's output and prints it itself (`out=$("$PROBLEMS" ... 2>&1)`; `printf '%s\n' "$out" >&2`), from the process that stays; the run-systemd test greps the unit's journal for the message, so the next such line is checked.
- Symptom: `docker cp` of a script into a container with `--tmpfs /tmp` lands nowhere. Cause: the tmpfs covers it. Fix: copy to `/root`.
- A check that reads the unit's journal for a line must not stop at the first `inactive`: wait for `inactive` and a non-empty journal (`Starting`/`Finished` come from the manager), or an `activating` state not yet reached reads as a finished one.

## Keeping the function of a package the pin put out (ORDER 458b)

A pin by name is a decision about names, not about what a person had installed. deb-multimedia's `libmlt7-perl` and `libmlt7-ruby3.3` depend on its `libmlt-7-7`, which the pins keep out, so the person lost them (Daniel, 2026-10-08: "do not remove functionality!"). Ours is the one we offer (Daniel, 2026-11-02), so the edition's MLT builds the same bindings and the person asks for ours.

1. Find who builds it. MLT 7.40's `src/swig/CMakeLists.txt` has `SWIG_PERL` and `SWIG_RUBY` (and `SWIG_PYTHON`, which Debian's mlt already builds). Debian's mlt packages Python only; deb-multimedia's `mlt7-dmo` 7.42.0-dmo1 passes `-DSWIG_PERL=ON -DSWIG_PYTHON=ON -DSWIG_RUBY=ON`, installs Perl to `usr/lib/${DEB_HOST_MULTIARCH}/perl5/5.42` and moves Ruby's `mlt.so` into `RbConfig::CONFIG["archdir"]` (credited: Christian Marillat's packaging shows the shape). Forky has Ruby 3.3 only (`ruby3.3-dev`), Perl 5.42.
2. Name it so that no archive has the name: `libmlt-perl` and `libmlt-ruby` (Debian forky and deb-multimedia forky have neither; check with `apt-cache search` in a rig with both). Each `Conflicts:` and `Replaces:` the other archive's package, because a shared file without Replaces makes dpkg refuse the unpack, and a Conflicts makes apt do the swap. Depends on `libmlt7 (= ${binary:Version})` and `libmlt++7 (= ...)`: the binding loads our libmlt, never the other archive's.
3. Put the pair in `NOT_SHADOWS` with the reason when `find-shadowing.py` lists the shared file (Perl: `mlt.pm` and `auto/mlt/mlt.so`; Ruby shares none, so it is not listed). Run it over the published Contents plus the new packages' file lists: exit 1 with the 458 list, 0 with the new one.
4. Build the next source from the published `+lc1` source with `repo/lc-successor.py --in-place --overlay DIR --next VERSION --item TEXT`, the overlay holding the changed `control`, `rules` and the two `.install` files (`packages/mlt-bindings/edit-source.sh` makes them from the unpacked published `debian/`), then `release/build-from-lc-dsc.sh` with the link and start gate. `transition-rebuilds` (plain-from-lc.py) does not fit a source whose `Build-Depends` has our own dependency before the Lean ones (mlt's `libmedia-gpu-route-dev`): it stops with "the lc1 build dependencies are not where debian_prepare puts them".
5. Prove it in the systemd rig (`tests/shadowed/bindings.sh`): a machine of today with `libmlt7-perl` and `libmlt7-ruby3.3` (they take our `libmlt7` out), the upgrade (the unit leaves `libmlt-7-7` and the engine names `libmlt7-perl` as what needs it), `apt-get install libmlt-perl libmlt-ruby` (Remv of both and of `libmlt-7-7`, Inst of ours), then the unit settles the rest; `perl -Mmlt` and `ruby -rmlt` load `libmlt-7.so.7.40.0` owned by `libmlt7` (read `/proc/self/maps`), and build a 1280x720 profile; `apt-get -s install libmlt7-perl` fails.

Traps:

- Symptom: the Perl module is not found with `perl -MMlt`. Cause: the swig module is named `mlt` (`%module mlt`), lowercase: `use mlt;`. Ruby: `require 'mlt'`.
- Symptom: Ruby cannot load `mlt`. Cause: upstream installs `mlt.so` to `${libdir}/ruby/vendor_ruby/`, which is not on Ruby's load path (`vendor_ruby/3.3.0` is). Fix: move it in `override_dh_install` to `RbConfig::CONFIG["vendorarchdir"]`.
- Symptom: the link gate says `libmlt7 ... Depends libmedia-gpu-route0 (>= 0.2.2) but none of the choices are installable`, after a clean compile. Cause: the gate's archive configuration (`sources.json`) names only public archives; our own dependencies come from the published tree. Fix: add `{"uri": "file:/repo", "suite": "mashtabba", "components": ["main"], "keyring": "/archive/keyrings/sparky-stereo-repo.gpg"}` (the tree's `sparky-stereo-repo.asc` without its armour: base64 between the blank line and the `=XXXX` checksum line) and mount the tree at `/repo`, as `build-from-lc-dsc.sh` does. The compile takes 20 minutes, so read `sources.json` for `file:/repo` first.
- Symptom: `build.sh` is refused for an uncommitted recipe ("no commit names its date"). Fix: commit the recipe first; the source's date is its commit's.
- Symptom: lane containers carry no lane prefix. Fix: `SPARKY_CONTAINER_PREFIX=lane` (build-from-lc-dsc.sh, mlt-bindings/build.sh).
- libpostproc: FFmpeg 8 dropped it, so our FFmpeg 9 has none and Debian forky has no `libpostproc*` package. Only deb-multimedia's ffmpeg-6-dmo has it: `libpostproc57` (runtime, still installable, used by its `libavfilter9` and `kodi`) and `libpostproc-6-dev`, which Depends on the `libav*-6-dev` set the pins keep out, so it cannot be installed. Nothing in Debian uses it; a person loses only the headers for building against FFmpeg 6.1. Found by reading `Depends`, `Recommends`, `Suggests` and `Build-Depends` of every package of deb-multimedia's `Packages.xz` for `postproc`, and `apt-get -s install` for the four names.
