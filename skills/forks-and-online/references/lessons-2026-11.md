# forks-and-online: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Moving build machinery out of a driver repository: back up first (mirror, old .git, uncommitted diff, tar, private originals), re-point briefs, keep symlinks only in the private build tree; a pre-commit hook refusing evidence/, captures/, REPORT*.md and never-named files; lanes clone and hand back patches, never workspace symlinks (lane machinery-placement-196)
- Find work that exists only locally: `git fetch` the fork heads into refs/forkcheck/*, then `git rev-list --branches --not --remotes --glob='refs/forkcheck/*'`; match each commit to the build repo's patch files with `git patch-id --stable`, then by subject for context-changed ones, then by content search for folded ones; for a kernel fork `gh api compare`, a 404 means the commit is absent; save patches of what is not online; `git status -uall` for uncommitted state. (lane k3d-parked-trees-381)

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: published boot packages (sparky-stereo-boot 0.1.4, grub-l10n 0.1.1 and 0.1.2) are missing from the build main. Cause: the lane branch was never merged, so later work built on a tree without them. Fix: merge the accepted commit and audit that every published package's source exists on main. (lane boot-no-fallbacks-345)
- Symptom: `git push` of asked work from a lane is refused by the auto-mode classifier ("Create Public Surface"). Cause: no scoped allow entry. Fix: add a scoped allow entry for pushes of existing branches to the edition's own forks, and have the main session run the listed fast-forward pushes. A failed fetch leaves `tmp_pack_*` files in objects/pack (harmless litter). Found by: the refusal text. (lane k3d-parked-trees-381)

## Tracing work left in a build folder (ORDER 617, 2026-11-16)

Cases met while tracing the clones the lane cleaner skipped, each with how the verdict was told apart. Read-only on the build folder: status, log, cherry, diff, stash list, remote -v, for-each-ref, show only; never fetch, checkout or write.

- Read-only check that something is on no pushed branch, without fetching and without touching the tree: `cat .git/packed-refs` plus `git for-each-ref refs/remotes refs/heads` (for-each-ref shows loose refs the packed file hides), `git rev-list --all --not --remotes` for commits on no known remote ref, `git stash list`, `git status --porcelain`. Proof of "on the remote" is then the fork's remote-tracking ref in that same listing, or the edition build repository's main holding the same content.
- **Patch-id match in main**: a skills-lesson commit is small and merges fast-forward; if the file's final form in main equals the commit's content, `git diff C^ C | git patch-id --stable` matches the patch-id list built from main's own history (`git log main | git patch-id --stable`). A match means in main by content. Told apart from "different commit, same subject" by never comparing subjects.
- **Literal ancestor**: the lane branch's commits are on main's history unchanged: `git merge-base --is-ancestor C main` (or main's tip containing C directly). Proof is a main merge commit whose second parent is the lane tip. Verdict: in main. (564's red-tree: lane tip 47418e4a is a main merge commit itself.)
- **Stale cached remote ref**: a partial clone's `refs/remotes/up/...` can sit at an older pushed head while the ledger (ORDER.md lines) records later pushes with head hashes, force-lease notes and the review bot's approval of that head (the bot reviews only what is pushed). Never fetch to check; the ledger lines are the proof that the "on no remote" list is stale. Verdict: delivered another way, with the ORDER lines cited. (w534: cached up ref cf147ad5cd, ledger proves rounds 6/7 pushed cc22e38774 and 899d993c05, bot approved review 12288.)
- **Published debian tarball as the landing place**: `tar -tf pool/main/.../*.debian.tar.xz` lists the patch numbers; each patch's `From:` line carries the lane commit hash, so a hash match proves the commit is in the published source package. When the `From` line names a regenerated hash, match by subject and diffstat instead. (kwin-487b s54-0001/0002; xwayland stereo3d5 0010/0011/0012 with From be427982/105b8392/cb98f931.)
- **Rebased-generation comparison when From lines were zeroed or rebased**: pair the clone commits with the fork's branch by identical subject, then compare each pair's sorted +/- line sets (`git show A | grep '^[+-]' | grep -v '^[+-][+-]' | sort` vs same for B). MATCH pairs are verbatim; DIFF pairs with zero clone-only lines mean the fork commit adds what the clone's later fix commits had (the fork is the newer generation), so clone-only content is carried. (ffmpeg-depth-as-3d: 28 MATCH / 7 DIFF, all DIFFs explained.)
- **Sparse/partial-checkout phantom deletions**: thousands of ` D` lines in `git status --porcelain` where every file still exists at the path mean the checkout was sparse/partial, not real work. Tell apart by `git ls-files --deleted | head` against `test -e` and by `git config extensions.worktreeConfig`/`core.sparseCheckout`. Verdict: no uncommitted work; the folder is scratch once branches match the remote. (waterfox locales.)
- **Binary-only modifications are build leftovers**: a ` M` entry on a built object (bin/linux64/libopenvr_api.so) with no source change and no local commit means a build script overwrote the shipped binary. Verdict: scratch, nothing to land. (openvr 478m1.)
- **Bench-only branch**: an extra branch whose only commits are benchmark tooling for reproducing the work, while the work commits themselves match main, is kept as the lane's evidence but needs no landing. Verdict: the work is in main; the branch is the partner's harness. (linux depth-as-3d k-bench 7c78e57572.)
- **Lane bundle as delivery proof**: when the lane handed a bundle back, `git bundle list-heads LANE/evidence/NAME.bundle` printing the lane head's hash proves the lane said the work is handed; combine with the lane REPORT's "accepted" line. The commit not being on any pushed ref is then fine by design. (dxr 478m2: bundle holds 61a22f97c.)
- **Uncommitted draft superseded by a reworded landing**: an uncommitted CHANGELOG draft in the clone whose lines do not appear verbatim in main's file but whose substance (package name, dependency, ORDER number and version) ships in a later released version is "delivered another way": grep main's file for the subject matter, then check the published deb's control (`dpkg-deb -I` Depends) for the dependency. (live-edid-245 meta 20261106.1/20261107.)
- **The same work asked again under a new number**: the clone's branch is named for a later re-issue of an order whose first landing is already accepted; the later lane's REPORT says already done. Trace both ORDER lines and cite both. (qt-csd-stereo order112; gpu-route-says-467.)


## Nested clones inside a lane folder (ORDER 617b, 2026-11-16)

The first trace listed one clone per folder; the folders held more. Each case below says how it was told apart and the command that told it. Same rules: read commands in the traced folder, anything that needs objects goes into a bare clone of your own (`git init --bare`, then `git fetch /literal/path '+refs/heads/*:refs/heads/*'`), bundles and diffs go to the lane's kept/ only. A network read (`git ls-remote URL`, a bare `git clone --filter=blob:none URL` into scratch) is allowed and is stronger proof than any cached remote ref.

- **Find every repository first**: `find ROOT -xdev -maxdepth 5 -name .git -not -path 'ROOT/.git'` lists files and directories alike. A lane folder named in a brief as "the root repository" may not be one: `git rev-parse --is-inside-work-tree` says "not a git repository" and `ls -la ROOT/.git` shows an empty directory (no HEAD, no objects), a stub (the lane's sandbox hides `.git` at a folder's top; that is a reading, not tested); another root had no `.git` at all. Then the clones are the folders `find` listed, and the root's loose files are scratch (build objects, APKs, logs) to be named, not traced. (stereodroid-sensors-382, flat-headset-no-fallbacks-346e, depth-as-3d-source.)
- **A `.git` that is a file is a linked worktree**: `cat CLONE/.git` shows `gitdir: ...` and `git worktree list` run inside it names the repository that really holds the objects, often in another lane folder, and `git branch -vv` marks that repository's checked-out branch with `+`. Its "origin is a local path" and its 41 "commits on no remote" are the other folder's. Tell it from a real clone by `ls -l CLONE/.git` (a one-line file, not a directory) and by `rev-list --count --all` (the whole history of the other repository). Prove the commits online by hash, not by the cached ref: `git ls-remote URL refs/heads/BRANCH` equal to the local branch tip means every ancestor is on the remote, and `git merge-base --is-ancestor DETACHED_HEAD TIP` covers a detached merge commit on top. (depth-as-3d-source/ffmpeg-base: code.ffmpeg.org depth-3d-source 9d4a2882, the same hash.)
- **A shallow clone whose history counts as "on no remote"**: `git rev-list HEAD --not --remotes` printed 2292 commits for a dependency checked out at a pinned commit. `git rev-parse --is-shallow-repository` said true and `.git/shallow` named only the tip of the remote branch: the clone was made at depth 1 and the pinned commit fetched by its hash, so its full history sits beside a one-commit remote ref and no remote ref contains it. Tell apart from real work with the upstream itself: `git clone --bare --filter=blob:none URL scratch.git`, `git merge-base --is-ancestor PINNED scratch.git/refs/heads/main`, and `diff <(git rev-list HEAD | sort) <(git -C scratch.git rev-list PINNED | sort)` empty, plus a clean `git diff --quiet HEAD`. Verdict scratch, nothing to bundle. (pupnp 79fc9f5d; ci-utilities and repo-metadata in kde-ci, both ancestors of upstream master.)
- **A dependency patched in place**: ` M` and `??` files in a checkout of someone else's SDK at a pinned tag. The project ships its change as a patch, so compare content, not history: `git archive HEAD | tar -x -C scratch/x`, `git apply` the shipped patch there, then `git hash-object` each of the patch's paths on both sides. Same hashes for all of them, and the same files absent where the patch deletes, mean the working tree is the shipped patch and nothing else; untracked files are covered because the patch creates them. Find the patch by the pin in the project's BUILDING.md and by `git ls-tree -r --name-only origin/main DIR | grep patches`; find the ORDER line by what the change does (here "play-services-vision replaced by ZXing": item 149). (deps/cardboard v1.35.0, 11 paths, all equal to flat-headset android/cardboard-viewer/patches/cardboard-zxing.patch.)
- **`git patch-id` prints nothing for a plain unified diff**: patch files written with `diff -u` and only `---`/`+++` headers (no `diff --git`) give an empty id, so a comparison by patch-id reports "no match" for them without any error. Count the ids before trusting a miss (`wc -l` of the output against the number of files); 9 of 22 patch files had an id and 13 did not. For those compare the sorted +/- line set (`grep '^[+-]' | grep -v '^[+-][+-]' | sort`), and say which method matched each.
- **A series squashed into one patch on a newer base**: a clone of 28 commits (two upstream snapshots, 22 patches, a rebased trio and a merge) against a project that later kept one patch named after the combined change. Do not compare commit by commit. Check out the clone's snapshot of the new base in a scratch work tree (`git --git-dir=scratch.git --work-tree=wt checkout COMMIT -- .`), `git apply` the project's patch, and `diff -rq` against a second work tree at the clone's tip: the only file that differed was the uncommitted one, and `git hash-object` of the clone's working file equalled the `index OLD..NEW` blob of a later commit of the project that says what it fixed ("a duplicate disconnect button introduced during rebasing"). Prove the snapshot commits are upstream's own with `git rev-parse COMMIT:path` for every path in a clone that has the upstream (3085 of 3085 equal). (pin-rebase in stereodroid-sensors-382, tip 193bf35 and floating_toolbar.xml.)
- **Shipped strings are the package's files, not its patches**: comparing uncommitted `.ftl` files with the recipe's patches reported 11 keys per language "only here", because the patches add only what the base lacks and the orig tarball already carried the rest. The shipped state is in the built deb: `dpkg-deb --fsys-tarfile DEB | tar -x -C scratch ./usr/lib/PROGRAM/browser/omni.ja`, then Python's `zipfile` reads `localization/LOCALE/browser/FILE.ftl`. Compare message by message (key, then the whole block with its attributes) the keys the working tree changed against the l10n repository's HEAD (`git show HEAD:FILE`). Three counts tell the cases apart: same text (delivered), present with other text (a superseded wording), absent (found). Here 0 absent, one key with older wording in 8 languages. A "brand rename" in the working tree was byte-equal in the shipped file too, so it was not kept out as an earlier trace had read it. (waterfox-stereo locales.)
- **A recount can come out lower than the brief**: "one changed file" in ci-utilities was not there. Read `git status --porcelain`, `git diff --stat`, `git ls-files -v | grep -v '^H'` (assume-unchanged and skip-worktree flags) and `git status --ignored` before writing a count; an untracked nested repository shows as a single `??` line and is a clone of its own to trace. Say in the report that the earlier figure is not reproduced.
- **A downloaded SDK folder with a `.keep` that names a condition**: nothing in it can be unique when every file was written on the install day. `find SDK -xdev -type f -printf '%TY-%Tm-%Td\n' | sort | uniq -c` showed 27,884 files on one day and 139 at zip's epoch (2009-12-31); `find SDK -newermt 'INSTALL DAY +30 min'` listed only directories. The package list is in the `package.xml` files (`path`, `revision`, `display-name`); look for what cannot be fetched again by name only (`-iname '*.keystore' -o -iname '*.jks' -o -iname 'local.properties' -o -iname '*.avd'`, an empty `avds/`), never print them. The condition in `.keep` is checked where it lives: `curl -s https://api.github.com/repos/OWNER/REPO/pulls/N` says `merged` and when. (android-sdk-346e: 13.3 GB, all re-downloadable, PR 14003 merged 2026-11-04.)

## The branch hook's first day (ORDER 612c, 2026-11-16)

Four gaps of [branch-keeper](../../../hooks/branch-keeper/README.md) met in its first day of real use; each now has a test that failed before its fix.

- **Symptom:** `git push origin --delete BRANCH` was refused ("not inside origin/main ... has no superseded row") for two old branches whose one commit `git cherry origin/main origin/BRANCH` shows with `-`, while `git branch -D` of the same work passed.
  **Cause:** the rule "in main by content needs no row" was written for the local deletion only; the remote deletion (`git push --delete`, `:BRANCH`, `--mirror`, `gh api -X DELETE`) knew only ancestry and the register.
  **Fix:** the remote deletion asks `git cherry` too and passes with one line when no `+` line is left; a `kept` row still refuses, and a branch with one change main lacks still needs its `superseded` row.
  **How found:** the cleanup of one repository on 2026-11-16, where two such deletions needed rows that said nothing more than the cherry did.
- **Symptom:** after a trace proved, clone by clone, that every local commit and every uncommitted file of 18 lane clones was in main, delivered another way, superseded or scratch, `rm -r` of those folders was still refused; commits could be bundled, uncommitted and untracked files never.
  **Cause:** the hook had one way to accept work on no remote (a bundle) and none for a verdict reached by reading.
  **Fix:** the clones register (`private/clones.tsv`: folder, verdict, proof, date of the trace). A row for the clone's own folder, with one of the four verdicts and a proof, lets it go with a line that quotes the row; a row for a folder around clones covers none of them; the row stops counting when a commit only that clone holds, a local branch, `HEAD`, a stash, their logs or an uncommitted file is newer than its date, and the refusal names what changed. `hook.py audit` lists the rows and which no longer count.
  **How found:** the trace's own hand-back, which ended with the folders proved disposable and no command that could remove them.
- **Symptom:** a long line, `cd /A/repo ... && git push ...; ... gh pr create --body "multi-line text"; ...; git branch -D BR; cd /A && PROGRAM; cd /B`, was refused with "the repository at /A could not be read" for the push and the deletion, which ran after `cd /A/repo`; short lines with `cd X &&` passed.
  **Cause:** the hook read one folder for the whole line: the first `cd DIR` in its text followed directly by `&&`, `;` or a line end. A first `cd` written another way (`|| exit 1`, a redirection, `--`, `-P`, inside `if` or braces, `pushd`) was skipped, so a later `cd /A &&` or a line of the quoted body that starts with `cd X &&` became every command's folder; a second `cd` into another clone was never followed, so a deletion there was judged in the first clone and passed unseen.
  **Fix:** each command is read in the folder its own line gives it, `cd`, `pushd` and `popd` followed as bash scopes them, git's `-C` options after; quoted text is never a `cd` ([development-hooks, the lesson](../../development-hooks/references/lessons-2026-11.md)).
  **How found:** the queue's copy of the line, run through the old reader, gave the right folder; the first `cd` was the variable, and twelve forms of it showed nine skipped; the red test then named "/", from `cd / && make` inside the quoted body. The refusal log keeps 200 characters of a line, so the original first `cd` itself was not seen.
- **Symptom:** `for r in a b; do git -C /X/$r push ...; done` and `git -C $R branch -D B` were refused or told as "could not be read (no such folder)"; `git branch -D $B`, `git stash drop $S` and `git worktree remove $WT` passed without a word.
  **Cause:** the hook read `$R` as a folder named `$R`, and looked a branch, a stash or a worktree named `$B` up, found none and let it through.
  **Fix:** a folder, branch, stash, remote or worktree written with a variable or a substitution is said as such: a deletion is refused ("name it literally, one command per repository"), a push or a new branch gets a line of context, a worktree to remove follows `on_unresolved_path` as `rm -r` does. So write deletions with literal folders and names, one line per clone.
  **How found:** the refusals of 2026-11-16 in a loop over clones, then a test of each place a name can stand.
