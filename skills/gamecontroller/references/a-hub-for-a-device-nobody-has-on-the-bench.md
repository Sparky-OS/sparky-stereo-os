# A Hub for a device nobody has on the bench

The Foottroller Hub separates one joystick reader from its two outputs. Read the maker's code first. A published Linux input reader can establish a useful mapping even when it feeds a different application.

## Working recipe

1. Find the maker's setup instructions, its public integration sources and prior implementations. Pin the revisions and compare input and output interfaces separately. For the Crampon, the maker's IsaacTeleop plugin describes six numbered axes and four buttons in Linux joystick Dev mode. The public Unity client describes the Hub datagrams. Write down any disagreements before setting a default. [Maker setup](https://foottroller.com/instructions) · [IsaacTeleop joystick plugin](https://github.com/smoothmover/IsaacTeleop-Foottroller/blob/f447a3f2f16ff34b996b362c8b4efc0d4fb7f288/src/plugins/foottroller/README.md) · [Unity client](https://github.com/smoothmover/foottrollersupport/blob/f9182997b60b5012ca2b0dd50bb66221bc9b89b8/Unity/FoottrollerNet.cs)
2. Record the actual input ABI for the chosen Linux interface. The Crampon path uses the kernel's joystick interface. Build an eight-byte record fixture with time, signed value, type and ordinal. Supply the initial axis and button records before movement. Use a pipe to hold the device present while a client connects and to let the test choose when it moves or disconnects. [Kernel joystick API, Initialization and Event Reading](https://docs.kernel.org/input/joydev/joystick-api.html#initialization)
3. Run the Hub and both observers in one container with no network and no input devices passed through. Give the game client separate adjacent UDP sockets. Check the handshake reaches its receive socket and decode the state against the real client formula and the earlier independent decoder. Check that a heartbeat extends a registered peer and expiry releases a client that sends none.
4. Intercept the producer's `open`, `ioctl`, `write` and `close` at libc. Record the gamepad axes, button capabilities, ranges, creation, the event batches and destruction. Compare every line to the expected sequence. A gamepad stick emits `ABS_X` and `ABS_Y`, the action pad uses positional `BTN_*` codes, and `SYN_REPORT` completes each batch. [Kernel gamepad, Detection, Action Pad and Analog Sticks](https://docs.kernel.org/input/gamepad.html#detection) · [uinput, Interface and Examples](https://docs.kernel.org/input/uinput.html#interface)
5. Run the same Hub with an absent input, a two-axis fixture, a partial record, an occupied socket and a refused create call. It should say what failed and how to proceed, leave no running output, and return an error. Send malformed datagrams from a second client and check neither of its ports receives a reply.
6. Save a real-kernel test for the bench machine. Use the uinput sysname to pick the exact event node. Start evtest and the KDE Game Controller page before sending motion. Match motion, button state and release, then check that closing the input removes the virtual device.

The fixture and independent UDP test are in the [Foottroller Hub recipe](https://github.com/Sparky-OS/sparky-stereo-os-build/tree/main/sparky-os/packages/foottroller-hub) and the [maker's public parser](https://github.com/smoothmover/foottrollersupport/blob/f9182997b60b5012ca2b0dd50bb66221bc9b89b8/Unity/FoottrollerNet.cs). The Hub test reads the earlier lane's Python decoder as a second oracle.

## Traps

- **Symptom:** replying to the discovery sender never connects the Unity client. **Cause:** the client listens on the source port plus one. **Fix:** return the handshake and state to the adjacent port, and keep heartbeat leases keyed to it. **Found by:** reading `init`, `reinit` and `ReceiveData` and testing actual UDP sockets with a distinct sending socket.
- **Symptom:** a standard-mode fixture can begin with motion and appear usable. **Cause:** motion on two axes alone says nothing about Dev mode controls. **Fix:** check the physical joystick's axis and button counts and require all mapped controls in its initial records. **Found by:** a two-axis-only replay returning the Dev mode diagnostic before either output starts. Firmware that advertises identical controls in both modes still needs device evidence.
- **Symptom:** a fixture with a half-written record can report false input if the next read starts at the wrong offset. **Cause:** a pipe can split an eight-byte joystick record. **Fix:** accumulate bytes and treat end of input mid-record as an error. **Found by:** splitting a valid record across two writes and separately ending a replay after three bytes.
- **Symptom:** a virtual controller from a container appears in the operator's session. **Cause:** uinput creates a device in the running kernel. **Fix:** check system calls in an isolated container with no real input nodes. Use a bench machine or a guest with its own kernel for real readback. **Found by:** reading the kernel uinput introduction and the [edition's previous uinput isolation finding](../../native-linux/references/3d-mouse-libspnav.md#traps).
- **Symptom:** foot heading or tilt may come from the wrong foot on a Crampon. **Cause:** the maker's knowledge base names HID-side axes while the maker's Linux code numbers joystick ordinals. **Fix:** keep both statements, ship the Linux ordinal mapping, and make each axis ordinal, sign and dead zone visible in settings. **Found by:** comparing the [knowledge base](https://foottrollerlabs.com/foottroller-knowledge-base.html) with the pinned Linux plugin and measuring a swapped-pair replay.

## What remains unproved

The synthetic records establish the Hub's interpretation of a declared input shape. The first real Crampon needs a capture of its identity, modes and initial events, one marked movement per physical axis and one press per button. The real kernel gamepad and KDE readback need the bench run. Game-engine runtime and SteamVR/Monado integration are independent checks.
