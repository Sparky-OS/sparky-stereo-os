# More than 80 buttons: EV_BTN, SDL and Wine

Written on 2026-11-06 (ORDER 15, milestone 1). Symptom first, then the recipe, then the traps.

## Why a joystick stops at 80 buttons

Symptom: a throttle, wheel or button box with 128 buttons shows 80 in `evtest`, SDL and Wine, and the last 48 do nothing.
Cause: `hid-input` gives every Button-page usage a key code (`BTN_JOYSTICK` up to `BTN_DEAD`, then `BTN_TRIGGER_HAPPY`) and the codes stop at `KEY_MAX` (0x2ff in Linux 7.3), which is 80 buttons.
Raising `KEY_MAX` moves the wall and grows every bitmap that userspace reads.
Tomasz Pakuła's "Input: New EV_BTN event for generic buttons" (RFC, linux-input and LKML, 2026-01-04) adds event type 6, `EV_BTN`, whose code is the HID button number starting at 1 and whose value is the state.
It has no ceiling at `KEY_MAX` (the series caps a device at `INPUT_MAX_BUTTONS`, 2048), joysticks keep their `EV_KEY` codes beside it, and `EVIOCGBTNCNT` returns the button count.
Others addressed the same wall differently and are not carried: Ivan Gorinov (2025-12-20, 112 codes) and Ricardo Esteves (2026-02-09, `KEY_MAX` to 0x31d).

## Find the newest version of a kernel series

1. The author's own archive is the first stop: `ratatoskr.run/linux-input/author/<Name>` lists every message of a person, newest first, and a thread page carries the whole thread as JSON-LD (replies included).
2. For the raw text of a patch use `lkml.iu.edu/<yymm>.<n>/<number>.html`: lines end in `<br>`, tabs are kept, addresses are masked as `xxxxxxxxx` (put the real domain back).
3. Compare with mainline by reading `include/uapi/linux/input-event-codes.h` from `raw.githubusercontent.com/torvalds/linux/master`.
4. The author's fork branch is not the posted series: Pakuła's `ev-btn` branch was an earlier draft (field `num_buttons` where the posted patches say `button_count`, and no `EVIOCGBTNCNT` commit).

## Carry an input series in the edition's kernel and check it builds, without a full build

1. Make the group `kernel/series/NN-name/` in the build repository: one file per posted patch, headers `From:` (the author), `Date:`, `Subject:`, his message and Signed-off-by untouched, then a bracketed note (link, review state, "drop this group when ..."), our `Assisted-by:` trailer, then `---` and the diff.
2. List it once, with a status comment, at the end of `series.txt`: every flavour applies that list, and the v3 and rt lists only add flavour patches (a second entry in a flavour list would apply the group twice and fail).
3. The published source package's `.orig.tar.xz` already holds the series applied (it is the retained, patched tree), so extract it and apply only the new group: `SKIP='^(0[0-9]|[123][0-9]|4[0-3]|90)-' sh apply-series.sh TREE FLAVOUR` (adjust the numbers) ends with "6 patch files applied"; `git apply` has no fuzz, so this is strict. Do it for base, v3 and rt, each from its own tarball, and compare the sha256 of the touched files.
4. Reverse the group (`git apply -R`, last patch first), check the file hashes are back to the original, apply again: proves the committed files, not only the first run.
5. Configure with the recipe, out of tree, with the tree mounted read-only: `sh kernel/configure.sh FLAVOUR /obj` (ends "102 of 102 requested values hold"), `make O=/obj -j4 modules_prepare` (about 50 s), then `make O=/obj -j4 W=1 drivers/input/ drivers/hid/` (about 80 s, 347 objects, writes the `.o` files and no `.ko`). Expect no warning in the touched files. The image needs the build tools and, because the configuration has `CONFIG_RUST=y`, rustc, rust-src, bindgen and libclang.
6. Prove the objects carry the change: `objdump -d drivers/input/evdev.o | grep 0x8004451c` finds the `EVIOCGBTNCNT` compare.
7. Prove the headers with a negative control: a C file with `_Static_assert(EV_BTN == 0x06)` and `EVIOCGBTNCNT` fails to compile against the container's stock `linux-libc-dev` headers and passes against `make O=/obj headers_install INSTALL_HDR_PATH=...`.

## SDL and Wine

- SDL: pull request 14758 (Pakuła, open draft, two commits, 2026-01-04) touches `src/core/linux/SDL_evdev_capabilities.c`, `src/joystick/linux/SDL_sysjoystick.c` and `SDL_sysjoystick_c.h`; the diff applies strictly to SDL 3.4.18. Debian's `libsdl2-2.0-0` is `sdl2-compat` on top of SDL3, so one SDL3 patch serves SDL2 programs too.
- Wine: merge request 9853 (draft, two patches to `dlls/winebus.sys/bus_udev.c`, `has_conflicts`) is written against Wine master. It does not apply to Wine 10.0 (the `lnxev_info` structure and the button loop it edits are not there; 5 of 6 hunks are rejected), so a Wine 10.0 package needs a port of the idea to the older `lnxev` code, credited to him.
- The kernel part is the one that decides: both consumers fall back to `EV_KEY` on a kernel without `EV_BTN`, so they can ship first.

## Traps

- Symptom: a fetch returns HTTP 200 and a page titled "Making sure you're not a bot!". Cause: Anubis, a bot check, on lore.kernel.org, git.kernel.org, patchwork.kernel.org and, for browser-like user agents, gitlab.winehq.org. Fix: do not solve it; use the mirrors above, and for gitlab.winehq.org a plain `curl` (default user agent) to `/-/merge_requests/N.patch` and `/api/v4/projects/wine%2Fwine/merge_requests/N`. Found by: `head -c 300` of the body.
- Symptom: the ratatoskr month pages answer 429 after a few requests. Cause: rate limit. Fix: query the author page once and the thread JSON once; do not loop over months.
- Symptom: `git apply --check` of patch 5 alone fails ("patch failed: drivers/hid/hid-input.c:770") while patches 1 to 4 pass alone. Cause: patch 5 re-indents the switch that patch 4 rewrites, so its context exists only after patch 4. Fix: check a series in order on a copy (apply, then reverse), never patch by patch on the pristine tree. Found by: the checks of the six files in a loop.

## Prove it at runtime without a full kernel build (milestone 2)

Recipe, all in containers and one QEMU guest, nothing on the host's input devices:
1. Reduced kernel from the same tree: `make tinyconfig`, merge a fragment (64BIT, SMP, TTY, SERIAL_8250_CONSOLE, PCI, VIRTIO_PCI, NET, INET, NET_9P_VIRTIO, 9P_FS, DEVTMPFS, TMPFS, PROC_FS, SYSFS, BINFMT_ELF, BINFMT_SCRIPT, UNIX, INOTIFY_USER, EPOLL, EVENTFD, TIMERFD, SIGNALFD, INPUT, INPUT_EVDEV, HID, HID_GENERIC, HIDRAW, UHID, MAGIC_SYSRQ), `olddefconfig`, check the options are `=y`, `make bzImage`: about 3 minutes on four CPUs, a 1.9 MB image. Build it twice from the same tree, once without the new group (the control) and once with it.
2. Guest userland without a disk image: `docker export` of a Debian container that has python3, libsdl3-0 and libsdl2-2.0-0 (sdl2-compat), extracted to a directory and served to the guest as its root over virtio-9p (`-virtfs local,path=ROOT,mount_tag=r,security_model=none,readonly=on` and `root=r rootfstype=9p rootflags=trans=virtio,version=9p2000.L`). Create empty `/out` `/run` `/tmp` in it first. A second 9p share, `out`, is the only writable place and carries the plan script and the results.
3. QEMU runs in a container with the host's `/usr` mounted read-only, `--device /dev/kvm --group-add <kvm gid>`, `-machine pc,accel=kvm -nographic -no-reboot -nic none -serial file:...`; the guest's `/init` mounts proc, sys, devtmpfs and the 9p shares, runs the plan and exits, and `panic=1` ends QEMU. Boot to result: about 10 seconds.
4. Libraries under test sit in `/opt/NAME/libSDL3.so.0` and a run picks one with `LD_LIBRARY_PATH`; sdl2-compat finds the same libSDL3, so SDL2 programs are tested by the same switch.
5. Matrix, each cell one boot: control kernel and new kernel, each with the unpatched and the patched SDL. Expect: control kernel `EVIOCGBTNCNT` errno 22 and no EV_BTN in the event types; new kernel 128 and `I: BTN=128`, 128 EV_BTN events one button at a time and 80 EV_KEY events; SDL3 and SDL2 report 128 buttons only with the new kernel and the patched SDL (79 in every other cell, the 80th is lost by SDL's `i < KEY_MAX` loop).
6. Build SDL for the test with cmake only (`-DSDL_UNIX_CONSOLE_BUILD=ON -DSDL_TESTS=OFF`, the two Debian patches applied by `patch -p1 -F0` first): two minutes, and a control build without the new patches from the same tree.

Traps met in the runtime proof:
- Symptom: SDL with the pull request reports 79 buttons on a kernel that offers 128, and the new log line says the kernel has no EV_BTN. Cause: the pull request falls back to `#define EVIOCGBTNCNT 0` when the build headers lack EV_BTN, and `ioctl(fd, 0, ...)` always fails, so every library built before the kernel headers carry EV_BTN never uses it. Fix: define the ioctl as `_IOR('E', 0x1c, unsigned int)` when the fallback is 0 (debian patch 0003 of libsdl3). Found by: the matrix, patched SDL on the new kernel.
- Symptom: pressing all 128 buttons at once gives 44 EV_BTN events and one SYN_DROPPED, and SDL then shows 24 buttons held. Cause: `input_estimate_events_per_packet()` counts 7 events for all keys and evdev sizes the client buffer from it (8 packets, rounded to a power of two), so one report that changes 128 buttons (EV_BTN + EV_KEY + MSC_SCAN) overflows it; SDL's EV_BTN path cannot resync because it skips `EVIOCGKEY` for EV_BTN devices. Fix: add `button_count` to the estimate (group 44, 0007); with it the same boot gives 128 of 128 EV_BTN events, no SYN_DROPPED, 128 held in SDL3 and SDL2. Found by: a held-together case, all buttons down in one report, in the same guest run.
- Symptom: a client that opens the device while buttons are held sees none above 80. Cause: `EVIOCGKEY` only knows EV_KEY and there is no way to read EV_BTN state (Ivan Gorinov, 2026-01-07). Found by: opening a second client with buttons 1, 5, 100 and 128 held.
- Symptom: QEMU container cannot reach Docker half way through a session (`Cannot connect to the Docker daemon`). Cause: the lane's proxy process ended while the socket file stayed. Fix: the main session restarts the proxy; keep the evidence and the scripts on disk so a run can resume.

Also checked: a 40-button device on the control kernel with the patched SDL prints no log line (40 buttons), so the line appears only for a device that uses the last key code. sim-rigs' `simultaneous/controller.py` runs unchanged in the guest once its VM-name asserts are removed in a copy (`SIM_LAYERS=evdev` then `sdl3`, `cd /out`, about 2 minutes each); on the fixed kernel both layers pass. Differences from the old 79/80 numbers: evdev (EV_KEY only) still tops out at 80 held; SDL3 now holds 81, 127 and 128 in one report and in the all-controls case (was 79); SDL3 sees 128 after a stalled consumer, evdev 80.

## Package the SDL3 patches and prove the package (milestone 3)

Recipe (libsdl3 `3.4.18+ds-1+stereo3d4+lc1`, recipe `sparky-os/media/libsdl3/stereo3d4` and `sparky-os/packages/libsdl3/make-plain.sh` in the build tree):
1. Put the four patches (DEP-3 headers, the pull request's two commits unchanged) and the changelog entry in the recipe folder and commit it first: the source's date is the recipe's last commit (`reproducible.py epoch`), a dirty recipe stops the build.
2. `make-plain.sh PUBLISHED.dsc WORK` unpacks the published `+lc1` source without patches, undoes Lean Code (`plain-from-lc.py --build-depends-at-end --drop-plan`, after unfolding the folded `Build-Depends` the tool cannot read and folding it back), adds the patches and the entry.
3. `release/build-dh-lean.sh WORK libsdl3-3.4.18+ds 3.4.18+ds-1+stereo3d4+lc1 REPO` projects, builds, runs the link and start gate and `check-debs` (about 25 minutes on four CPUs). It needs `SPARKY_LC_ARCHIVE_DIR` (a folder with `sources.json` and its keyrings, mounted at `/archive`), `SPARKY_LC_PREVIOUS_DIR` for the earlier builds, and the edition's repository as `REPO`.
4. Stage `amd64/`, `source/`, `SHA256SUMS` and `.keep`; check it with `LC_ALL=C sha256sum -c SHA256SUMS | grep -vc ': OK$'`.
5. Prove the package, not the cmake build: extract `libSDL3.so.0` from the staged `libsdl3-0` deb into `/opt/sdl3-new` of the guest and run the same matrix. New kernel with the package: 128 buttons in SDL3 and SDL2, all held, 0 mismatches, no log line. Control kernel: 79 and the log line. 40-button device: no line.

Traps met:
- Symptom: `override_dh_builddeb` fails after `check-debs` passed, with "archive execution requires bubblewrap and unprivileged user namespaces". Cause: the gate runs every case under bubblewrap and `build-dh-lean.sh` did not install it into the image. Fix: it installs `bubblewrap` now. Found by: the line above the make error.
- Symptom: the gate case for `libsdl3-dev` fails with "Reached two conflicting assignments ... libsdl3-0 Breaks libegl-mesa0 (< 26.1.6-1+stereo3d13~)". Cause: the gate's archive list held only Debian and its friends, and the package breaks the stock Mesa the list offered. Fix: the edition's own repository is one more source in `sources.json` (`file:///repo`, suite `mashtabba`, its dearmored key under `/archive/keyrings`). Found by: `case-*-solve.log` in the link scratch folder.
- Symptom: `plain-from-lc.py` stops with "Build-Depends does not end with the lc1 build dependencies" or "the lc1 build dependencies are not where debian_prepare puts them". Cause: the dependencies end a folded (multi-line) `Build-Depends`, which the tool reads only on one line (the FFmpeg source has the same limit). Fix: unfold, run the tool with `--build-depends-at-end`, fold Debian's text back without the six. Found by: the assertion text, then `sed -n 48,52p debian/control`.
- Symptom: `plain-from-lc.py --lc-successor` says the first entry is not an edition entry. Cause: this source's top entry is the ordinary `UNRELEASED` lc1 entry. Fix: no `--lc-successor`.
- Symptom: the Wine build-dependency solver says `libcapi20-dev (= 1:3.27-3.2+b1)` has no choices. Cause: the flat repository of Debian trixie inputs held the amd64 and i386 packages of one name; `dpkg-scanpackages` lists the last one. Fix: copy `*_all.deb` and `*_ARCH.deb` only.

Both architectures from the one source package: `release/build-from-lc-dsc.sh DSC ARCH IMAGE REPO OUT` builds one architecture of a `+lc1` source from its `.dsc` (the image of that architecture, the gate, `check-debs`); run it with `sparky-lc-migration:20261020-i386` for the i386 twin after `build-dh-lean.sh` has made the `.dsc`. Check the pair: the same version on every Multi-Arch: same binary, and `cmp` of every file under `/usr/share` (md5 lists of the extracted non-dbgsym debs): for libsdl3 stereo3d4 the 53 files are identical except dpkg-stereo's per-architecture paths and manifests (`dpkg-stereo/hr/PKG/ARCH/...` carries the same hashed files, `dpkg-stereo/lc/PKG/ARCH.json` differs by design). The arch:all `libsdl3-doc` comes from the amd64 build only (`-b`); the i386 build is `-B`. The library rebuilt from the changed patch headers is byte-identical to the first build (same sha256), so a header-only change does not move the binary.

Wine in the same guest: the DirectInput probe (`wine-rig.py`, sim-rigs) works in a 9p-root guest with the stock Wine package, Xvfb, `LD_LIBRARY_PATH` for the library under test and a fresh prefix in tmpfs (`wineboot -u` under `xvfb-run`).
- Symptom: with the evdev backend (`DisableInput=0`, `Enable SDL=0`) the probe says "synthetic controller not enumerated" and winebus logs `err:hid:set_report_from_event TODO: Process Report (26696, 65533)` with changing garbage values, even for the stock package. Cause: the guest kernel had `CONFIG_INPUT_JOYDEV=y`, so the fixture also appears as `/dev/input/js0` in the `input` subsystem; Wine 10.0's libudev path adds every `input` node that has a devnode, opens `js0` and reads it as `struct input_event` (24 bytes) while joydev sends 8-byte `js_event` records, so type and code are stack garbage. The direct path (no libudev) only takes `eventN` names. Not the cause: `CONFIG_COMPAT`/`IA32_EMULATION` (same errors with both off) and the PS/2 devices (same with `i8042` off). Fix in the guest: no joydev in the kernel fragment. Found by: the `udev_add_device ... node "/dev/input/js0"` line in the `+hid` trace, after the number of TODO lines stayed 32 in three kernel variants. Whether a real system with joydev loaded shows the same in Wine 10.0 was not tested.
- Symptom: the same probe still does not enumerate after that fix. Cause: the guest's `/run` was the read-only root (a 9p share), so the fake udev database (`/run/udev/data/c13:N` with `E:ID_INPUT_JOYSTICK=1`, needed because no udevd runs and Wine takes the device usage from those properties) was never written. Fix: `mount -t tmpfs run /run` in the guest's `/init`. The event node's number depends on the kernel (`c13:64` + the event minor, and `+input:inputN`).
- Result with the fixes (kernel with the series, evdev backend, stock Wine package): 79 buttons and one `err:hid ... TODO (6, N)` per EV_BTN event (stock Wine does not know EV_BTN); with the winebus object of the patched Wine: 128 buttons, no error line, 127 of 128 presses seen. Through the SDL bus with the packaged libsdl3: 128 buttons, 127 of 128 seen. Button 128 is missing through both backends, so it is lost above winebus (hidclass/dinput), not in the EV_BTN code.

## The Wine package, the node filter and button 128 (milestone 4)

Recipe: `sparky-os/packages/wine-stereo` (`prepare-ev-btn.py`, `build-ev-btn.sh`, three patches under `patches/`); `build-ev-btn.sh source WORK PUBLISHED.dsc` makes the one source (the published `+lc1` source, `quilt push`, one changelog entry), `build-ev-btn.sh build WORK amd64|i386 IMAGE REPO INPUTS` builds an architecture from it. About 80 minutes on four CPUs for amd64 when the machine is quiet, 3 hours under load (load average 48), then the gate (several minutes for libwine). Check `/` (30 GB floor) and `/mnt/build` (it showed 31 to 41 GB free; the tree is about 5 GB) before and during; a guard loop that stops the container below the floors is cheap.

Traps:
- Symptom: the gate stops the Wine build at `override_dh_builddeb` with "unknown archive source configuration field" after `check-debs` passed (an hour lost). Cause: the Wine source embeds an older Lean Code toolkit than the one that built libsdl3; it accepts only `uri`, `suite`, `components`, `keyring`, `check_valid_until` in `sources.json`, and the shared file had the newer `architectures` field on the CUDA entry. Fix: a `sources.json` for Wine without the CUDA entry. Found by: the one line `unknown archive source configuration field` at the end of the build log and the field list in `debian/sparky-lean-toolkit/lean/archive.py`; read that list before starting a long build.
- Symptom: the staged amd64 folder has no `.sparky-build.json`. Cause: `build-ev-btn.sh build` moved only debs, changes and buildinfo, and the record sits in the build folder that was deleted to save space. Fix: copy the record out with the debs; if lost, `lean.release check-debs` on the staged debs with `sparky_provenance_init` writes one again with the same recipe commit, image and source date (new invocation id).
- Symptom: a package extracted into the guest fails with "Library zlib1.dll not found (needed by user32.dll)". Cause: `x86_64-windows/zlib1.dll` and the i386 one are links the dependency `libz-mingw-w64` adds to libwine's directory, so a bind mount of the package's directory hides them. Fix: copy those two links from the stock install into the extracted tree; or install the package with its dependencies.
- Test of a changed Wine: bind-mount the extracted `usr/lib/x86_64-linux-gnu/wine` over the stock one and a copy of `usr/share/wine` (stock plus package) over `/usr/share/wine`, run the same probe.

Results (kernel with the EV_BTN series, no joydev; `/run` tmpfs with a udev database; packaged Wine `10.0~repack-12+stereo3d8+lc1`): evdev backend 128 buttons, 0 of 128 presses wrong, 0 error lines; SDL bus with the packaged libsdl3, 128 buttons, 0 wrong. Control kernel (no series): 79 buttons through both. Stock Wine on the series kernel: evdev 79, SDL bus 128 with button 128 lost. With joydev built in: stock Wine opens `/dev/input/js0` (452 garbage error lines), the package logs `ignoring "/dev/input/js0", name doesn't match event%u`.

Button 128: `hid_joystick_read_report()` in `dlls/dinput/joystick_hid.c` tested `usages->Usage >= 128` and logged `fixme:dinput:hid_joystick_read ignoring extraneous button 128`; the array has 128 entries (usage 1 to 128 at index 0 to 127), so the test is `> 128`. Found by: the `fixme+dinput` trace of the SDL-bus run, then reading the function; Wine master still has the line (checked 2026-11-07) and no open merge request or bug mentions it. `winebus.sys` (`hid_device_add_button_count` takes a `BYTE`, so 255 is its limit) and `hidparse` are fine for 128.

An EV_BTN device without a count: create one with `/dev/uinput` (`UI_SET_EVBIT` 6 plus a few `BTN_` keys; its `EVIOCGBTNCNT` gives 0) and start Wine with `Enable SDL` 0; winebus logs `err:hid:build_report_descriptor the device has EV_BTN but EVIOCGBTNCNT gave no button count`. The SDL bus claims a uinput device first when it is enabled.
