# Camera controls: what is a setting, the apply order and the best mode (ORDER 678 and 682, 2026-11-26)

The Camera page (`sparky-stereo-camera`, [the page](camera-page.md)) saved the camera's whole state: every control whose reading differed from its default.
On an iMac14,1 that put White Balance Temperature (inactive while automatic white balance is on, its reading moving by itself) and Iris, Relative (range 0 to 0, a movement) in the store, and every plug-in failed on both and kept two problems.
Check freshness first: written on 2026-11-26 from `sparky-stereo-camera` 0.1.3, the kernel's V4L2 documentation and uvcvideo at v7.3, PipeWire 1.6.9, WirePlumber 0.5.19 and Qt Multimedia `6.11.2-3+stereo3d16`.

## Recipe

1. **One rule decides what is a setting** (`keepRule`, `src/v4l2camera.cpp`), for the page, the command and the apply step: a control that has a range (or is a menu or a boolean), that the camera both takes and reports, and that is active when it is read.
   Every flag of `VIDIOC_QUERYCTRL`'s "Control Flags" table (`Documentation/userspace-api/media/v4l/vidioc-queryctrl.rst`) has its row:

   | Flag or kind | The clause | Saved |
   |---|---|---|
   | `V4L2_CTRL_FLAG_DISABLED` | "permanently disabled and should be ignored by the application" | not listed at all |
   | `V4L2_CTRL_FLAG_GRABBED` | "temporarily unchangeable, for example because another application took over control" | no new value; one saved while it was free is kept |
   | `V4L2_CTRL_FLAG_READ_ONLY` | "permanently readable only" | no |
   | `V4L2_CTRL_FLAG_UPDATE` | "changing this control may affect the value of other controls" | yes, set first; read the others again after it |
   | `V4L2_CTRL_FLAG_INACTIVE` | "not applicable to the current configuration and should be displayed accordingly" | no new value; one saved while it was active is kept and waits |
   | `V4L2_CTRL_FLAG_SLIDER` | a presentation hint | yes |
   | `V4L2_CTRL_FLAG_WRITE_ONLY` | "typically present for relative controls or action controls" | no |
   | `V4L2_CTRL_FLAG_VOLATILE` | "the value of the control changes continuously" | no while active; with INACTIVE it is an auto cluster's manual control in automatic mode (driver-api `v4l2-controls.rst`, "Auto Clusters": "marked inactive and volatile"), a setting that waits |
   | `V4L2_CTRL_FLAG_HAS_PAYLOAD` | "an array, string, or ... a compound type" | no |
   | `V4L2_CTRL_FLAG_EXECUTE_ON_WRITE` | "the control represents an action on the hardware" | no |
   | `V4L2_CTRL_FLAG_MODIFY_LAYOUT` | "may modify the layout of the buffer" | yes, set before the mode |
   | `V4L2_CTRL_FLAG_DYNAMIC_ARRAY` | "a dynamically sized 1-dimensional array" | no |
   | `V4L2_CTRL_FLAG_HAS_WHICH_MIN_MAX` | minimum and maximum readable through `V4L2_CTRL_WHICH_MIN/MAX_VAL` | yes (no effect) |
   | `V4L2_CTRL_TYPE_BUTTON` | an action | no |
   | `PAN/TILT/FOCUS/ZOOM/IRIS_RELATIVE`, `ZOOM_CONTINUOUS`, `PAN/TILT_SPEED` | `ext-ctrls-camera.rst`: "turns the camera ... by the specified amount", "at the specified speed": a movement | no: a saved one moves the camera at every plug-in |
   | integer with maximum not above minimum | no range | no |

2. **A default outside its own range is the value the driver holds** (`effectiveDefault`): the V4L2 control framework (`ROUND_TO_RANGE`) and uvcvideo (`uvc_ctrl_clamp`) clamp an integer to its range and round it to its step, so the A10's sharpness (0 to 100, default 120) holds 100 after a reset. Compare readings with that, or every Apply saves 100.
3. **The apply order:** the saved controls flagged `MODIFY_LAYOUT`, then the saved mode (or the best mode, step 5), then the other saved controls in passes (`V4l2Camera::setControls`): each control queried for its flags (`VIDIOC_QUERY_EXT_CTRL` by id) just before it is set, those flagged `UPDATE` first, an inactive one left for the next pass, until a pass sets nothing more. A governing control goes first whatever its id: `FOCUS_ABSOLUTE` (0x009a090a) is governed by `FOCUS_AUTO` (0x009a090c), so the order of ids is wrong there. A setting still inactive at the end keeps its saved value and no problem; a real refusal (a value the camera rejects, a busy camera, a camera gone) is told and kept once by `sparky-stereo-problems` and cleared when it works.
4. **An old store is cleaned in the person's session, never by a maintainer script** (Debian Policy 10.7.5; the packaging skill: a package never writes into home folders). The entry carries `version=2` from 0.1.3; an entry without it is cleaned the first time its camera is present and the apply has no refusal: a value of a control that is not a setting is removed, and so is a value equal to what the camera holds as its default (0.1.3 never saves one). A value of a control that is inactive now **stays and waits**: an old store cannot tell the person's own manual value from a reading the automatic mode moved (trap below). Each removal and each waiting value is a journal line that says only what is known ("not a setting: a motion control"; "equal to the camera's default"; "inactive now; its saved value N waits for it"), and the problem kept for a removed entry is cleared.
   A waiting value is set as soon as its control is active again: at plug-in after its governing control, and when the person switches the governing control on the page or with the command (`applyWaiting`), before anything is saved, or the save would take the camera's own reading instead.
   A camera asked for by name is asked for again for 3 seconds before "No camera called NAME is present." (exit 1); a camera PipeWire lists whose device opens and does not answer is said by every verb ("... is not connected any more"), never printed as an empty list; the unit retries such a camera at its next pass instead of marking it done.
5. **The best mode** (Daniel, 2026-11-18: "the best resolution then best framerate in this order of priority"): for a camera with no saved mode, the largest picture and, at that size, the highest frame rate; two sizes of one pixel count give the wider one; one size and rate in two formats give the one that needs no decoding; then the driver's order (`bestMode`, `sparky-stereo-camera best NAME`). A known machine's caveat wins: a reference in `sparky-stereo-hardware`'s `known-machines.json` with `"owner": "sparky-stereo-camera"`, `"camera": "VVVV:PPPP"` and `"formats": [...]` names the formats that camera, in that machine, delivers correctly.

## Where each program takes its mode from

| Consumer | Its mode when it asks for none | Source |
|---|---|---|
| The Camera page and its unit | the saved mode, else the best mode, set on the V4L2 device at plug-in and when the page opens | `applyChoice` |
| A program that opens the V4L2 device and keeps its current format | the device's mode, so the page's | not measured in this run |
| Qt Multimedia (FFmpeg backend, 6.11) | its own: at least 29 frames a second first, then the largest picture, then the pixel format, then the rate | `QPlatformCamera::findBestCameraFormat`, set with its own `VIDIOC_S_FMT` |
| A PipeWire client with no preference of its own | the first mode of the driver's list | PipeWire's `spa_v4l2_enum_format` offers one `EnumFormat` per discrete size in the driver's order, the first frame interval as the default; the device's current mode is not read |

So the page cannot make Qt or PipeWire programs start at the best mode or at a saved mode: that is a change in those two packages (measured below).

## The fixture: a control of each flag, PipeWire's own V4L2 source, the page without its QML

- The virtual camera of [the proof rig](../../stereo-proof-rig/SKILL.md) (`scripts/virtual-camera/vcam-shim.c`, an `LD_PRELOAD` library) reads `videoN.cfg`: `ctrl NAME TYPE MIN MAX STEP DEFAULT [OPTION...]`, with one option per flag (`inactive readonly writeonly volatile update slider grabbed exec layout dynarray whichminmax disabled`), `id=`, `value=` (the reading at plug-in), `clamp` (uvcvideo's clamping), `refuse`, and an auto cluster as uvcvideo makes it: `master=NAME:MANUAL` (inactive while the master is not at its manual value, `EACCES` to a set then, as `uvc_ctrl_is_accessible`) and `auto=N` (the moving reading the automatic mode gives). `size WxH R1,R2` gives a size its own frame rates. Every mode and control a process sets goes to `videoN.log` with the process name.
- `scripts/virtual-camera/controls/` has the fixtures of this run: the iMac's two controls (`video30.cfg`), the A10's real camera (`video31.cfg`, from its `v4l2-ctl --list-ctrls` and `--list-formats-ext`), a control of each flag (`video32.cfg`), several sizes and rates in two formats (`video33.cfg`), the Vaio case (`video34.cfg` with `machines/`), a held camera (`video35.cfg`).
- **PipeWire's own V4L2 source on the shim:** start `pipewire` with the shim preloaded (the shim's descriptor is a `/dev/null` descriptor, a character device, so `spa_v4l2_open`'s `S_ISCHR` check passes) and create the node by hand, WirePlumber's monitors disabled:

      pw-cli create-node spa-node-factory '{ factory.name=api.v4l2.source node.name=cam-modes node.description="Virtual camera modes" api.v4l2.path="/dev/video33" object.path="v4l2:/dev/video33" media.class="Video/Source" media.role=Camera object.linger=true }'

  A client then negotiates for real (`gst-launch-1.0 pipewiresrc target-object=cam-modes num-buffers=1 ! fakesink`): the shim logs the `S_FMT` PipeWire sends; streaming fails after it (no buffers), which does not matter for the mode.
- **What Qt picks:** `qt-probe /dev/videoN` starts a `QCamera` with no format (`QT_MEDIA_BACKEND=ffmpeg`, the shim preloaded, `/dev/videoN` a broken symbolic link so `QDir::System` lists it) and the shim logs Qt's `S_FMT`.
- **The page, with and without its QML:** `kcm-probe PLUGIN.so load current=NODE mode controls set=ID:VALUE setmode=F:W:H:FPS defaults save error followers grab=FILE.png` loads the installed KCM as System Settings does (`KQuickConfigModuleLoader::loadModule` with a shared `QQmlEngine`) and calls its own `load()`, properties and invokables; `followers` and `grab` build its `mainUi()` in an offscreen window (`QT_QUICK_BACKEND=software`) and read an item by its `objectName` or save the drawn page. The shim's `videoN.gone` file makes a camera open and answer `ENODEV` to every ioctl but `VIDIOC_QUERYCAP`, as a camera going away or starting.
- `rows.sh` runs the rows in one container per run (root installs the `.deb` under test with apt, then everything as uid 1000); `store.py` reads the page's QSettings INI (group names are percent-encoded, keys `controls\ID`).

## Traps (symptom, cause, fix, how found)

- **The write-only flag alone does not catch a relative control.** Symptom: the iMac's Iris, Relative read 88 and was saved, although uvcvideo's table gives `IRIS_RELATIVE` only `SET_CUR`. Cause: uvcvideo adds `GET_CUR` from the camera's own `GET_INFO` answer, so the control is readable, and without `GET_MIN`/`GET_MAX` its range is 0 to 0. Fix: the specification's relative and speed ids and "no range" are rules of their own. Found by reading `uvc_ctrl.c` (`uvc_ctrl_fill_xu_info`, the static `uvc_ctrls` table) against the iMac's numbers.
- **No `V4L2_CTRL_FLAG_UPDATE` from uvcvideo.** Symptom: a page that follows only `UPDATE` never shows the temperature becoming active when automatic white balance goes off. Cause: uvcvideo marks the slave `INACTIVE` (`master_manual`) and sets no `UPDATE` on the master. Fix: after a set, compare the other controls' flags and read the page again when one changed (not on a value that only moved: a dragged slider would be rebuilt under the pointer).
- **A refused mode vanished from the page.** Symptom: a camera held by another program refused a new size and the page showed nothing. Cause: `readDetails()` clears `m_modeError` first, and `setMode()` and `resetControls()` called it right after setting the error. Fix: say the error after the read (`showError`). Found by the `page-shows-a-refused-mode` row, red on 0.1.2.
- **Five packing names untranslated since 0.1.2.** Symptom: "Automatic", "Both views in one block, ..." and "Frames in turn, ..." in English in every language. Cause: 0.1.2 took the packing list from the layer, and the template and catalogues were not made again. Fix: `sh Messages.sh` then `po/tools/make-po.py po LAYER_PO`, with `LAYER_PO` the layer's catalogues at the pinned commit (`git show COMMIT:po/LANG/stereo-layer_qt.po`), and compare every old `msgstr` with the new (no existing one may change).
- **`pw-cli create-node` answers `syntax error in properties, line:1 col:132: Expected object key`.** Cause: `object.path=v4l2:/dev/video30` unquoted; SPA-JSON reads the colon as a separator. Fix: quote every value that holds a colon or a slash. Found in the run's `nodes.log`.
- **PipeWire and WirePlumber log `Failed to connect to session bus: Did not receive a reply` in a container.** Cause: no passwd entry for the uid the session runs as. Fix: write one (`rig:x:1000:1000::HOME:/bin/bash`) before starting the bus.
- **`find_package(KF6 COMPONENTS ...)` fails: no `KF6Config.cmake`.** Debian ships each framework's package only: `find_package(KF6CoreAddons)`, `find_package(KF6KCMUtils)`; the quick KCM class is in `KF6::KCMUtilsQuick`.
- **The kernel's documentation from git.kernel.org is a bot page of 7.3 kB** ("Making sure you're not a bot!"). Read the same files from the GitHub mirror at the tag (`raw.githubusercontent.com/torvalds/linux/v7.3/...`); check the first line before reading a fetched file.
- **`Missing toolkit input: packages/dpkg-stereo/LICENSE`** when the recipe's `build.sh` runs from a sparse clone of the build tree: `lean.debian_prepare` copies that file into the source; add `sparky-os/packages/dpkg-stereo` to the sparse checkout.
- **A camera plugged in again within one pass of the user service stays at the driver's mode.** Symptom: the rig's quick replug (node destroyed and created again) and `watch` logs no second "saved settings applied". Cause: the service knew a camera by node name and node id, and PipeWire gives a freed id again. Fix (0.1.3): `object.serial` (`PW_KEY_OBJECT_SERIAL`), which is never given twice. Found by the `watch-plugged-camera-starts-at-best` row and the watch log.
- **The link gate stops with `previous edition dependency qualification failed; provide the matching previous sibling snapshot`.** The predecessor (`SPARKY_LC_PREVIOUS_DIR`) needs the sibling packages it was built against: list the pinned layer and declare files in `SPARKY_LC_PREVIOUS_SIBLINGS_FILE`. Before that, `check-link needs --archive-config / --scratch` means the gate has no `SPARKY_LC_ARCHIVE_CONFIG` (Debian, deb-multimedia and the published tree as `file:/repo`, each with a binary keyring) and no `SPARKY_LC_SCRATCH` on `/`; it also needs the public network and `seccomp`, `apparmor` and `systempaths` unconfined for bubblewrap.
- **`pipewiresrc target-object=NODE` ends with `target not found`.** The stream needs `stream-properties="props,media.type=Video,media.category=Capture,media.role=Camera"`, as [the page](camera-page.md) already says for a stream without a target.
- **An old store cannot tell a person's value from a moving reading.** Symptom (on the A10, a real EasyCamera 0bda:57fb, 2026-11-26): the person set White Balance, Automatic 0, the temperature 3000 and Automatic 1; after the upgrade the clean-up removed `3000` and the journal said "it was saved while the control was inactive". Cause: 0.1.0 to 0.1.2 saved a snapshot, and an inactive control's reading is either the person's manual value (uvcvideo keeps it: the A10 read 3000) or a value the automatic mode moved (the iMac read 5537, 5547, ...); nothing in the old store says which, so the line stated what nobody measured. Fix: keep an old value of a control that is inactive now; it waits without a problem and is set when the control is active again; the journal says only what is known. How found: the main session's run on the A10 and the store it left (`controls\9963802=3000` before, gone after).
- **A camera listed by PipeWire whose device does not answer gives an empty answer with exit 0.** Symptom (A10): one minute after the service restart, `formats`, `mode` and `best` answered `[]` or an empty mode with exit 0, and `list` once answered `[]`; a minute later everything was right. Cause: `V4l2Camera` ended every enumeration on any error, as if the list had ended (`VIDIOC_ENUM_FMT` answers `EINVAL` past the last entry, but a device going away or starting answers `ENODEV` or `EIO`), and the unit marked such a camera done. pw-dump itself is not the cause: it binds every global and dumps only after its core sync returns (`pw-dump.c`, `on_core_done`), so an empty `list` means the graph had no camera node at that moment. Fix: `lastError()` after each enumeration and after reading the mode; every verb says a device that does not answer; a name not listed is asked for again for 3 s; the unit retries. How found: the rig's `gone` switch reproduced the A10's answers exactly on the earlier 0.1.3 (`formats` `[ ]` exit 0, `mode` all empty exit 0); the A10's own kernel log for that minute (`journalctl -k`, a USB reset or a uvcvideo probe) was not read here.
- **`bash -n` says `unexpected EOF while looking for matching` on a line far below.** An apostrophe inside `${1:?the build's folder}` opens a quote; write the message without one.

## Perks

- `sparky-stereo-camera controls NAME` prints each control's `keep` (the rule's answer), its raw `flags`, `effectiveDefault` and whether its value could be read: the table above for any real camera, from one command.
- `sparky-stereo-camera best NAME` prints the best mode, the camera's USB ids and the machine's caveat, without changing anything.
- The journal says what the apply did that is not a failure (a setting waiting, an entry cleaned, the best mode set), so a person's "why did my camera change" has an answer.
