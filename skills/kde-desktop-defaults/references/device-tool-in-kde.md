# A device tool joined to KDE: a System Settings page, a panel entry and click actions (ORDER 696, 2026-11-18)

A command-line tool for a device (HeadsetControl for USB gaming headsets, the first) is accepted into the edition only together with its place in KDE: a page in System Settings and the actions a person clicks (Daniel, 2026-11-18: "I accept if we integrate it with kde framework properly"; "meaning kconfig pages, click actions and such").
`sparky-stereo-headset` is the first such package; this is its recipe, which the next device tool follows.
Check freshness first: written on 2026-11-18 from `sparky-stereo-headset` 0.1.0, KDE Frameworks 6.30.0, Plasma 6.7.4, Qt 6.11.2, HeadsetControl 4.3.0, UPower master of that day.
It sits beside [the Camera page](camera-page.md), the other device page of the edition; the camera page keeps its choices in an ini file of its own, this one in KConfig (Daniel: settings are kept in KConfig and nowhere else).

## Recipe

1. **Reconcile what exists, at the source, before writing.** For headsets: HeadsetKontrol (Kirigami program, GPL-3.0, TheBill2001, on GitLab and mirrored on GitHub, not on invent.kde.org, version 2.0.4, only a Vietnamese translation, in Debian: no, in the AUR: yes; its tray icon is always shown, its settings are in its own window, no System Settings page); the plasmoids headset-plasmoid (gort818, last push 2019) and plasmoid-headsetcontrol (lazy-stripes, last push 2022); HeadsetControl-GUI (Qt), the GNOME extension. None is a KCM, none follows the person's headset from plug to plug; the verdict was "ours to write", the others credited as read.
2. **Where Plasma shows batteries, read in plasma-workspace** (`components/batterycontrol/batterycontrol.cpp`, 6.7): the Power & Battery applet lists only what UPower (`org.freedesktop.UPower`, `EnumerateDevices`, `DeviceAdded`) announces, and it knows the headset kind (`UP_DEVICE_KIND_HEADSET`, `UP_DEVICE_KIND_HEADPHONES`). UPower itself takes a device from sysfs power_supply, BlueZ, a UPS on hiddev, an iDevice or a Watts Up Pro meter and has no provider interface; a USB headset's battery lives in a vendor report only the tool reads, so UPower never lists it. A device of kind "battery" would be taken for the machine's own battery (`UP_DEVICE_KIND_BATTERY` is the applet's `Primary`), so a fake power_supply is not a way in. Joining the list takes a change in UPower or in the applet's model; until then the battery is shown by the panel entry, the page and the low-battery notice below. **This is the open part of ORDER 696.**
3. **The page is a KCM** (`kcmutils_add_qml_kcm`, `KQuickConfigModule`, plugin metadata with `X-KDE-System-Settings-Parent-Category` `audio-and-video`, a weight, translated Name and Description). Controls come from the tool's own capability list (`headsetcontrol -o json`: `capabilities`, `battery`, `equalizer_presets`) and a table of settings with their option, range and capability: nothing the device lacks is shown, not even disabled. With no device the page says so and says what to do. Only what the person changed is written (a group per device in `~/.config/<name>rc`, KConfig) and sent: the device keeps every setting never touched here. Apply writes the KConfig entry only when the tool took the value.
4. **The panel entry is an applet in the system tray** (`plasma_add_applet(ID QML_SOURCES ... GENERATE_APPLET_CLASS)`, metadata with `EnabledByDefault: true` and `X-Plasma-NotificationAreaCategory: Hardware`, as Plasma's own camera indicator): `Plasmoid.status` is `ActiveStatus` while the device is connected and `PassiveStatus` otherwise, so there is no icon without a device. A C++ QML plugin (`ecm_add_qml_module`, `GENERATE_PLUGIN_SOURCE`) runs the tool without blocking the shell (an async `QProcess`, one short question every 30 s) and keeps the choices through the same KConfig code as the page. The menu is `Plasmoid.contextualActions`: lights, prompts, levels, one entry for each preset the device has (built by an `Instantiator`), and the page through the standard slot (`Plasmoid.setInternalAction("configure", action)` with `KCMLauncher.openSystemSettings`). The pop-up holds the same controls for a left click.
5. **A user service applies the saved choices when the device appears** (the way KDE repeats a screen's setup): `lib/systemd/user/NAME.service`, `WantedBy=default.target`, started also by a udev rule on the device (`TAG+="systemd"`, `ENV{SYSTEMD_USER_WANTS}+="NAME.service"`) written from the tool's own device list (`headsetcontrol -u`) by a script, with a test that the two lists are equal. It tells the person when the battery is at or below PowerDevil's own peripheral level (`powerdevilrc`, `[BatteryManagement]`, `PeripheralBatteryLowLevel`, 10 when unset) through KNotification with a `.notifyrc` (events `lowBattery`, `applyFailed`); a saved choice the device refuses is told, never dropped silently.
6. **Ten languages in three places:** the page and the command in `kcm_NAME`, the applet in `plasma_applet_ID` (the same catalogue under its own name), the notices in the `.notifyrc` (`Name[xx]`, `Comment[xx]`), the plugin metadata in `Name[xx]`. `ki18n_install(po)` installs `po/LANG/DOMAIN.po`; generate them from one table and check that every `%N` of the English sentence is in each translation.
7. **The detection row installs the page with the program** (hardware layer: the same ids list, both packages planned; a copy of the tool the person built by hand in `/usr/local` is theirs, and neither package is planned beside it).

## Proof without the device

A recorded device for the udev rules (umockdev) and a stand-in of the tool for its answers: a script named like the tool, first in `PATH`, that prints the tool's own JSON for the recorded device and refuses what the device lacks, plus the real tool on its built-in test device (`headsetcontrol --test-device`) for every capability. Say exactly what is stood in (the dongle, the radio link, the headset; no HID traffic). A Plasma login in a container: the rig recipe ([session start order](../../stereo-proof-rig/references/session-start-order.md)) with a private session bus, KWin on a virtual output with a render node, kactivitymanagerd, plasmashell and a panel made by `evaluateScript` (launcher, spacer, system tray, clock), captures through KWin's ScreenShot2, clicks through KWin's fake input. Red without the package (no page in `kcmshell6 --list`, no entry), green with it.

## Traps

- **Symptom:** an applet's menu or tray entry never shows the actions of the connected device, though the command line sees them. **Cause:** the QML binding calls a `Q_INVOKABLE` (`headset.has("Lights")`); a binding is re-evaluated only when a property it read changes, and a method call registers nothing, so it was evaluated once, before the device was there. **Fix:** capabilities and values are properties with a `NOTIFY` signal (`hasLights`, `lights`). **Found by:** the real tool's test device listing five settings on the command line and none in the menu.
- **Symptom:** `use of deleted function 'QString::QString(const char*)'` in a `QJsonObject{{"key", value}}`. **Cause:** KDE's compiler settings define `QT_NO_CAST_FROM_ASCII`. **Fix:** `QStringLiteral("key")`.
- **Symptom:** equalizer presets in alphabetical order, so `-p N` sets another preset. **Cause:** `QJsonObject` sorts its keys and HeadsetControl's number is the position in its own list. **Fix:** read the key order from the printed text.
- **Symptom:** `kwin_wayland: Operation not permitted` in a container. **Cause:** the binary carries a file capability (`cap_sys_nice`) the container lacks. **Fix:** run a copy of the binary.
- **Symptom:** ScreenShot2 answers `Screenshot got cancelled`. **Cause:** no render node in the container. **Fix:** give `--device /dev/dri/renderD128` and put the user in a group of that gid (`runuser` drops the group otherwise).
- **Symptom:** `kf.coreaddons: The plugin ... explicitly states an 'Id' in the embedded metadata`. **Fix:** leave `Id` out of the applet's `KPlugin` metadata.
- **Symptom:** the build stops at `unmet build dependencies: node-acorn nodejs python3-yaml`. **Cause:** `lean.debian_prepare` adds the Lean Code stages' own build dependencies to a conventional source. **Fix:** the builder image carries them, as the camera package's does.
- **Symptom:** the build stops in the link gate with `Depends: headsetcontrol ... [no choices]`. **Cause:** the gate resolves Depends in its frozen universe and the dependency is staged, not published. **Fix:** a signed local archive made from the stage (a throwaway key, `dpkg-scanpackages`, `apt-ftparchive release`, one more entry in the gate's `sources.json`); say so in the report.
- **Symptom:** the first right-click on the tray entry shows its menu, later ones show the tray's own menu ("Configure System Tray…"), the clock's menu opens every time. **Cause:** not found; left clicks and the first right-click work every time. **Fix:** none yet, so the pop-up holds the same controls as the menu.
- **Symptom:** `QProcess: Destroyed while process is still running` in plasmashell's log. **Fix:** the destructor kills the child.
