# The on-screen keyboard: Plasma Keyboard, KWin's input method and Fcitx 5

**For** whoever changes how text is typed by touch on the edition: how KWin, the input method and the keyboard fit together, Plasma Keyboard as the keyboard of Fcitx 5 (the bridge) and how to see it working, typing each required language in the session rig, and the traps met (row 71, November 2026).

Daniel, 2026-10-14: "we should also revamp the best (integrated with kde) virtual keyboard - as a measure for VR", "multilanguage is required".
The accessibility study's answer, accepted: Plasma Keyboard is the keyboard, Fcitx 5 does the conversion for Japanese, Korean and Chinese.

## How the pieces fit

- **KWin runs one input method.** `kwinrc [Wayland] InputMethod` names a desktop entry; KWin starts its program with a private Wayland connection (`WAYLAND_SOCKET`) and talks `zwp_input_method_v1` with it (`src/inputmethod.cpp`, `startInputMethod()`). Text fields reach it through text-input v1, v2 or v3.
- **Plasma Keyboard as the input method** (Latin sessions on a computer with a touch screen of its own, row 567): Qt Virtual Keyboard runs inside it, its commits and preedit go to the field through `zwp_input_method_context_v1`, and its window is a `zwp_input_panel_surface_v1` that KWin shows as an `InputPanelV1Window` (`inputMethod` true in KWin's window list). KWin shows it when the last input came from a touch screen or a pen and, with the edition's KWin, only in tablet mode (`InputMethod::shouldShowOnActive()`, `[Wayland] InputMethodTabletOnly`).
- **Fcitx 5 as the input method** (Japanese, Korean and Chinese sessions: `sparky-stereo-look`'s `first-login-input-method` writes `org.fcitx.Fcitx5.desktop` into the person's `kwinrc` at the first login): Fcitx 5 converts the keys of a hardware keyboard, and until row 71 no on-screen keyboard showed at all.
- **Fcitx 5's keyboard bridge** (`fcitx5 src/ui/virtualkeyboard`, the addon "DBus Virtual Keyboard" in Debian's `fcitx5-modules`): Fcitx 5 draws no keyboard. In its on-screen keyboard mode it owns `org.fcitx.Fcitx5.VirtualKeyboardBackend` (`/virtualkeyboard`, interface `org.fcitx.Fcitx5.VirtualKeyboardBackend1`: `ProcessKeyEvent(uuubu)`, `SelectCandidate(i)`, `PrevPage`, `NextPage`, `SetVirtualKeyboardFunctionMode(u)`) and calls the keyboard that owns `org.fcitx.Fcitx5.VirtualKeyboard` (`/org/fcitx/virtualkeyboard/impanel`, interface `org.fcitx.Fcitx5.VirtualKeyboard1`): `ShowVirtualKeyboard`, `HideVirtualKeyboard`, `UpdatePreeditArea(s)`, `UpdatePreeditCaret(i)`, `UpdateCandidateArea(asbbii)`, `NotifyIMActivated(s)`, `NotifyIMDeactivated(s)`, `NotifyIMListChanged`. Its keyboard mode starts with `ShowVirtualKeyboard` on `org.fcitx.Fcitx5` `/virtualkeyboard` (`org.fcitx.Fcitx.VirtualKeyboard1`) and ends at the first physical key, which hands back to its own candidate window.

## Plasma Keyboard as Fcitx 5's keyboard (the edition's plasma-keyboard 6.7.4-2+stereo3d1 and +stereo3d2)

`plasma-keyboard --fcitx` is that keyboard. It is a second process beside KWin's input method, so it is not an input method itself:

| Part | What it does | Why this way |
| --- | --- | --- |
| Start | an autostart entry, `/etc/xdg/autostart/org.kde.plasma.keyboard.fcitx.desktop`; the program ends at once, with one line, unless KWin's `InputMethod` names Fcitx 5 and `plasmakeyboardrc [General] showWithFcitx` is true | KWin starts only one program; the setting is off in the package and on where the hardware layer finds a touch screen of the computer's own (its folder in front of `XDG_CONFIG_DIRS`), so existing accounts get it with no file of theirs touched |
| When it shows | KWin's `org.kde.kwin.VirtualKeyboard` on `/VirtualKeyboard`: on `activeChanged`, and on `showRequested` (every request of a field, also a second touch on a field that already has the focus; KWin +stereo3d67), it reads `active` and calls `willShowOnActive()`; when KWin would show a keyboard it asks Fcitx 5 to show, and shows when Fcitx 5 calls it | the touch, pen and tablet-mode rule stays KWin's |
| The field in view | when it shows and hides it calls `setOnScreenKeyboardShown(bool)` on the same interface; KWin finds the caller's layer-shell window by the caller's process and keeps the focused window clear of it as of its own panel | KWin's own rule (`Window::setVirtualKeyboardGeometry`), no coordinates from the keyboard, no protocol a client speaks changes; a KWin without the method is said once in the log |
| Its window | a layer-shell surface (LayerShellQt) at the bottom, `KeyboardInteractivityNone`, made Qt's focus window on the client side; it wants the active screen (`setWantsToBeOnActiveScreen`), and when a field asks while it is shown on another screen than KWin's active output (`org.kde.KWin.activeOutputName`) it is mapped again there (+stereo3d2) | KWin never gives it the keyboard focus, so the text field keeps it and Fcitx 5 keeps its input context; a layer surface keeps the output it was mapped on, and KWin puts its own input panel on its active output, which follows the last touch |
| Its keys | Qt Virtual Keyboard types into a focus item of its own; each commit and key becomes an X keysym with Fcitx 5's key states, sent by `ProcessKeyEvent` | Fcitx 5's engine converts them as it converts a physical keyboard's; with `keyboard-us` Fcitx 5 forwards them unchanged |
| The bar | the preedit Fcitx 5 hands over, the candidates (a touch calls `SelectCandidate`), the pages, the input method (a touch, or the layout's language key, lists the group's input methods from `org.fcitx.Fcitx.Controller1` and switches with `SetCurrentIM`) | |
| Layouts | `layouts-fcitx`: Korean keys labelled with Dubeolsik jamo, Chinese (Taiwan) keys with Dachen bopomofo and tones; Japanese and Chinese (China) the QWERTY of the fallback layout; every other locale Plasma Keyboard's own | the engines read QWERTY positions (romaji, pinyin, Dubeolsik, Dachen) |
| When Fcitx 5 does not answer | the bar says so ("Fcitx 5 does not answer. The keys type plain text, without conversion.") and the keys go through KWin's fake input (`keyboard_keysym`, version 6); the sentence is in the system's negative-text colour (`Kirigami.Theme.negativeTextColor`) mixed towards white in steps of 5 % until its contrast on the keyboard reaches 4.5:1 (WCAG 2.x), with Breeze's #da4453 on the keyboard's #262423 that is 3.6:1 before the mix | no silent fallback; KWin grants the protocol to the entry `org.kde.plasma.keyboard.fcitx.desktop`, whose `Exec` is the absolute path; every text readable (Daniel, 2026-11-25) |

How to see it working, in a session: `busctl --user tree org.fcitx.Fcitx5.VirtualKeyboard` shows the keyboard's object; after a touch on a field, `busctl --user status org.fcitx.Fcitx5.VirtualKeyboardBackend` answers (Fcitx 5 is in its keyboard mode); the keyboard's debug lines are `QT_LOGGING_RULES=org.kde.plasma.keyboard.debug=true` ("KWin: text field active, show the keyboard: true", "Fcitx 5 keyboard backend registered", "Fcitx 5 keyboard visible: true"); KWin's window list shows a window of class `plasma-keyboard` with `inputMethod` false.

## How KWin keeps a field in view, and how the keyboard for Fcitx 5 gets the same

Measured on the published set first (KWin 6.7.4-2+stereo3d64, a Latin session, KWin's own input panel at 0,756 1920x324), Kate's field at the bottom of the window:

| Kate's window | What KWin does | What Kate is told |
| --- | --- | --- |
| maximized, 0,0 1920x1080 | shortened to 1920x756, ending where the keys begin | text-input v2 `input_panel_state(1, overlap)` |
| a normal window in the lower half, 360,540 1200x520 | moved up to 360,236, the same size | the same, overlap 0 after the move |
| full screen | left as it is; the keys cover its bottom | the overlap (622 080 px) |

The code: `InputMethod::updateInputPanelState()` (`src/inputmethod.cpp`) gives the window of the focused text field `Window::setVirtualKeyboardGeometry(panel frame)` while KWin's panel is shown and not an overlay, and sends text-input v2 the overlap. `setVirtualKeyboardGeometry` (`src/window.cpp`) keeps the window's geometry for the restore, skips full-screen and desktop windows and everything when `kwinrc [Windows] OverlayVirtualKeyboardOnWindows` is true (default false), and otherwise moves the window up, then shortens it, to end at the keyboard's top inside the maximize area; on hide it gives the geometry back. text-input-unstable-v2 says why the overlap is sent: "That can be used to make sure widgets are visible and not covered by a virtual keyboard."

KWin +stereo3d67 gives the keyboard for Fcitx 5 the same path: `org.kde.kwin.VirtualKeyboard.setOnScreenKeyboardShown(bool)` records the caller's process (`QDBusConnectionInterface::servicePid`), finds that process's shown `LayerShellV1Window`, and `updateInputPanelState()` uses its frame where it would use its own panel's while its own panel is not shown at the bottom (Fcitx 5's own panel is its candidate popup, an overlay). The window gets its place back when the keyboard says it is hidden, its window closes or its program leaves the bus. Nothing a client speaks changes, so no client needs a change, and a window KWin's own rule leaves alone (full screen) is left alone for both keyboards.

## The second touch on a focused field

A field asks for the keyboard with text-input's `show_input_panel` (v2, v3) or the internal context's request; KWin called `InputMethod::show()`, which acts on its own panel or input method only, and `activeChanged` comes only when a field becomes active or inactive. So in the four languages a touch on a field that already had the focus (from the pointer, with focus following the mouse, or in a maximized window that is already active) showed nothing. KWin +stereo3d67 routes the three requests through `InputMethod::requestShow()`, which emits `showRequested()` (relayed as the scriptable D-Bus signal `showRequested()` of `org.kde.kwin.VirtualKeyboard`) and then calls `show()`; the bridge treats the signal as it treats `activeChanged`, so KWin's own rule still decides.

Searched first (KWin's default branch since v6.7.4 and its merge requests and issues, 2026-11-25): nothing upstream says a field's request on D-Bus or lets a keyboard that is not the input method say what it covers. Merge request 10138 (Devin Lin, merged) fixes the `visible` property of the same D-Bus object; merge request 9697 (open) shows the keyboard on a chosen display. Merge request 9601 (Vlad Zahorodnii, merged on master) is carried in +stereo3d67: on 6.7.4 the filter that keeps `zwp_input_method_v1` and `zwp_input_panel_v1` to KWin's own input method never ran.

## What Fcitx 5 mode does not offer

Plasma Keyboard's long-press accents (its alternative keys) belong to its input-method mode and are not offered in Fcitx 5 mode, where Fcitx 5's engine decides what a key gives. The Latin sessions keep them: Polish "ń" is the long press on "n" (`alternativeKeys: "nń"` in `pl_PL/main.qml`).

## Upstream's reworked keyboard (master, for Plasma 6.9)

Read and run on 2026-11-25, master 2af42e6 (newest tag v6.8.3; none of this is in a release yet):

- **Merge request 109** (Devin Lin, merged 2026-10-14, "Introduce new input engine and framework to replace Qt VKBD"): Qt Virtual Keyboard is no longer a dependency; the keyboard has its own engine (`virtualkeyboard/`: input engine, keyboard controller, text composers, a word-candidate model) and layout packages under `keyboardpackages`. It still runs only as KWin's input method (`zwp_input_method_v1`; otherwise "Cannot run plasma-keyboard standalone"), and physical keys it grabs are used only for its accent overlay and keyboard navigation, every other key is forwarded unconverted.
- **Merge request 113** (Devin Lin, merged 2026-11-13, "Add Chinese, Japanese and Korean layouts and text composers"): Japanese on Anthy (Romaji, twelve-key and desktop layouts), Korean on libhangul (Dubeolsik, composition only, no Hanja), Chinese on libpinyin (Pinyin) and libchewing (Zhuyin). Nothing they learn is kept: no `anthy_commit_segment`, no `pinyin_train`/`pinyin_save`, Chewing's user database is `":memory:"`. They are not Fcitx 5's engines (Mozc, Fcitx 5's own libime Pinyin) and read none of the person's Fcitx 5 settings.
- **On the edition's stack** (Plasma 6.7.4, Frameworks 6.32, Qt 6.11.2): configure stops at `find_package(PlasmaQuick 6.7.90)`; with that floor lowered to 6.7.4 it configures, builds and installs, with Debian's `libpinyin15-dev`, `libchewing3-dev`, `libhangul-dev`, `libanthy-dev` and `libanthyinput-dev` and the edition's `qt6-multimedia-dev`. As KWin's input method in a session: 한국어 and 中文 typed by touch; Japanese left `nihongo` unconverted with Debian's Anthy (master prefers anthy-unicode, which Debian does not package; its own Anthy tests fail the same way).
- **Its layout choice:** with no layout enabled it shows the American English desktop layout; `enabledLocales` is dropped (`KeyboardPanel.qml` calls `layoutIdsForLocales`, which no class defines), so only the settings page's "enabled layouts" list (`enabledKeyboardLayoutIds`) chooses one.
- **For the bridge:** its Qt Virtual Keyboard parts do not apply to master; master's text-composer interface (keys in, preedit and candidates set asynchronously, `selectCandidate`) fits a Fcitx 5 composer, with a non-input-method backend and the layer window kept from the bridge.

## Proving it: the session rig

The rig is [the welcome-login rig](first-run-welcome.md#the-session-proof) adapted: one fresh container and one new account's login per case, KWin on a virtual 1920x1080 output on the NVIDIA card (CDI), a sysfs fixture that the hardware layer reads as a computer with a touch screen of its own (`SPARKY_STEREO_SYSFS`), `KWIN_VIRTUAL_TOUCH_SCREEN=1` so that KWin has a touch device, tablet mode set as General Behavior writes it, and touches sent through KWin's fake input (`t:X,Y`, the rig's `fakeinput`, granted by its desktop entry's `X-KDE-Wayland-Interfaces`). Scripts: [`stereo-proof-rig/scripts/on-screen-keyboard/`](../../stereo-proof-rig/scripts/on-screen-keyboard/).

1. Images: `mkrig.sh` builds the published set (Debian testing pinned by digest, the edition's signed tree, deb-multimedia, SparkyLinux's repository, Kate, Plasma Keyboard, Fcitx 5 with the four engines, every locale); `mklayer.sh` adds one layer installed by apt, keeping apt's plan: Gwenview, Konsole, zenity, the Stereo Browser and Qt's `qml` tool for red; the set a round starts from for STAGED; the packages under test for GREEN.
2. A typing case (`type-case.py`): Kate opens an empty file and saves it every 2 seconds; a touch elsewhere, then a touch on the text; KWin's window list says which keyboard showed (`inputMethod` true: KWin's input panel; class `plasma-keyboard`: the keyboard for Fcitx 5); the keys are found in a capture from the layout's own `main.qml` (`keys.py`: background from the top rows, key runs on each row's middle line, the bar above the first row); in a CJK session the input method is chosen first on the keyboard's bar; then the word's keys and its engine's finish are touched and the saved file is read back.
3. The other cases are step scripts run in the same login (`STEP=`): `hw-type.sh` (a hardware keyboard through Fcitx 5, `HW_LANG` ja, ko or zh_CN, then a touch and a physical key), `retouch.sh` (a field focused by the pointer, then touched), `kcm-page.sh` (the settings page), `step6-3d.sh` (the keyboard over a stereo picture on a 3D output, both eyes captured, measured by `measure-3d.py`), `step3-3d-moved.sh` (a declared stereo window holding a field in the lower half, which KWin must move; a Qt Quick window with the stereo layer's `StereoPicture` over a `TextField`, measured by `measure-moved.py`), `step-fcitx-activated.sh` (a Fcitx 5 started by D-Bus activation in a Latin session; its own self-diagnosis says whether it bound KWin's input-method protocol), `twoscreens.sh` (`OUTPUTS=2`: which screen the keyboard shows on).
   `type-case.py` takes `TARGET` (konsole, zenity, systemsettings, browser: the field placed relative to the window from a calibration capture, read back where the program can print it, else the field's pixels compared relative to the window's frame), `INVIEW` (lower, max, full: Kate's field at the bottom of such a window; KWin's window list and Kate's own Wayland log say what moved and what Kate was told), `SCALE` (the output's scale, set with kscreen-doctor; captures are converted to logical coordinates) and the language plans `ja-pages` (Mozc's pages turned by the bar's ›), `zh_CN-swipe` (Pinyin's whole list, the bar swiped) and `pl-long` ("Dzień dobry", the ń by long press: `fakeinput`'s `td:`, `tm:` and `tu` steps). `contrast.py` measures the told sentence's contrast on the bar (WCAG 2.x, proved on a drawn control first).
4. `prove.sh OUT` runs every case red (the published set), staged where a round starts from earlier staged packages, and green (the packages under test), and writes one row per claim; it exits 1 when a row is not as expected.

## Traps met (row 71)

- **Symptom:** in a Latin session (Plasma Keyboard as KWin's input method) the keyboard vanished after a test merely asked Fcitx 5 something over D-Bus. **Cause:** the call started Fcitx 5 by D-Bus activation; a Fcitx 5 started that way binds KWin's input-method protocols too (KWin's Wayland filter does not keep them to the program it started) and its popup surface takes KWin's only input panel (`InputPanelV1Window`, one at a time), so Plasma Keyboard's keys were no longer drawn. **Fix:** every call to Fcitx 5, in the keyboard and in a rig, goes without auto-start (`QDBusMessage::setAutoStartService(false)`, `busctl --auto-start=no`, `NO_AUTO_START` in GDBus): an absent Fcitx 5 then answers "no such service". **Found by:** KWin's log at the moment Fcitx 5 drew its popup (`kwin_virtualkeyboard: Replacing input panel KWin::InputPanelV1Window(... surface=A ...) with KWin::InputPanelV1Window(... surface=B ...)`), after which the rig found no rows of keys and nothing was typed. In KWin's window list Plasma Keyboard's panel has the class `kwin_wayland`, because KWin starts it on a private socket.
- **Symptom:** the saved document already holds the Japanese, Korean or Chinese text while the conversion is still open, so a check that reads the file passes too early. **Cause:** KTextEditor (Kate) keeps a pending conversion (the preedit) in its buffer and saves it. **Fix:** besides the file, measure how many more pixels of the preedit's highlight (247,159,82) Kate's window has than right after the touch: a pending conversion adds 410 to 723, committed text 2. **Found by:** a run that "typed" 日本語 with Mozc's candidate list still open.
- **Symptom:** a converted word never commits. **Cause:** each engine commits differently: Mozc converts at the first Space, lists candidates at the second, and commits with Enter; Pinyin commits when a candidate is chosen; Chewing and Hangul commit with Enter. Kate also drops trailing spaces when it saves. **Fix:** finish each language's word its engine's way; end a Korean word with Enter, not a space.
- **Symptom:** the bar's input method button is empty. **Cause:** Fcitx 5 reports the current input method to its keyboard only while it is in keyboard mode, and not again after `SetCurrentIM`. **Fix:** read `CurrentInputMethod` from `org.fcitx.Fcitx.Controller1` when the keyboard is shown and after every switch.
- **Symptom:** `dpkg-source` refuses the code patch, or the installed `layouts-fcitx` lacks the Japanese layout. **Cause:** a 3.0 (quilt) patch cannot carry a symbolic link or an empty file (Qt Virtual Keyboard's `*.fallback` markers are empty). **Fix:** the source holds only the two `main.qml`; CMake writes the markers (`file(TOUCH)`) and the links (`file(CREATE_LINK ... SYMBOLIC)`) in `install(CODE)`.
- **Symptom:** on a 3D output the keyboard sat 2 px behind the screen, and a maximized stereo window shrank when it opened. **Cause:** LayerShellQt's default scope makes a layer KWin treats as an ordinary window (sunk by the depth rules), and an exclusive zone resizes every maximized window on the output, whether or not it holds the focused field. **Fix:** scope `dock` (KWin's `Dock` type stays at the screen's plane) and exclusive zone 0; the focused window is kept clear of the keys by KWin's own rule (`setOnScreenKeyboardShown`, above), as for KWin's own panel. **Found by:** `measure-3d`: disparity 2 and 154 185 changed pixels behind the keyboard, then 0 and 0. Round 1 wrote here that KWin's own panel "neither moves nor resizes windows": wrong, measured in round 2 (the table above).
- **Symptom:** in the rig, Kate disappears behind another window before the touch. **Cause:** the edition's focus follows the mouse with automatic raise, and the fake pointer rests over the other window. **Fix:** keep Kate above, move the pointer away from it, then touch.
- **Symptom:** the package's link gate cannot install it: `libavcodec63 ... Depends libaom3 (>= 1:3.15.3) but none of the choices are installable`. **Cause:** `qml6-module-qtquick-virtualkeyboard` pulls Qt Multimedia, which the edition builds against deb-multimedia's FFmpeg; a gate archive list without deb-multimedia cannot resolve it. **Fix:** the gate's `sources.json` names deb-multimedia beside Debian and the edition's tree.
- **Symptom:** `validate-po-patches.py` says "no file section" for a translation patch. **Cause:** it reads git-style diffs only (`diff --git`, `index`). **Fix:** make the patch with `git diff --no-index`, and give a new catalogue's header `a/` and `b/` paths of the same file.
- **Symptom:** KWin's new integration test of the keyboard for Fcitx 5 waited forever for the window to be shortened. **Cause:** the test's mock input method maps a top-level (bottom) panel, and `InputPanelV1Window::isShown()` is true for a mapped panel KWin never hid (`hide()` hides only a panel ready for painting), so KWin rightly kept clear of its own panel and ignored the other keyboard. **Fix:** `Test::inputMethod()->setMode(Test::MockInputMethod::Mode::Overlay)`, which is Fcitx 5's shape (its panel is the candidate popup, an overlay). **Found by:** two checks added to the test (the keyboard window's pid is the test's, the tracked window is the field's) passed, and a third (`panel()->isShown()` false) failed.
- **Symptom:** a D-Bus-activated Fcitx 5 in a Latin session took over the panel in round 1, and in round 2's rig it did not, yet the filter fault was still there. **Cause:** the takeover needs Fcitx 5 to draw its popup; binding the protocol does not. **Fix:** measure the binding itself: Fcitx 5's self-diagnosis in the session's log (`Using Wayland native input method protocol: 1`) and the globals an ordinary client is offered (`zwp_input_method_v1` in Kate's `WAYLAND_DEBUG` log); with KWin +stereo3d67 both are gone. **Found by:** reading the activated Fcitx 5's start lines beside the case's result.
- **Symptom:** the build record of a successor says `recipeDirty: true` although its own recipe was committed. **Cause:** the record reads the whole clone, and another recipe in it (Plasma Keyboard's) had uncommitted changes when the build started. **Fix:** commit every recipe of the round before the first build that goes to the stage, then build the stage's packages at that head. **Found by:** the KWin +stereo3d67 record.
- **Symptom:** a KWin test does not link: `undefined reference to KWin::InputPanelV1Window::staticMetaObject`. **Cause:** `QCOMPARE` on an enum declared with `Q_ENUM` asks for its meta object, which libkwin does not export to tests. **Fix:** `QVERIFY(a == b)`. **Found by:** the linker's message.
- **Symptom:** a candidate chosen on Mozc's second page was committed, and the check still said it was not. **Cause:** Fcitx 5 hands each candidate with its comment after a space, and the comment can nest brackets ("Ｎｉｈｏｎｇｏ [[全] アルファベット]"); a pattern for one pair of brackets kept the comment as part of the text. **Fix:** strip from the first " [" to the final "]". **Found by:** the result's expected text beside the committed one.
- **Symptom:** after a swipe along Pinyin's candidates and a touch, the document holds a character and unconverted letters ("蚣wen"). **Cause:** Pinyin hands all candidates at once (135 for `zhongwen`), and past the first few they are characters for the first syllable only; choosing one leaves the rest composing, and the bar then lists the rest's candidates. **Fix:** finish the word as a person does, with a touch on the bar's first candidate for the rest, and judge the swipe by the longest candidate the typed text starts with. **Found by:** the bridge's log of the candidates Fcitx 5 handed over, beside the typed text and the preedit's highlight (320 pixels still pending).
- **Symptom:** with two screens, a touch on a field of a window on the second screen shows KWin's own keyboard there (en), and the keyboard for Fcitx 5 on the first (ja). **Cause:** a layer surface stays on the output it was mapped on, and LayerShellQt's default takes the output of the QWindow's screen, Qt's first. **Fix:** the window wants the active screen (KWin's active output follows the last touch), and a keyboard already shown elsewhere is mapped again where `org.kde.KWin.activeOutputName` says. **Found by:** the two-screen row once the rig's pointer no longer stole the focus: the active window was the touched one on Virtual-1 and the keyboard's frame on Virtual-0. Open: on one change of screen the window is mapped again up to three times (the field asks several times before Qt reports the window's new screen); the end is right, and remembering the screen already asked for would map it once.
