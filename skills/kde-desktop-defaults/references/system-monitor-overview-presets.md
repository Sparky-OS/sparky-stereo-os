# System Monitor's Overview, fitted to the computer by a hardware probe

Daniel, 2026-10-17 (queue row 182): "system monitor overview presets for different configs like multiple GPUs and CPUs - current default is too narrow for both test targets (this and a10)"; "auto apply by hardware probe".
KDE's Overview (plasma-systemmonitor 6.7.4) shows one pie for `cpu/all/usage` and one for `gpu/all/usage`, the average of every card.
Ctrl+Alt+Del opens System Monitor on the edition, so its first page is what a person sees of the computer's load.

The edition's package `sparky-stereo-systemmonitor` (in [the build tree](https://github.com/Sparky-OS/sparky-stereo-os-build), `sparky-os/packages/sparky-stereo-systemmonitor`; a Depends of `sparky-stereo-desktop`) does it with page files and a probe; no patch to KDE's programs.

## Recipe

1. **Where pages live.** plasma-systemmonitor reads every `*.page` file of each `AppDataLocation` folder: `~/.local/share/plasma-systemmonitor`, then `/usr/local/share/...`, `/usr/share/plasma-systemmonitor` (`src/page/PageManager.cpp`, `PageManager::load()`); for one file name the person's folder wins.
   A page in the person's folder is theirs: they edit it in place and Edit Pages offers to remove it; a page under `/usr/share` can only be hidden or reset.
2. **What the person chose** is `~/.config/systemmonitorrc`, `[General]`: `pageOrder`, `hiddenPages`, `startPage`, `lastVisitedPage`, `sidebarWidth` (`src/page/systemmonitor.kcfg`; defaults `overview.page,applications.page,history.page,processes.page`, none hidden, `overview.page`).
   Edit Pages (`PageSortDialog.qml`) writes the whole order and the whole hidden list, and "Start with:" the start page.
   A page that is in no `pageOrder` goes to the end of the sidebar, visible.
3. **The page file** is KConfig: `[Face-ID][Appearance]` (`chartFace=org.kde.ksysguard.linechart|textonly|piechart|horizontalbars|facegrid|applicationstable`, `Title`, `Title[pl]`..., `showTitle`), `[Face-ID][Sensors]` (`highPrioritySensorIds`, `totalSensors`: JSON lists, regular expressions allowed), `[Face-ID][SensorLabels]` (`SENSOR-ID=label`, `SENSOR-ID[xx]=label`: read as a localized key, so a label carries its ten languages; libksysguard `SensorFaceController`, `sensorLabels`), `[Face-ID][FACE][General]` (the face's own settings), then `[page]` (`Title`, `icon`, `version=1`) and `[page][row-N][column-N][section-N]` (`face=Face-ID` or `isSeparator=true`; `isTitle=true` makes a row a heading).
   A face id is any group name.
   The sections of one column sit side by side; three sections in a card cut a title to its first words (measured on the A10).
   A localized `Title[xx]` is read as KConfig reads any localized key, so a page carries its own translations; a plain `title` key would override every language.
4. **Sensor names per driver, ksystemstats 6.7.4** (`plugins/gpu/`): cards are the PCI devices of class 0x030000, 0x030200 or 0x038000 of AMD, NVIDIA and Intel, numbered `gpu0`, `gpu1` in udev's order (device paths compared component by component, so an NVIDIA card under root port 00:01.x comes before an iGPU at 00:02.0 or 00:08.1); other vendors are skipped.
   | Driver | usage | video memory | temperature | power |
   |---|---|---|---|---|
   | amdgpu | `usage` from `gpu_busy_percent` | `usedVram`, `totalVram` from `mem_info_vram_*` | `temperature`, the `amdgpu` hwmon's temp1 through lm-sensors | `power1` (lm-sensors' feature name: `power1_input`, else `power1_average`); `power` is an empty placeholder |
   | nvidia (nvidia-smi) | `usage` = dmon's sm+enc+dec | `usedVram` (dmon fb), `totalVram` (`--query`) | `temperature` (gtemp) | `power` (pwr) |
   | i915 | `usage` through `ksystemstats_intel_helper` and the i915 PMU | none | none | none |
   Every card also has `name`; the CPU has `cpu/cpuN/usage` per logical processor of `/proc/cpuinfo` and `cpu/all/usage`.
5. **The probe**, `/usr/libexec/sparky-stereo-systemmonitor/overview-pages --login`, from `/etc/xdg/autostart/sparky-stereo-systemmonitor-pages.desktop` (`TryExec=plasma-systemmonitor`): reads the same facts as ksystemstats (sysfs, the amdgpu hwmon, `nvidia-smi --query-gpu=index,pci.bus_id,memory.total` and `nvidia-smi dmon -c 1 -s pucm`, the Intel helper's file capability and `perf_event_paranoid`, `/proc/cpuinfo`), composes the presets into the person's folder (one GPU, the one with `boot_vga`, always; every GPU only with two display devices or more, measured or not, so no two presets carry one title; up to 8 threads in one chart with a line each, or one chart per thread laid out in the page's own rows, four to eight to a row), each thread under its own label `Thread N` (N its processor number plus one, from `/proc/cpuinfo`'s `processor` lines, gaps kept) through `[Face-ID][SensorLabels]`, each preset titled by what it shows (`1 GPU, CPU`: the processor's threads in one chart; `2 GPUs, threads`: a chart for each thread), and the first time only sets `startPage`, `pageOrder` and `hiddenPages` (KDE's Overview and the other presets hidden) when none of the three is set in the person's or the administrator's file and the person has no own `overview.page`.
   A state file (`~/.local/state/sparky-stereo-systemmonitor/state.json`) keeps the computer's fingerprint and the digest of each page written: at the next logins only the PCI list and the thread count are read; when they change, the presets whose bytes still equal their digest are composed again, an edited one is the person's and a removed one stays removed.
   `--explain` prints the facts and the preset and writes nothing (that is how a computer that must not be touched is read).
6. **What is not reported is said, never shown as zero.** ksystemstats creates `usage`, `temperature` and `power` for every card with the value 0 and keeps it when the file is missing (`SysFsSensor::update()` returns early), so a card without `gpu_busy_percent` (the A10's Hainan) shows 0 %, an AMD card shows "Power 0 W" and nvidia-smi's `-` becomes 0.
   The preset lists only the sensors the driver reports, and titles the card's text face (or a section of its own) "Not reported to System Monitor: usage, power".

## Proof

- **Fixture tests** (`tests/run.sh` in the package, in a container with python3, `libkf6config-bin`, ksystemstats and `sparky-stereo-problems`): twelve computers built as sysfs trees in the kernel's shape, every preset parsed back, the login flow on a person's folders (first choice once, the fast path without nvidia-smi, a hardware change, an edited and a removed preset, a person or an administrator who chose already, a probe that fails and its problem kept then cleared).
- **The rig with a real System Monitor**, [`scripts/system-monitor/`](../../stereo-proof-rig/scripts/system-monitor/README.md) in the proof rig skill: a virtual Stereo KWin on the NVIDIA card through CDI, ksystemstats on the session bus (on the host's own sysfs read-only, or on a recorded machine through umockdev), the login hook as the autostart entry runs it, System Monitor maximised; the screen captured, every label read through AT-SPI, ksystemstats' sensor list kept; red (the published state, KDE's Overview) and green per machine; the person's switch to KDE's Overview through Edit Pages, a next login's hook and a restart.
- **The bench, a real login** ([`real-login-kit.sh`](../../stereo-proof-rig/scripts/system-monitor/README.md)): on the test laptop, under its bench lock, the machine's state first; the package installed; SDDM's autologin switched to a fresh account (made from the machine's `/etc/skel`), so Plasma's own session start runs the autostart entry through `TryExec`, `OnlyShowIn` and systemd's XDG autostart generator (`app-sparky\x2dstereo\x2dsystemmonitor\x2dpages@autostart.service`, its result and exit status read with `systemctl --user -M ACCOUNT@ show`); System Monitor opened in that session, full screen, read and captured; then the package purged, the machine's own autologin back, the account removed, and the state compared.

## Traps (symptom, cause, fix, how found)

- **A card shows 0 % or 0 W that the driver never reported.** Cause: ksystemstats' placeholders (above). Fix: the page holds only reported sensors and names the others. Found: `kstatsviewer --list` in the rig lists `gpu/gpu1/usage` and `gpu/gpu0/power` for the A10's cards, whose sysfs has neither `gpu_busy_percent` (the Hainan) nor `power1_input`.
- **AMD power is `power1`, not `power`.** Cause: `LinuxAmdGpu::discoverSensors()` names lm-sensors features by their own names except temp1. Fix: `gpu/gpuN/power1` for amdgpu, `gpu/gpuN/power` for NVIDIA. Found: the station's list shows "GPU 2 Power" and "GPU 2 PPT" side by side.
- **Intel usage is 0 on Debian.** Cause: Debian's ksystemstats has no postinst, so `ksystemstats_intel_helper` has no CAP_PERFMON, and `perf_event_paranoid` is 3; 6.7.4 also builds a discrete card's PMU name without its separator (fixed on master). Fix: the probe calls Intel usage not reported unless the helper has the capability or the paranoid level is 0 or below. Found: `os.listxattr()` on the installed helper and `/var/lib/dpkg/info/ksystemstats.*`.
- **Why the first choice is written once, into the person's file.** A probe that wrote the start page at every login would undo the person's later choice; a machine default under `/etc/xdg` would be read below the person's keys but could not give each person their own removable pages. Measured: after the person chose KDE's Overview in Edit Pages, the `startPage` key is gone from their file (KConfigSkeleton removes a value equal to the kcfg default when no system default exists, `KConfigSkeletonGenericItem::writeConfig()`), a next login's hook leaves the file byte for byte, and the restart opens KDE's Overview.
- **"This page is missing some sensors and will not display correctly."** Cause: every entry of a face's sensor lists, an id or a regular expression, is resolved by a `SensorQuery`; an entry that finds no sensor is listed as missing (libksysguard 6.7.4 `faces/SensorFaceController.cpp:151-153`, `SensorResolver::execute()`), and any face with a missing entry raises the banner (plasma-systemmonitor 6.7.4 `src/page/PageContents.qml:107`, `FaceControl.qml:96`). In a container with `--network none` and no disks, the Disks (`disk/(?!all).*/...`) and Networks (`network/(?!all).*/...`) expressions match nothing, so KDE's own Overview shows it too; on the A10's real login the preset shows no banner. Fix in a rig: none needed; `verify.py` passes the banner only when every unmatched entry is a `disk/` or `network/` expression and fails it for anything else. Read the rig's red row before blaming a page.
- **The sidebar cuts a title** (0.1.0's "Overview: every GPU, many threads" read "Overview: every GP…"; then 0.1.1's first wording, measured whole at 10 pt in the rig, read "2 GPUs, all threa…" on the A10's real login). Cause: the sidebar keeps about 126 px for an entry's text at its default width (`sidebarWidth` unset), at 10 pt and at 11 pt alike (the sidebar is about 170 px wide in both captures), and Qt elides the rest with "…". KDE's default font is Noto Sans 10 pt (13.333 px at 96 dpi), but a fresh account made from SparkyLinux's account template (`/etc/skel/.config/kdeglobals`, `font=Noto Sans,11,...`, owned by no package, on machines installed from SparkyLinux such as the A10) draws at 11 pt, so every title is 10 % wider there; a rig account made by `useradd -m` without that template measures the 10 pt case only. Edit Pages and the page header show the whole title, the sidebar does not. Fix: fit the title, never widen the sidebar: the GPU part with this computer's own count and the shortest processor part, "CPU" (one chart) or "threads" (a chart each), at most 120 px at 11 pt in all ten languages for 0 to 9 cards (the widest, Traditional Chinese "1 個 GPU，執行緒", 117.9 px; most fit at 12 pt); `tests/compose.py` measures every title at 11 pt with Pillow, and the rig measures them on screen at 11 pt (`FONT_PT=11`) and at 10 pt. How found: the review read the sidebar; then the A10's real login showed the first fix cut, and its text matched Noto Sans 11 pt ("Applications" 85 px against 84.3 predicted, 74 px in the rig); the font came from `/etc/skel`. Measure on the real login, not only in the rig.
- **The sidebar check passed a title it never saw.** Symptom: the A10's real-login row passed "its title is whole in the sidebar" while the capture shows the ellipsis. Cause: the window was not maximised, so the AT-SPI boxes (relative to the window's surface) pointed at the wrong pixels, no ink was found, and "no ellipsis found" was read as "whole". Fix: `measure_sidebar.py` reports `cut: null` (not measured) when it finds no text and takes the surface's place from `window-offset.txt` when one is given; `verify.py` passes only `cut: false`; the A10 kit puts System Monitor in full screen through a KWin script, so the frame box equals the screen. How found: looking at the capture after the verdict, as the review does.
- **Two threads under one name in a facegrid** (0.1.0 on the station: "Core 3" and "Core 8" twice, no "Core 5" or "Core 9", different on every run). Cause: every cell of KDE's facegrid loads its chart with `FaceLoader { groupName: "FaceGrid" }` (libksysguard 6.7.4 `faces/facepackages/facegrid/contents/ui/FaceControl.qml:44`), and `FaceLoader::Private::setupController()` builds each cell's controller on `parentController->configGroup().group(groupName)` (`faces/FaceLoader.cpp:237`), so all cells of one grid share one configuration group. Each cell's `SensorFaceController` takes its `Sensors` group from it (`faces/SensorFaceController.cpp:379`); its constructor resolves the sensor that group holds, the previous cell's, and sets it without a guard when the lookup returns (lines 406-409), while `setHighPrioritySensorIds` compares the cell's own sensor with that shared entry and writes over it (lines 521-525). When the constructor's lookup returns after the cell's own, the cell shows the previous cell's sensor under that sensor's name: one name twice, one missing. It depends on lookup timing: round 1 showed it with the station loaded by other lanes (85 to 100 %), the next five 0.1.0 runs (three on the station, two on the SMT fixture, eight busy loops in the container) showed every name once, so a passing run proves nothing about a facegrid. KDE's master (23cb1f2c, 2026-11-23) is the same; not reported (no KDE contributions for now). Fix: no facegrid; one chart face per thread in the page's own rows, or one chart for every thread, each with its sensor id written out (`cpu/cpu6/usage`, never `cpu/cpu\d+/usage`) and a `[Face-ID][SensorLabels]` entry per id, `Thread N` with N the processor number plus one; `verify.py` fails a page where two threads show one name or any processor lacks its label, `tests/compose.py` checks one sensor and one label per processor on a fixture with SMT siblings sharing core ids with gaps (0 1 2 4 5 6) and processor 5 offline. How found: the labels read through AT-SPI on the station's live row, then the facegrid's QML and the loader read for where a cell's settings live.
- **Rig: System Monitor does not start.** `Could not load the Qt platform plugin "wayland"` with `No shell integration named "xdg-shell"`: the image lacks `qt6-wayland` (KWin pulls only the client library). `module "org.kde.desktop" is not installed`: `qml6-module-org-kde-desktop` (Debian's name of KDE's Qt Quick Controls style). `org.kde.kquickcontrols` for a face's details: `qml6-module-org-kde-kquickcontrols`.
- **Rig: `kstatsviewer --details` never ends.** It keeps printing; bound it with `timeout`.
- **Rig: Edit Pages cannot be reached through AT-SPI.** Kirigami's sidebar toolbar keeps "Edit or Remove pages…" in its overflow menu, and the dialog is a popup AT-SPI does not show. Fix: open the overflow by fake input (the toolbar's right end), press the menu item through AT-SPI, then drive the dialog by pointer at positions read from a capture (keys sent to its "Start with:" list did nothing; a click on the item works).
- **Rig: a recorded machine's page shows the host's cards** (the recorded A10's preset, with its notes, filled with the station's RTX 3060). Cause: ksystemstats quits when its last client disconnects unless it runs with `--remain` (`src/main.cpp`, `Daemon::setQuitOnLastClientDisconnect`); the instance under umockdev answered the first sensor list, quit while the hook ran, and System Monitor's first call made D-Bus start a plain one on the host's sysfs. Fix: `umockdev-run ... -- ksystemstats --remain`, and a check that each card's name as ksystemstats listed it is the name System Monitor shows. How found: a German capture showed "NVIDIA GeForce RTX 3060" on a two-AMD recording; after the capture `ps` showed one ksystemstats whose parent was 1 and `kstatsviewer gpu/gpu0/name` answered the host's card. The checks on the page and on the first sensor list had all passed: check what the screen shows against the recording.
- **Rig: `umockdev-record` aborts** with "Cannot call udevadm": the image needs `udev`. umockdev records `/sys` only: `/proc/cpuinfo` stays the host's, so a recorded machine has the host's threads.
- **Bench: the test account's login runs every autostart entry, and the machine's own autologin runs ours on the way back.** A real login is SDDM's autologin switched to a fresh account (a drop-in in `/etc/sddm.conf.d` that links to a file in `/run`, so a restart of the machine midway falls back to its own autologin), then put back. The first run put the machine's autologin back before purging the package: the returning session ran the autostart entry and composed the presets into that person's folder (kept their arrangement, added the presets to `hiddenPages`); their files were put back to the baseline's bytes by hand within three minutes, checked by SHA-256. Fix: purge the package first, then restore SDDM, then remove the account; the corrected kit left the person's files byte for byte. Also seen: sparky-stereo-boot rewrites the boot files from whichever session holds seat0 ("boot follows sm182test: eDP-1 2d, no kernel arguments"), and the machine's own session writes them back when it returns (only `main-output.json`'s `time` field differs); other autostart entries (AnyDesk's tray, the update check) leave files in `/tmp` owned by the test account's uid: remove them by owner before the account goes.
- **Rig: a computer's processors without changing the host.** runc lets a file be mounted over `/proc/cpuinfo` (`-v fixture:/proc/cpuinfo:ro`; `run-case.sh CPUINFO=FILE`), and ksystemstats then makes one CPU object per `processor` line of it while `/proc/stat` stays the host's; build the fixture from the host's own blocks (renumbered physical and core ids, a processor left out) so every line ksystemstats reads is real.
- **Rig: AT-SPI boxes are the window's, not the screen's.** Qt on Wayland reports an object's extents relative to its window; add the title bar's height (the screen's height minus the frame's, for a maximised window) before reading pixels of the capture.
- **A line chart drops to 0 at its newest point in the first minute** while its label shows the current value (95.2 %). KDE's own History page does the same in the same rig (`APP_ARGS=--page-id history.page`), and the A10 shows it too: it is the line chart face before its history fills, not a page's sensors. Read values from the labels, not from the line's last point.

## Perks

- A page carries its own ten languages: no catalogue is needed at run time, and KDE's existing translations of shared words (CPU, Memory, Swap, Disks, Networks, Applications, Overview, the sensor names) can be reused word for word.
- ksystemstats names a card from the udev database: `LinuxBackend.cpp:57` calls libksysguard's `KSysGuard::gpuName()` (`processcore/gpu_utils.cpp`), which takes `ID_MODEL_FROM_DATABASE`, then `ID_MODEL`, then "VENDOR GPU", else "GPU %1"; an NVIDIA card then takes nvidia-smi's name (`NvidiaGpu.cpp:65`). In a container without `/run/udev` an AMD card is "GPU 2" (its Name sensor reads "GPU 2 Name: GPU 2") while the hardware database in the same image knows it (`systemd-hwdb query pci:v00001002d00001638` gives "Cezanne [Radeon Vega Series / Radeon Vega Mobile Series]"; modalias hex in upper case), and a umockdev recording made with `/run/udev` mounted keeps its real name. A real login has udev's database and shows the names.
