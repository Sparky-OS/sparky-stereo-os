# lean-code: lessons from the lanes of 25 October to 6 November 2026, and ORDER 638 (17 November)

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Test the exit status of verify, not only its text: unit test with 12 cases (0.1.36 fails 3, 0.1.37 passes 12); real damage stays counted (changed projected bytes, an old form whose owner does not list the path, a conffile in an old form, a changed projected manifest row) (lane dpkg-deep-verify-398)
- Conffiles on a lean system: the edition's native dpkg advertises capability 2 (Provides dpkg-lean-code) and recognises the lc1 mark: a conffile is accepted as unmodified only when (1) the owning package's original hash matches, (2) the current bytes exactly equal an independent re-render of the original, (3) the running binary's capability signal; a record cannot select a handler or executable. Proof set: conffile-verifier-test.py 17, conffile-events-test.py 16, conffile-transactions-test.py --installed 9 (names: unchanged_projection_upgrades_silently, split_unpack_configure_keeps_old_record, remove_then_reinstall_no_prompt, purge_after_unpack_removes_records, renderer_changed_same_run, renderer_changed_earlier_run, renderer_changed_conf_old, missing_verifier, forged_projection_cannot_hide_edit). Reviewer rerun in clean containers: green 9 of 9, red baseline `Ran 9, FAILED (failures=6, errors=1)` with the forged edit replaced without a prompt (lane dpkg-lean-conffiles-376)
- Perl quote-like operators (qr{...}x, q, qq, m, s) must be projected as checked code: all five formerly preserved dpkg Perl modules now use normal checked projection with comments in the HR companion. Proof chain: red on old renderer (124 failing subcases), green 60 methods, authored and projected `sq` matched comparison both 12,790, `check-debs` and `check-identity` on all 12 .debs, then the link gate, stage rechecked before and after (18 hashes unchanged) (lane lean-perl-quotelike-372)
- Make two Multi-Arch: same twins coexist when one is lean-projected: the edition's dpkg accepts only recorded projections of the twin's exact bytes and otherwise refuses with Debian's own message (Policy 5.6.34.3: "must either install no file there, or a bit-identical file"). Package Pre-Depends on the dpkg build (apt unpacks the Essential dpkg first by default; Immediate-Configure off needs Pre-Depends) and a virtual `dpkg-lean-code` Provides (lane dpkg-stereo-multiarch-363)
- Restore needs the original .deb: order cache, then sources, then a snapshot service query by file hash, with checks and then APT's `partial/` name; `--deb` is all or nothing and is read in place. Snapshot JSON: `result[{architecture, hash}]`, `fileinfo{sha1:[{archive_name, first_seen, name, path, size}]}`; one hash appears for both debian and debian-ports; percent-encoded epochs and `+` work; file names drop the epoch. `apt-helper download-file` errors look like `E: Failed to fetch URL 404 Not Found` or `Unable to connect`/`Could not resolve`, it runs as `_apt` and retries about 3 times (lane dpkg-stereo-restore-365)
- The link gate applies the APT preferences that supplied edition packages ship in /etc/apt/preferences.d (named by conffiles or md5sums), after its own exact pins, for every case; reads flat repository sources (suite ending in "/", components []) and an optional per-source architectures list. Install the new archive configuration only after the code is in main; the old code refuses it. With 5 sources the refresh needs 17 GiB free at the default floors (lane nvidia-dkms-link-gate-329)
- Running the lean gate (bubblewrap) inside a Docker container needs `--security-opt seccomp=unconfined --security-opt apparmor=unconfined --security-opt systempaths=unconfined` (nested bubblewrap needs the proc mount; also user namespaces with SYS_ADMIN); the gate needs SPARKY_LC_ARCHIVE_CONFIG and SPARKY_LC_SCRATCH, the preparation system needs bc and perl, and the archive config must list the edition's repository with its public key when a package depends on an edition package. A minimal bubblewrap preflight catches this before a long build (lane libc-dev-cross-256 / dp-stereo-257-m4c / dpkg-lean-conffiles)

- Every processor for per-file work (ORDER 638, 2026-11-17): `lean/parallel.py` `ordered(function, items)` gives `function(item)` for each item in the items' order, one file per task, on `processors()` workers: the process's affinity, no more than its cgroup's CPU quota (`/sys/fs/cgroup/cpu.max`; Docker's `--cpus` sets only the quota, so `os.sched_getaffinity` alone sees all 12 processors in a 4-CPU container, while coreutils `nproc` already gives 4). It runs the source projection (`source_tree.project_tree`), the payload projection with the xz of each authored original (`package.prepare`), `check_debs`, the ELF inventories of the link gate and, through `Archive.freeze` and `Archive.private`, the gate's packages side by side. Decisions, records, writes and printed text stay in the calling process, in order, so the output is the same bytes as before. The renderer files are not touched: the identity stays lean 0.1.29's. Each step prints its seconds and processors.

- The house floors in the gate (ORDER 638): `Archive` and `space()` default to 1 GiB on the root file system and, for the scratch, its own disk's floor (1 GiB on `/`, 2 GiB on another); a raised floor still applies, below 1 GiB is refused. The gate's own working room for a kernel flavour is small (build 18 v3: 0.7 GiB at its peak); a case of a big desktop package unpacks about 3.5 GB of roots, so packages checked side by side can reach a floor together: then `check_link` stops the pool, lets the running checks release their roots and checks that package and the ones after it one at a time, said in one line.

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: a package build stops in `override_dh_builddeb` with `.../org/kde/kirigami/controls/ListSectionHeader.qml: check failed: acorn could not tokenize the authored file` (Debian's Kirigami 6.32 rebuilt as `+lc1`), though the file is valid QML and Qt loads it.
  Cause: the QML check handed QML to acorn as ECMAScript, and `@` is no ECMAScript token; in QML it is one (Qt's lexer, `qqmljslexer.cpp`: `case u'@': return T_AT;`), opening an annotation before an object or a member (`qqmljs.g`: `UiAnnotation: T_AT UiAnnotationObjectDefinition`, `UiAnnotatedObject`, `UiAnnotatedObjectMember`; Qt 5.15 and later), here `@Deprecated { reason: "..." }` before `property alias label`. A failed check stops the build (`package.py`: `check failed:` is one of the three fatal reasons), so every QML file with an annotation stopped its package.
  Fix (toolkit 0.1.32, row 825): for a `.qml` file the Node helper reads `@` as a token of its own (an acorn parser extension: `getTokenFromCode(64)` finishes a `@` token), chosen by the file's name, which `project.project()` already has; a JavaScript file keeps ECMA-262's grammar and still fails its check on `@`; the render is unchanged. `tests/test_qml_annotations.py`: annotations before the root object, a child object and properties, with and without arguments, over several lines with a comment inside, `@` in comments, strings and template literals; a changed annotation, a moved line break and a dropped `@` refused; Debian's own file through `LEAN_TEST_KIRIGAMI_LISTSECTIONHEADER` (it carries its author's address, so it is not copied into the tree). Red on 0.1.31 (6 of 8), green on 0.1.32; the whole suite gains exactly those 8.
  Found by: acorn's own message for the file with the gate's options, `Unexpected character '@' (55:4)`, then Qt's grammar for the token. Sweep (row 77 milestone 3): the published repository's 38 packages that install QML (1,056 files) carry no annotation; Debian's Kirigami 6.32 carries one; Qt Declarative 6.11.2's tarball has two in its Fluent WinUI 3 style and ten in its own test data. A QML string over several lines is another QML difference: the reader cannot lex it and leaves the file authored with that reason (54 files in Calamares, Krita and Qt's sources), which never stops a build.
  What it obliges: a renderer file moved, so the version and its identity row; a client installed before 0.1.32 (dpkg-stereo 0.1.41 carries lean 0.1.29, 0.1.42 carries 0.1.30) meets a package built under 0.1.32 on the person's system: measure `dpkg-stereo --deep --verify` there before a round takes such a package (lane si752's verify row).

Fix: 0.1.43 keeps the record under the new version when the file is still the recorded projection and the new Conffiles hash is the recorded original's. Found by: three versions of one fixture (the same conffile in 1.0 and 2.0, changed in 3.0) on the published dpkg-stereo 0.1.41 (lane boot-menu-629)

Fix (0.1.37): OLDFORM and AFTERINST are information, named in the summary but not counted; MISMATCH and LCCHANGED stay damage; incomplete checks exit 2. A missing shipped file stays counted. Cause: restore demanded that the current renderer reproduce the older projection, but migrations restore earlier renderers' forms and re-project them. Fix: for a non-conffile, the owning package's md5sums identify the original and the recorded sha_lean must equal the installed bytes; conffiles keep the exact-render rule. Found by: the lean suite plus the installed c-drop-lines test that showed `original-mismatch` on real 0.1.19-era records (lane lean-test-baseline-397)
- Symptom: restore refuses every record written by dpkg-stereo before 0.1.27 (`original-mismatch`). Fix: treat an empty md5_orig as "the owning package's md5sums decide"; a recorded md5 must agree; test fixtures must carry what real old records hold (empty). Found by: running the installed proof with an old tree on real old records, not the fixture (lane lean-test-baseline-397)

- Symptom: `publish-tree.sh` refuses a package the build's link gate passed: "link check failed: ... stereo imports lost: NAME (the previous build called them)".
  Cause: a stereo call retired on purpose was declared only where the build could see it (the source tree), and the publisher has only the archives.
  Fix: a stereo call retired on purpose is declared in `debian/sparky-lean-retired-stereo-imports` (symbol as `nm -D` prints it, white space, reason); `lean.debhelper` writes it into the lc1 manifest of every archive as `retired_stereo_imports`, bound by the control mark, and `linkcheck.compare()` reads it only from the archive, at the build and at publication alike: each recorded symbol becomes a note in the log, every other lost import still blocks.

- Symptom: one test of the suite fails when the tree is mounted into a container, `test_appstream_off_publishes_what_main_published`: "Command '['git', 'show', '<commit>:sparky-os/repo/publish-tree.sh']' returned non-zero exit status 128", with "fatal: detected dubious ownership in repository at '/tree'" in the captured output.

- Symptom: the build's link gate stops a plugin package: "link check failed: /usr/lib/x86_64-linux-gnu/qemu/ui-gtk.so: 3 new undefined: error_free, error_reportf_err, warn_report_once_cond (the previous build resolved them)", far above `debian/rules:771: binary-helper] Error 1`.
  Cause: a plugin takes the symbols it leaves undefined from the program that loads it and from the plugins loaded before it. The published QEMU GTK module leaves 139 symbols to the loader (`LD_BIND_NOW=1 ldd -r`): 113 exported by `qemu-system-x86_64` (`--export-dynamic`) and 26 by `ui-opengl.so`, a module of another package in the same directory that QEMU loads first. The gate traces the plugin alone, and with a previous build every undefined symbol had to be in that build's result, so a module calling one more function of its program was blocked.
  Fix (ORDER 156b): a shared object outside the system library directories, whose previous build already left symbols to its program, may leave it new ones when every executable of the same build that supplies all the old ones (counting the build's shared objects in the plugin's directory) also supplies the new ones (`supplied_by_programs` in `lean/linkcheck.py`; exports read with `nm -D --defined-only` from the build's sibling packages); the gate says it in a note. No such program, a program without the symbol, a program that does not supply the old ones, or a library in a system library directory still block (five tests in `test_linkcheck.py`; on the unchanged gate the note test fails and the four blocking ones pass). On the real packages: the unchanged gate blocks `qemu-system-gui`, the changed one passes it with a note naming `qemu-system-i386` and `qemu-system-x86_64`.
  Found by: `grep -n 'link check failed' -A2` in the build log; then `nm -D --defined-only` on the built `qemu-system-x86_64` (all three exported); then a first version of the rule, which looked at the program alone, failed the next build the same way, and `ldd -r` on the published module with `nm -D --defined-only` over the module directory named `ui-opengl.so` as the supplier of the other 26.
  Prove a gate change on the real objects before another long build: pack the failed build's staged `debian/PACKAGE` folders with `dpkg-deb --build` and run `python3 -m lean.release check-link --archive-config FILE --scratch DIR --previous-dir PUBLISHED --siblings-file LIST NEW.deb` on the host (a copy of the gate's `sources.json` with host paths); it takes minutes.
  The toolkit travels inside the source (`debian/sparky-lean-toolkit`), so a gate fix means making the successor source again (same version and date, other bytes) and building again.

- Symptom: a pool of workers fails with "An attempt has been made to start a new process before the current process has finished its bootstrapping phase" or `BrokenProcessPool` inside a rebuilt standalone source. Cause: workers started as fresh interpreters (`spawn`, and `forkserver`, Python 3.14's default) import the caller's main module again, and the `build.py` a standalone recipe writes calls `release.build_tree` at its top. Fix: forked workers (`fork`), which never import it again and keep what the caller primed (the Rust token digests, a test's patch). Found by: `test_standalone`'s round trip, with the inner build's stderr printed by a wrapper around `subprocess.run`.
- Symptom (would be): two processes write to one acorn, bash or JVM checker and read each other's answers. Cause: a fork inherits the module globals holding the parent's checker process and its pipes (`lang_js._node`, `lang_shell._bash`, `lang_jvm._process`). Fix: each worker drops them at start and starts its own; a `multiprocessing.util.Finalize` at exit closes what it started and keeps the Zig and Rust tools its parent built (removing the parent's temporary folder from a child would break the parent). Found by: reading every module global of the `lang_*` files before choosing the start method.
- Symptom: the pool's processors fall to one after a few minutes; ten workers idle, one busy. Cause: tasks handed out in batches of consecutive files: one batch held a directory of huge generated headers (amdgpu's `asic_reg`), 8 min of one worker against 1 min 45 s for the others. Fix: one file per task. Found by: the processor time of each worker process (`ps -o cputime` on the container's pids).
- Symptom: a toolkit test that patches `project._verify` sees no failure once its package has several files. Cause: a patch lives in the process that made it; fresh workers check with the real function. Fix: forked workers inherit the patch; the test stays as written.
- Symptom: `xz` output differs between two machines. Cause: `-T1` is the single-threaded format, every other count the multi-threaded one, whose blocks do not depend on the number of threads (xz 5.8.4: `-T+1`, `-T2`, `-T6`, `-T+12` and `-T0` give one SHA-256, `-T1` another). Fix: `-T+N`, multi-threaded mode at any N. Found by: compressing 60 MB of kernel source with each count.
- Symptom: the round's check-link runs for hours on one processor, one apt-get at a time. Cause: one `Archive` per architecture, its apt state (`Dir::State`, `Dir::Cache`, locks, pins) shared by every package, and every input's file list read one archive at a time. Fix: `Archive.freeze` reads inputs on every processor and admits them in order; `Archive.private` gives each forked worker its own apt state over the same frozen lists (hard links: apt replaces a list by renaming over it; lock files and `partial` folders are not linked); a local universe or a cached input made by two workers at once is the same bytes, and the second writer accepts the first's. Found by: reading `check_link`, `Archive.__init__`, `run` and `universe` for every path written.
- **Symptom:** after an upgrade on a machine installed from an early image, dpkg-stereo says "the verifier is missing or its executable or library is not trusted" for every projected conffile the upgrade changed (five of dbus's, in the measured run), ends with "conffile verification did not complete: N conffiles used dpkg conflict handling", and `sudo dpkg-stereo --repair` fails for the same N afterwards (ORDER 707).
  **Cause:** two faults that meet. (1) dpkg-stereo 0.1.0 to 0.1.7 were built with the build user's umask (0002) and shipped `/usr/lib/dpkg-stereo` and `lean` as 0775; `umask 022` entered the recipe in 0.1.8. dpkg keeps the mode of a folder it finds (Debian Policy, chapter 10, "Permissions and owners": changing the permissions of a directory a package owns needs explicit action, usually in the postinst), so the folders stayed group-writable through every upgrade. The trust check that refuses a group-writable folder is right: dpkg's native caller (`leancode_verifier_open`, patch 0005) walks `/`, `/usr`, `/usr/lib`, `/usr/lib/dpkg-stereo`, `conffile-verify` and refuses any step another user can write, before it runs anything, and the verifier walks `lean/` the same way. Exit 14, and dpkg falls back to its own conffile rules. (2) `--repair` rechecked a refused conffile only by its MD5 against the package's, so a file dpkg had installed and the post-invoke had projected (the usual end of the fallback) never settled even with the folders right.
  **Fix:** the package that owns the folders sets them: the preinst of an upgrade and the postinst take group and other write off what root owns under `/usr/lib/dpkg-stereo` (and the recipe `chmod 0755` on every folder it ships, whatever the build's umask); the refusal names the folder and the failed check (`conffile_events.trust_findings`, ten languages); `--repair` sets the same tree right, says so, and settles a file that is its package's bytes or the exact projection of its package's original. The check is not loosened, nothing outside the tree is touched, no conffile is written.
  **How found:** the recipe's git history (`git log -S'umask 022' -- build.sh` gave 0.1.8), then a throwaway container with the published packages and the folders at 0775 reproduced the sentence word for word with a generated package pair; a stub in place of `conffile-verify` showed dpkg refusing before it ever ran (folder 0775) and running it when only `lean` was 0775.
- **Rule: a package whose runtime trusts its own folders by mode sets those modes itself.** The recipe fixes the mode of every folder it ships, a maintainer script repairs an existing machine's (dpkg never will), and the program that refuses says which path failed which check instead of "not trusted". Test it with a generated package pair on a machine whose folders are in the bad state: the upgrade is refused (red), the successor is installed, the same upgrade completes (green), a folder made group-writable afterwards is still refused and named, `--repair` mends only the package's own tree, and a person-edited conffile keeps its bytes (recipe `test/modes-test.sh`, `test/conffile-events-test.py`).
- **Rule: a published package is built from a commit of the build tree.** A build made from a scratch repository (a `git archive` of an older commit plus a patch) records a recipe commit that exists nowhere, so nobody can find what built it. Rebase the fix onto current main, build from that branch head, and let the package carry main's toolkit, said in its changelog when the renderer's identity moves; then measure that move on a machine projected by the previous version (`dpkg-stereo --verify --deep`: the count of OLDFORM rows and of counted problems). Found in the review of ORDER 707.

- Symptom: a local rebuild of a Lean Code source stops in `override_dh_builddeb` with "check-link needs --archive-config / --scratch (or SPARKY_LC_ARCHIVE_CONFIG / SPARKY_LC_SCRATCH)". Cause: the gate (`lean.release check-link`, called by `lean.debhelper`) reads those two variables and nothing else; a build outside the edition's builders has neither. Fix: the helper builds archive.json from the computer's own apt sources and gives the build a private scratch (sparky-stereo-ffmpeg-fdk, link-config). A small architecture: all package reaches the same call in seconds: without the variables the message above, with link-config's archive.json "archive-qualified link check passed for 1 packages" (ORDER 462). Found by: reading the call in release.py, then running it on a package of one file.
- Symptom: a fix reached the machine but the failed build is never tried again. Cause: the update check skipped a version that had failed ("not tried again for the same version") and the failure record (migrated from an older helper) did not say which helper failed. Fix: record the helper's version with the failure and retry once when it differs or is missing. Lesson: a deterministic failure is retried when its cause may have changed, never on a timer.
- **Symptom:** `lean.debian_prepare` stops with `Existing execute_before_dh_auto_configure: preserve and integrate its behavior explicitly` on a Debian source whose own `debian/rules` defines that hook (glib2.0: `execute_before_dh_auto_configure: cross-tools`). **Fix (ORDER 768b):** the step now keeps a configure or clean hook the rules file defines and appends `HOOK: .WAIT sparky-lean-source-project` (or `-restore`) with the toolkit's commands in that target, so they run after the hook's own prerequisites and before its recipe, also under `make -j`; dh's plain-first rule decides which forms of the hook it joins; a rules file with none of the targets gets the old text byte for byte, and `override_dh_builddeb` is still refused, with `debian/rules:LINE:`. `repo/plain-from-lc.py` reads the kept form too, by checking the tail against the step's own `lean_rules`. Details and the proof: [a Debian base library with one upstream commit](../../edition-packaging/references/a-debian-base-library-with-one-upstream-commit.md), trap 1.
- Symptom: a package build ends after `dpkg-deb` with "isolated execution unavailable: bwrap: setting up uid map: Operation not permitted" in `override_dh_builddeb`, although bubblewrap works in the same container. Cause: the source declares `Rules-Requires-Root: binary-targets`, so dpkg-buildpackage runs the binary targets under fakeroot, and bubblewrap inherits fakeroot's `LD_PRELOAD`, believes it is uid 0 and cannot map that user (`fakeroot bwrap --unshare-all --ro-bind / / true` fails the same way; plain `bwrap` passes). Fix: when the rules change no owner (only modes), the recipe sets `Rules-Requires-Root: no` (dpkg-deb still gives every file root:root); otherwise the gate would have to start bubblewrap without fakeroot's variables, a change to `lean/archive.py` (`Qualified.run`) not made here. Found by: the log's last line, then the two one-line runs above in the builder image (KiCad, ORDER 50 step 3; Debian's kicad declares binary-targets, GRASS declares nothing and passed).
- Symptom: a program the link and start gate starts aborts during a recipe build, and the crash lands in the station's crash list (`coredumpctl list` shows it with COREFILE none, "terminated abnormally without generating a coredump"), although the recipe's `docker run` carries `--ulimit core=1`. Cause: the recipe's own shell inside the container ran `ulimit -c 0` (the older rule); runuser and bubblewrap keep the limit they are given, so the gate's programs ran with 0, and for a piped `core_pattern` only a limit of exactly 1 stops the helper. `ulimit -c 1` is no fix: bash counts the core limit in 1024-byte blocks, so it asks for 1024 bytes over docker's 1-byte hard limit and fails with "cannot modify limit: Operation not permitted" (a `set -e` build stops at that line). Fix: no core ulimit in a container's shell; `docker run --ulimit core=1` alone sets it; `tests/supply-chain/check-container-core.py` refuses any. How found: `/proc/self/limits` read at each layer (container `1 1`, after the shell's ulimit `0 0`, under `runuser` `0 0`, inside the gate's `bwrap` arguments `0 0`; without the ulimit `1 1` at all four), and bash's own `ulimit -c` reading 0 where `/proc/self/limits` reads 1, which is how 0 looked equal. Never abort a program on purpose to test the limit. (ORDER 742)
- Symptom: a crash record names `ld-linux-x86-64.so.2 --inhibit-cache --library-path ...` and is blamed on the build running at that minute. Cause: that is the gate's loader form for every program it starts; the program is the last word of the record's Command Line (`coredumpctl info PID`), here `/usr/bin/spectacle --version`, which no package of the build carried. Fix: read the whole command line before naming the build; the gate's smoke check starts only the programs of the package under check. (ORDER 742)
