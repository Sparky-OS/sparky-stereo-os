# native-linux: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: the test machine panics with the drm_panic screen during a "fill VRAM" stress. Cause: the test looped on "gem_create(VRAM) succeeds"; amdgpu adds GTT to the allowed domains for user buffers, so when VRAM was full buffers went to system memory until RAM (11.3 GiB) and swap were gone (journal: 13 OOM kills from baloo_file to systemd, "Free swap = 4kB"). Fix: stop when `mem_info_vram_used` says the card is full or after a buffer cap, refuse a VRAM size it cannot read; never stress a GPU the compositor uses; `systemctl isolate multi-user.target` does not stop the user session's kwin_wayland. Found by: reading the previous boot with `journalctl -k -b -1` (the log ended in the OOM dump, pstore empty). (lane amdgpu-devcoredump-deadlock-417)
- Symptom: every X11 child-window row fails on every run in KDE's stock CI images; stereoChild->surface stays null. Cause: stock Xwayland 24.1.13 gives a manually redirected child the surface of its toplevel, so no WL_SURFACE_SERIAL. Fix: build the edition's Xwayland (xwayland patches 0001, 0002, 0006) into a copy of the CI image once per version; --xwayland edition|stock|auto. Found by: running the same tests with Xwayland built from the repository's orig plus 8 patches (lane kwin-x11-child-243)
- Symptom: ARGB to NV12 buffer switch in a browser terminates with SIGSEGV after an exact first frame; NV12 to ARGB renders all 4096 test pixels wrong (max channel error 128). Cause: 6.7 texture-plane update path on a same-device format change. Fix: commit 61400cf626, both directions tested; every ARGB pixel exact, NV12 within one quantization level. Found by: a controlled baseline with texture code identical to +21 (lane kwin-wiz3d-outputs)
- Symptom: a client with its own `wp_viewport` that asks for two views dies with fatal `wp_viewporter error 0 "the specified surface already has a viewport"`. Cause: a two view Wayland surface needs Mesa's own wp_viewport (buffer twice as wide shown at window size) and a wl_surface can have only one; GLFW, SDL 3, Blender, Godot and GTK 4 create their own. Fix: libraries ask for stereo and leave the viewport to Mesa for a stereo window. The EGL request is `EGL_EXT_multiview_window` (`EGL_MULTIVIEW_VIEW_COUNT_EXT` at eglCreateWindowSurface); EGL configs have no stereo attribute; GLFW refuses before calling EGL (egl_context.c:113-117); GtkGLArea draws into its own FBO. Found by: test e0-stereo-viewport-gpu. (lane magnum-stereo)
- Symptom: a mono EGL window that read GL_FRONT once draws at half its width (38400 of 76800 pixels; GLX 38383 of 76766; Debian Mesa 76800). Cause: `st_manager_add_color_renderbuffer()` marked a window stereo for any colour buffer added on demand, front-left included. Fix: Mesa commit "mesa/st: only a right-eye buffer makes a window framebuffer stereo"; plus "egl/wayland: make two-view window surfaces stereo at their first right-eye use" (starts one view, no viewport, no declaration, switches at the first right-eye draw). Found by: the "no cost to 2D windows" check. (lane magnum-stereo)
- Symptom: two view surfaces at `set_buffer_scale(2)` are twice too large (320x240 window with 640x480 buffer covers 76800 pixels mono and 307200 per eye in stereo). Cause: Mesa sets the viewport destination to the buffer size of one view (egl_stereo_set_destination in platform_wayland.c) and cannot read the buffer scale a client set. Fix: not fixed; open question (library or compositor knows both). Found by: `kwin_wayland --scale 2` capture. (lane magnum-stereo)
- Symptom: GLFW/Magnum through GLX on Xwayland: colours arrive per eye but the geometry is wrong (first GL_VIEWPORT 160x240 for a 320x240 window; scene drawn in the left half of each eye, green cube 272 px per eye against 1190 on Wayland, 13 of 24 edges within 1 px). Cause (likely): GLX version 3 sizing (glx_dri3_set_drawable_size and KWin's doubling of a declared X11 window); X11 window reads 640x240 once declared. Fix: not fixed; a program that sizes its viewport from the window or first framebuffer size gets the wrong one. A colour test passes, so a geometry check is required. (lane magnum-stereo)
- Symptom: the brief said a KAuth path existed in Graphics 0.2.5 and the work stalled. Cause: the base had none. Fix: read the code before trusting the brief; follow the Memory page's KAuth pattern: a fixed-path helper that takes exactly one typed boolean, takes a lock, keeps other settings and comments, writes atomically, accepts no path or command. Found by: grepping the base. Test allow and deny on a private system bus (allow 4 passed, deny 4 passed). (lane no-fallbacks-drivers-346f2)

- Symptom: a program that draws its 3D scene through Qt Quick's two eye passes on a Vulkan swapchain with two layers (Mesa packs and declares it) shows one eye twice on a side by side (full) output, in a guest that draws in software; its status line says both eyes are drawn; the same program declaring a pair of views itself shows two eyes. Cause: Qt Quick's threaded render loop drew a frame made for an expose once and put it into both eye targets (`polishAndSync(inExpose)`, `syncAndRender()`), and asked for no frame after it; QtWayland exposes a window again after each frame callback later than 100 ms, and Qt makes the swapchain again each time. Fix: the loop draws an expose's frame as a pair too, the left eye synchronized as in any frame and the gui thread held until both are presented (qt6-declarative 6.11.2+dfsg-3+stereo3d3, patch s3-0001, "Quick: draw a frame made for an expose as a pair too"); asking for one more frame after the expose made the picture alternate, because that frame's callback was late again. Found by: recording every committed buffer to the last one (the first frame of each new swapchain had equal halves, the others 39,280 differing pixels), `qt.scenegraph.renderloop=true`, a plain two-layer Vulkan client that stayed right over three swapchains (so not Mesa, not KWin), and two runs that showed two eyes: `QSG_RENDER_LOOP=basic` and `QT_WAYLAND_FRAME_CALLBACK_TIMEOUT=0`. A flat picture under a real output is not the compositor's until the last committed buffer has been read (lane kwin-drm-vulkan-declared-flat-555)

## Measured facts

- libstereo-declare 1.7.0: stereo_declare_x11_child / stereo_remove_x11_child (remove deletes the declared place); CHILD_PLACE kept apart from the child's rectangle, precedence in X11StereoChild::place(); a child may carry CONTENT_ONE_VIEW_SIZE at version 8. ctest 6 of 6; first test run 30 failures on stubs (lane kwin-x11-child-243)
- Debian's libsdl2-2.0-0 is sdl2-compat over SDL 3, so a native SDL 2 or 3 game using the system SDL and asking SDL_GL_STEREO gets two eyes on Wayland with the edition's libsdl3 (before: 2D, attribute reads 0); a game bundling its own SDL keeps its behaviour; sdl2-compat forces X11 for programs linking libX11 (src/sdl2_compat.c:953-968), which then go through the GLX route. Magnum: use GlfwApplication for stereo (Sdl2Application has no stereo flag). (lane magnum-stereo)
