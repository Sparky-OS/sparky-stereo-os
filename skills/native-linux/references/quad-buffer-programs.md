# Programs that draw OpenGL quad-buffer stereo, swept on the edition's desktop

A program that asks for a stereo visual and draws `GL_BACK_LEFT` and `GL_BACK_RIGHT` needs no change on the edition: Mesa gives the window two views and declares it as full side by side, and Stereo KWin does the rest (see the [contract](../../sparky-stereo/SKILL.md#part-one-the-contract)).
This page records the sweep of 18 November 2026 (ORDER 26): which program has which switch, which route it takes, the capture recipe and the traps.
Versions are those of that day: Mesa 26.1.6-1+stereo3d24, Xwayland 24.1.15-1+stereo3d3, Stereo KWin 6.7.4-2+stereo3d58 from the published tree, Debian testing for everything else.

## The short recipe

1. One throwaway container from `debian:testing` with the published tree as an apt source (pin 1001) **and deb-multimedia** (our Blender and FFmpeg libraries need `libaom3 >= 1:3.15.3` from it; without it apt answers `libavcodec63 ... [no choices]`).
2. A fresh `HOME` for every case (KWin keeps its output configuration and window states there) holding `.config/kwinrc` with `[Xwayland]` `XwaylandEisNoPrompt=true`, so `xdotool` reaches X11 clients.
3. `dbus-run-session`, then `kwin_wayland --virtual --xwayland --socket=w --width 1280 --height 800`, the program on `DISPLAY=:0` (Xwayland) or `WAYLAND_DISPLAY=w`, wait, `capture.py` twice, `x11_props.py` for the declarations. The GPU is a render node (`--device /dev/dri/renderD128 --group-add 125`) or the RTX 3060 through CDI (`--device nvidia.com/gpu=0`); with no GPU ScreenShot2 answers `Cancelled`.
4. On the NVIDIA row source the session's own `/etc/xdg/plasma-workspace/env/sparky-stereo-opengl.sh` (unpack the published sparky-stereo-hardware; it needs `kreadconfig6`, from `libkf6config-bin`, or it exports nothing) with `SPARKY_STEREO_OPENGL_CONF` naming a file that holds `desktop=nvidia` and `opengl=zink`.
5. Read the capture as two RGB arrays. A stereo capture is twice the output's width; a one-view capture is not stereo. Count differing RGB pixels, count them outside the declared area, measure the shift in pixels with its sign, and run the swapped reading, which must fail.

## Eye tags that work

| Program | The tag | Why it can fail |
|---|---|---|
| any scene | a near object tagged green (nearer than the zero-parallax plane, crossed, shift negative) and a far one tagged red (uncrossed, shift positive); the centroid of each colour in the right eye minus the left | swapped eyes flip both signs and fail |
| osgviewer | the program's own `--stereo LEFT_EYE` and `--stereo RIGHT_EYE` renderings of the same window, compared pixel for pixel with each eye of `--stereo QUAD_BUFFER` | 0 differing pixels for the right pairing, 16,464 for the swapped one |
| glxgears | none of its own (both eyes use one colour); the source says the left eye's scene is moved by `+0.5*eyesep` with an asymmetric frustum; the measured shift is reported and the identity rests on a calibration client | see Not proven in the lane report |
| calibration client | `scripts/quad-buffer-sweep/qbtest.c` (a red square in `GL_BACK_LEFT` at x=-0.2, a blue one in `GL_BACK_RIGHT` at x=+0.2): shift +128 px in a 640 px window, as predicted from 0.4 * 640 / 2 | proves the rig and Mesa's mapping before any program is trusted |

`osgviewer`'s home position normalises the model, so the model's size changes nothing: do not predict its shift from world units, use the per-eye renderings.
Block matching along rows gives a median over textured blocks; report the minimum and the maximum too (the edges of a flat shape match anywhere, so -200 px outliers appear).

## Traps

- **Symptom:** FreeCAD's Quad Buffer entry changes nothing and Mesa prints `GL_INVALID_OPERATION in glDrawBuffer(invalid buffer GL_BACK_LEFT)` under `MESA_DEBUG=1`. **Cause:** Quarter's viewport is a `QOpenGLWidget` (`CustomGLWidget` in `Quarter/QuarterWidget.cpp`), `View3DInventor` fills its `QSurfaceFormat` with samples only, never `setStereo(true)`, and Coin's `QUAD_BUFFER` mode draws to the two back buffers of a mono context. **Found by:** `MESA_DEBUG=1`, then reading the 1.1.3 sources. Upstream removed the feature on 2026-06-09 (FreeCAD pull request 30634, "Remove stereo views", also closing issues 27816, 21496 and 30633).
- **Symptom:** ParaView's `--stereo` window is flat and the program's log shows `paraview is shown flat: the desktop's X server could not show the two pictures of its 3D window together`. **Cause:** a declared child window's first presents complete as copies, Mesa takes the pair back (rule of ORDER 561b); it is the case of [x11-declared-child-limits-and-first-pair.md](x11-declared-child-limits-and-first-pair.md) (ORDER 697 and 698, staged Mesa +26 and KWin +59). **Found by:** five and six repeated runs per GPU, the capture's `stereo` flag and the notice in the log.
- **Symptom:** the same notice is printed by a top-level GLX program (`glxgears -stereo`, the calibration client) on the AMD card while two captures seconds later are a pair. **Cause:** not found; the notice appears to come from the first copied presents and the pair returns. It is a false alarm for the person and belongs to Mesa's `u_stereo_pair` rule.
- **Symptom:** Debian's Blender 5.2.2 aborts (`blender.crash.txt`, no symbols) when its window's display mode is set to Time Sequential, on Wayland and on X11; without stereo it runs. **Cause:** our published Blender is 5.0.1 with the edition's patches and pins above Debian's 5.2.2, so the patches are not on 5.2. **Found by:** `TMPDIR` pointed into the lane folder so the crash file survives the container.
- **Symptom:** the NVIDIA row measures nothing, KWin logs `eglInitialize failed` and Xwayland `GBM Wayland interfaces not available`. **Cause:** the session script exports `__EGL_VENDOR_LIBRARY_FILENAMES` with Mesa's vendor file first, which a virtual KWin on the NVIDIA render node cannot use; a real session's KWin runs on the DRM backend. **Fix in the rig:** keep the variable away from KWin and Xwayland and export it again for the program only (GLX programs use `__GLX_VENDOR_LIBRARY_NAME=mesa`). **Found by:** `kwin.log`.
- **Symptom:** `QT_QPA_PLATFORM=xcb` set by the caller has no effect. **Cause:** the rig script exported it empty. **Symptom 2:** Qt's Wayland plugin reports `No shell integration named "xdg-shell" found`: `qt6-wayland` is not in the image, so Qt programs ran on Xwayland only.
- **Symptom:** a click or key from `xdotool` does nothing. **Cause:** KWin's Xwayland input prompt; set `XwaylandEisNoPrompt=true` in the rig's `kwinrc`. A native Wayland client (Blender) never receives XTEST events: set what it needs in its preference file (`show_splash` false through `blender -b --python-expr ... save_userpref()`).
- **Symptom:** Debian's ParaView has no `paraview` Python module, so `--script` fails (`ModuleNotFoundError`). **Fix:** open a legacy VTK file (`two.vtk`, two squares at different depths) and press Apply with a key and a click.
- **Symptom:** a case measures the one before it. **Cause:** a shared `HOME` keeps KWin's `kwinoutputconfig.json` and the programs' settings. **Fix:** a fresh `HOME` per case.
- **Symptom:** the edition's Jmol (its display as a declared 3D area, row 50) opens the Display menu cut at the 3D area's top edge, in every language, so "Enable 3D" cannot be seen to switch 3D off; with Enable 3D off the menu is whole. **Cause:** Swing draws a light popup inside the frame, under the area's own X window; the area made popups heavyweight with `JPopupMenu.setDefaultLightWeightPopupEnabled(false)`, but a `JPopupMenu` copies that default in its constructor and a `JMenu` constructs its popup at its first `add`, so the menu bar's menus, built before the area, kept light popups. **Fix:** when the area is made, search the frame's component tree for every `JMenuBar`, walk each as a `MenuElement` tree and call `setLightWeightPopupEnabled(false)` on every `JPopupMenu` in it (jmol patch 0003, row 50 step 5); a popup that is not lightweight asks `PopupFactory` for type 2, a heavyweight window of its own, which stacks above the area. Do not rely on `getRootPane().getJMenuBar()`: Jmol adds its menu bar to its panel with `add("North", menubar)`, so that returns null, and the patch's first form, built that way, walked nothing and changed nothing on screen. **Found by:** the X tree with the menu open (`xwininfo -root -tree`: no popup window, only the frame and the area), the cut falling exactly at the area's top, `javap -c -p javax.swing.JPopupMenu` (the constructor's `getDefaultLightWeightPopupEnabled` then `putfield lightWeightPopup`; `getPopup` choosing type 0 or 2), and the rebuilt package's menu still cut, which sent me back to JmolPanel's `setupDisplay`. To open a Swing menu in the rig, activate the window and send its mnemonic with `xdotool key --clearmodifiers`; a localized menu bar has its own mnemonics (German "Anzeige" is not Alt+A, which opens "Ansicht").

## ParaView, re-tested on the published tree (21 November 2026)

Debian's ParaView 6.1.1+dfsg1-3, unchanged, on the published tree r1118a (Stereo KWin +stereo3d59, Mesa +stereo3d26, Xwayland +stereo3d3), a 1920x1080 virtual output, one fresh session per run.
Fixture: a legacy VTK file of two squares, the far one 2x2 at z = 0 coloured by scalar 0 (blue), the near one 0.8x0.8 at z = 1 (red), opened with `--data` and Auto Apply, the window maximized by a KWin script.

**How ParaView makes its pair (read in Debian's sources):** `--stereo-type` sets the Render View's `StereoType` (Remoting/Views/vtkSMRenderViewProxy.cxx, the client's type taken as given); the view is VTK's `QVTKOpenGLStereoWidget`; VTK 9.6 shears each eye's projection by plus or minus half its `EyeAngle` (2 degrees, ParaView sets none of its own) about the camera's focal distance (vtkCamera.cxx, `vtkPerspectiveTransform::Stereo`), in eye space before the frustum: two parallel off-axis cameras `D tan(1 deg)` to each side, zero parallax at the focal point. The closed form is `disparity = 2 f tan(EyeAngle / 2) (1 - D / depth)` pixels, `f` the focal length in pixels; the rig solves `f` and the near square's depth from the two squares' captured widths (sizes 2 and 0.8, depths one apart) and takes the focal point at the box's centre, as VTK's ResetCamera does.

## VTK's draw-buffer state fault in its Qt windows

Found and fixed in row 50, step 5 (21 November 2026), in Debian's vtk9 9.6.2+ds-3 (the edition's vtk9 9.6.2+ds-3+stereo3d1+lc1).

- **Symptom:** a VTK program in Crystal Eyes stereo (a quad-buffered `QVTKOpenGLStereoWidget`, ParaView with `--stereo`) prints `Generic Warning: ... vtkOpenGLState.cxx:222 Error in cache state for GL_DRAW_BUFFER got 1027 expected1029` at every frame, each followed by a stack line; ParaView shows them in its Output Messages window. 1027 is `GL_BACK_RIGHT`, 1029 `GL_BACK`. A mono window and the left eye never warn.
- **Cause:** `QVTKOpenGLWindow::paintGL` resets VTK's state cache, renders, then blits the left eye into `GL_BACK_LEFT` and the right eye into `GL_BACK_RIGHT` through `QVTKRenderWindowAdapter::blit` (GUISupport/Qt/QVTKRenderWindowAdapter.cxx), which bound the target and set its draw buffer with Qt's own `glBindFramebuffer` and `glDrawBuffers`, outside `vtkOpenGLState`. The cache kept the `GL_BACK` it read at the reset; the first VTK call of `vtkOpenGLRenderWindow::BlitDisplayFramebuffer` runs `vtkOpenGLState::CheckState`, which reads `GL_DRAW_BUFFER` from OpenGL and counts `GL_BACK_LEFT` as `GL_BACK`, so only the right eye mismatches.
- **Fix:** bind the target and set its draw buffer through the state object (`vtkglBindFramebuffer`, `vtkglDrawBuffer`), as the same function already disables the scissor test and as VTK merge request 4818 (Cory Quammen, 2018) moved `QVTKOpenGLNativeWidget`'s blit off a direct `glDisable`. `vtkglDrawBuffer` also writes the draw buffer into every stacked entry of that framebuffer, because a draw buffer belongs to its framebuffer, so the `Pop` at the end of `paintGL` leaves cache and OpenGL equal. VTK's own `BlitDisplayFramebuffersToHardware` already sets `GL_BACK_RIGHT` through the state.
- **How the cause was found:** the count per run in ParaView's log; reading `CheckState` (the `GL_DRAW_BUFFER` block and its `GL_BACK_LEFT` folding) and decoding 1027/1029; then the blit path from `paintGL` to the first `vtkgl*` call.
- **Which library:** Debian's paraview carries no Qt widget code of its own: `/usr/bin/paraview` NEEDs `libvtkGUISupportQt-9.6.so.1` from Debian's shared vtk9 (`libvtk9.6-qt`), and the running process maps `/usr/lib/x86_64-linux-gnu/libvtkGUISupportQt-9.6.so.9.6`. So the fix is in vtk9, and every program that loads VTK's Qt support gets it.
- **Upstream, searched on 2026-11-21:** VTK master (3b39346a) has the same `blit` and `paintGL` as 9.6.2; no commit since 2025-06 touches the Qt adapter; no merge request or issue names this desync. VTK's AI policy (AI_POLICY.md, 2026-10-26) asks for the person's own name on the commit, no AI co-author, the disclosure in the merge request template.
- **A test that needs no ParaView:** `sparky-os/tests/paraview-stereo/vtk-quad-buffer-blit` in the build tree draws a cone in a `QVTKOpenGLStereoWidget` in Crystal Eyes for 60 frames and counts the warning through the output window's `WarningEvent` (exit 0 none, 1 some, 77 no stereo context). Red, on Debian's vtk9 9.6.2+ds-3: exit 1 with 117 to 123 warnings in 60 frames, on Wayland and on xcb, on the AMD card and the RTX 3060 (zink). Green, on the edition's 9.6.2+ds-3+stereo3d1: exit 0, no warning in 60 frames, on both routes and both cards. The test's capture comes 1.2 s after its start: without warnings to print the program can finish its 60 frames before that (it did on the RTX 3060), so the capture is not the verdict; the warning count and the stereo context are, and a program that stays open (ParaView) shows the pair.
- **Traps:** Debian's VTK CMake package names `MPI::MPI_C` in `VTK::mpi`'s link interface, so a consumer finds MPI first (`find_package(MPI REQUIRED COMPONENTS C)`, with C enabled in `project()`) or configuring fails with "The link interface of target "VTK::mpi" contains: MPI::MPI_C but the target was not found".

## ParaView as an edition package (row 50, step 5)

ParaView 6.1.1+dfsg1-3+stereo3d1+lc1 offers one stereo output, the declared pair (Crystal Eyes, which the edition's Mesa packs and declares), and keeps its own eye separation (a program that draws its own pair).

Where its stereo types live in 6.1.1, and what the edition's build does with each:

| Place | Upstream | Edition |
|---|---|---|
| `--stereo-type` (Remoting/Core/vtkRemotingCoreConfiguration.cxx, `ParseStereoType`) | seven types, default Anaglyph | 'Crystal Eyes' only, the default; the six others refused with a sentence that says what to use instead |
| Render View `StereoType`, `ServerStereoType` (Remoting/Views/Resources/views_remotingviews.xml, panel group "Stereo") | eleven entries, shown when stereo is on | Crystal Eyes, Left, Right, None (and Same As Client); not shown in the properties panel |
| Screenshot `StereoMode` (utilities_remotingviews.xml, SaveScreenshotOptions) | Red-Blue, Interlaced, Dresden, Anaglyph, Checkerboard, Side-by-Side Horizontal beside the eye choices | No change, No stereo, Left Eye Only, Right Eye Only, Both Eyes |
| The view's widget (Qt/Core/pqQVTKWidget.cxx) | stereo-capable (`QVTKOpenGLStereoWidget`) only with `--stereo`, chosen when the view is made | the same, decided by the Render View setting "Enable 3D" (on by default) at start |

- **Enable 3D at start, not live:** ParaView makes each view's widget once (pqView::widget) and nothing replaces it; a stereo window that draws one picture keeps a stale right eye, and "Convert To" makes an empty view. So Enable 3D (Settings, Render View; and the View menu) takes effect at the next start, said by ParaView's own `RestartRequired` hint in the Settings dialog and once from the menu.
- **The setting is read before the first view:** `vtkInitializationHelper` loads the user settings before the main window is built, so `ParaViewMainWindow`'s constructor reads `.settings.RenderViewSettings.Enable3D` with `vtkSMSettings::GetSettingAsInt` and sets `vtkRemotingCoreConfiguration` (two setters added).
- **Old settings and state files:** a `StereoType` or `ServerStereoType` naming one of the six (a state file saved by another ParaView, a saved view default) becomes the pair, or None with Enable 3D off, in a queued slot of `pqRenderView` on the property's ModifiedEvent, and the person is told once.
- **A desktop without 3D areas:** the stereo-capable window's context comes back without two views; `QOpenGLWindow::frameSwapped`, once, checks `context()->format().stereo()` and tells the person once.
- **What stays in the binary:** Debian's shared vtk9 keeps every stereo type in vtkRenderWindow for the other programs that load it.
- **Sentences:** gettext domain `paraview-stereo` (`vtkPVStereoEdition.h`), catalogues built with msgfmt by the patched Clients/ParaView/CMakeLists.txt. The Settings dialog shows XML labels through `QCoreApplication::translate("ServerManagerXML", ...)`, so a small `QTranslator` answers that context for the setting's label and description. Debian's ParaView ships no interface translations, so its menus are English in every language and a translated sentence names "View" as the person sees it.
- **Build:** Debian's 6.1.1+dfsg1-3 with patches 0001 (one output, Enable 3D, the menus, the refusals) 0002 (the Wayland caution at INFO) and 0003 (Enable 3D off without the stereo format request; notices after the first frame) and `translations/paraview-stereo.po.patch`, against Debian's libvtk9-dev (ParaView compiles none of VTK's Qt adapter, so its binaries are the same on either vtk9): 50 minutes on four threads, the work folder 5.3 GB at the end with the debug information compressed (Debian's buildd: 31 minutes on six threads, 7.1 GB with plain `-g`), the stage 248 MB. Compared with Debian's three packages: nothing left; added the nine `paraview-stereo.mo` catalogues and the Lean Code manifests; libpqCore and the `paraview` program only gain symbols (`pqRenderView::keepStereoPair`, the View menu's Qt objects); the changed headers, `paraview_client_main.cxx.in` and `simple/io.py`'s `SaveScreenshot` text are the patches'; icons differ only in their PNG `tIME` chunk.

Traps:
- **Symptom:** with Enable 3D off the edition's ParaView crashed at every start (segmentation fault, exit 139). **Cause:** the edition makes Crystal Eyes the configured stereo type, and `pqQVTKWidget`'s constructor asks the stereo widget for its stereo format whenever the type is Crystal Eyes, while with Enable 3D off it makes the native (mono) widget, so the stereo widget is a null pointer (Qt/Core/pqQVTKWidget.cxx, after "if active stereo requested"). **Fix:** request the format only when the stereo-capable widget was made (`this->useStereo && ...`, patch 0003). **Found by:** every Enable 3D off row exiting 139, then gdb with paraview-dbgsym in a rig image (`pv-gdb-case.sh`): frame `QVTKOpenGLStereoWidget::setFormat (this=0x0)` from `pqQVTKWidget::pqQVTKWidget (isStereo=false)`.
- **Symptom:** a told-once notice (a `QMessageBox` opened with `open()` over ParaView's main window) never appears on Wayland although its code runs. **Cause:** Qt recreates a top-level's platform window when the first render-to-texture widget is added to it (VTK's `QVTKOpenGLNativeWidget`, which ParaView's colour map editor adds once data is shown: the main window gets a second show event; Qt's QOpenGLWidget page: "the associated native window may get implicitly destroyed and recreated if the QOpenGLWidget is the first of its kind within its window ... new in Qt 6.4", since the window's surface type changes from RasterSurface to OpenGLSurface), and a dialog over the window it replaces is closed by the window system on Wayland, and stays open but below the new window on xcb. A PyQt6 probe (`notice_probe.py GL`) shows both; a box with no parent survives but also ends below the new window. **Fix:** keep the notice a dialog of the main window, open it after the view's next frame (`pqView::endRender`, `Qt::SingleShotConnection`) once the main window is exposed, watch the main window's `QPlatformSurfaceEvent::SurfaceAboutToBeDestroyed`, close the dialog if it is still open 0.3 s later, and open it again over the new window when it closed within 3 s of that event (so a person's own OK later is final); keep it window-modal (`open()`), since Qt's QDialog page says a parent alone does not keep a dialog on top of its parent, modality does; write the sentence to the log too (`Qt/Core/pqStereoEditionNotice.h`, patch 0003; the probe's `GL-REOPEN` mode shows it on both routes). **Found by:** KWin's window list every 3 s (`pv-notice-case.sh`: the notice never listed), gdb time stamps on `QDialog::open`, `QMessageBox::closeEvent` and `ParaViewMainWindow::showEvent` (closed 0.7 s after the second show), then the probe (`notice_probe.py GL` and `GL-ORPHAN`). Moving the notice after start-up alone did not help: the recreation comes when the editor is added, about 12 s in.
