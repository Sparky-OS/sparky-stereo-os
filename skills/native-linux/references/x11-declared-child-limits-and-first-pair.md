# A declared child window: its depth limits and its first pair (ORDER 17, milestone 5 round 2)

A program whose 3D area is a child window (CloudCompare, gmsh's FLTK view, Togl in Netgen, ParaView's render view, a Qt window that embeds a GLX child) declares the child, not its top level. This page is what Stereo KWin, Xwayland and Mesa owe such a child and how each part was found. Written 2026-11-18 from KWin 6.7.4-2+stereo3d59, Mesa 26.1.6-1+stereo3d26 and Xwayland 24.1.15-1+stereo3d3, measured in the proof rig (kwin_wayland --virtual --xwayland, AMD render node).

## Recipe

1. The child lists itself in its top level's `_KDE_NET_WM_STEREO_CONTENT_CHILDREN` and declares `_KDE_NET_WM_STEREO_CONTENT` 3 on itself (Mesa's GLX does both at the first swap).
2. Stereo KWin (declaration support 11 on the root, `_KDE_NET_WM_STEREO_CONTENT_SUPPORTED`) redirects the child and then writes `_KDE_NET_WM_STEREO_DEPTH_LIMITS` on it: CARDINAL/32, two values, sunk then popped, 24.8 fixed point, pixels of a view 1920 wide (2560 1024 = 10 and 4). It writes again when the person's limits, the output or the child list change, and deletes it when the child's declaration or the child goes. The top level gets no property of its own unless it declares itself.
3. The program reads it from the child, never from the top level: `stereo_depth_x11_get_limits(display, child, &limits)` and `XSelectInput(child, PropertyChangeMask)` (see [depth-limits-declare.md](depth-limits-declare.md)). `-ENODATA` means offered, not delivered yet: a program that draws once says so or waits for the event; it never invents a separation.
4. Mesa's GLX, on DRI3 and the software path, waits for that property (at most half a second) before the first present of a declared child, when the root announces support 11 and the window is not a top level. `LIBGL_DEBUG=verbose` prints `stereo child 0x...: the compositor took the child after N us`; a compositor that does not answer is said on stderr and the presents go as before.
5. Mesa's pair rule (ORDER 561b: one copy tolerated, two take the declaration back, three flips return it) ignores a completion with mode SUBOPTIMAL_COPY: it is neither a copy nor a confirmed flip (EGL on X11, the Vulkan stereo layer and both GLX paths).
6. A Wayland subsurface that declares stereo content and follows the depth (`kde_stereo_depth_v1`) gets the limits as a top-level does, also when it starts following after its window is shown (s59-0003).

## More traps

- **A toy that selects PresentCompleteNotify on the child itself gives a different result.** `PRESENT_TRACE=1` showed the completions (mode 0 then mode 3 on +58, mode 3 first on the final stack) and in the same runs the capture was flat; the same runs without it were pairs. Use the trace to read the sequence, count pairs without it.
- **A toy that exits before the capture is flat in the capture.** `HOLD_MS` must outlast the screenshot (12000 against a seven second wait); a first batch of timeout runs showed 1280 only for that reason.
- **LIBGL_ALWAYS_SOFTWARE=1 in the session's environment breaks the screenshot** ("Screenshot got cancelled"): KWin takes it too. Put it in the program's own environment.
- **A run directory made by a container as root cannot be cleared by a later run as another user:** the new run reads the old files. Give each case a fresh name, or clear by a container.
- **`pkill -f NAME` in a tool shell kills the shell that carries NAME in its own command line.** List with `ps -eo pid,args | grep ...` and kill by pid.

## Traps, symptom first

- **Symptom:** the child never gets `_KDE_NET_WM_STEREO_DEPTH_LIMITS`; `stereo_depth_x11_get_limits` answers `-ENODATA` for ever on a KWin that announces 10.
  **Cause:** s52-0001 (KWin +stereo3d52, "Tell a window that declares stereo content the depth limits of its output") wrote the property on the window that declares only; `X11StereoChildren` tracked the children but nothing wrote on them.
  **Fix:** `X11Window::updateStereoDepthLimits()` writes on every tracked child that holds content, `X11StereoChildren::unwatch()` deletes it, the child list change schedules the update, and the announced support is 11 (s59-0001). Test `testStereoChildWindowDepthLimits`, red on +58 and green on +59.
  **How found:** reading the one writer, then `props2.py` on the child (the property list of every window of the tree) in a session of +58.
- **Symptom:** a declared Wayland subsurface that asks for the depth after its window was shown gets no `depth_limits`.
  **Cause:** `StereoDepthStates` watches only the top-level surface's `stereoDepthFollowed()`; a subsurface's follow scheduled nothing.
  **Fix:** the follow is announced up the subsurface tree (s59-0003); test `testLimitsOnDeclaredSubsurface` (s59-0004), red on +58, green on +59.
  **How found:** the test written to check the Wayland side was red on both.
- **Symptom:** a program that draws once (or draws on demand) shows its child flat, Mesa says "is shown flat", and nothing brings it back; the 3D area is a pair only after the program makes a new drawable.
  **Cause, two parts.** (a) Mesa declares at the first swap and presents at once; Stereo KWin redirects the child some tens of milliseconds later and Xwayland gives it a surface only then, so the first presents are real copies (`xwl_present_check_flip` reason 1, no surface). (b) The first flip on the new surface completes as SUBOPTIMAL_COPY while the compositor's dmabuf feedback is unread (`xwl_present_maybe_set_reason`); when both feedback flags are set the second flip does too; Mesa read the mode as a copy and two such took the declaration back although both pictures had reached the surface. A flat child never flips, so the three flips that should bring it back never come.
  **Fix:** (a) the first present of a declared child waits for KWin's limits property (patch 0043); (b) SUBOPTIMAL_COPY is not a copy for the pair rule (patch 0044). The rule of ORDER 561b is unchanged: a real copy still counts, one is tolerated, two take the declaration back. Test: `tests/glx-child-first-pair.c` with `check-glx-child-first-pair.py` (red on Mesa +25, green on +26).
  **How found:** the toy child with `EARLY=1` (the declaration written before the swap) was a pair when the swap came 80 ms later and flat at 30 ms: a race. Then Xwayland rebuilt with a print in `xwl_present_check_flip`, `xwl_present_flip` and `xwl_present_flip_notify_vblank` for non-top-level windows (`scripts/xwayland-print-present-decisions.txt`): old Mesa gave four COPY decisions with reason 1; Mesa with the wait gave FLIP with mode 3 on the first present and sometimes on the second. With the wait and Xwayland made to report mode 1 for children the toy was a pair 10 of 10, which isolated the two parts.
- **Symptom:** two identical eyes handed to KWin come out differing by one 8-bit code value at some output pixels after the one resize (55 pixels on the AMD node, 97 on NVIDIA for a 1920x921 eye shown at 1268x608).
  **Cause:** the area filter computed each eye's weights in whole-buffer coordinates, where the right eye's offset changes the rounding.
  **Fix:** the weights are computed in each eye's own texels, the four texels fetched explicitly (s59-0005, found and written by lane 501; the shader is the same in +54 and +58, the patch applies with no fuzz and no offset). Test `StereoDownscaleTest::identicalEyes` (s59-0006): red on +58's shader and green on the new one on both render nodes (`EGL_PLATFORM=surfaceless` with `__EGL_VENDOR_LIBRARY_FILENAMES` naming Mesa's or NVIDIA's vendor file, the NVIDIA card through CDI); the CloudCompare and F3D rows did not move.
  **How found:** lane 501 compared the two halves of a flat picture after KWin's downscale.
- **The wait looks long in a log.** It is 20 to 50 ms on a loaded rig and 1 to 4 ms idle; it is once per drawable declared.
- **A property written by KWin is not "KWin holds the surface".** The limits arrive after the redirect request is on the connection, which is enough for the child to be flippable by the time the program presents; it is not an acknowledgement of the surface serial (a CI Xwayland never associates one), so no test waits for a surface.
- **A rig session under load flatters or hides the race.** Under four builds the threshold of the early declaration moved from 30 to 80 ms; count runs on a quiet machine and report the count, not one picture.
- **`dpkg -i` of the Mesa set into a rig image installs five packages** (the ones the image has). `libgl1-mesa-dri` carries `libgallium`, so the GLX library and the driver always travel together.
- **Quick GLX-only builds do not stand in for the package.** A meson build of `libGLX_mesa` alone (softpipe, no radeonsi) offers "no stereo visual"; use it only to compile-check a GLX change, then build the package.

## Netgen's drawing area: a child declared before its window is on the screen (ORDER 50, 19 November 2026)

- **Symptom:** Netgen with `-stereo` (Tk window, Togl drawing area) is flat on the published stack: the capture is one output wide, Mesa says "stereo child 0x...: the compositor did not take the child in 500 ms" and then the problems engine's "netgen is shown flat". Measured on the AMD node (radeonsi, DRI3) only; the NVIDIA card was not run.
- **Cause:** Tk creates the Togl child and draws once while the top-level window is still unmapped (`map_state` 0), and maps it 0.5 to 0.7 s later (here 0.58 s and 1.27 s after the start). Stereo KWin takes a child only through its X11 window, so nothing answers within the wait of patch 0043; the presents completed as copies take the declaration back, and the map that follows finds a flat child. The listing in `_KDE_NET_WM_STEREO_CONTENT_CHILDREN` came and went (`[child]` at 0.58 s, `[]` at 1.20 s) before the window was ever mapped.
- **Fix (Mesa patch 0045, `glx_x11_stereo_child_hidden`):** a child is not declared at a swap while `XWindowAttributes.map_state` is not `IsViewable`; the first swap after the window is mapped declares it and then waits for the adoption as 0043 says. A top-level window is declared as before.
- **How found:** `x11watch.py` (one Python Xlib loop, 50 ms, printing every change of the four `_KDE_NET_WM_STEREO_*` properties and the map state of the top-level windows) in a fresh session: the property times against the map time. `xwininfo -root -tree` showed the chain top-level (Tk wrapper), Tk toplevel, GL child.
- **Proof, one fresh session per run, same cube geometry, `netgen -stereo -geofile=cube.geo`:** published Mesa +stereo3d26 on the AMD node: flat (`stereo` false, 1280 wide). The A/B on a Mesa built from the same source with softpipe (so both runs draw in software): unpatched 3 runs of 3 flat; patched 3 runs of 3 stereo (2560 wide), the child taken after 39 us, the declaration after the window was mapped (1.04 s map, 1.10 s declaration), the face of the cube 9 px apart (left eye 480 to 808, right eye 471 to 799, vertical 0), the Tk menu, toolbar and status rows 0 differing pixels.
- **Trap, the stand-in build:** a `libGLX_mesa` built alone does not run with the package's `libgallium` (the symbol version is the full soname, `libgallium-26.1.6.so` against `libgallium-26.1.6-1+stereo3d26+lc1.so`), and Tk then fails in `XCreateIC` with `BadWindow` (the program dies before the GL child exists). Build the whole Mesa with `-Dgallium-drivers=softpipe -Dllvm=disabled -Dplatforms=x11 -Db_ndebug=true -Dglvnd=enabled -Dglx-direct=true -Dvulkan-drivers= -Dvulkan-layers=`, `DESTDIR=... ninja install` (about 1030 steps, 10 minutes on four threads) and give only the client `LD_LIBRARY_PATH` and `LIBGL_DRIVERS_PATH` to the prefix; KWin and Xwayland keep the package's Mesa. Run the unpatched sources through the same recipe as the control: the radeonsi run and the softpipe run are different paths (DRI3 and the software one), and the patch is in both.

## Mesa +stereo3d28 on the package path: a child declared once its window is viewable, and again when it comes back (ORDER 50c, 19 November 2026)

Upstream Mesa has nothing on a GLX drawable of an unviewable window (issues and merge requests for "unviewable", "IsViewable" and "GLX unmapped window drawable"; no commit on `src/glx` names it; the stereo declaration is ours), so both patches are ours and Mesa's authors of the four GLX files are credited in ATTRIBUTIONS.
- **The two routes, as the edition runs them:** AMD, Xwayland with glamor on the render node: Mesa's GLX on radeonsi, DRI3. NVIDIA: the session's own environment, from the published `sparky-stereo-hardware` package: unpack it (`dpkg-deb -x`), write `/etc/sparky-stereo/opengl-stereo.conf` as `desktop=nvidia` and `opengl=zink`, point `SPARKY_STEREO_OPENGL_CONF`, `SPARKY_STEREO_HARDWARE_LIB` and `SPARKY_STEREO_HARDWARE_SHARE` at the unpacked files and source `etc/xdg/plasma-workspace/env/sparky-stereo-opengl.sh` in the case, not in KWin. Install `libkf6config-bin` in the rig image: without `kreadconfig6` the script exports nothing and the row measures NVIDIA's own GL, flat, with no error.
- **0045, red then green (Netgen `-stereo`, a cube):** published +stereo3d26: 3 of 3 flat on each route (1280 wide, "stereo child ...: the compositor did not take the child in 500 ms", then "is shown flat"); +stereo3d28: 3 of 3 a pair (2560 wide), the cube's blue face 9 px apart at both edges (left eye x 480 to 808, right eye 471 to 799), vertical 0, 0 differing pixels outside the cube's rows, Netgen without `-stereo` 0 differing pixels against the published build.
- **0046, the remap fault (symptom, cause, fix, how found):** a stereo child whose window is unmapped, or minimised (KWin unmaps a minimised X11 window), and comes back stays flat for good, and Mesa tells the person "is shown flat" about a window that was not on the screen. Cause: the child's presents made while the window is away complete as copies (the compositor holds no surface for a window that is not on the screen), two copies take the declaration back, and a flat child never flips, so nothing declares it again. Fix: a present that completes as a copy while the window is not viewable (`glx_x11_stereo_child_away`, the map_state test of 0045, one round trip and only for a copy) is left out of the pair rule, and the first completion after the window is viewable again drops the child from its window's list and declares it anew, so KWin takes it again and the next swap waits for its limits (0043). DRI3 (`glx_dri3_present_completed`) and software GLX (`drisw_present_events`). Found by: the fixture `glx-child-late-map` with `REMAP=N` against the published Mesa (`after remap 1 _KDE_NET_WM_STEREO_CONTENT: none`, three times) and a KWin script that sets `minimized` on the window.
- **0046, red then green:** unmap and map three times (fixture `EARLY_MAP=1 REMAP=3`): +26 flat after each map and told "is shown flat", +28 declared after each and a pair (2560 wide), not told, on radeonsi and on zink. Minimise and restore three times through KWin (`scripts/kwin_script.py`, `w.minimized = true` then `false`, a capture 5 s after each restore): +26 2560 wide before and 1280 after each restore, +28 2560 on all four captures, on both routes. A child of a window mapped from the start, a window that is never viewable (nothing declared, nothing said) and a top-level quad buffer window are unchanged.
- **Nothing else moved (same numbers, +26 against +28, both routes):** `glxgears -stereo` (pair), F3D `--stereo` (898 and 894 differing pixels between eyes), PyMOL (red +1.578, green -2.979, blue -9.233 px), CloudCompare +stereo3d2 (3D switched on by a click at the last toolbar button; red -1.921, green 0, blue +2.733 px), the model viewer 0.1.2 (a PLY mesh; three squares at -2, 0 and +2 px), one gl-stereo saver (`gl-stereo-run /usr/libexec/xscreensaver/glplanet -window`, a pair, the eyes differ), Netgen without `-stereo`, and on AMD the 32-bit clients (an i386 `glxgears -stereo`, the fixture built with `gcc -m32`).

### Traps of building Mesa's next source and its i386 twin (symptom, cause, fix, how found)

- **Symptom:** `apt-get build-dep` in the container says every package "is not installable". **Cause:** `sparky-lc-migration` is an image without apt lists or the edition's source. **Fix:** commit a prepared image from it (the edition's repository mounted at `/repo`, the apt pin 1001, deb-multimedia, `apt-get update`, `build-essential debhelper devscripts dpkg-dev python3 bubblewrap`), one per architecture, and give it to the build script. `docker commit` has no `-q`. **Found by:** `build-dep.log`.
- **Symptom:** the build stops in `override_dh_builddeb`, or its last `check-link` fails, with "libegl-mesa0 : Depends: sparky-stereo-problems (>= 0.1.2) but it is not installable". **Cause:** the link gate solves in a frozen universe of Debian and the edition's packages you hand it; `sparky-stereo-problems` (amd64 only) is in none of them. **Fix:** a siblings file naming `/repo/pool/main/s/sparky-stereo-problems/sparky-stereo-problems_0.2.4_amd64.deb`, the fifth argument of `build-stereo3d28.sh`, which now passes it as siblings and previous siblings in the build and in the last `check-link` (the +27 scripts passed only the previous-siblings variable). The i386 build needs none (the build dependency and the dependency are `[amd64]`). **Found by:** `grep -n "not installable" build.log`.
- **Symptom:** the provenance call stops with "no source date for ." **Cause:** the recipe folder is not committed. **Fix:** commit (a WIP commit is fine, squash before the last build).
- **Symptom:** the `.dsc` hash changes between two runs of `next-source-stereo3dNN.sh`. **Cause:** the source's date is the recipe folder's last commit; any later commit under `packages/mesa` (a README, a test, a script) changes both hashes and the build record's `recipeCommit`. **Fix:** finish the folder, commit, run the script twice and compare, build from that commit, and touch nothing in the folder after.
- **Symptom:** the new `mesa-vulkan-drivers` has a shorter Depends than the published amd64 one (no `libudev1`, no `libxcb-keysyms1`) and meson says "Run-time dependency libudev found: NO". **Cause:** Debian's Mesa source does not Build-Depend on `libudev-dev` or `libxcb-keysyms1-dev`; the earlier amd64 build had them installed by chance, the published i386 twin did not (so the two architectures differed), and a build on a later day lost them without a message. **Fix:** declare both in `Build-Depends` (`[linux-any]` for libudev), as `debian-changes-stereo3d28.py` does: libudev gives the Vulkan WSI's `VK_KHR_display` a udev monitor for display hotplug (`src/vulkan/wsi/wsi_common_display.c`, `HAVE_LIBUDEV`), libxcb-keysyms gives the X11 Vulkan WSI the F1 capture hotkey (`wsi_common_x11.c`, `XCB_KEYSYMS_AVAILABLE`); both link into every `libvulkan_*.so`. The i386 twin then gains `libudev.so.1` and `libxcb-keysyms.so.1` in NEEDED and `libudev1`, `libxcb-keysyms1` in Depends, installable beside the amd64 ones. **Found by:** comparing the `.deb` files with `readelf -d` under `LC_ALL=C` (a Portuguese `readelf` prints "Biblioteca partilhada" and a script that greps "Shared library" sees nothing: the first comparison said "0 differences" and was wrong).
- **Time and disk:** the amd64 package build is 50 to 70 minutes at four threads with the machine loaded, i386 45; 10 GB of build tree each; the gate wants 12 GiB free on `/`. Put the two trees on different disks so both run at once, and remove root-owned `link-scratch` leftovers through a container, by literal path. `SPARKY_MESA_RESUME=1` re-runs the package step of a compiled tree without compiling (6 minutes), its build record covers only that step.
- **A rig session's container name is fixed per lane:** run rows one after another.

- **Symptom (rig):** Dolphin the file manager aborts with "Could not load the Qt platform plugin xcb" or "No shell integration named xdg-shell". **Cause:** the rig has neither `libxcb-cursor0` nor `qt6-wayland`. **Fix:** install them (Qt's xcb plugin wants the first since 6.5). The line `Activated service 'org.kde.KScreen' failed: ... signal 6` in the same log comes from D-Bus activating KScreen without `DISPLAY` and does not stop Dolphin (`timeout 12 dolphin` gives 124).
- **Symptom (waiting):** a build that runs for an hour cannot be waited on with `sleep`. **Fix:** a loop `timeout 175 sh -c 'while docker ps --format "{{.Names}}" | grep -q NAME; do sleep 10; done'` per call, and `tail -1 work/build.log` for the step count.
- **A `Breaks` is not a hold (ORDER 774, dolphin-emu +stereo3d2):** with `Breaks: mesa-vulkan-drivers (<< 26.1.6-1+stereo3d29~)` and only Mesa +26 offered, `apt-get -s install dolphin-emu` printed `Remv mesa-vulkan-drivers` and `Remv mesa-vulkan-layer-stereo` and installed the emulator; with +29 offered it printed the `Inst` lines of all seven Mesa packages and the emulator, nothing removed (Debian Policy 7.3 describes Breaks as stopping the other package being configured; apt may satisfy it by removal when no newer version exists).
