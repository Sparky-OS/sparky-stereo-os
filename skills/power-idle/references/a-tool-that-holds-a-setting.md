# A tool that holds a power setting: CoreCtrl without a password, in the tray, one writer per setting

**For whoever makes a hardware tool the person installs (CoreCtrl, LACT) work in the edition without a password at login, start it in the tray, and keep the power profile's daemon off the settings the tool holds, and only those.**
Written on 2026-11-27 (queue rows 168 and 601, package `sparky-stereo-corectrl` 0.1.0, then 0.1.1 after the main session's review), with CoreCtrl 1.5.2, LACT 0.10.1, power-profiles-daemon 0.30, tuned 2.27.0, polkit 128 and systemd 262 of Debian testing, measured in a container rig and on the bench notebook (AMD A10, acpi-cpufreq, Carrizo and Hainan cards on amdgpu).

## Recipe

1. **The rule, where packages put rules.** A vendor rule in `/usr/share/polkit-1/rules.d`, the code of the tool's own documented rule (CoreCtrl's guide: its two actions, `subject.local`, `subject.active`, a group), with the group Debian's polkit names as administrators (`50-default.rules`: `unix-group:sudo`). It names the tool's actions only, so it does nothing where the tool is not installed (`pkcheck` answers "Action ... is not registered").
2. **A hand-made copy is replaced by the package, not masked.** polkit 128 reads `/etc`, `/run`, `/usr/local/share` and `/usr/share` rules folders together, ordered by file name, `/etc` first on a tie (polkit(8), "AUTHORIZATION RULES"); a file of the same name does not hide another. The postinst sets aside an unowned `/etc/polkit-1/rules.d/90-corectrl.rules` whose code (comments and spacing aside) is the guide's rule for sudo, keeps it in `/var/backups/PACKAGE`, says so, and the prerm puts it back at removal. Any other rule there is the person's: left, said once.
3. **The tray start through the tool's own setting.** An entry in `/etc/xdg/autostart` with `TryExec=` the tool (Desktop Application Autostart Specification 0.5, 2.2: "MUST NOT be autostarted" when it does not match an installed program) and the name of the tool's own desktop file, so a copy made the way the tool's guide says (`~/.config/autostart/org.corectrl.CoreCtrl.desktop`) replaces it, and the Autostart page's switch (`Hidden=true` in a file of the same name) turns it off. The "start minimized" default goes in `/etc/xdg/ORG/APP.ini`: a Qt program's `QSettings(IniFormat, UserScope, ORG, APP)` reads it after the person's own file (Qt's QSettings documentation, "Platform-Specific Notes"), so the tool's own checkbox stays the person's.
4. **Hold only what the tool manages, read as the tool reads it.** CoreCtrl writes a control only while it is on (`control.cpp`, `Control::sync`: `if (active()) syncControl(ctlCmds);`), from the moment its helper answers `started` (`org.corectrl.helper`, `/Helper`; call it with no auto-start). What it applies is a stack (`session.cpp`): the global profile, then the profile of each program its helper reports starting (signals `appExec` and `appExit`, `org.corectrl.helper.pmon` on `/Helper/PMon`, the program's name and a signature, both `ay`; the policy lets anyone receive them), and on top a manual profile. Each component (CPU, GPU) comes from the highest profile in which it is on, else from the global profile (`profileview.cpp`).
   - The profiles: `$XDG_CONFIG_HOME/corectrl/profiles/EXE.ccpro` (else `~/.config`), a zip archive holding `profile.xml`: `<PROFILE active name exe>`, `<CPU active physicalId>`, `<GPU active index deviceid revision [uniqueid]>`, and in each a control mode `<ID active mode>`; a missing attribute or element takes CoreCtrl's default (on, and a mode that writes).
   - The processor is written while `CPU_CPUFREQ_MODE` is on in mode `CPU_CPUFREQ`; an amdgpu card's power level while `AMD_PM_PERFMODE` is on in any mode but `NOOP`; a radeon card's power state while `AMD_PM_POWERSTATE_MODE` does. `NOOP` is the window's "Do not control"; only the chosen mode's control is on (`controlmode.cpp`).
   - Which element is which: the processor by `physicalId`, the "physical id" of `/proc/cpuinfo`; a card by `uniqueid` when both have one, else by `index` (its render node's number less 128), `deviceid` and `revision` in capitals (`gpuxmlparser.cpp`).
   - Read the folder through `/proc/PID/root` of the CoreCtrl process (the folder as CoreCtrl sees it), and follow the folder (a saved change), the helper's signals and the helper's coming and going.
   - LACT holds a card while lactd runs and its current settings (`current_profile`'s `gpus`, else the default `gpus`) name the card.
5. **One writer per setting, per daemon.**
   - power-profiles-daemon's CPU drivers (amd_pstate, intel_pstate): it has no runtime switch, so a runtime drop-in in `/run/systemd/system/power-profiles-daemon.service.d` repeats its own `ExecStart` with `--block-driver=amd_pstate --block-driver=intel_pstate`, and it is restarted; only where it would load one of them (the driver's `status` file and a policy with `energy_performance_preference`), and only while the processor is held.
   - its amdgpu_dpm action (opt-in in 0.30, one switch for every card): off through its own `SetActionEnabled` while any card is held, the person's own choice otherwise; read live from `ActionsInfo` and followed through its `PropertiesChanged`.
   - tuned: a runtime cpu instance of the service's own (`instance_create` with `devices=*` and a priority after the profile's), given the processors with `instance_acquire_devices`, removed at the end; taken again at every `profile_changed`.
6. **Keep the person's choice of each action, and tell who changed it.** LACT turns amdgpu_dpm off at every start of its daemon, for every card, and never gives it back (`lact-daemon/src/system/power_profiles_daemon.rs`, called from `Server::new`), and the daemon saves its running state as the choice at its next profile change. So keep the person's choice in a file of the service's own, change it only on a `SetActionEnabled` call from someone other than LACT and the service itself, and set the action to it whenever no card is held. The caller is found with the bus's Monitoring interface (`BecomeMonitor`, for root) and `GetConnectionUnixProcessID` asked at once; the service is `Type=notify` and `Before=lactd.service`, so it listens before LACT's first call at boot.
7. **Tell once, through the engine.** A notice (`sparky-stereo-problems keep --severity notice`) says which program holds which setting; it ends when that program, still running, no longer holds it, or when it is removed (a program merely closed keeps it). A notice of a conflict (two tools on one card) ends with the conflict. What cannot be followed is said: a manual profile that would set something nothing keeps the daemons off.
8. **Prove it at the write.** In a rig, bind a recorded processor tree (plain files) over `/sys/devices/system/cpu` and trace `openat` of the daemons with strace; on real hardware, `kprobe:kernfs_fop_write_iter` in bpftrace with the dentry name gives every sysfs write with its process. Red: the published packages (or the predecessor), where both write; green: the package; release: the daemon alone.

| --- | --- | --- |

| a program's profile (processor and cards on) over a global profile with both off (bench, the real helper) | 0.1.0: held whether the program runs or not | held 0.27 s after the helper's `appExec`, the person's action back 0.27 s after `appExit` |

## Traps

- **Symptom:** a person who set CoreCtrl's processor control to "Do not control" has no Performance profile while CoreCtrl runs. **Cause:** holding a setting because the helper is started, while CoreCtrl writes a control only while it is on. **Fix:** read the stack CoreCtrl applies (recipe 4). **Found by:** the main session's review, from `Control::sync`; then measured on the bench: with the mode `NOOP` CoreCtrl's helper wrote the governor 0 times after another program changed it, with the mode on 8 times.
- **Symptom:** the service holds every setting although the profile says otherwise, while `knob-owner status` run by hand reads the profile right. **Cause:** the unit's `PrivateTmp` hid the person's `/tmp`, where the profiles were (a test's `XDG_CONFIG_HOME`), and an unreadable folder was taken as CoreCtrl's defaults in silence. **Fix:** read the folder through `/proc/PID/root` of the CoreCtrl process; log a folder that cannot be read. **Found by:** the service's journal against the status on the bench.
- **Symptom:** a manual profile turned on from CoreCtrl's tray is not followed. **Cause:** CoreCtrl keeps it in memory only (`Session::manualProfile_`) and tells no other program. **Fix:** none outside CoreCtrl; say it when the manual profile would set something nothing keeps the daemons off.
- **Symptom:** a change made in CoreCtrl's window takes effect but the service does not follow it. **Cause:** the window's Apply applies; only Save writes the profile file (`ProfileManager::update` against `ProfileManager::save`). **Fix:** none needed: an unsaved change is dropped by CoreCtrl at quit; the service follows at Save.
- **Symptom:** the person's amdgpu_dpm "on" is "off" after every boot, though nothing of the edition turned it off; the state file still says on until the next profile change. **Cause:** LACT's daemon turns the action off at every start (recipe 6). **Fix:** recipe 6. **Found by:** the boot's journal on the bench: `lact[...]: disabled conflicting power-profiles-daemon action amdgpu_dpm` 0.4 s after the daemon started, D-Bus activated by lactd; then LACT's source. The edition's Hardware Setup turns the same action on for matched Radeon machines with AMD processors, so without the service LACT undoes it at the next boot.
- **Symptom:** the caller of LACT's `SetActionEnabled` "had left the bus". **Cause:** LACT's start-up connection closes right after the reply, and at boot (load 10) the main loop asked for the caller 0.19 s late. **Fix:** ask `GetConnectionUnixProcessID` asynchronously from the bus thread as soon as the monitor sees the call, classify the process there (its program or its `lactd.service` cgroup), then hand over to the main loop; keep a timing fallback (an "off" while lactd has just started) and say it in the journal.
- **Symptom:** a GDBus monitor connection is closed by the bus. **Cause:** a monitor must never send, and GDBus answers an incoming method call it has no object for. **Fix:** a filter added before `BecomeMonitor` that drops every incoming method call (after reading it) and passes everything else, including the connection's own `BecomeMonitor` call.
- **Symptom:** CoreCtrl exits at start: "Cannot create core components", "cannot create directory ... [XDG_CACHE_HOME/corectrl]". **Cause:** it creates its folders without parents, and Qt's cache location already ends in the program's name. **Fix:** for a test with other XDG folders, make `XDG_CACHE_HOME/corectrl` first (an account's `~/.cache` exists). A profile is edited only while CoreCtrl is stopped: it reads its profiles at its start.
- **Symptom:** a measured change "never" happens. **Cause:** `powerprofilesctl` takes about 0.35 s a call, so a poll misses an "off" that lasts 0.3 s. **Fix:** time short changes from the journal (`-o short-precise`).
- **Symptom:** in a container, `pkcheck` answers "Not authorized" for an action whose default is `auth_admin_keep`, as if the session were remote. **Cause:** polkit counts a session as local only when it has a seat, and `runuser -l` makes a seatless background session. **Fix:** a PAM login session on seat0: `systemd-run --wait --pipe --expand-environment=no --uid=USER -p PAMName=login -p Environment=XDG_SEAT=seat0 -p Environment=XDG_SESSION_TYPE=x11 -p Environment=XDG_SESSION_CLASS=user ...` (a container's seat0 has no VTs, so logind accepts it); `loginctl show-session` then says `Seat=seat0 Remote=no Active=yes`. **Found by:** comparing `pkcheck` with `loginctl show-session` in the two kinds of session.
- **Symptom:** CoreCtrl in a container prints "Cannot start helper" and exits 255; the journal says `Cannot subscribe to proc events`. **Cause:** its helper listens to the kernel's process connector, which a container cannot open. **Fix:** a stand-in that owns `org.corectrl.helper`, answers `started`, rewrites the governor every 500 ms while the test's processor control is on and sends `appExec`/`appExit`; the real program on real hardware. LACT's package needs GTK 4 and libadwaita, so an offline rig uses a stand-in for its start-up call too, run as `lactd.service` from LACT's own unit.
- **Symptom:** a published power profile change "works" in Plasma, yet the card's level or the governor is back half a second later. **Cause:** CoreCtrl's sync loop. **Found by:** bpftrace on `kernfs_fop_write_iter`.
- **Symptom:** after a hold ends, the person's amdgpu_dpm "on" is "off". **Cause:** power-profiles-daemon's `save_configuration()` writes each action's runtime state into `[Actions]`, so an action blocked with `--block-action` is saved as off at the next save. **Fix:** `SetActionEnabled`, with the person's choice kept by the service. **Found by:** the state file read after a hold on the bench, then `src/power-profiles-daemon.c`.
- **Symptom:** the service acts 16 s after the person turns the action on, after the daemon already wrote the card. **Cause:** `SetActionEnabled` changes the daemon in memory; its state file is written at the next profile change. **Fix:** read `ActionsInfo` and follow the daemon's `PropertiesChanged` (it sends every property after its drivers restart).
- **Symptom:** the service never starts at boot, and the journal says `Job ... deleted to break ordering cycle`. **Cause:** `After=power-profiles-daemon.service` in a unit wanted by multi-user.target, while power-profiles-daemon is `After=multi-user.target`. **Fix:** no ordering after the daemons (follow them on the bus); `Before=lactd.service` is safe, lactd being `After=multi-user.target`; a recipe test that refuses the first and wants the second. **Found by:** a real boot only; the rig started the unit from the maintainer script, where no cycle shows. `systemd-analyze verify multi-user.target` shows it.
- **Symptom:** tuned stops right after it starts on a Plasma desktop. **Cause:** PowerDevil asks for power-profiles-daemon on the bus, D-Bus starts it, and its unit `Conflicts=tuned.service`. **Fix:** tuned on the edition comes with tuned-ppd (which provides the daemon's bus name); for a test, mask power-profiles-daemon and unmask it after.
- **Symptom:** tuned's log has `ERROR ... Instance 'NAME' not found`, or a second `instance_create` fails. **Cause:** `get_instances` lists active instances only, and asking `instance_get_devices` for a missing one is an error line. **Fix:** look for the instance in `get_instances`; accept "already exists" from `instance_create`.
- **Symptom:** tuned's replies fail with `returned type ((bsa(ss))) but expected (bsa(ss))`. **Cause:** each method of `com.redhat.tuned.control` returns one structure. **Fix:** wrap the reply type once more and take `[0]`.
- **Trap, tuned's instances:** with no `devices` option the matcher iterates `None` as soon as there is a device to move; at the default priority the new instance sorts first and takes the cpu plugin's latency role (`plugin_cpu.py _instance_init`); moving devices out of an instance makes tuned write back the values it saved (`hotplug.py _remove_device_process`), which is the 70 to 90 ms window above. Debian ships `/etc/tuned/post_loaded_profile` as a conffile, so another package cannot use the post-loaded profile.
- **Symptom (rig):** power-profiles-daemon loads only its placeholder on a recorded processor bound under `/sys`. **Cause:** its `ProtectSystem=strict` makes that tmpfs read only in its namespace, so its probe's write fails. **Fix:** a rig drop-in `ReadWritePaths=/sys/devices/system/cpu`; real sysfs is writable. Also restart it after the bind: it may have started at boot on the real tree.
- **Symptom (rig):** tuned has no cpu instance on a recorded processor. **Cause:** systemd's sd-device (pyudev) refuses a device directory on tmpfs ("No device at ..."). **Fix:** none in a container; tuned's cpu plugin is proved on real hardware.
- **Symptom:** bpftrace prints nothing. **Cause:** it took up to two minutes to attach on the notebook (reading BTF), and `-q` hides "Attached". **Fix:** start it once in the background, wait for its "Attached" line, and count each row by its time window.
- **Symptom:** `powerprofilesctl set` over SSH: "Not Authorized: ...switch-profile". **Cause:** an SSH session is remote for polkit. **Fix:** run it as root on the bench.
- **Symptom:** a file set aside in `/tmp` before a reboot is gone. **Cause:** the edition empties `/tmp` at every boot. **Fix:** keep anything that must survive a reboot elsewhere (a verified copy restored it here); a test's CoreCtrl folders in `/tmp` go with it, which is what a test wants.
- **Symptom:** a container ID record lists other lanes' containers. **Cause:** `docker events` on a shared daemon reports every container. **Fix:** filter by name (`--filter container=PREFIX-...`) before recording.
- **Note:** `dpkg -r` keeps conffiles, so the autostart entry and the tray default stay until purge (Debian's "rc" state); `TryExec` keeps the entry inert without the program.
