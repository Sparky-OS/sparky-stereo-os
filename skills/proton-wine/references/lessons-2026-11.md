# proton-wine: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: TrackMania Nations Forever quits after 1 s with status 0 and leaves an empty `Nadeo.ini`; with the empty file present it reaches device reset and swapchain and still quits. Cause: the game reads Nadeo.ini from the current directory and the sheet's command ran from the shell's folder (not a Wine or WoW64 matter). Fix: `wiz3d-launch` runs the game in the folder of its .exe when the command names it by path. Found by: running from its own folder (reaches the first menu) against `$HOME` (quits) under headless KWin. (lane wiz3d-lutris)
- Symptom: TrackMania dies at the swapchain with "X connection to :99 broken" under Xvfb. Cause: plain Xvfb has no DRI3, a rig artefact. Fix: test real games under KWin's Xwayland only. Also Wine's own d3dcompiler (vkd3d) refuses the game's HLSL (`E5001: Unexpected modifier used on a function`, `E5030: Unknown modifier vs_2_0`) so the launcher's prefix creation adds winetricks d3dx9 and d3dcompiler_43 (WIZ3D_WINETRICKS=0 skips). (lane wiz3d-lutris)
- Symptom: a 16-bit installer (SimCity Classic SETUP.EXE) ends after 1 s with status 5 in a 64-bit (WoW64) prefix: `err:environ:init_peb starting L"C:\windows\syswow64\winevdm.exe" in experimental wow64 mode`, `err:module:loader_init "krnl386.exe16" failed to initialize, aborting`, status c0000005. Cause: WoW64 mode does not run 16-bit programs. Fix: run in a 32-bit prefix (WINEARCH=win32); "fails" is defined from evidence only: NE header, Wine's words (`Bad EXE format`, `winevdm.exe" failed`, `failed to initialize, aborting`, `unable to dispatch exception`, `Exception frame is not in stack limits`, `Unhandled exception`, `unhandled page fault`, `stack overflow`) or an end within 30 s with nonzero status. The bare `in experimental wow64 mode` line appears for every 32-bit program and is NOT evidence; a quick end with status 0 and nothing said is not a failure. Remember the choice per program with its reason and how to undo it; say it in plain words. (lane wiz3d-lutris)
- Symptom: only the left eye reaches the screen in about half of the native stereo packing cases (topAndBottom, topAndBottom right first, sideBySide failed, sideBySide right first passed), Wine logs `warn:vulkan:win32u_vkQueuePresentKHR Present returned status 1000001003` (VK_SUBOPTIMAL_KHR) 129 to 169 times. Cause: a race: when the game window is declared before the game creates its Direct3D device, KWin has already doubled the X window when Wine creates the Vulkan surface; the X client window was created at the Win32 size and nothing resized it, so DXVK got a 1600 wide swapchain for an 800 wide client (`xwininfo` child 800x600 failing, 1600x600 passing). Fix: patch stereo3d/0004 in `X11DRV_vulkan_surface_create` records the client size and runs `vulkan_surface_update_size()` at creation. Found by: running the cases in different orders (order run), Wine warnings on, and `xwininfo`. Result with the fix: every packing and both eye orders pass, left square at 239.5, right at 271.5, disparity +32.0 px, 0 VK_SUBOPTIMAL lines. (lane wiz3d-lutris)
- Symptom: stereo Lutris with the switch off: the game quits after 10 s. Causes: the "system" DXVK entry named its links after the files (`d3d9.dll.so`); `Wiz3DManager.disable()` removed both the proxy and the link to the real Direct3D 9 and relied on the DXVK manager to restore one, which does nothing when that version is not downloaded (LUTRIS_SKIP_INIT, fresh install), so no d3d9.dll was left. Fix: links carry the DLL names; disable() gives `d3d9_real.dll` its name back. Proof: the prefix's system folder is byte for byte the DXVK only baseline after switching off. (lane wiz3d-lutris)
- Symptom: build fails with ELOOP in make_vfs.py (wiz3D). Cause: xwin 0.6.7's splat of the Windows SDK contains `include/10.0.26100 -> .` (and under lib); timing and manifest dependent (one build passed, three failed). Fix: skip links back up the tree; pin the xwin SDK version in debian/fetch-xwin.sh. (lane wiz3d-lutris)
- Symptom: `wineserver: command not found` in tests and tools calling `wineserver -k`. Cause: Debian's Wine 10.0~repack-12 puts wineserver only in `/usr/lib/x86_64-linux-gnu/wine/`, wine comes through alternatives. Fix: ship or link /usr/bin/wineserver in the stereo wine package. (lane wiz3d-lutris)
- Symptom: `xdotool` key presses do nothing in Wine windows under headless KWin (0 pixels changed), log `[xwayland ei] Unhandled event EI_EVENT_SYNC`. Fix: drive dialogs from inside Wine with a small mingw program that sends BM_CLICK to a button by caption (winclick.exe, wired as `SECOND:win:Title:Button`). (lane wiz3d-lutris)

## Perks of the part

- Lutris's own `d3d_extras` covers `winetricks d3dx9 d3dcompiler_43`; Lutris's "Prefix architecture: Auto" could read the exe header (`lutris.util.wine.wow64.exe_kind`) before the first run for every game. (lane wiz3d-lutris)

## Measured facts

- Wine and DXVK build facts: Debian's wine and dxvk are in sid not forky; the patches (3 Wine, 4 DXVK) apply to the pristine Debian tarballs; the build needs trixie unicode data, trixie vk.xml and -Wno-error on sid; libwine built against sid depends on `libavcodec63 (>= 7:9.0.2)`; the fork's `frames` suite takes about 6 minutes and is worth running for every wiz3D upload. (lane wiz3d-lutris)


## gamescope: build and prove the nested present mode

Recipe (ORDER 274, 6 November 2026; gamescope master 309eee74 plus ValveSoftware/gamescope#2438):

- Read `.github/workflows/main.yml` of master and copy its steps. At that date: container `archlinux:base-devel`, `pacman -Syu`, the package list in the workflow, `submodules: true`, then three meson setups (gcc with `-Dinput_emulation=disabled --werror --auto-features=enabled`; the same with `-Denable_openvr_support=false`; the same with `-Db_coverage=true`) and `meson test -C build-coverage --suite gamescope -v`. Run it as root in a container with `--ulimit core=0 --cpus 4`, the source mounted. Result to expect: both builds link `src/gamescope`, 17 tests Ok, 0 Fail (about 20 minutes on 4 CPUs, 0.9 GB image).
- No unit test touches `vulkan_make_swapchain`, so the change is shown by running a nested gamescope. Red and green use the same tree: `git checkout origin/master -- src/rendervulkan.cpp`, `ninja -C build-gcc`, copy the binary, restore the file, rebuild.
- To see the mode the driver was given, not only what gamescope logs, preload a 30-line shim that interposes `vkGetDeviceProcAddr` and `vkCreateSwapchainKHR` and prints `presentMode`; gamescope loads its device functions through `vkGetDeviceProcAddr`, so interposing the plain symbol alone misses it.
- Run `gamescope --backend sdl -W 640 -H 360 -- sleep 5` with `DISPLAY` on Xvfb and `SDL_VIDEODRIVER=x11`, one fresh start per value of the variable. Result: master gives mode 2 (FIFO) for every value; the change gives 2 for unset and `fifo`, 2 plus an error line naming the three values for an unknown word, 0 for `immediate`, and 2 plus the error line for `mailbox` on NVIDIA, whose X11 surface does not offer MAILBOX.
- The probe's `grep` keeps only the lines it was written for; when a change adds a log line, read the raw log once (`docker cp` it out of the stopped container) before calling a case unchanged. The unknown-word error first looked absent for that reason (6 November 2026).

Traps:

- Symptom: nested gamescope on lavapipe (`vulkan-swrast`) under a headless weston prints `Missing required extension: VK_KHR_present_id` and `VK_KHR_present_wait`, then `Failed to create backend`. Cause: the nested backend requires both and lavapipe lacks them. Fix: use a real driver through CDI (`--device nvidia.com/gpu=0`) and Xvfb. Found by: reading the stderr of the run, not only grepping it (a grep for the expected lines hid it, every case just printed nothing).
- Symptom: pull requests from a fork show "no checks" on Valve's repository. Cause: the workflow runs for outside contributors are created with conclusion `action_required` until a maintainer approves them (`gh api repos/ValveSoftware/gamescope/actions/runs`). The workflow runs on pushes to `master` and by hand (`gh workflow run main.yml --ref BRANCH`), but only where Actions are on: GitHub keeps them off on a new fork until its owner turns them on in the Actions tab, and on our fork `gh api repos/danielcamposramos/gamescope/actions/workflows` listed none (checked 6 November 2026), so run the recipe above locally.
- Symptom: a gamescope child process survives the run and holds the display. Cause: `timeout` kills gamescope but not its Xwayland. Fix: kill them by PID from `ps -eo pid,comm`, never `pkill -f`.
