# stereo-video: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Saving a 3D correction into a file: question dialog first (byte sum proves nothing is written while open), the writer reads back, success unmarks the stored choice; oracles that are not our reader: mkvmerge -J for StereoMode 0 to 20, libavformat for 1 to 14 and st3d; byte-identical files after every refusal. Marktest 516 checks, 0 failed; C++ test 14 cases, mutation (swap line deleted) 3 of 14 fail. Dragon's test needs ffmpeg and mkvtoolnix and FAILS (not skips) without them. Skill has mkvpropedit and values 0 to 14 only (lane depth-group-2b-411)
- Native MV-HEVC spatial video (iPhone MOV/MP4) in mpv, Haruna, Dragon, Gwenview video and VLC: a Qt free component requests the active VPS views at get_format, pairs distinct eyes at equal pts, copies native planes into left first full side by side, keeps the base view as the 2D fallback (also right eye base), rejects mismatched timestamps, duplicate views, incompatible size/SAR/colour. Proof: independent FFmpeg eye decodes of the same 96 frames per eye (left/right position selectors), a 54 case compositor matrix on two GPUs, seven corrupted-copy negative controls through check-debs and check-link, native 320x240 per eye in a 640x240 buffer declared once. (lane spm-wine-41)
- Proving a flattened or unpacked view's shape: draw each view at the size it is meant to be shown with a white square that is square on screen, squeeze it to its coded size, pack it, then mux every declaration under test (no SAR, VUI SAR, frame packing SEI only, Matroska StereoMode with DisplayWidth/DisplayHeight of one plane, with none, with the whole pair, FFmpeg's own muxer). Check each fixture with ffprobe, mkvinfo and mediainfo before use, then run the program's exact command line and measure the output's SAR and display aspect and the square after scaling to square pixels (`scale=round(iw*sar/2)*2:ih,setsar=1`): 1.0 is right, 2.0 or 0.5 is a doubled SAR. A label (half or full) can be wrong where the shape is right, so measure the shape. (lane jellyfin-review-528)

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: depth video rotated by the player shows the depth map unrotated. Cause: group 2 thought Qt had no setter; Qt 6.11 QVideoFrame has setRotation/setMirrored. Fix: patch 0025 turns picture, depth map and layer by the frame's normalized transformation before libstereo-dibr and the drawn frame carries none; tests depthRotated 90/180/270/mirrored: red exit 13, green 52 passed (lane depth-group-2b-411)
- Symptom: `Assertion p_dst->hwaccel_threadsafe || (!dst->hwaccel && !dst->internal->hwaccel_priv_data) failed at libavcodec/pthread_frame.c:415`, exit 134, with frame threads when a hardware pixel format is offered and software is chosen. Cause: ff_get_format() does not call ff_hwaccel_uninit() when the chosen format is not hwaccel. Fix: `if (ret < 0 || !(desc->flags & AV_PIX_FMT_FLAG_HWACCEL)) ff_hwaccel_uninit(avctx);` (FFmpeg PR 25398, test fate-get-format at THREADS=1 and 4, red `private=1 hwaccel=0`). Found by: a reproducer with a cuda probe case and 4 threads. (lane ffmpeg-hwaccel-carry-410)
- Symptom: MP4 st3d right-first (value 4) cannot be saved. Cause: FFmpeg 9.0.2 `mov_read_st3d` reads values 0 to 2 only while the Spherical V2 RFC defines 3 (custom) and 4 (right-left); FFmpeg writes st3d only in MP4 mode and writes vexu/eyes/stri next to it. Fix: refuse with the reason; next work is st3d 4 in mov.c and movenc. Also mkvpropedit on FFmpeg made Matroska (no room after Tracks) moves Tracks to the end and FFmpeg finds it through the SeekHead. (lane sview-messages-349b)
- Symptom: VLC with the PipeWire output has no sound until a seek, then drops ("playback way too late (256 ms): flushing buffers", "playback way too early (-858 ms): playing silence"), for MP4 files whose audio starts after the video (edit list `[(666 ms empty), (70869 ms from 0)]`). Cause: three faults in vlc-plugin-pipewire 3: vlc_pw_stream_get_time() reported a delay before the start date; stream_process() did not count the start silence in chunk->size; the start was computed from timing data of the cycle's start. Debian's VLC is not hit because Debian lowers the plugin priority to 155 under PulseAudio's 160. Fix: no delay until the stream has started, start silence counted in chunk and delay, buffers hold only what the cycle asks for (patch 0002-vlc-stereo-start-on-time). Rejected after measurement: filling every buffer with only requested frames (xrun on each stall) and PW_STREAM_FLAG_EARLY_PROCESS (-26 ms bias). Found by: headless PipeWire + WirePlumber null sink, `pw-record` of the sink monitor compared with a reference decode (onset, gaps, jumps, lag spread). (lane players-shared-layer)
- Symptom: "SEI on every frame" assumption wrong: MOV004.mp4 (LG Optimus 3D) carries its frame packing SEI only in the first access unit (H.264, side by side, left first, repetition period 1), FFmpeg marks 30 of 1832 frames. Cause: H.264 D.2.26 persistence to the next IDR. Fix/rule: players keep the first mark for the stream. Test fixtures should include a keyframe only SEI. (lane players-shared-layer)
- Symptom: VLC Stereo window closes but the process and tray icon stay; minimized then closed hangs 24 of 24 times. Cause: VLC's OpenGL output on Wayland leaves Mesa's swap interval at 1; Mesa waits for the compositor frame callback inside eglSwapBuffers, KWin sends no frame callback to a minimized window, so the vout thread never returns pictures, decoder waits in picture_pool_Wait, playlist waits for the input, Qt main thread waits in pthread_join. Fix: after the context is created make it current and `eglSwapInterval(display, 0)` under USE_PLATFORM_WAYLAND (mpv's vo_wayland does the same). Found by: stacks of the hung process (main in libqt_plugin join, input in input_DecoderDelete, decoder in picture_pool_Wait, EGL thread in wl_display_dispatch_queue), then 24 of 24 exits with interval 0. Closing an unminimized window headless never hung. (lane players-shared-layer)
- Symptom: VLC Stereo Wayland full screen fails (double click, F, Esc, controller button) while X11 works. Causes: Qt delivers the second click as a press flagged MouseEventCreatedDoubleClick plus the double click event, so VLC counts two double clicks; no mouse tracking on the video widget so no mouse-moved reaches the vout; the native QWindow keeps its own cursor which never hides (QtWayland 5.15 sets cursors seat wide). Fix: patch 3d-0046 (33 lines): mouse tracking, drop the flagged press, mirror the cursor to the native window only while over the video, controller as Qt::ToolTip on Wayland so it becomes an xdg_popup. Found by: real compositor input (KWin fake input), a read-only Qt probe, KWin window list. Lesson: prove input fixes with compositor input, never a Qt sendEvent sequence (the earlier test passed on a synthetic sequence). (lane players-shared-layer)
- Symptom: mpv logs "autostereo: Inserting stereo conversion filter ... 3840x1080 => 3840x2159" and shows only the left view. Cause (read from code): f_auto_filters.c sets the one view `dar` from the VO's capability (`vo->stereo_view`) before any declaration succeeded; if the declaration is refused the picture is 3840 wide in a one view window. Fix: take the decision from the outcome (vo->stereo_declared, VO_EVENT_STEREO_DECLARED once, filter inserts the aspect only afterwards). Also mpv cannot tell marked 2D from unmarked (MP_STEREO3D_MONO = 0 equals unset). (lane players-shared-layer)
- Symptom: shipped patch stacks differ from the fork branches (Qt Multimedia patch 0009 absent from the fork branch; Dragon's fork branch still has a 2.5/1.2 copy that the shipped package lacks). Cause: no tag on the fork per shipped version. Fix: start every milestone from the shipped stacks and tag each shipped package version on each fork. The shared library itself still holds the old guess (`width*2 >= height*5`, `width*5 <= height*6`). (lane players-shared-layer)
- Symptom: the halves test passes a flat 2D clip as a pair. Cause: it looks at the first frame only (title card, flat first frame). Fix: judge a few frames spread over the first seconds. Matroska muxers write DisplayWidth/Height equal to the frame for side by side, so "plane = frame" can mean either; author with one eye's display size. (lane players-shared-layer)
- Symptoms and causes found by failing first: baseline mpv paired adjacent base frames; baseline Qt supplied base only frames; first raw mux lost enhancement parameter sets (fixture failure); mpv renderer leaked one chroma sample at the eye boundary (native eye width check fails on both GPUs); Qt's first native view conversion leaked chroma at the packed boundary; the old Quick writer failed 8 of 12 format combinations (Dragon got a black picture); VLC's first pairing failed because AVFrame.pts was unset (use best effort pts); VLC's format cache recorded a live eye correction but kept old pixels until reconfiguration; a base only Quick probe sampled a zero area rectangle. Each was caught by an oracle (eye and frame address labels, motion across three captures, circular disc, independent source pattern). (lane spm-wine-41)
- VLC X11 path shows 3D flat: display.c declares the video child XID with stereo_declare_x11 but the top level never lists it; use `stereo_declare_x11_child(display, toplevel, xid, STEREO_SBS_FULL, video class, 0, view_w, view_h)` and `stereo_remove_x11_child` on close. The published +15 did not contain round 207's work because the chain went +10, +13 (from +10), +14, +15 (check that a later package contains the earlier patch numbers). (lane readme-headset-door-277, vlc-fullscreen-249)
- Symptom: a half side by side or top and bottom view flattened to 2D comes out twice too wide (SAR 2:1, DAR 32:9) or too narrow (SAR 1:2) although a SAR 1:1 control is right; Jellyfin #18060 at e278114 (`crop,scale=iw*2:ih,setsar=sar*2`). Cause: a filter that scales the SAR by a constant assumes square source pixels described per packed frame. FFmpeg's `scale` carries an unset SAR through unset, and `setsar` then reads it as 1; a SAR that already describes each view (Matroska) is doubled again. Fix: set the SAR on the whole frame before the crop and the stretch, double it only when it describes the packed frame, and say how that is decided (the frame at its SAR 2.5:1 or wider side by side, 1.2:1 or narrower top and bottom, holds full views). How found: the review's probe, then fixtures with a square drawn at display size, run through jellyfin-ffmpeg 8.1.3-2. (lane jellyfin-review-528)
- Symptom: a Matroska half side by side file probes as SAR 2:1, DAR 32:9, and a program that "restores" the squeeze doubles it. Cause: FFmpeg's Matroska demuxer folds DisplayWidth/DisplayHeight times the stereo multiplier into the stream SAR, so the SAR describes one view (RFC 9559 18.10); with no DisplayWidth at all the default is the coded width, which also gives 2:1. Writers differ: FFmpeg's muxer writes DisplayWidth = width x SAR / 2 (a SAR 1:1 1920x1080 left_right file declares 960x1080 views), mkvmerge by default writes the whole frame's width (right for half, 3840 for a full 3840x1080 file, issue jellyfin#11355), and mediainfo 25.04 reads DisplayWidth as the whole frame's (PAR 0.5 for a per-plane full file). With DisplayUnit 4 (unknown) FFmpeg folds nothing and reports the codec's SAR. Fix: read the SAR of a stereo Matroska track as per view; never apply the half-format stretch to it twice. How found: mkvinfo, ffprobe and mediainfo on the same fixtures. (lane jellyfin-review-528)
- Symptom: a hardware crop of an 806-line full top and bottom view comes out 402:403 (383:384 once Matroska stores an integer DisplayWidth). Cause: `setsar` evaluates in double and stores `av_d2q(value, max)` with max 100 by default, so 403/201 becomes 2/1 and 128/45 becomes 91/32; libplacebo then derives the output SAR from the uncropped frame (vf_libplacebo.c config_output and the per frame path), while vpp_qsv keeps the input SAR whatever it scales. Fix: `setsar=...:max=1000000` (78 of 78 SAR products exact, 10000 still rounds 14). How found: setsar's verbose log line for each SAR and factor; the route ran on an AMD Renoir iGPU with jellyfin-ffmpeg's bundled RADV. (lane jellyfin-review-528)
- Symptom: a 2D view cut out of a 3D source on a hardware route still carries the 3D mark (Matroska StereoMode, Stereo 3D side data), and with libx264 the output's frames abort any FFmpeg 8 filtergraph with error -17 (File exists). Cause: only the software chain ran `sidedata=mode=delete:type=STEREO3D`; libplacebo and vpp_qsv copy the frame's side data, the muxer writes StereoMode and libx264 writes the SEI, which gives two Stereo 3D entries per decoded frame. Fix: delete the side data ahead of the hardware crop too (it works on drm_prime frames). How found: fixtures that carry a mark; earlier fixtures without one could not show it. (lane jellyfin-review-528)

## Measured facts

- Clauses for frame packing SEI work: general_non_packed_constraint_flag is H.265 7.4.4 p.90 (not 7.4.3.3) plus D.3.16 p.350, sub-layer flags p.91; a prefix SEI unit takes nuh_layer_id and nuh_temporal_id_plus1 of its VCL NAL (H.265 D.3.1 p.324); persistence ends at a message with the same id, a new CVS or end of bitstream (H.264 D.2.26 p.391, H.265 D.3.16 p.353 to 354); the cancel flag cancels any previous message in output order; H.264 tile format type 7 needs CroppedWidth and CroppedHeight multiples of 3 (D.2.26 p.388, equations D-30 to D-33); spatial_flipping_flag H.264 p.389, H.265 p.352; quincunx H.264 p.388, H.265 p.351; frame0_self_contained_flag must be equal in all messages of a CVS (H.264 p.390). Editions: H.264 V16 06/2026, H.265 V11 01/2026. Existing line only says "The decoder owns SEI lifetime, cancellation and coded-sequence boundaries" (metadata-and-geometry.md:14). (lane ffmpeg-25395-review-416)
- Layer scoping: H.265 D.3.1 a non nested frame packing message applies to the layer of its SEI NAL unit and D.3.16 scopes persistence to that layer (one arrangement per layer, latest in output order); D.3.24 nested messages apply to every layer in the nesting lists and need bitstream_subset_flag 0; H.266 D.6.2 nested uses NestingLayerId[0]; H.264 F.13.2, G.13.2, H.13.2 define nested frame packing for SVC, MVC, MVCD but G.13.2.2 limits MVC nesting to payloadType 23 or less. FFmpeg's VVC decoder fails an access unit on any NAL with nuh_layer_id above 0 (AVERROR_PATCHWELCOME) and its parser glues a layer 1 picture unit to the next access unit (1 of 10 frames decodes); the HEVC parser splits on base layer NAL units only so a prefix SEI of another layer lands at the end of the previous packet. (lane ffmpeg-24628)
- Debian testing ships vlc 3.0.24-3 with Qt 6 while VLC Stereo was still 3.0.24-1 with Qt 5. Stock HEVC proof clips made with libx265 4.0 carry no frame packing SEI (`frame-packing` ignored through libx265), so regenerate with the edition's patched x265 for a true HEVC SEI test. (lane players-shared-layer)
- VLC presented 95 paired frames of 96 (initial frame omitted) and this is recorded, not described as 96 displayed pairs; mpv 33 Meson tests pass on the authored build but the Debian recipe enables none, so report it as such; Qt installed suite 62 frame format cases and 20 independent eye cases, Quick suite 31 cases per GPU. Keep a synthetic base only clip as the iPhone qualification control so base only compatibility cannot pass as stereo success. (lane spm-wine-41)
- Web video findings: the stereo layer's shape rule declares a mono 2.40:1 scope film (1920x800) as side by side; MP4 st3d does not say half or full width (WebM DisplayWidth does, RFC 9559 18.10); WebRender folds compositor surfaces back for opacity, rotate, rounded clip ancestors and backdrop-filter (can_promote_to_surface); declarations on the element's own surface: marked video 1, unmarked via shape policy 1, canvas 1. Disparity measured +24.0/-16.0 marked video, +18.0/-12.0 unmarked, +30.0/-20.0 canvas, 0.0 outside. (lane waterfox-stereo)
- Hardware decode proof set (installed packages, two GPUs): recorded decoder corpus compares all YUV components with software, source depth, timestamps, frame identity, stereo marks, persistence/cancellation, both eye orders and 2D controls; 84 runs of MLT, Qt Multimedia and VLC over single GPUs and both hybrid preferences; 12 Vulkan/GL software/hardware capture pairs with maximum RGB difference 0; negative controls from published packages (wrong GPU order, software decode, CUDA on the AMD display) exit 1; published FFmpeg reproduces the fallback crash with exit 134. Decoder only CPU 23%/17% (Renoir) and 23%/13% (RTX 3060) software/hardware over about 20.5 s. H.264 High 10 stays software on both GPUs, HEVC 12 stays software on Renoir, VLC stays software for HEVC 12 (P012 mapping absent); no reduced depth output is substituted. 7 of 32 candidate cases miss a zero settled drop target (1 to 9 drops, 46.16 to 48.19 flips/s) and are recorded, not hidden. (lane ums-3d-bugs-178-gpt)
- MVC is H.264 Annex G in the V16 (06/2026) edition and Annex H in the 2009 edition; check the edition before citing an annex. (lane glossary-403)

- Clauses for the depth and multilayer HEVC fields FFmpeg parses (H.265 V11, read in the local edition, ORDER 174): AuxId is ScalabilityId[i][3] and the dimension_id values follow the set bits of scalability_mask_flag in index order, F.7.4.3.1.1 (Table F.1: 0 texture or depth, 1 multiview, 2 spatial or quality, 3 auxiliary; Table F.2: AuxId 1 alpha, 2 depth); the 3D reference displays information SEI (payloadType 176) is G.14.2.3 (syntax) and G.14.3.3 (semantics): mantissa_ref_display_width and mantissa_ref_viewing_distance are Max(0, exponent + prec - 31) bits long, up to 62; nuh_layer_id is 0 to 62 and 63 is reserved, 7.4.2.2. How the checks were built is in the contrib-ffmpeg lessons. (lane ffmpeg-depth-bugs-174)
- **FFmpeg's `view` on a frame packing SEI is the position in the pair, not the eye.** Symptom: a frame sequence with content_interpretation_type 2 shows the eyes exchanged although the player reads `AV_STEREO3D_VIEW_LEFT` and `RIGHT`. Cause: `h2645_sei.c` sets `view` from current_frame_is_frame0_flag alone and `AV_STEREO3D_FLAG_INVERT` from type 2, so frame 0 is reported as left while H.264 Table D-10 makes it the right view. Fix: the eye is view XOR invert; use `view` to align the pair and the flag for which eye comes first. Matroska StereoMode 14 has the flag and no view; on MV-HEVC `view` is the real eye and the flag is not set. How found: x264 `--frame-packing 5` with the SEI's content type patched to 2, then `showinfo` printed `frame alternate (inverted), view: left` for frame 0 (sView PR 187).
- SAR semantics for packed frames: H.264 V16 D.2.26 NOTE 2 (p.387) says the VUI SAR gives the shape of the packed frame as a 2D decoder shows it, and each upconverted constituent frame keeps that SAR, so under a codec SAR a view takes the packed frame's shape (H.265 V11 D.3.16 NOTE 1 describes the same upconversion without the SAR sentence). Matroska's DisplayWidth/DisplayHeight (RFC 9559 18.10) and the ISO/IEC 14496-12:2026 PixelAspectRatioBox under a StereoVideoBox (13.5.4.1: "2:1 or 1:2" for spatial packings) describe each view instead. Nothing in FFmpeg's output says which one a stream's SAR is. (lane jellyfin-review-528)
