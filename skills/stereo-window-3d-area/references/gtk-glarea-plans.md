# GTK pieces still to build: GIMP (GTK 3), a GL player, deep colour

Written on 2026-11-08 (ORDER 137, milestone 2), from the sources of GIMP 3.2.6, Celluloid 0.29 and GTK 4.24.1.
Plans, not builds.
The built part is in [GTK 4 and GtkGLArea](gtk-glarea.md).

## GIMP 3.2: the canvas is cairo, not GL

- `grep` for `GtkGLArea`, `gtk_gl_area`, `GdkGLContext` and `epoxy` in GIMP 3.2.6's `app/` and `libgimp*` finds nothing; the build needs `gtk+-3.0 >= 3.24` only.
- The canvas: `GimpDisplayShell` connects `draw` handlers (gimpdisplayshell.c) and `gimp_display_shell_draw_image()` (app/display/gimpdisplayshell-draw.c) renders the image through GEGL into `shell->render_cache`, a cairo image surface in device pixels (chunked, `gimp_display_shell_render()`), and paints it with `cairo_set_source_surface()` and `cairo_paint()`. The tools and guides are `GimpCanvasItem`s drawn with cairo over it. The projection format, the colour management filter (`gimpdisplayshell-profile.c`, `-filter.c`) and the display transform all end in that 8 bit cairo surface.
- So there is no GL area to give a surface of its own, and the route "a native child GdkWindow with the same two views" would only move cairo's 8 bit picture.
- The plan: the stereo content of GIMP is a document with depth, not a rendered scene. Two ways, which differ for the person and so both are options (memory every-path-a-user-option): (1) the depth layers design (picture plus depth assembled into full side by side by libstereo-dibr, memory depth-content-options-shared-library: best measured default, the person's options strength and gap filling), shown as an area of the canvas; (2) the image drawn twice with its layers shifted by their own depth, as the desktop does for its UI (memory stereo-plasma-depth-rules: "faked 3D becomes stereo by doubling, not by cameras").
- Where it goes in the code: `gimp_display_shell_draw_image()` draws the render cache once; for stereo it draws it into a surface twice as wide (`render_cache` and the paint of each chunk once per eye, with the per-layer shift applied in `gimp_display_shell_render()` through the GEGL pipeline), and the surface becomes the picture of a stereo area.
- What GTK 3 needs for that: a surface of its own under the cairo drawing. GTK 3.24.52's Wayland backend has a window type for it, `GDK_WINDOW_SUBSURFACE` (gdk/wayland/gdkwindow-wayland.c, `should_map_as_subsurface()`, a `wl_subsurface` with its own position), and GTK 3's own `GtkGLArea` draws its FBO into the toplevel's cairo surface with `gdk_cairo_draw_from_gl()` (gtk/gtkglarea.c): a stereo `GtkGLArea` for GTK 3 renders as now and gives the two views to such a window, with the same declaration as GTK 4's on it, and the X11 route of GTK 4's page (a child X window) for `GDK_BACKEND=x11`. That is the GTK 3 piece to build, after Daniel's choice between (1) and (2); it does not touch GIMP's drawing until then.
- Deep colour (Daniel's ask for the working canvas): the render cache is `CAIRO_FORMAT_ARGB32`/`RGB24`. Cairo 1.17.2 and later has `CAIRO_FORMAT_RGBA128F` and `RGB96F`; a 16 bit or float cache and a GTK 3 path that hands such a surface to the compositor are both missing (GTK 3 draws every window through 8 bit buffers).

## Celluloid 0.29 (GTK 4): a player in a GtkGLArea

- The video area is a `GtkGLArea` (src/celluloid-video-area.c, `gtk_gl_area_new()`); its `render` handler emits a "render" signal, and `celluloid_model_render_frame()` (src/celluloid-model.c) reads `GL_FRAMEBUFFER_BINDING` and calls `mpv_render_context_render()` with `MPV_RENDER_PARAM_OPENGL_FBO` and `FLIP_Y`. That is exactly what the stereo area expects: the handler runs once per eye and renders into the framebuffer GTK bound, so for a stereo file the model asks mpv for the view of `gtk_gl_area_get_current_eye()`.
- Per eye, mpv: the file's input packing is a player option (CLAUDE.md, 2026-10-31: "a player adds the input corrections (the input packing, and a per-file "Swap left and right eyes") for every media file shown in 3D, declared or not, since a declaration can be wrong"). Our mpv build reads the declaration (SEI, Matroska StereoMode, MP4 st3d) and takes the packing apart; the eye for a render is chosen with the packing's view selector and the swap (the option names are the edition's mpv build's own; take them from its patches when the build starts).
- Per-file state, where Celluloid and mpv keep it: Celluloid sets `watch-later-directory` (celluloid-player.c, `{"watch-later-directory", watch_dir}`) and runs `write-watch-later-config` when a file is left (celluloid-mpv.c). That directory holds one file per media file (named from the path's hash) with the start position and the options in mpv's `watch-later-options`. That is "the same place the resume position of continue playback is saved" (memory never-touch-the-user-file, Daniel 2026-10-23): the two corrections go into `watch-later-options`, so they are saved and forgotten with the resume entry, and the file is never touched on its own.
- The offer to write the file (memory never-touch-the-user-file): "offer the user to save to the file", "when accepted, it's apply to the file and leave the option unmarked", for the formats whose writers we have (Matroska StereoMode through mkvpropedit, MP4 st3d in place, as sView 26.9+stereo3d4 does); a layout the container cannot describe is refused with the reason and the choice kept.
- No correction on 2D content: the menu entries are shown only for a file shown in 3D (declared or chosen).
- Celluloid's 3D options, and only these: enable 3D (the area's `stereo` property, on by default for a file that is stereo), render resolution per eye (the area's size times the scale today; an option to render each eye at a chosen size and let Stereo KWin do the one resize, as the pact says), and a shortcut to Display Settings (KScreen's page); plus the two input corrections above. No output modes, no swap of the output.
- GTK side already there: the render signal per eye, the opaque picture, the honest failure (a file that cannot be shown per eye says so in the window, from `stereo-error`, in Celluloid's own words), X11 and Wayland.

## Deep colour and HDR for a GtkGLArea

- Today the area is 8 bit: its texture is `GL_RGBA8` (or `GL_RGB8` for a stereo area) and `gdk_gl_texture_builder_set_format()` gets `GDK_MEMORY_B8G8R8A8_PREMULTIPLIED` (`B8G8R8X8` for stereo), with GDK's default colour state (sRGB).
- GDK has the parts: float and 16 bit memory formats (`GDK_MEMORY_R16G16B16A16`, `_FLOAT`), `gdk_gl_texture_builder_set_color_state()`, the colour states (sRGB, linear, Rec. 2100 PQ and linear, the CICP ones), and `gdksubsurface-wayland.c` already sets the colour state of an attached dma-buf through `wp_color_management` (`gdk_wayland_color_surface_set_color_state()` with the fourcc and the premultiplication), after `gdk_wayland_color_surface_can_set_color_state()` says whether the compositor takes that pair.
- The plan, in GTK's style: properties `GtkGLArea:color-state` (a `GdkColorState`, default sRGB) and a depth (8, 16, half float, float; the standard's 10 and 12 bit depths ride in the 16 bit and float formats, memory deep-colour-full-standard: "10, 12 and 16 bpc", never capped) that choose the texture's internal format, its `GdkMemoryFormat`, the dma-buf fourcc the compositor gets (`AB30` for 10 bit, `AB48` for 16 bit, `AB4H` for half float) and the colour state of the attached subsurface; the stereo copy then blits float or 16 bit views, and the X11 route reads the depth back as the same.
- What Stereo KWin's declared subsurface must carry: the colour description of the surface (the `wp_color_management` image description) and the buffer's depth, per view, and treat both views alike; GTK sends them together with `set_content(3)` on the same surface. Whether KWin applies a surface's colour description to a declared stereo surface is not measured: the first test is a half-float area in Rec. 2100 PQ declared as stereo, captured on the HDR output, with the colour state, primaries, transfer function, range and precision recorded one by one.
- Evidence rule: stereo evidence does not establish HDR correctness (the general skill): the stereo checks stay as they are; HDR is a separate set of rows (the surface's configuration and a read-back for the depth; the compositor's colour pipeline for the rest).
