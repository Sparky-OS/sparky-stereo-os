# GTK pieces still to build: GIMP's depth layers and deep canvas, and what is left

Written on 2026-11-08 (ORDER 137, milestone 2) from the sources of GIMP 3.2.6, cut on 2026-11-26 (milestone 4) to what is left, and rewritten the same day after GIMP's milestone 1 (the canvas per eye, GIMP 3.2.8).
The built parts are in [GTK 4 and GTK 3 and GtkGLArea](gtk-glarea.md); GIMP's canvas per eye, its route, proof and traps are in [an editor's canvas per eye](../../stereo-pictures/references/an-editors-canvas-per-eye.md).

## GIMP, milestone 1 (built): the canvas per eye

Each eye is rendered by GIMP's own render code into a render cache of its own, from that eye's sources (an eye layer, or the eye's view of a packed picture in both halves), and the two pictures go up as textures into one stereo GtkGLArea that lies under the canvas items (GimpCanvas's underlay). The eye's sources are a list (`GimpDisplayShellEyeSource`: a buffer in image coordinates, its abyss, the part of the image it fills), which is where the depth layers plug in.

## GIMP, milestone 2: the depth layers (queue row 148)

Daniel's design (2026-10-15 ~22:40): "we'll add a special layer type that group other layers in one depth value the artist sets, with 0.000 precision ... the same 2D movement you do with the mouse + a handy key pressed at the same time make it "pop", other make it sink". A depth layer holds other layers at one depth; layers in no depth layer are at the screen (0); no nesting that adds up; two keys, not one key with a drag direction; the engine in a library that GIMP (C) and Krita (Qt) both call; a tool has no limits (unclamped, remembered, no forced warning); each eye gets the layer shifted by half the value, opposite ways (the doubling rule, never cameras); modes 1 and 2 stay.

The page's earlier plan (2026-11-08) named two ways of depth in GIMP, which differ for the person and so are both options: the depth layers below, and a picture with a depth map assembled into full side by side by libstereo-dibr (memory depth-content-options-shared-library), shown as an area of the canvas. This milestone builds the layers; the depth-map way stays planned.

1. **The model in libstereo-policy** (C, `stereo-depth.h`; Krita reaches it through the stereo layer's Qt side):
   - `int stereo_depth_parse (const char *text, double *separation)` and `int stereo_depth_format (double separation, char *out, size_t size)`: the value as text, three decimals in the C locale ("12.500"), refusing NaN and infinities and nothing else (no clamp);
   - `double stereo_depth_eye_shift (double separation, int eye)`: -s/2 for the left eye, +s/2 for the right (positive is behind the screen, the sign round 1's depth d already uses);
   - `int stereo_depth_shift_rgba (const void *src, int width, int height, int stride, int bytes_per_sample, double dx, void *dest)`: one view of a layer shifted by dx, a copy for a whole dx, resampled for a fractional one at the edition's quality, for the plug-in's export and for Krita; GIMP's canvas shifts through GEGL (`gegl:translate` with GIMP's interpolation), the same numbers.
   - Tests: parse and format round trips, the sign, a whole shift equal to a copy sample for sample, a half-pixel shift against a computed reference.
2. **The layer type in GIMP's core:** `GimpDepthLayer` (`app/core/gimpdepthlayer.[ch]`), a subclass of `GimpGroupLayer` with a `depth` property (gdouble, three decimals, unclamped); the Layers dock shows the value and edits it, Layer > New Depth Layer makes one from the selected layers, PDB procedures (`gimp-depth-layer-new`, `-get-depth`, `-set-depth` in `pdb/groups/depth_layer.pdb`) let the plug-in bake exports.
3. **Each eye's picture:** two eye projections of the image (a `GimpProjectable` per eye whose graph follows the image's layer stack and puts a `gegl:translate` of the eye's shift after each depth layer's node), invalidated by the image's own updates. The display's stereo module gets a third kind of image, "depth layers", whose source per eye is that eye's projection buffer (the source list of milestone 1 takes it as it is). An image with depth layers and the eye layers too is a question to ask before building (not settled by the design).
4. **XCF:** a depth layer is saved as a group layer with a persistent parasite `gimp-depth-layer` holding the value as text, so stock GIMP opens it as a plain group (everything at the screen) and loses nothing; `app/xcf/xcf-load.c` turns such a group into a `GimpDepthLayer` and `xcf-save.c` writes it, as GIMP already reads its symmetry parasites there (`gimp-image-symmetry:GimpTiling`). Export bakes the pair as MPO, JPS or PNS through the plug-in (a flattened view of each eye's projection).
5. **The two keys:** held over the canvas while the tool's normal drag goes on, as GIMP holds Space to pan (`app/display/gimpdisplayshell-tool-events.c`) and Krita holds V for its straight ruler (an input action in `libs/ui/input`, bound in `kritadefault.profile`). Free in both, read from GIMP 3.2.8's action tables and tool registrations and from Krita master's `krita.action` and `kritadefault.profile` (2026-11-26): J, 7, 8, semicolon and apostrophe (GIMP also leaves L and V free, but Krita uses L for a snapshot and V for the ruler; comma and period are Krita's preset keys). Proposed: 7 sinks and 8 pops (side by side on every layout's top row, the lower number sinking); J is the spare. Still to read before choosing: the keys Krita's tool factories set themselves (`setShortcut` in `plugins/tools`), which invent's code search answers only with a login, and the AZERTY layouts, where the top row gives digits only with Shift. Rebindable in both programs.
6. **Proof:** a depth layer at +12.000 and -4.500 over a background at 0: each eye's picture against a control computed from the layer (whole and fractional shifts), the background equal in both eyes, the pop and sink keys changing the value by the drag (read from the property), the XCF read back by our GIMP and by Debian's (a plain group), the MPO export's two frames.

## GIMP, milestone 3: the deep and HDR canvas

Daniel's design (2026-10-15 ~23:10): "gimp ramp up on the working canvas is included, deep sdr/hdr color + hdr - passing to the compositor just like 3D information ... our job is make sure to code it to the specs - inside our contract only!" Every depth the standard defines (10, 12, 16 bits), deep colour SDR as well as HDR, declared to the compositor; GIMP never tone-maps for a screen.

1. **A deep render cache:** the eye caches and pictures in `CAIRO_FORMAT_RGBA128F` (cairo 1.18.4 in Debian testing has it), rendered with `gegl_buffer_get()` into the float premultiplied format that matches it ("RaGaBaA float" in the display's colour space) instead of "cairo-ARGB32"; the textures `GL_RGBA16F` or `GL_RGBA32F`, uploaded with `GL_FLOAT`.
2. **The area's depth and colour state:** `gtk_gl_area_set_format()` by the image's precision (8 bit as now; 16-bit integer images in 16 bit where the driver exports it, else half float; float and double images in float, handed over as half float, the deepest dma-buf format) and `gtk_gl_area_set_color_state()` from the image's profile mapped to ITU-T H.273 code points (sRGB 1/13, linear sRGB 1/8, Rec. 2100 PQ 9/16, HLG 9/18; a profile with no code points converted to linear Rec. 2020, 9/8). GIMP's display transform (`gimpdisplayshell-profile.c`) then converts to that described state instead of to the monitor's profile, after soft-proofing and the display filters; Stereo KWin converts per screen.
3. **A deep picture without stereo:** GTK 3 draws a plain area into its 8 bit window, so a 2D image reaches the compositor deep only through the same surface without the declaration (one view): GTK's piece first (row 137), then GIMP's canvas uses the area for every image above 8 bits or with a wide or HDR profile, 3D or not.
4. **What GTK owes for it:** the memory route (`wl_shm` ABGR16161616 and its half float form) for a 16-bit integer picture on NVIDIA's EGL and zink on NVIDIA, which export no 16-bit dma-buf, and for a software renderer; an API for the luminances and mastering data (`set_luminances`, the mastering display and content light levels), without which KWin takes PQ's defaults and shows the reference white at about half (measured in GTK 4).
5. **Upstream:** GIMP's open merge request [!2755](https://gitlab.gnome.org/GNOME/gimp/-/merge_requests/2755) (wp_color_manager_v1 to read the monitor's profile in libgimpwidgets, by v4vansh, open since 2026-04-09) is the other half of the same protocol: GIMP converting to the screen's profile itself. A canvas on a described surface of its own skips that conversion and the rest of GIMP's interface keeps it. Read !2755's state again before building.
6. **Proof:** the ramp of 256 steps over 1/256 of the range counted where it is rendered and in each eye's buffer at a virtual HDR output (milestone 3's private KWin), for 8, 10, 12 (a 12-bit HEIF loaded at 16 bits), 16-bit integer, half float and float images; what KWin received (fourcc, primaries, transfer function); the red row where the description is ignored.

## What earlier milestones left, still open

- **A 16 bit integer stereo area on a driver that exports no 16 bit dma-buf** (NVIDIA's EGL and zink on NVIDIA, in GTK 4 and GTK 3 alike: the area says "cannot export its picture as a dma-buf"). The memory route above is the way that keeps every bit.
- **Luminances and mastering data.** A colour state carries primaries, transfer function, matrix and range, nothing else, in GDK 4 and in GDK 3's, so a PQ picture reaches KWin without its peak and KWin makes room for 10000 cd/m²: the reference white is shown at about half (measured in GTK 4: 110 cd/m² on a 1000 cd/m² output). It needs an API for the protocol's `set_luminances` and the mastering display and content light levels.
- **Hybrid log-gamma on a stereo area.** KWin lists no HLG transfer function, so the pair cannot be described: owed by KWin. GDK 4 converts it itself for a plain area; GDK 3 converts nothing, so its left view alone shows the values as written and the area says why.
- **A colour state on X11.** An X window has no description; a stereo area with a state other than sRGB, or deeper than the window's visual, says so (GTK 4 and GTK 3).
- **A 2D widget over an X11 stereo area in GTK 4** (`glarea-stereo-test --stereo --overlay` on X11: the label is hidden). GTK 3 shows it when the window has an alpha channel, by placing the child below the window without a frame and keeping a hole; GDK 4 needs the same, as a `GdkSubsurface` over the child window so that GSK cuts the hole in the toplevel.
- **GTK 3's X11 window on zink** shows only its GL area under Xwayland (Debian's GTK 3 too): GTK 3's own fault, recorded with the lane's failures; the edition's NVIDIA sessions run GLX programs on zink, so a GTK 3 program with a GL area on X11 is affected there.
