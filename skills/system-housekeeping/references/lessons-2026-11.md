# system-housekeeping: lessons from the lanes of 25 October to 6 November 2026

Harvested by ORDER 429 from the accepted lane reports; each line names the lane it came from.
A trap gives its symptom, its cause, its fix and how the cause was found; a recipe gives the commands and the result to expect.

## Recipes that worked

- Which mode did GRUB really hand over: on x86 `/sys/kernel/boot_params/data` is world-readable; the video type at offset 0x0f and width and height at 0x12 and 0x14 give the mode with `gfxpayload=keep` (0x70 at 1920x1080x32 matched the configured gfxmode). Use it for a boot check. (lane boot-no-fallbacks-345)
- Proof by user: as a normal user `--preview` lists only her own mailbox, dead.letter and msmtp queue; as root 13 expected paths. As a normal user `--clean system_mail.mailboxes` prints `Access denied: /var/mail/bob` and `Errors: 2` and leaves the files. CleanerML has no per-option condition (only `os` per action and `<running>` per cleaner), so a queue-of-removed-program option needs a generated file plus dpkg triggers or an upstream `unless_exe`. (lane bleachbit-system-mail-415)
- Vendor-gated service, ORDER 43 (thermald only on Intel, nvidia-imex only on a configured IMEX domain): `apt-get -s install sparky-stereo` in a container with the edition's apt (4,007 `Inst` lines) shows thermald pulled only by sparky-stereo-hardware-support, urfkill and nvidia-imex by nothing; detection fixtures printed `intel-desktop: THERMALD` and `amd-desktop: no-thermald` on 0.1.24 where 0.1.22 gave Intel desktops none; the settling step ran in four containers (Intel and AMD, automatic and manual): Intel automatic became manual, AMD automatic was removed with its configuration kept, both manual cases untouched, a second run did nothing; the upgrade removed nothing (no `Remv`) and the step on AMD removed exactly thermald. (lane thermald-intel-43)
- A systemd container that boots real units (ORDER 460, 463): `docker run -d -t --cgroupns=private --cap-add SYS_ADMIN --security-opt apparmor=unconfined --tmpfs /run --tmpfs /run/lock -e container=docker --entrypoint /bin/sh IMAGE -c 'mount -o remount,rw /sys/fs/cgroup && exec /usr/lib/systemd/systemd'`, then wait for `systemctl is-system-running` to say running or degraded. `docker restart` of that container is a real boot of the same disk: the failing boot can be run again, red and green. No device is passed in; a FIFO made with `mkfifo /dev/NAME` stands in for a device node a daemon only opens.
- A daemon whose failure comes after a hardware check, proved without the hardware (urfkill): put the missing device in as a FIFO, and a tiny `LD_PRELOAD` shim that makes libudev list one fake input device, so the real code reaches the step the report is about (here the session checker: "GetSeats Failed ... ConsoleKit ... failed to setup session checker" on Debian's build, active on the fixed build).
- Two units that cannot run together (ClamAV): enable both with the old package's state (`systemctl enable`), start the daemon, then the once unit: "Failed to lock the log file". Switch the second off with `systemctl disable` and Debian's `was-enabled` stays false at the next configure of the package (measured with `dpkg-reconfigure -fnoninteractive clamav-freshclam`); `deb-systemd-helper` itself refuses to run outside dpkg ("was not called from dpkg").

## Traps: the symptom, the cause, the fix, how it was found

- Symptom: the skills helper's `link` would have cut a station from 31 skills to 7 core skills. Cause: the package gate compared `${Status}` with "ok installed", which dpkg never prints ("install ok installed"). Fix: query `${db:Status-Status}\n` (one word per architecture) and test with dpkg's own database through a private DPKG_ADMINDIR (two-architecture, held, removed-with-config cases): 42 of 42. The skill's system-housekeeping text mentions db:Status already (lane publish-qtmm12-skills-281)
- Symptom: bench tests of GRUB menu rewriting are red (7 FAILs, menu empty) or pass vacuously. Cause: Debian's `zz-update-grub` hook skips in containers, `grub-mkconfig` calls `${sbindir}/grub-probe` by full path, and in the C and C.UTF-8 locales glibc's gettext translates nothing whatever `LANGUAGE` says (German and English were the same string, so comparisons passed). Fix: run `update-grub` in the test, stub the probe at its own path, generate a locale (`localedef -i de_DE -f UTF-8 de_DE.UTF-8`) and set LANG to it. Found by: the first run's empty menu and English output after a correct merge. (lane kernel-keep-298)
- Symptom: initramfs-tools' `update-initramfs.conf` cannot be overridden. Cause: the file belongs to `initramfs-tools` (0.151), the switch is at update-initramfs lines 400-401, and there is no conf.d or environment override. Fix: divert it, but a conffile diverted in place cannot be renamed back on remove, so use a symlink at the original name plus the edition's own conffile beside it. Without a postrm rewrite the GRUB menu keeps merged translations until the next update-grub after the package is removed. (lane kernel-keep-298)
- Symptom: `grub-editenv` fails in a container ("failed to get canonical path of `overlay'") even on a valid file or `create`, while `grubenv.new` works. Cause: overlayfs. Fix: stub it in removal cases. Also: containers see the host's /sys/class/drm read-only, so `update-grub` in a container measures the host's screens through the edition's GRUB fragment. (lane boot-no-fallbacks-345)
- Symptom: sparky-beep tools open their window with exit 0 and no message when HOME is unusable, beep.conf unreadable or the tune folder unreadable (28 of 36 fail). Fix: one helper (beep_init_or_stop) runs init, reads the errors and prints the reason on the terminal, in the journal (logger -t) and in the program's own dialog (lane no-fallbacks-look-346f5)
- Symptom: a kept /home loses bleachbit.ini. Cause: the installer copies /etc/skel over a kept /home. Fix: the offered `--ignore-existing` copy. Found by: reading the installer step; not this package's fault. (lane bleachbit-system-mail-415)
- Symptom: a systemd unit of a vendor-specific daemon fails at every boot and `thermald --systemd` run by hand in a container exits 0. Cause: the daemon prints "Unsupported cpu model or platform" and leaves before it takes its bus name, so the failure is the unit's (`Type=dbus`), not the exit status. Found by: running the unit's own ExecStart line with the unit's flags in a container on an AMD host and reading the message, then the unit file's Type. A `--no-daemon` run prints a different path.
- Symptom: `systemd-analyze condition --unit=X` says nothing about an `ExecCondition=` line. Cause: it evaluates only `Condition...=` and `Assert...=`; run an ExecCondition command with `sh -c` under each fixture. (The drop-ins this found were dropped on 2026-11-07: a hand-installed service is the person's.)
- Symptom: a shipped script or drop-in has lost its comments (240 bytes of 900). Cause: Lean Code strips comments from every shipped file; the explanation lives in the authored source and the `-lc-hr` companion. Test the built `.deb`, not the source tree.
- Symptom: rebuilding a metapackage for one change changes other metapackages too (`sparky-stereo-system` gains a firewall package, the developer task gains nine command-line tools). Cause: main holds list changes of other lanes that are not published yet. Fix: build only the one meta (`PACKAGES=name VERSION=... bash packages/sparky-stereo-meta/build.sh`) and diff every Depends, Recommends and Breaks line of a full build against the published index before choosing; the full build's only wanted difference was the removed Depends. Found by: parsing the published `Packages` index and the new `.deb` control files with a script.
- Symptom: `lists/make-meta.py` stops on a missing `Packages` or builds metas at the wrong kernel version. Cause: it reads `REPO/Packages`, a flat index, for versions. Fix: write the published amd64 and all `Packages` into one file in a scratch folder and set `REPO` to it; a build on the host and one in the edition's container gave byte-identical control files (same `Sparky-Lean-Code` hash).
- Symptom: `tests/container-detection.sh` ends with `sparky-stereo-problems: command not found` (exit 127). Cause: `payload.sh` runs the catalog step, which the script's bare container lacks. Fix: use `tests/container-deb-detection.sh` with the built `.deb` (red with the published one, green with the new one).
- Symptom: a test container cannot install the edition's metapackages ("Depends amd64-microcode ... no choices", then "sparky-xterm"). Cause: the container needs Debian's `contrib non-free non-free-firmware` components and SparkyLinux's `core` and `tiamat` suites as well as the edition's repository. Install the edition's `sparky-stereo-apt` from a downloaded `.deb` after moving the hand-written `sparky-stereo.sources` aside, or dpkg stops at its conffile prompt.
- Symptom: a container install of `sparky-stereo-hardware-support` stops with "firmware-ipw2x00 agree question could not be asked". Cause: the package asks for a licence acceptance and the frontend is noninteractive. Fix: `echo "firmware-ipw2x00 firmware-ipw2x00/license/accepted boolean true" | debconf-set-selections` first.
- Symptom: a private `apt-get -o Dir::State=... update` on the host still printed the host's apt hook notices. Cause: the host's `/etc/apt/apt.conf.d` hooks were read despite `Dir::Etc::parts`. Fix: never run it on the host; use a container (package programs and their hooks run in containers only).

## Perks of the part

- Scratch-folder triage: `du -x`, bounded find maxdepth 9; classify each folder as SAFE (published long ago, listed in a lane's `.artifacts`), KEEP (parked work, unpushed commits), NOT SAFE (a link gate's scratch, named "never touch" in briefs); a folder's size in notes may be wrong (22 GB, not 9.3 GB); keep only the cited 1 MB files. (lane k3d-parked-trees-381)

## Measured facts

- Debian's split for failing boot steps: a failed `update-grub` fails the package; a failed `grub-install` warns and continues (grub-efi-amd64, shim-signed); a service start never fails a package (debhelper `|| true`); kernel hooks run with `run-parts --exit-on-error`, so one failing hook stops the later ones. Debian's plymouth-quit unit ignores `plymouth quit`'s status; a drop-in that counts failure only while a splash still runs changes what `systemctl --failed` shows. (lane boot-no-fallbacks-345)
- Symptom: clamav-freshclam-once.service fails at every boot with "Failed to lock the log file /var/log/clamav/freshclam.log". Cause: the freshclam daemon holds the lock and Debian's clamav up to 1.4.4+dfsg-1 enabled the daemon, the once service and its timer; 1.4.4+dfsg-2 (Debian bug 1134489) stopped enabling the once pair on a new install, and an upgrade keeps what the older package enabled. Fix: once, where the daemon and the pair are all enabled, disable the pair and say so; the person can switch either on again. Found by: the bug's own log, then the same failure in a container with the old state.
- Symptom: urfkill.service fails at every start with "failed to setup session checker". Cause: Debian's urfkill 0.5.0-8 lost a backslash in debian/rules, so `--with-session-tracking=systemd` became a comment and configure took ConsoleKit (`strings urfkilld | grep -ci consolekit` is 6 on Debian's build, 0 on the fixed one). Fix: the edition's build with the line restored; Breaks on the older version. Found by: reading debian/rules after the log named ConsoleKit.
- Symptom: the unit seems to fail for another reason in a container ("failed to setup arbitrator", then "failed to setup input device monitor"). Cause: no /dev/rfkill and no input device with a platform parent; these come before the session checker. Fix: the FIFO and the udev shim above.
- Symptom: a leftover package's unit is kept off by an ExecCondition guard, yet the person still sees a failed unit and a notice that offers to start it. Cause (measured): the guard does skip the unit and seven quick starts do not reach the start limit, so the failure is not the guard; the engine's generic handler offers `systemctl restart` for any failed service. Fix: mask the engine's handler for that unit by name (`UNIT.d/50-sparky-stereo-problems.conf` as a link to /dev/null) and name a handler of the package's own that keeps the failure with no repair. Not found: why the setup unit failed on the two real machines (their earlier boot's journal was not readable by the lane).
- Symptom: a package that is automatic and left behind has to go, but `apt-get purge` inside the maintainer script fails or is lost. Cause: the running apt holds the locks and rewrites its state file when the run ends. Fix: the postinst starts a oneshot unit with `systemctl --no-block start`, which waits for `apt-get -o DPkg::Lock::Timeout=-1 check`, simulates the purge (`apt-get -s purge`, nothing else in the Remv lines), then purges; the same unit is wanted by multi-user.target while its marker file exists. A package the person chose (manual, ZRAM=on in the old file) is kept.
- Symptom: tests/no-compressed-swap.py of kernel-settings fails on the published 20261106.1 (zram paths, Conflicts). Cause: it still checks the 20261103.3 design (Conflicts, no zram paths), before the opt-in; retire-zram.py also fails at its swap assertion the same way before and after. Not fixed here; both stand red on main.
