# An EDID for a claim: build it, validate it, and read what a kernel makes of it

Use it when a question about a sink is "what does the kernel's EDID parser do with this declaration": a sink that sets 3D_present with no mandatory timing, a sink that declares one 3D format on one VIC, a reserved bit or a reserved value of the HDMI Vendor-Specific Data Block, a shipped device's EDID from a public collection.
It needs no VKMS patch and no kernel build: any kernel package that ships the `bochs` display driver answers in a QEMU guest, through the connector's debugfs EDID override.
The stereo parser's output is read from the modes the probe helper rejects, so the connector needs no `stereo_allowed`.
Written on 2026-11-08 from the technical note on a side by side only sink (lane hdmi-technical-note-475); the kernels measured were Debian's stock 7.3.3 and the edition's 7.3.1-stereo3d16, and both gave the same answers.

## The recipe

1. **Write the EDID from the specification's table, not from an example.** A 128-byte base block (VESA E-EDID 1.3, the structure HDMI 1.4a 8.3 asks for) and one CTA-861 extension (revision 3) with a Video Data Block, the HDMI VSDB laid out after HDMI 1.4a Table 8-16 (tag 3, OUI 03 0c 00, physical address, byte 6, Max_TMDS_Clock, then byte 8 with HDMI_Video_present, byte 13 with 3D_present and 3D_Multi_present, byte 14 with HDMI_VIC_LEN and HDMI_3D_LEN, then 3D_Structure_ALL, 3D_MASK and the 2D_VIC_order_X entries) and a Video Capability Data Block (`e2 00 4a`). Set the checksum of each block last. Keep the generator small and name every byte in a comment, so the file is its own documentation. Vary only the field under test between files, so a difference in the result has one cause.
2. **`edid-decode --check FILE.bin` until it ends with `EDID conformity: PASS`.** A real display's EDID may fail on its own quirks (a Sony television of 2012 fails only because its range limits exclude its 24 Hz timings): keep it as the real case and say which line fails. The failures a generated EDID meets, and their fixes, are in the traps below.
3. **Read what the kernel makes of it.** Unpack the kernel package (image and modules), compute the `bochs` module's dependencies with `modinfo -F depends` (the package has no `modules.dep`; `depmod` writes it at install) and decompress the `.ko.xz` files, because BusyBox `insmod` reads plain `.ko` only. On 7.3 the order is `drm`, `drm_kms_helper`, `drm_client_lib`, `drm_shmem_helper`, `bochs`. Pack a static BusyBox, the modules, the EDIDs, a static `lsmodes` (the bench's `src/lsmodes.c`, which lists a connector's modes with `DRM_CLIENT_CAP_STEREO_3D` set) and an init script into an initramfs, and boot: `qemu-system-x86_64 -M pc -cpu max -accel tcg -m 1024 -display none -monitor none -serial stdio -no-reboot -kernel vmlinuz -initrd initrd.cpio.gz -append "console=ttyS0 rdinit=/init log_buf_len=16M loglevel=4 panic=-1" -vga none -device bochs-display,edid=on`. Without KVM a case takes about a second after a boot of about ten seconds.
4. **In the guest, for each EDID:** `echo 0x4 > /sys/module/drm/parameters/debug` once after loading the modules; then `dmesg -c >/dev/null`, `cat FILE.bin > /sys/kernel/debug/dri/0/Virtual-1/edid_override`, `echo detect > /sys/class/drm/card0-Virtual-1/status`, `cmp FILE.bin /sys/class/drm/card0-Virtual-1/edid` (the override took), `lsmodes /dev/dri/card0 NAME` (the modes the connector lists), and `dmesg | grep "Rejected mode"`.
5. **Read the rejected lines as the parser's output.** The `bochs` connector has no `stereo_allowed`, so every stereo mode the EDID parser added is dropped by `drm_mode_validate_flag()` and printed by `drm_mode_prune_invalid()` as `Rejected mode: "1920x1080": 60 148500 1920 2008 2052 2200 1080 1084 1089 1125 0x40 0x20005 (NO_STEREO)`: name, vrefresh, clock, the horizontal and vertical timings, type, flags, status. The 3D layout is bits 14 to 18 of the flags (`DRM_MODE_FLAG_3D_*`: 1 frame packing, 2 field alternative, 3 line alternative, 4 side by side (full), 5 L + depth, 6 L + depth + graphics + graphics-depth, 7 top-and-bottom, 8 side by side (half)); `0x20005` is side by side (half) with positive syncs. Interlaced stereo modes are rejected as `NO_INTERLACE` instead, still the parser's output. A mode rejected as `STALE` is a leftover of the previous EDID on the same connector, not a result.
6. **Run the same files on a second kernel** (the stock one and the patched one) and compare the two tables; a parser difference shows as a different list for the same file.

## Traps met (symptom, cause, fix, how found)

- **Symptom:** `edid-decode --check` fails with `The HDMI Specification requires EDID 1.3 instead of 1.4`, `EDID 1.3 does not support week 0xff`, `'Bare Limits' is not allowed for EDID < 1.4`, `GTF can't be combined with non-continuous frequencies`, `The chromaticities match sRGB, but sRGB is not signaled` or `Missing VCDB, needed for Set Selectable RGB Quantization`. **Cause:** fields written from E-EDID 1.4 habits into the 1.3 structure HDMI wants. **Fix:** version bytes `01 03`, a real week number, range limits with byte 10 = `00` (default GTF) and no bare limits, features byte with bit 2 set when the chromaticity is sRGB, and a Video Capability Data Block `e2 00 4a`. **Found by:** the Failures list of `edid-decode --check`, one run per fix.
- **Symptom:** `CTA-861: Multiple native progressive timings are defined`. **Cause:** a native bit on a Short Video Descriptor and a native detailed timing count of 1 for the same timing. **Fix:** one of the two; the generated files keep the DTD native and the SVD plain.
- **Symptom:** the guest prints no `Rejected mode` line although `drm.debug=0x4` is on the kernel command line. **Cause:** a module parameter on the command line is applied by `modprobe`, which reads `/proc/cmdline`; BusyBox `insmod` does not. **Fix:** `echo 0x4 > /sys/module/drm/parameters/debug` after loading, and print the value back. **Found by:** `lsmodes` listed only 2D modes for a 3D television's EDID with nothing in `dmesg`.
- **Symptom:** `dpkg-deb -x` of Debian 14's `linux-image-7.3.3+deb14-amd64` gives a 1.9 KB package with maintainer scripts and no kernel. **Cause:** since Debian 14 the signed image package only depends on `linux-binary-REL` (the kernel, at `/usr/lib/modules/REL/vmlinuz`) and `linux-modules-REL` (the modules, `.ko.xz`, no `modules.dep`). **Fix:** download those two; `linux-base-REL` is not needed to boot the guest. **Found by:** `dpkg-deb -I` on the small file.
- **Symptom:** a Virtual connector listed the EDID's modes but a debugfs override is "not applied" on a VKMS device of a stock kernel. **Cause:** stock VKMS's `get_modes` adds its own modes without reading an EDID, and the probe helper applies the override only when the driver returned no mode. **Fix:** use the `bochs` driver (QEMU `bochs-display` or `VGA`), whose `get_modes` reads the device EDID through `drm_edid_read_custom()`, which takes the override first; `edid=on` on the device, or `bochs` finds no EDID header and skips that path.
- **Symptom:** a shipped headset's EDID gives one more rejected stereo mode on the edition's kernel than on stock, `640x480p@60 flags 0x24005 (H_ILLEGAL)`. **Cause:** the edition's DisplayPort series lists a frame-sequential mode (layout 9) from a detailed timing with the stereo bits, and this EDID carries a field-sequential 640x480 DTD with negative porches. **Fix:** none needed; count it as the kernel difference it is, not as an HDMI VSDB result.

## Facts measured on 2026-11-08 (Debian 7.3.3 and 7.3.1-stereo3d16, same results unless said)

- A 1080p60 panel that lists VIC 16 and VIC 1 and sets 3D_present with HDMI_3D_LEN 0 gets no stereo mode: `add_hdmi_mandatory_stereo_modes()` duplicates only the 2D modes the sink lists that match its table (1080p24, 720p50, 720p60 frame packing and top-and-bottom; 1080i50 and 1080i60 side by side (half)).
- The same panel with 3D_present 0, HDMI_3D_LEN 2 and one entry `08 10` (2D_VIC_order 0, 3D_Structure 1000, 3D_Detail 0001) gets exactly 1920x1080p60 side by side (half): `do_hdmi_vsdb_modes()` reads the 2D_VIC_order_X entries whether or not 3D_present is set. A reserved bit in the 3D_present byte changes nothing (the parser ignores it), and 3D_Multi_present 11 is handled as 00.
- A Sony KDL-46HX855 EDID gets the mandatory set for the timings it lists plus its declared structures, 23 stereo formats in all.
- The Avegant Glyph EDID from linuxhw/EDID (3D_present 1, 3D_Structure_ALL frame packing, 480 to 720-line formats only) gets frame packing on every listed VIC and top-and-bottom on 720p50 and 720p60, and nothing at 1080 lines.
- Boot to the end of eight cases: about 16 s under TCG with two virtual CPUs.

## Perks

- The whole run needs one small Docker image (QEMU, `busybox-static`, `edid-decode`, `gcc`, `kmod`, `python3`) and no device of the host; the EDID files are the only input that changes between questions.
- The `Rejected mode` list is a complete record of the parser's stereo output, including interlaced formats a VKMS bench never lists.
- The same guest reads a shipped device's EDID from a public collection (linuxhw/EDID keeps the hex in its text files) beside the synthetic ones, so a claim about "what sources assume" can be checked against a real declaration.
